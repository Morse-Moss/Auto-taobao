# 详情页自采实跑记录（2026-10-26）

不是结论，是过程记录。写下来是因为第一次成功、后续被滑块挡住，中间有覆盖事故，必须说清楚。

## 第 1 轮：成功

```
node runtime/collect-taobao-detail.mjs \
  --items 597600994634,678598686014 \
  --out-sku …/sku.csv --out-sku-attr …/sku-attr.csv --out-review …/reviews.csv \
  --review-pages 1 --frequency 3-5
```

| 商品 | SKU 数 | 评价 | 说明 |
|---|---|---|---|
| 597600994634（TW特拉维尔） | 60 | 40 条 / 共 800 | 属性「长度」1.3–1.8m × 「颜色分类」10 值，值带图 |
| 678598686014（SSWW浪鲸） | 50 | 40 条 / 共 700 | 属性「长度」0.8–1.4m × 「颜色分类」8 值 |

产出：sku.csv 110 行、sku-attr.csv 4 行、reviews.csv 80 行。抽检内容正确：
评价时间、好评、图片数、购买 SKU、正文、图片链接都对得上。

**当时价格与库存两列是空的**——`skuBase.skus[]` 只有 `propPath` 和 `skuId`，
价格库存在 `skuCore.sku2info[skuId]`（见 `sku-core-shape.json`）。这一轮之后才补的合并逻辑。

## 第 2 轮：被滑块挡住

补完价格合并逻辑后重跑同一批商品，两条都失败：

```
1/2 597600994634 失败：Runtime.evaluate 超时（60000ms）
2/2 678598686014 失败：Runtime.evaluate 超时（60000ms）
```

关掉前面探针崩溃遗留的两个 about:blank 标签页后单商品重试，仍挂。

换一个没打过的商品（679380994840）验证，给出明确结论：

```
失败：Runtime.evaluate 超时（25000ms）（页面出现验证控件，需人工处理后再跑）
```

即：不是代码问题，也不是某个商品被限，而是**详情页整体进入滑块验证态**。
触发条件推测是同商品在半小时内被请求 6 次以上（首轮 2 次 + 探针 4 次）。未证实。

## 事故：成功轮的 CSV 被覆盖

第 2 轮失败时，采集器按原路径写出了 0 行的 CSV，把第 1 轮的 110/80 行覆盖掉了。
已删除这三份空表（留着会被当成"采过但是空的"，比没有更误导）。
所以本目录现在没有第 1 轮的原始 CSV，只有结论与 `sku-core-shape.json` 的结构实录。

**教训**：写盘前要么先判空不落盘，要么带时间戳/轮次后缀。

### 已修复（同日）

`writeCsvFile` 现在默认拒绝用 0 行覆盖：

- 本次 0 行且目标文件已有数据 → 跳过写入，原文件保持不动，日志写明「保留原文件里的 N 行」；
- 本次 0 行且目标文件不存在 → 不创建只有表头的空表（空表会被下游当成「采过了，这个商品没有 SKU」）；
- 只有显式给 `--allow-empty` 才写空表。

`exports` 一并给出 `existingDataRows` / `writeCsvFile`，由 4 条用例守着这条行为
（含「原文件必须原封不动」的断言）。合计 41/41。

## 第 3 轮：仍然被挡，但这次没有副作用

同日稍后带写盘保护再跑一次单商品（`r3/`），原始输出：

```
[详情] 1/1 597600994634 失败：Runtime.evaluate 超时（25000ms）（页面出现验证控件，需人工处理后再跑）
[详情] 跳过写入 …/r3/sku.csv：本次 0 行，文件不存在，不创建空表
[详情] 跳过写入 …/r3/sku-attr.csv：本次 0 行，文件不存在，不创建空表
[详情] 跳过写入 …/r3/reviews.csv：本次 0 行，文件不存在，不创建空表
[详情] 完成：0/1 个商品成功
EXIT=1
```

`r3/` 下只有 `raw.json`（失败收据，记下哪个商品为什么失败），三份 CSV 一个都没生成。
写盘保护在真实失败路径上验证有效——事故不会再重演。

另外做了一次零网络的只读探测（附着到已存在的标签页读 DOM，不开 tab、不导航、不发 mtop）：
`s.taobao.com` 搜索页 `hasPuzzle:false`、正文是正常搜索结果，未检出验证态。
说明限制只在**详情页**这一侧，搜索页不受影响。

## 现在怎么恢复

需要在调试浏览器（:9222，edge-debug-profile）里人工打开任意一个淘宝详情页，
把滑块过一次，然后重跑。验证态解除前不要连续重试——只会加重风控。

代码侧的应对已经加上：
- mtop 调用超时从 60s 收紧到 25s，避免把整批拖死；
- 失败时探测页面是否出现验证控件，并在错误里直接写明「需人工处理后再跑」。

# 2026-09-28 商品数据看板「带日期条件的引用」全空 —— 修复

## 现象

飞书「商品数据看板」（`tbldkz3pU4VQ7Rjt`，2264 行 ＝ 73 个商品 × 31 天）：

| 引用列 | 匹配条件 | 修前有值率 |
| --- | --- | --- |
| 店铺 / 图片 / 型号 | 只按「商品ID」 | **2264 / 2264 ＝ 100%** |
| 访客数 / 支付金额 / 收藏人数 / 加购人数 | 商品ID ＋ **日期相等** | 1275 / 2264 ＝ 56.3% |
| 询单量（引询单表） | 商品ID ＋ 日期相等 | 438 / 2264 ＝ 19.3% |

按天看「访客数」：09-01~09-19 每天 56~70 行有值；**09-20 起连续 12 天整天全空**。

## 根因

飞书「查找引用」的日期条件是**时间戳精确相等**，而两张表的日期存法相差 8 小时：

| 表 | 日期存法 | 2026-09-23 的值 |
| --- | --- | --- |
| 看板（**人工维护**，全仓无任何代码引用它） | 北京时间零点 | `1790092800000` |
| 底单 2026-09-01 ~ 09-19（非本套脚本写入） | 北京时间零点 | `1790092800000` |
| 底单 **2026-09-23 起**（本套脚本写入） | **世界时零点** | `1790121600000` |

脚本写的是 `Date.UTC(y, m-1, d)`，产出世界时零点 ⇒ 比看板早 8 小时 ⇒ 条件不成立。
这也正好解释「09-19 之前好、之后空」：那 19 天的历史数据不是这套脚本写的，用的是北京时间零点。

代码位置（改写前）：`product-core.mjs:38`、`inquiry-core.mjs:43`、`promotion-core.mjs:26`。

`01-before-match.txt` / `02-before-extra.txt`（只读脚本，改数据前落盘 ⇒ 修后不可复现）。

逐个 (商品ID, 日期) 比对看板 × 底单：时间戳完全相同 **1275**；

示例：看板 `1790092800000`（+8 读 09-23）vs 底单 `1790121600000`（+8 读 09-23），差 `28800000` 毫秒 ＝ 8 小时。

## 修复

### 一、数据（678 行，见 `receipt.json`）

判据：目标值 ＝ 该时间戳「按 +8 读法得到的那一天」的北京时间零点。
**该公式幂等** —— 本来就是北京零点的行，目标值等于自身、不会被改动
（询单表那几天的「只有日期」占位空行因此自动跳过）。

| 表 | 改动行数 | 日期分布 |
| --- | --- | --- |
| 商品数据底单 | 419 | 09-23(88) / 09-25(167) / 09-26(165) —— 其中 1 行已在试改阶段改过 |
| 商品询单数据底单 | 74 | 09-23(21) / 09-25(30) / 09-26(23) —— **占位行不动** |
| 商品推广数据底单 | 185 | 09-25(93) / 09-26(92) |

**先试改 1 行**（`--probe`）再全量：底单记录 `recvw8KqR1ZZ3H`（商品ID 617149791732）那行的
「商品访客数」＝ `2`；看板对应行 `recvlnxJwkVUtT` 改前「访客数」＝ `null`、**改后 ＝ `[2]`**。
⇒ 引用是实时重算的，改完立刻出数，不需要等任何定时任务。

### 二、代码（防复发）

- `skills/sycm-product-data/scripts/product-core.mjs`：写入改用 `toBeijingMidnight()`；
  `planProductImport` 的日期读法改用 `readBeijingDay()`
- `skills/sycm-inquiry-data/scripts/inquiry-core.mjs`：写入与 `planInquiryImport` 的读法同上
- `skills/sycm-promotion-data/scripts/promotion-core.mjs`：写入改用 `toBeijingMidnight()`
- 同步改了日期期望值：`product-core.test.mjs`、`product-report-core.test.mjs`

`readBeijingDay` 是「加 8 小时再取日期」，对**北京零点**与**世界时零点**两种存法都读得对
⇒ 迁移期新旧混存也安全。

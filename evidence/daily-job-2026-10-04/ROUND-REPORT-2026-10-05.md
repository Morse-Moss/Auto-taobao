## 三、修的是什么（第 5 步一个字的错，让 8 家全挂）

`collect-shop-report.mjs` 的调用点原来是：

```js
const MATCHER = new RegExp(rowTitleMatcher(rowTitle));   // ← 坏在这里
```

而 `rowTitleMatcher()` 返回的是一段**判据源码文本**（`'/日报/.test(rowText)'`）。  
把它包成 `new RegExp(...)`，就变成「去匹配那串字面字符」，于是**任何行都命中不了**：

```
new RegExp('/日报/.test(rowText)').test('日报 取数报表 小宁 2026-04-13 …')  →  false
```

后果与线上症状逐字吻合：`daily` 恒为空 ⇒ 轮询 10 轮全落空 ⇒ 报「等不到『日报』这一行的预览按钮」，  
而那一行**其实好好地在那儿**（感知层 `visibleText` 里就有）。

这行是 `b29f64c`（**今天 11:12**「报表清单在 iframe 里」那次改动）引入的，一直没被触发 ——  
11:18 起的每一轮都死在更早的 `promotion-submit`，根本走不到第 5 步。

**真机验证**（修复后）：

```
[2/4] 2.5s：预览按钮 2 个，日报行 #0（命中复核=true，视口内=true）   ← 第 2.5 秒就命中
[3/4] 统计区间 2026-09-05 ~ 2026-10-04 含目标日 2026-10-04 ✓
[4/4] 点「下载报表」→ 新文件：日报_20261005_6e08….xlsx（19785 bytes）
```

修复前同一处是「10 轮全落空、且日志里连点名后缀都没有」。

## 五、今天新发现、**还没修**的一个缺陷：运行锁释放不掉

- 每轮退出时 `release()` → `fs.unlinkSync(锁)` 被**宿主的安全删除代理**拦下：  
  `SAFE_DELETE_BULK_CONFIRM_REQUIRED {"count":1461,"threshold":50,"scope":"turn"}` ⇒ 锁留在盘上。
- 下一轮 `acquire()` 的 `reclaimIfStale()` **内部也是 unlink，同样被拦**，  
  而调用点 `try { … } catch { reclaimedFrom = null }` **把这个错误吞成了「没回收」**  
  ⇒ 兜底报 `workflow lock busy: merchant-automation`，**指向「别人正在跑」这个错误方向**。
- 实测：13:36 那次重跑就是这么被拦死的，而锁里的 pid 133884 **确已死亡**

- 本轮处理：三次都是**先留证、再 `rm`**（`stale-lock-recovered*.json` 三份）。**没有改代码。**

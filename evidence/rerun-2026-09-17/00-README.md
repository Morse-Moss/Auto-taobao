## 第三件新事实：历史日的「同行同层均值」取不到 ⇒ 回填必须显式降级

```
    at extractInquiryMetrics (inquiry-core.mjs:40)
```

不是 bug：`inquiry-core.mjs` 第 34~37 行的实测注释早就写明「预设「1天」（昨日）给 7 行、含同行对比行；
**自定义日期只给 3 行**，同行两行都不返回」。现场复核（用与 `readSycmTable` 逐字相同的表达式读 19041）：

```
    ["2026-09-17","3","3","0","0.00",...]
    ["汇总值","3","3","0","0.00",...]
    ["平均值","3","3","0","0.00",...]
```

⇒ 昨天跑 09-17（当时它是「昨日」）拿得到基准（`evidence/daily-report-2026-09-17-*` 那四代单据里
`peerBenchmark=PEER_AVAILABLE rows=7`），今天补跑同一天就拿不到。**默认 fail-closed 是故意的**：
默认降级会掩盖「本该有基准却没有」的真故障。

补跑动作（`12-backfill-dryrun.txt` / `13-backfill-commit.txt`，先干跑再写）：

## 代码改动：把「历史日降级」这根线接进驱动

`run-multi-shop-day.mjs` 原来**没有**透传 `--allow-missing-peer`（能力在生产者有、消费者没接，
本项目反复出现的形态）。本轮补上：

- 驱动新增 `--allow-missing-peer`，**默认关** ⇒ 不传时参数表与从前逐字相同；
- 只作用于 `backfill`，push / readback 不受影响（那两个脚本不认这个参数）；
- 判据：`run-multi-shop-day.test.mjs` 三条（默认关 / 显式才传且只传一次 / 不污染别的阶段）；
- **突变验证**（`D:/Retire/probe-live/64-mutate-multishop-allow-peer.mjs`）：
  M1 接线断了、M2 默认值反了、M3 污染 push —— 三条**全部被抓住**且命中到期望的断言消息，
  之后按备份还原、sha256 逐字节一致（`37f00be7…`）、复跑绿。

顺带修了验证脚本自身的一个 bug：第一版拿断言消息去比对 `not ok` 的**标题行**，
于是三个突变全报「未命中」—— 那不是判据没作用，是验证脚本比错了地方（断言消息在标题下面的详情里）。

## 第四件新事实：体检对「商家共用浏览器」的期望页面是**过期的**

驱动的一轮级体检要求 19022 上有「生意参谋工作页 + 飞书底单页」各恰好一个。
多店铺模式下，生意参谋在**各店自己的**浏览器上，19022 只被 push/readback 用来读飞书页
（两个脚本里都没有 sycm 的引用）—— 而这条判据是单店时代的遗留。

更麻烦的是它**会假绿**：当 19022 的生意参谋会话已过期时，页签 URL 是
`sycm.taobao.com/custom/login.htm?_target=http://sycm.taobao.com/qos/service/frame/shop/performance/new#/shop`
—— 片段匹配发生在 `_target=` 参数里，于是**登录页被算成工作页**，体检放行。

本轮先按现状让它过（19022 上确实有登录页，且本轮 push/readback 真实成功 ⇒ 该页对这两个脚本无用途），
**判据本身没有改**（改它要配测试与突变，留给下一轮）。

体检另外正确拦下过一次真问题：19022 上原本有**两个**一模一样的生意参谋登录页
（启动 URL 一个 + Edge 恢复页签一个），`TARGET_PAGE_AMBIGUOUS` 是真判据命中；
关掉重复那一个后回读确认剩 1 个。

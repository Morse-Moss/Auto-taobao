# 「跑完关掉、跑前再起」会不会有风险 —— 只读取证（2026-09-23）

用户原话（2026-09-23）：

> 「如果每轮关再续跑会不会有风险？」

本批次**没有起停任何进程**。全部结论建立在三种只读来源上：链自己的纯函数、仓库内的代码路径、
以及当前现场的量账。

## 一、结论

- **数据面没有风险**：关进程不删 cookie，也不删浏览器密码库 —— 它们在 profile 目录里，是文件。
- **链不会因为「窗口里没有工作页」而卡住**：体检之前有一段「归位」，冷启动状态下它会自己把缺的
  页面建出来（`create` → `/new?…&pinned=1`）。这一条是**实测**（见 §二），不是读代码猜的。
- **唯一一条硬风险不在「关」这一侧，而在「起」之后**：整条链**没有任何一步检查登录态**。
  某家店掉了登录，不会在开跑前被发现，只会等到采集阶段炸，然后发一条「请人到场」的告警。
- 因此建议：**先补两件配套（收敛启动入口、造登录态体检能力），再切「关再续跑」**；
  且即使切，也只关五家店（省 6.1 GB），不要连商家浏览器一起关。

## 二、页面缺不缺：冷启动不会挡整轮（实测）

做法：把「冷启动后窗口里只有一个 `about:blank`」这个状态，直接喂给链自己用的两个纯函数
`planPageActions` + `planRequests`（`runtime/shop-pages.mjs`）。`dry:false` ⇒ 拿到的是**真要做的
动作**（`create`），不是 `would-create`；`targets: []` ⇒ 一个写请求都不发。

原始输出：`02-cold-start-pages.txt`（复核命令见文末）。结果：

| 窗口 | 期望页面 | 冷启动下的动作 | 需要人决定的 |
|---|---|---|---|
| 五家店（任一家） | 生意参谋工作页、阿里妈妈报表页 | 两个都 `create`（2 条 `/new`） | **0** |
| 商家浏览器 | 生意参谋工作页、飞书底单页 | 两个都 `create`（2 条 `/new`） | **0** |

为什么成立（代码路径，不是推测）：`skills/sycm-alimama-daily-report/scripts/run-multi-shop-day.mjs`
的 `runHealthCheck()` 在体检**之前**无条件调 `normalizePages({ proxyPort, expected })`（不传 `dry`，
所以是真写）；`runtime/page-normalize.mjs` 又整段复用 `shop-pages.mjs` 的
`planPageActions`（缺页时先领回、领不回来才新建）。所以「冷启动 ⇒ 一页都没有」落在 `create` 这一支，
`judgeNormalize` 的 `NOT_DONE` 名单里不含 `create` ⇒ 归位判 `ok`。

顺带一条**正面**结论：新建的页是「刚加载」的，恰好消掉了当前那个失败模式 ——
生意参谋的「1天」是相对预设、只在页面加载时解析一次，页面停在上一轮渲染上时读数会一直是旧日期
（2026-09-21 首次定时真跑就栽在这上面）。冷启动天然没有这个状态。

## 三、起的一侧：已经接好了

- 定时链的步骤口径在 `runtime/daily-job-plan.mjs`：**第一步 `ensure-instances`
  （`scripts/start-all.mjs`，幂等、已就位的一个都不碰），第二步才是全链**；
  且第一步 `blocking: false` —— 它失败不阻断第二步，因为「今天能不能写」的权威判据在链的第 0 步体检里。
  > 2026-09-23 晚补记：这份 README 是**当时**的读取结果。同日晚该计划已改成**三步**
  > （起实例 → 只读登录态体检 → 全链，见 `evidence/login-preflight-2026-09-23/`），
  > 也就是说本文 §四 那条「没有任何一步检查登录态」的风险已经补上了 —— 但补的是
  > **定时链之前那一眼**（把结论写进日志），体检层本身（L1）一个字没改。
- 入口 `scripts/run-daily-job.mjs`：退出码取全链那一步，`start-all` 的结论只记录。
- 所以「跑前再起」不需要新造：它已经在这条链里了。

## 四、真正的风险：起完之后没人检查登录态

体检的全部判据（`runtime/xws-platform-health-preflight.mjs`）是：调试端口在不在、
profile 是不是我们的、出网代理通不通、期望页面是不是恰好一个。**里面没有「登录态还有效吗」。**
文件里对此有明确交代：

- L2（账号标识选择器）：`'账号标识选择器四个平台一个都没采到（LOGIN-CRITERIA-MEASUREMENT-2026-09-18.md §7），需要先换定位手段…'`
- L3（会话凭证 vs 长期标记）：`'现在分不出「会话凭证」与「长期标记」——用错会把登出后的残留当成已登录，因此先不做。'`

后果：掉登录这件事不会在开跑前被拦下，而是在采集阶段炸，产出一条 `needs: ONSITE` 的告警。

自动恢复**只有一半靠谱**。仓库里其实有自动登录能力
（`skills/sycm-alimama-daily-report/scripts/login-merchant.mjs --commit`：驱动浏览器自己的密码库
填充 + 补一次可信手势；失败 fail-closed 成 `NO_SAVED_CREDENTIAL` / `CAPTCHA_REQUIRED` /
`LOGIN_NOT_CONFIRMED`，并会叫人）。但它的前提是那个 profile 的密码库里有这份凭据，而
`tmp/login-commit-3shops-ok.mjs` 的头注释记着：**盖文天猫的密码库没有这份凭据（`autofill=false/false`），
自动填不了 ⇒ 必须人工登一次并勾「保存密码」**。所以在五家里至少有一家不能自动恢复。

注意这条风险与「关不关」**正交**（不关也会掉登录）。关掉会让它变成「每天开一次」的暴露频率。

## 五、还有两件必须配套的事

1. **关的方式必须走脚本，别让人去点窗口叉。**
   `scripts/stop-all.mjs`：默认只打印，要 `--yes`；先断代理、后断浏览器；每个被停的进程都要带证据
   （浏览器由**它自己**回报 profile，代理认命令行里的店名），证据不到就**拒停**；停后隔 1.5 秒
   **回读**进程表确认真的没了，没停干净非 0 退出。
   人手点叉 / 强杀可能留下不干净的 profile 状态；而若「会话恢复」把旧页签带回来，同主机多于一页会被
   归位判成 `ambiguous-drift`（只报不猜）⇒ 那家店一步都不跑（2026-09-20 实测过这个 fail-closed）。
2. **先把启动入口收敛成一个。** 现场有 **4 个 `start-all-hold.mjs` 并存**：
   PID 8040（带 6 个实例）、14536（`--only competitor`）、55720 与 21352（裸跑）。
   它们本身不干活，只占内存，并让「谁起的、谁负责」说不清。

## 六、与「窗口固定显示店名」的冲突（本轮新增）

标志页**不在期望页面清单里**，所以归位不管它。冷启动会把窗口清成只有一个 `about:blank`，
于是昨天刚挂好的店名每次都要重挂 —— 除非把挂标志页接进启动流程。

这条冲突**今天就已经在发生**（不是假设）：当前 7 个窗口里只有 3 个显示店名
（盖文淘宝 / 盖文天猫 / 科塔淘宝），里可林与网林天猫的窗口标题已经变回
「生意参谋 - 零售电商大数据产品平台」「下载任务管理_万相台无界版」——
标志页还在（各家 `labelTabs=1`），只是被采集把激活页签切走了。

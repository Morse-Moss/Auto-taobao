## 1. 评级判据（线上公式原文，本周表 tbllWI45sK0DfHpr）

「竞品分类」是飞书公式字段，完整表达式（已把字段 id 还原成中文名）：

```
IF(
  OR( <浴缸前置条件>, ISBLANK([价格]) ),
  "不适用",
  IF(AND([月收货人数计算值]>=80, [月收货金额]>=200000), "A-爆款竞品",
    IF(AND(FIND("人造石",[材质分类])>0, [月收货人数计算值]>=10), "B-高价值竞品",
      IF([价格]>=8000, "C-差异化竞品",
        IF([价格]<1000, "D-价格/流量型竞品", "无分类")
      )
    )
  )
)
```

<浴缸前置条件> 的实际含义：标题必须含「浴缸/浴桶/浴盆/洗澡盆」，且**不得**含「洗脚池/洗脚盆/泡脚盆/足浴/宠物/狗洗澡/猫洗澡/婴儿/新生儿」，
而且必须落在「成人/大人/老人/独立式/嵌入式/靠墙式/深泡/可移动」之一，同时排除「上门安装/维修服务」以及
「龙头/花洒套装/角阀/下水器/排水器/盖板/扶手/靠枕」等配件，另外排除「儿童浴盆/折叠/充气/便携」类。

### 一处需要更正的我方旧记录
之前的项目笔记把 C/D 写成「客单价带分类 ≥8000 / <1000」。**实际公式用的是 `价格` 字段**，
`ISBLANK()` 判的也是 `价格`；`客单价带分类` 在这条公式里**根本没有被引用**。
`客单价带分类` 是另一个独立字段，值形如 `[{"text":"1000以下","type":"text"}]`，是文本分档而不是数字——
按数值去解析它会得到 1000 这种假值。沿线沿用这个错误记录会导致复算口径偏差，本报告予以更正。

### 判据的结构性后果
- A 是**双门槛**：人数 ≥80 **且** 金额 ≥200000。两者必须同时成立。
- B 的**第一项就是 `材质分类` 含「人造石」**。这一项不是采集列（见第 4 节），它一旦为空，B 恒为 0，与人数无关。
- C/D 只吃价格，与人数无关——所以价格侧一直正常出分类，掩盖了 A/B 的输入缺失。

## 3. 真因一：本周采集包里根本没有「人数 ≥80」的商品（决定 A）

本周导入所用的合并产物 `runtime/weekly-2026-09-13_2026-09-19-merged.csv`，
自带 1417 行、16 列（**无材质列**）、平台仅淘宝 1121 / 天猫 296、类目仅普通浴缸 1238 / 按摩浴缸 174 / 步入式浴缸 5，
月收货人数分桶 `0:332 / 1-9:1039 / 10-29:41 / 30-79:5 / 80-199:0 / ≥200:0`。

**这份包内最大月收货人数 = 48。** A 需要 ≥80，因此本周无论公式怎么算都不可能出 A。

### 不是采集没跑，而是「跑的那一批」丢了高销量区段
同一天有两次采集：

| 时间 | run | 产物 | 行数 | max | 旗舰店 | 浪鲸 |
|---|---|---|---|---|---|---|
| 09-15 15:08–15:58（首次，page 24 卡住） | `9e46eef9…` | `final/浴缸-adaptive-merged.csv` | 1476 | **200** | — | 63 |
| 09-15 17:59–18:48（切成 10 段重跑） | 10 个分段 run | `weekly-2026-09-13_2026-09-19-merged.csv` | 1417 | **48** | 258 | **0** |

首次采集的合并产物里就有 A 候选：

```
m=200  [陈强卫浴工厂店] 新品浴缸…欧式浴盆            金额=126000    -> 人数达标、金额不达标
m= 81  [ssww浪鲸浴缸旗舰店] SSWW浪鲸深泡浴缸…         金额=213086.84 -> 满足 A（本周把这条丢了）
```

**也就是说：如果本周用的是首次那份，A 会是 1 条。**
重跑之所以丢掉它，是因为重跑切成了 10 段（1-4 … 37-40），每段拿到的导出都是一小片：

```
1-4   Top147 @17:59  max=48      13-16 Top179 @18:10  max=2
5-8   Top149 @18:03  max=5       17-20 Top153 @18:13  max=1
9-12  Top184 @18:06  max=3       21-24 … 37-40 @18:38-18:48  max=1 / 0
```

十份片段并起来 1695 行、去重后 1417 行——**行数看着像一份完整榜单，但没有任何一段落在高销量区段**。
逐份判定（只读脚本 `diagnose-raw-export-head.mjs --day=2026-09-15`）显示：max 随段号单调下降
（48 → 5 → 3 → 2 → 1 → 1 → 1 → 1 → 0 → 0），零值行数反向上升（0 → … → 140 → 192 → 154），
这是**在列表里越走越深**的典型形态，不是「本周市场只有这么多量」。

### 为什么之前没发现
每份导出的 `序号` 都是 `1-N`，采集侧的校验只看 `rows / columns / rank_range / empty_links / duplicate_links`，
**不看内容是否覆盖了高销量区段**。所以一份 147 行的尾段切片和一份 1476 行的完整榜单，
在采集校验器眼里是同一种东西（两者都是 `rank_range 1-147` / `1-1476`）。

同一现象在 08-30 低值周复现：09-12 那天唯一的大导出 `Top1358 @17:44` 的 max 也只有 46。
反过来，09-13（产出 09-06 高值周）的 `Top1399 @11:55` max=200、`Top485 @12:38` max=200，头部在包里。

## 4. 真因二：`材质分类` 整列为空（决定 B）

`材质分类` **不是采集列**——合并 CSV 的 16 个列头里没有它。它是「竞品分析 V2」的属性分类字段
（multi-select，取值如 亚克力 / 陶瓷,铸铁 / 人造石 / 无注明 / 不适用），由分类环节写入。

四周实测（`diagnose-weekly-ab-criteria.mjs`）：

| 周表 | 材质分类 为空的行 / 总行数 | 含「人造石」的行 | 其中人数≥10 的行 |
|---|---|---|---|
| 08-23 | 670 / 1461 | 77 | **8** |
| 08-30 | **1423 / 1423** | 0 | 0 |
| 09-06 | **1462 / 1462** | 0 | 0 |
| 09-13 | **1417 / 1417** | 0 | 0 |

注意 08-23 那一行的自洽性：**含「人造石」且人数≥10 的行数 = 8，与该周 B 的实际条数 8 完全一致**。
这反向证明了公式本身是对的（`FIND("人造石",[材质分类])>0` 与 `人数>=10` 的组合判据按预期工作），
**B 为 0 唯一的原因是输入字段空了**。

空的原因（2026-09-15 晚续查，已追到具体环节）：

1. **属性字段在代码层没有任何写入方。** 全仓搜索能碰 `材质分类` 的只有三处，都不作用于周表：
   - `skills/xws-to-feishu-base/scripts/migrate-competitor-v2-analysis.mjs` —— 只对**竞品主表**写哨兵值（`无注明` / `不适用`），且回执写 `aiRunTriggered: false`（**它明确不跑 AI**）；
   - `runtime/competitor-history-publish-core.mjs:138` —— `材质分类: selectFirstMaterial(source.商品标题)`，只写**竞品历史总表**，与周表无交互；
   - `runtime/update-competitor-class-labels.mjs` —— 那是 A/B/C/D **标签改名**迁移（`A-高销量高GMV竞品` → `A-爆款竞品`），且指向已废弃的旧租户 appToken，不是属性填充。
2. **周表是「只克隆结构、不克隆数据」建出来的。** `runtime/prepare-weekly-competitor-table.mjs:60` 的 `CLONABLE_TYPES = {1,2,3,4,5,7,11,13,15,17,18}` **不含 19(Lookup)/20(Formula)**，脚本自己打印 `deferring ... formula/lookup fields`。实测字段数：08-23 周表 39 个、08-30/09-06/09-13 各 35 个，**39 − 4 = 35**，缺的正是 `尺寸`、`适用空间`（Lookup）与 `待补数据项`、`数据状态`（Formula）。所以新建周表不仅属性字段是空列，连「还缺什么」的提示字段都没了。
3. **08-23 周表有 791 行真值，是因为它带着数据整表迁移过来**（字段结构与竞品主表对齐，只差 `SKU采集明细` / `当前周状态` 两个关系/汇总字段）。旧租户在 2026-08-19 与 08-25 的快照里 `材质分类` 就已经有值（`runtime/competitor-v2-analysis-migration/before-20260819T023942Z.json`、`runtime/competitor-class-label-migration/before-20260825T102043Z.json`），说明那批值是**在飞书侧靠提示词跑 AI / 人工填**产生的（提示词见 `references/competitor-v2-ai-prompts.md`），**从来不在自动化链里**。

所以结论是：**没有哪一步「漏跑」，是这一步从来没被自动化过**；08-23 之后改用 35 字段空壳表建周表，这条依赖人工/AI 的动作就彻底断了，B 从此结构性为 0。
（旧租户已废弃，无法回查「飞书 AI 字段是否曾自动填充新行」——这一点是推断，不是实测，故单列。）

## 5. 对「是不是周一开始累计、今天才周二所以数据少」的检验

**否定。四条反证：**

1. **指标口径不是本周累计**。`月收货人数` 是淘宝的「近 30 天收货人数」滚动值，不是「本周从周一累加」。
   同一商品跨周对比也支持这点：09-06 与 09-13 两周共款 888 条，取值完全相同的 621 条（69.9%）。
2. **完整周期同样是低值**。08-30~09-05 那周是在周期结束后的 09-12 采的（完整 7 天），max 仍然只有 46。
3. **周期完整的高值周存在**。09-06~09-12 周期完整、09-13 采集，max = 200，A 出了 1 条。
4. **同一天、同一关键词、同一参数，两份导出量级不同**。09-15 15:08 的 `Top613` max=200，
   17:07 的 `Top46` max=48；而采集参数在两次运行里都是 `sort=sales / channel=all / price 0-∞`（见 checkpoint `options`）。

变量是**采集批次覆盖到列表的哪个区段**，不是日历天数。周二这个因素可以排除。

## 6. 「低值周口径来源」的回答

已定位到层面，但**没有定位到最后一跳**，如实分开说：

**已确证（有可复现证据）**
- 低值周的定义可以精确化：**该周采集包里最大 `月收货人数` ≤48**（08-30 周 46、09-13 周 48），
  而高值周是 100 / 200。
- 来源在**采集导出环节**，不在下游任何一环：
  - 不在公式（B 的 8 条自洽复现、A 在 09-06 正常命中）；
  - 不在字段语义（3169 个同日交叉观测仅 5 条不一致，且都是「该份导出该行无此列」）；
  - 不在排序参数（历史 manifest 全是 `sort=sales`，且实测每份导出都是销量降序，文件名「价格从高到低」是插件命名 bug）；
  - 不在周期起止（见第 5 节）。
- 直接成因是**导出覆盖的区段**：同一会话里，导出会随着列表视图越走越深，
  `序号` 每次从 1 重新编号，于是「行数/序号看起来完整」与「内容只有尾段」可以同时成立。
- 高值/低值交替因此**不是市场波动，而是「那一次采集有没有落在头部」**。

**未定位（下一跳）**
- 为什么 09-15 15:08 的那次落在头部、17:59 之后的十段全部落在尾段。已知相关变量：
  首次运行 `proxy = 127.0.0.1:3458`，重跑用的是项目专用 3457；
  首次运行在 page 24 卡住后被我按「放宽判据重跑」切成 10 段。
  **是「重跑时列表没有回到顶部」还是「两个代理背后是不同的浏览器会话/账号态」，
  需要一次受控对照才能分（同一次 session 里，先在顶部导一份、再滚动后导一份，比较内容）。**
  在拿到这个对照之前，不写结论。

# 窗口标志页：接管空白页，而不是新建（2026-09-23）

用户原话（本条要求的全部）：

> 1.店铺才补，相当于替换原本的空白页，不要空白页了

拆成两句话：

- **店铺才补** ⇒ 只做五家店这条线，**竞品 9222 与商家 19022 不动**（它们现在仍然没有标志页）；
- **相当于替换原本的空白页，不要空白页了** ⇒ 挂标志页时不要新开一个页签，
  而是把窗口里那个链路用完没关的 `about:blank` **原地**变成标志页。这样页签条数不增加、位置也不变，
  窗口里从此不再躺着一个空白页。

## 一、改了什么（`runtime/shop-window-label.mjs`）

1. `ensureLabelTabOn` 新增一条分支：没有标签页时，**先找第一个 `about:blank` 接管**（`/navigate` + `/pin`），
   连空白页都没有才走原来的 `/new`。其余空白页不在这个函数里关（「替人关掉别的页」是另一个决定，交给 `--prune`）。
2. 三个来源用**同一组字段**表达，不靠「某个键不存在」反推：
   `reused:true`＝复用已有标签页；`reused:false, adoptedBlank:true`＝接管空白页；`reused:false, adoptedBlank:false`＝新建。
3. CLI 报告里带出 `adoptedBlank` 与 `extraBlanks`（后者附一句「还剩 N 个空白页，加 --prune 一并关掉」）——
   否则「空白页怎么没了」只能靠猜。
4. 补了一段顺序说明：清理（prune）排在挂标签页**之前**，所以 `--label --prune --commit` 这种组合下
   空白页会先被关掉、走不到接管那条路（结果仍然对，只是那个标签页是新建的）。
   要它**原地**接管，分两步下达：先 `--commit --front`，再 `--prune --commit`。**这个顺序没有改**（见第四节）。

## 二、怎么验的（四层，逐层加严）

| 层 | 判据 | 结果 | 原始输出 |
| --- | --- | --- | --- |
| 离线用例 | `node --test runtime/shop-window-label.test.mjs` | **50 / 50 / 0**（基线 47 ＋ 新增 3） | `01-offline-tests-50of50.txt` |
| 突变 | 把源码改坏，看新判据会不会红、且红在期望那一条 | **4 / 4 CAUGHT**，还原后 sha256 与原始**逐字节一致** | `02-mutation-4of4.txt` |
| 真机（造状态） | 把「无标签页 ＋ 有空白页」真造出来，看空白页的 targetId 是不是**原地**变成标签页 | 是；窗口里空白页 0 个；页签数不增加 | `03-live-adopt-verify.txt` |
| 真机（五家店） | `--commit --front` 后回读 | **5/5 `reused+pinned+fronted`**，`failed:0`；科塔那个空白页被 prune 关掉 | `06`/`07`/`08` |

新增的三条用例各自钉住一件事：

- 有空白页时**接管、绝不新建**（并断言 `/new` 一次都没发）；
- 接管时**只取第一个**，剩下的报出来（顺序稳定，否则每轮接管的可能是不同的页签）；
- 既有标签页又有空白页时**复用标签页**，不去接管空白页（否则会变成两个标签页）。

突变四个（M1 接管分支变死代码 / M2 接管时不钉住 / M3 取最后一个空白页 / M4 把「接管」写成 false）全部被点名抓住。

### 为什么「真机造状态」这一步不能省

离线用例用的是**假代理**，它只能断言「脚本发了 `/navigate`」；
而「代理的 `/navigate` 到底能不能把一个 `about:blank` 导航走」只有真浏览器能回答。
这正是本项目反复吃过的「函数级用例全绿 ≠ 接线接上了」。

造状态的做法：关掉里可林当时那个标签页（它本来就会被代理 15 分钟回收，这里只是把「下一轮会自然发生的事」提前一次），
然后跑 `--commit`。证据里那条关键行是：

```
空白页那个 targetId（C27132AA7D2871F0C10D65F3517BAA17）现在指向：file:///...shop-window-label.html?...
接管成功（原地变成标签页）：是
```

同一个 targetId 前后都在 —— 这就是「替换」而不是「新建」的定义。

## 四、一个副产物：任务栏标题里的**数字不可信**

里可林窗口标题写「和另外 3 个页面」（＝4 个标签），而三种互相独立的方法都给出 **3 个 page target**：

- 代理 `GET /targets` → 3 条（`11-authoritative-targets-likelin.txt`）；
- 浏览器直连 `/json/list` → 3 条；
- CDP `Target.getTargets`（**权威**，连 iframe 一起列）→ 3 个 page ＋ 2 个 iframe。

而且再置前一次，那个数字也不变（不是刷新滞后）。

⇒ 结论：**标题里的标签数不能当「窗口里有哪些页签」的判据**（判页签必须问 CDP）。
这与 `../../docs/ops/FULL-AUTOMATION-STATE-CONTRACT-2026-09-21.md` §十四 那条纪律同源
（跨机自动化别用任务栏/窗口列表判现场）—— 这次是它的一个具体实例。

标题里**当前标签的名字**这一半是可信的（它就是激活页签的 `document.title`），这一批正是靠它验收的。

## 五、没做的（边界，别当成漏了）

1. **竞品 9222 与商家 19022 仍然没有标志页** —— 按用户「店铺才补」。
   要补需要把覆盖范围从 `SHOP_BROWSERS`（五家店）泛化到 `PROJECT_PORTS`。
2. **「跑完自动置前」没有接进采集收尾**。现在这五个窗口能显示店名，是因为这一轮手工执行了 `--front`；
   下一轮采集一切回生意参谋，标志页仍会被挤到后面。要让它**固定**，需要把
   `shop-window-label.mjs --commit --front` 接进收尾（或 `start-all` 之后）。
   `scripts/` 下目前没有任何地方引用这个脚本。
3. **prune 与 label 的先后顺序没改**（结果等价，代价是「原地接管」要分两步下达）。
   `main()` 里没有被离线用例覆盖（用例都是函数级），所以这个改动只靠真跑能验 —— 不做更划算。

## 3. 发现（这一节是「后续修复与优化」的入口）

### 发现 1（P1，真缺陷）：证据代次目录缺「店铺」维度，多店铺串行会互相覆盖

**现象**：`run-daily-report.mjs` / `run-inquiry-backfill.mjs` 的产物目录只按报告日取名
（`evidence/daily-report-2026-09-17-rerun6/`），**没有店铺维度**。
`--commit` 的策略是 `latest`（并入最新一代），于是四家店串行跑时，
后一家的 `plan.json` / `paste.tsv` / `receipt.json` / `inquiry-backfill-*.json`
**会覆盖前一家的同名文件**，一个目录里最后只剩最后一家。

**本轮的真实损失**（不夸大也不掩盖）：

| 丢的什么 | 为什么 | 事实还在哪 |
| --- | --- | --- |
| 里可林的 `inquiry-backfill-plan.json` + `inquiry-backfill-receipt.json` | 生成后立刻被网林的同名文件覆盖（当时我还没开始抄副本） | `likelin-taobao/14-…txt`、`15-inquiry-commit.txt`、审计 id 17 |
| 网林天猫的 `receipt/plan/paste` 副本 | 抄进台账**之后**，我又执行了一次「全抄 5 件」，用科塔的同名文件把这三件覆盖了（**我的操作失误**，见 `wanglin-tmall/generation/READ-ME-证据被覆盖.md`） | `wanglin-tmall/06-daily-report-commit.txt`、审计 id 14、两条独立回读 |

**没有任何业务事实丢失** —— 每个 recordId、每个字段值、每次审计都有独立来源。
但「一键拿到那一家店的完整产物」这条能力在本轮是缺的。

**修法建议**（未实施，等指令）：把店铺并进目录语义，例如
`evidence/daily-report-<date>-<shopKey>[-rerunN]`，或保留现有代次目录但在其下按店铺分子目录。
注意一个约束：`main()` 里 `resolveOutputDir` 排在 `extractSources` **之前**（注释写明
「先定产物落哪一代，再动任何东西」），而店铺名要读完 xlsx 才知道 ⇒ 改的时候要么拆成两级
（日期级先定代次、店铺级在其下），要么显式接受「先读源文件、再定目录」并补上这条顺序理由的改写。

### 发现 2：采集把生意参谋页留在预览页 ⇒ 回填前必须「回位 + 重跑落位」

四家店**无一例外**在采集后停在 `report_generation`。回填脚本要求的是
`qos/…/shop/performance` + 活动页签 `询单到付款`，直接跑会报
`expected one 当日询单人数 table, got 0`。
SOP 已在 §10.1 表下、§10.2、§10.4 写了这条，**但 §10.1 的九步表里没有把「回位」画进顺序**。
建议把它升格成表里的一步（第 4.5 步：`sycm 回位 → 重跑 date-picker --site sycm`）。

补充一条本轮实测的细节：`date-picker.mjs --site sycm` 会**自己切页签**（trace 里能看到
`step: tab, expectTab: 询单到付款, alreadyActive: false`），所以「先回位、再落位」两步都要做，
只做回位不够（回位后页签回到默认的 `汇总分析`）。

### 发现 3：数据源的文本标记 `NULL` 撞上数字字段 —— 现在的处置是「留空 + 留痕」

09-17 这天，四家店当天无成交，数据源对 `UV价值` / `无线端UV价值` 给的是**文本 `NULL`**，
而飞书这两列是**数字**字段。原实现直接抛错（`cannot preserve text marker NULL in numeric field UV价值`）
⇒ 四家店同时推不动。

处置（**已实施并验证**）：数字字段遇文本标记（`NULL` / `null` / `-`）⇒ **该格留空 + `console.warn` 留痕**。
不定 0 的理由：写 0 把「当天无成交」变成「价值为 0」这种假事实，还会污染同比/环比；
留空的代价是「无数据」与「漏采集」在页面上分不出来，所以**必须留痕**。

- 代码：`skills/sycm-alimama-daily-report/scripts/daily-report-core.mjs` 的 `toFeishuValue`
- 测试：`daily-report-core.test.mjs` 新增「数字字段遇到数据源的文本标记 ⇒ 留空并留痕（不写 0，也不抛错）」
- 突变验证：把判据改成写 0 / 退回抛错 / 删掉 warn 三种坏法，**三种都让那条测试红并点名**；
  还原后逐字节一致、复跑 8/8 绿。
- 落库实测（`13-final-verify-0917-fixed.txt`）：四家的 `UV价值`/`无线端UV价值` 都是 `<null>`（键在、值为空）。

**同一个数据源标记，在同一张表里落地成两种形态**（这是既成事实，不要试图统一）：

| 列 | 飞书类型 | 09-17 落库形态 |
| --- | --- | --- |
| `UV价值` / `无线端UV价值` | 数字（type 2） | 空 |
| `PC端UV价值` / `全站推广花费` | 文本（type 1） | 字符串 `"NULL"`（盖文天猫那行也是这样） |

**这一条需要你表态**：如果希望四列形态一致（例如都留空，或都写 `NULL`），
那就是改字段类型或改转换规则的事，与本次推送的数据无关（本轮已经按现状落库）。

### 发现 4：报表文件名判据不能写死（每店不同）

盖文淘宝的报表叫 `日报2_20260918_90f3f449….xlsx`（前缀多一个 `2`、hash 段与别家不同），
而判据原先写死 `日报_` ⇒ **下载成功了却报「30s 内没等到新的店铺报表」**。
已把判据放宽为 `/^日报\d*_\d{8}_[0-9a-f]+(?: \(\d+\))?\.xlsx$/u`，加了两条断言，
并做了突变验证（改回窄版立刻红）。五个 hash 段的实测对应：

| hash 段 | 店铺 |
| --- | --- |
| `adc987ef` | 盖文旗舰店 |
| `b3de46ce` | 里可林家居 |
| `80bec2d7` | 网林家居旗舰店 |
| `90f3f449` | 盖文全卫定制 |
| `aefdcd05` | 科塔全卫定制 |

另外：**文件名里的日期是「下载日」，不是「数据日」** —— 所以「这份是谁的、哪一天的」只能读内容。

### 发现 5：两张表的日期字段名不一样

底单叫「统计日期」，询单表叫「**日期**」。用错名字的表现是「当天 0 行」，
看起来像「还没写过」。查/写这两张表时先确认字段名。

### 发现 6（自己的坑，记下来免得再犯）：期望值不许从「显示值」抄

终局探针第一次报 `FAIL`，原因是期望值抄了 openpyxl 读出的 `2,059`（带千分位），
而落库是 `2059`。**这是探针的错，不是数据的错**。
教训：拿源文件的**显示形态**当期望值、拿落库的**规范化形态**做比较，必然假红/假绿。
比较前先归一到同一种形态（这里就是去掉千分位）。

### 发现 7（P1 风险，本轮实测）：商家浏览器的身份不稳定，且现在和某家店撞店

只读复测（`15-identity-recheck.txt`，不点不导航）的结果：

- **19022 的生意参谋页头是「里可林家居」**，而 **19031（`likelin-home`）也是「里可林家居」**
  —— 两个不同 profile 的窗口，生意参谋里指向**同一家店**。
- 19022 **没有阿里妈妈页**（这一条对「推广段能不能在 19022 上跑」是硬约束）。
- 19022 同时开着飞书底单页、生意参谋页、还有待办页，是这套流程里最重的一个窗口。

为什么这是风险：这套链里**唯一稳定可靠的店铺身份判据是源 xlsx 的「店铺名称」列**
（推送脚本正是这么取身份，所以今天四家推送的落库店名全对）。但只要将来任何一步
去读 19022 的生意参谋页头来「确认是哪家店」，它读到的会是**里可林家居** ——
在正确的数据上做一次错误的身份判断，比不做判断更糟。

同一个 profile「今天登进谁」是**浏览器密码库里第一条凭据**决定的
（`docs/ops/MULTI-SHOP-AND-INTERACTION-DECISION.md` §4.2 第 3 条已记过一次同样的现象）。
本轮这条**有明确起因**：SOP §11.3 记的那次「商家浏览器的持久 profile 掉了生意参谋会话、
重新登录后登进了里可林家居」—— 也就是说 19022 的身份**今天已经变过一次**，
这也解释了为什么 03:24 / 07:38 还能用它推盖文旗舰店、而现在它的页头是里可林家居。
⇒ 建议：**不要用共享的商家浏览器读任何站点身份**；要么让身份只能从源产物里读，
要么在采集脚本里对「这个窗口应该是哪家店」加断言（`--expect-shop` 已经在做这件事，
缺的是「谁来提供这份期望值」——现在由人工参数提供，多店铺时应该由登记表自动带出）。

**顺带一条要查清的事**：盖文旗舰店 `09-17` 那一行是当天 **03:24 与 07:38 两次推送**留下的
（审计 `id=8 → recvvxsGEeVN4X`、`id=12 → recvvyuoVc9nXi`，两次源文件都是 `日报_20260918_adc987ef….xlsx`，
两次的字段核对数都是 244）——也就是「推一次、删掉那天、再推一次」。**本轮没有留证据说明那份 xlsx
是哪个窗口采到的**，而 19022 现在的页头又不是盖文旗舰店。下次要查这条时，
从审计表的 `source_shop_file` + 采集脚本台账两头对。这也说明一条改进：
采集段也应把「用哪个代理/浏览器采的」记进审计，现在只有推送段有 `browser_port`。

三条硬事实（本轮再次应验）：

1. **采集脚本只认代理**（它们打 `/targets` `/eval` `/navigate` `/click` `/clickPoint`），
   裸 CDP 端口只有 `/json/list` ⇒ 每个店铺窗口必须各配一个代理进程。
2. **代理「连哪个浏览器」是 import 期常量**（`CDP_BROWSER_PORT`）⇒ 换浏览器必须重启进程，
   所以「按店铺实例化」＝一家店一个代理进程（19041-19044）。
3. **浏览器实际身份 ≠ profile 名**，也 **≠ 运营叫法**：盖文淘宝那家在阿里妈妈显示的是
   `随心品质定制:阿彦`（老会员号沿用旧品牌名）。跨站点比名字没有意义，必须逐站点各取各的、各自比对。

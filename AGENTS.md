# 生意参谋自动化项目

## Scope

- `skills/` contains the project-owned SYCM export and Feishu import skills.
- `evidence/` contains validation outputs and run evidence; do not treat it as live input.
- `runtime/` contains project-local notes or future launch wrappers.
- The logged-in Edge profile, credentials, and cookies remain outside this project.
- The active Feishu credential file is resolved from `runtime/feishu-targets.mjs` (currently the kcne tenant: `E:/小红书/.env.feishu-kcne.local`); pass its path to import commands and never copy its values into this project. Never hardcode tenant app tokens or base/table ids — read them from that single source of truth.
- Read `docs/ops/LESSONS-2026-09-14_15.md` before changing a state machine, a release path, or collection semantics: it lists the failures that have already cost time here.
- Read `docs/ops/REPAIR-PROTOCOL.md` before starting any repair: a fix is not done until the same-family scan (three questions), the attack pack, and the verification status are all reported. `docs/ops/COLLAB-CONVENTIONS.md` defines the default acceptance criteria for repair-class tasks when the user's instruction does not spell them out.

## Operating Rules

- Xiaowangshen browser work uses the project's debug Edge on port `9222` (`--user-data-dir=D:\Retire\edge-debug-profile`, which has the 小旺神 extension) plus CDP proxy `3457`; exports pass `XWS_PROXY=http://127.0.0.1:3457` and `XWS_BROWSER_ID=edge-isolated`. The SYCM/Alimama daily-report workflow uses its separate merchant Edge on `19022` (`D:\Retire\edge-daily-report-profile`) plus proxy `19023` and browser id `edge-daily-report`. All four values live in `runtime/browser-ports.mjs` — read them from there, never hardcode a second copy. Do not use the shared proxy on `3456` (another project's), and treat `9223`/`3458` as other projects' ports since 2026-09-16. No production file may point at another project's proxy: `runtime/browser-ports.mjs` exports the registry plus a test that fails on any `http(s)://<host>:3456` literal in shipped code or a `SKILL.md` (comments explaining the ban are allowed, and the allowlist is empty on purpose).
- The two chains must never share one browser instance: SYCM/Alimama/Feishu need the merchant account, while the 小旺神 extension only works on the buyer account. Getting this wrong fails silently — clicks and navigation succeed on the other account's browser.
- Route ownership is a table, not a habit — `ROUTES` in `runtime/browser-ports.mjs` is authoritative and `docs/ops/PROJECT-BROWSER-AND-PORTS.md` §1.3 is its readable digest. Buyer browser (`9222`/`3457`) carries the competitor chain (小旺神 market analysis, SKU, FAQ, question library) on `s.taobao.com` / `item.taobao.com` / `detail.tmall.com`. Merchant browser (`19022`/`19023`) carries keyword search-rank (生意参谋 搜索排行), the 灰豚 keyword-heat route (its own independent account — it sits there only so the whole keyword route needs one browser), the daily report (生意参谋 + 万相台/阿里妈妈 + Feishu), the weekly Feishu paste, and the reserved 千牛/卖家工作台 slot (`myseller.taobao.com` / `qianniu.taobao.com`). Assign a chain by the account its target site requires, never by which browser happens to be open. A seller-version account cannot use 小旺神 at all, so a merchant login on the buyer profile silently degrades collection rather than failing. A test also cross-checks that a route's declared browser matches the ports and browser ids its own skill scripts reference — editing one side alone turns it red.
- Rediscover page targets before each browser action; never persist target IDs.
- 页面判据只认**几何与命中**（`getBoundingClientRect` 的面积/坐标比例、`document.elementFromPoint` 的命中结果、`getComputedStyle` 的 position/z-index/display）：不认 class 名（平台改版就换），也不假设「相关元素都在某个容器的子树里」。读到 `0` 个候选时它**不是结论**，要换一个更宽的口径再数一次，并把两个口径的数都写进日志与错误文案（2026-10-28 三家推广卡在掩膜的兄弟节点上就是这么栽的）。规则、存量扫描与复发定位判据见 `docs/ops/PAGE-JUDGEMENT-FAILURES.md`。
- 一条能力**没做**或**这一步没走**时，日志里那句「跳过 / 暂不 / 未注入 / 不做」必须自带**待办**：说清替代路径是什么，或者说清这件事登记在哪、什么条件下补。只写「跳过」而不写「然后呢」，就是把降级写成了一句读起来像正常的日志 —— 后续所有读日志的人（含下一轮的我）都会把它当成已完成。两种合格写法：`没有注入 pressEscape ⇒ 跳过 ESC 这一步（改用有序候选表，见下一条日志）`、`商品底单采集没有遮挡处置（无现场，登记在 docs/ops/REPAIR-PROTOCOL.md 的挂起项、判据是它真出一次）`。不合格写法：`跳过`、`暂不处理`、`TODO`。
- "Released when done" is not the default and must not be assumed: `scripts/run-daily-job.mjs` without `--batches` has **no stop step at all** (its plan is only ensure-instances → login-preflight → chain), so a collection finishing leaves every browser and proxy running. Only `--batches N` goes through `scripts/run-batches.mjs`, whose release-after-batch is the one real caller of `scripts/stop-all.mjs`. When release is being verified or relied on, use `--batches` and say so explicitly.
- Never accept "released" from `scripts/stop-all.mjs`'s exit code alone: its release path has a known false-green (it reads the process table with a sync spawn, gets `EBUSY` under a sandboxed session, then asserts "nothing is running, nothing to do" and still exits 0). Confirm release by re-reading each port (`Get-NetTCPConnection -LocalPort <port> -State Listen`, twice — the first read can be stale) and, when it matters, by counting `msedge` processes.
- One target date, one `run-batches`. Check `runtime/.workflow-locks/merchant-automation.json` **before** doing anything expensive (measuring memory, choosing a batch size, starting instances), and read its `owner` as a three-way signal rather than "busy or not": another chain's owner (`run-daily-job` / `product-data`) means wait; a dead pid means the code will reclaim and you may proceed; but `run-batches:promotion-daily` holding the lock **for the target date you are about to run is a duplicate trigger of this same task, not a conflict** — 2026-10-26 measured two sessions arriving for one 11:00 round with the first already running. In that case do not start a second run, do not kill the first, and do not treat it as an error: monitor the in-flight round (`evidence/promotion-batches-<date>/b*/summary.json` + `batches.log`; `run-receipt.json` only lands when the round closes) and report its result, saying plainly that this session only monitored. `scripts/run-batches.mjs` acquires the lock as its first step and exits 1 with `运行锁冲突` rather than stealing a live lock, so a mistaken second launch cannot double-write Feishu — that is a safety net, not a reason to skip the check. Gate order is injury-check → lock → memory, because a held lock means the memory reading buys nothing. Current promotion-round memory thresholds and batch sizes live in `docs/ops/DAILY-FLOW-SCHEDULE.md`; never carry a second copy of the numbers here.
- A shop whose promotion reports are genuinely empty on the platform is not a failure and must not be chased as one. 网林家居 is the standing case: its 精准人群推广 spend went 12.77 CNY on 10-18 to 0 from 10-19 onward, with impressions and clicks 0 in the same window, and 关键词推广 spend 0 long-term — verified 2026-10-26 against the Feishu daily-report ledger (one row per shop per day), which is an independent source from the promotion chain. Leave the rows blank, do not alert, and reject the reflex to repair the collection path.
- Stop for login, CAPTCHA, QR/SMS, account-risk, security, permission, or other platform controls. Do not dismiss or bypass them.
- Modify only authorized Feishu copies, never the original template.
- Preserve displayed ranges and `-` values verbatim.
- After selecting 50 rows per page in SYCM, wait for the table itself to refill to at least 50 rows; the selector can show 50 while stale data is still rendering, which can skip ranks 11-50.

## Acceptance

## Development delivery check

- A local commit is not a delivered change. Before reporting completion, run `npm run check:delivery -- --commit=<sha>` and report `mainline_contains_commit`, `remote_contains_commit`, and `worktree_clean` separately.
- A worktree or feature branch may remain only when the handoff explicitly names its path, branch, commit, and next absorption action. Do not infer that a pushed branch changed `main`.
- The primary checkout is the default for bounded development. Use a worktree only for explicit isolation or concurrent work, and record its path, branch, base commit, owner, and absorption action.
- Before a local commit, run `npm run check:staged` and `npm run test:staged`; do not use `--no-verify` to bypass a failing check. Fix the check, narrow the staged scope, or stop at the evidence boundary.
- `npm run test:staged` has a wall-clock budget (default 1800 s per command, `--budget-seconds=N`, `0` = unlimited). Over budget it kills the whole process tree and exits **3 = INCOMPLETE**: that is neither a pass nor a failure, so report it as "no verdict" and never as green or red. Raise the budget (`--budget-seconds=7200`) or run the named command deliberately when you actually need that verdict — do not read a timeout as a test failure.
- Do not run `npm run test:staged` while a browser-driven chain (daily report, keyword, competitor) is in flight, or when machines are about to be handed over. Selecting a skill's implementation change runs **that skill's whole test suite**, including end-to-end files that spawn the real CLI as child processes; measured on 2026-09-25 that selection ran 664 cases in **7.6 hours**, 92% of it spent in 7 cases that each wait out the CLI's own 60-minute download deadline. It is a long, resource-holding run, not a quick check.

## Failure-exit gate (four questions before any chain goes on a schedule)

Born from the 2026-10-11 07:00 promotion round: the chain was wired into production scheduling with a shell (batches, evidence, release) but no kernel (no alert, no self-repair, no hold-on-unfixable, no summary signal) — 8 shops failed silently and the browsers were released. A chain that cannot answer these four questions is not allowed on a production schedule, no matter how green its happy path is:

1. **Does a failure alert?** A failed shop or failed round must reach notify-feishu through the shared alert path (`--alert-file` file-based handoff, deduped by fingerprint, delivered only on failure). "The log has the error" is not an alert.
2. **Does it self-repair?** A failed shop must go through the repair layer with candidates from the closed set (`DISMISS_OVERLAYS` / `RESET_PAGES` / `RELOAD_PAGE` / `REAPPLY_DATES`), or explicitly declare "no self-repair capability" via the summary signal below — never silently neither.
3. **If a shop cannot be repaired, does the round hold the browsers?** A failed round with unfixable shops must not release browser instances (release-after-batch reads `unfixableShopsOf`; a chain that writes no summary is invisible to it and will always release).
4. **Does its `summary.json` carry the unfixable signal?** Every chain entry must write `summary.json` with `shops[].status/error` and, for failed shops, `repairRequest.candidates` (empty array = "scripts cannot fix this, a human must look") — that is what release decisions, escalation, and agent handoff all read.

Mechanism/judgment separation check (applies to review, not just scheduling): escalation, perception, repair, and notify mechanisms live in the shared layers (`runtime/` + the daily-report skill's shared scripts). A new chain whose own files **contain** an implementation of these mechanisms instead of importing them fails review — duplicated failure-handling code is how the four questions above silently become false. The 07:00 incident chain had zero imports of the working failure kernel; a grep for the kernel's exports in the new chain's entry file is the minimum check.

- SYCM export: ranks contiguous and unique, source fields present, and CSV/XLSX validated.
- Feishu import: exact source-row count, first/last rank match, five source fields in order, no duplicate rows, and copied views/tables remain present.
- Xiaowangshen API import: authorized target table starts empty, all 16 fields exist, `商品图片` is attachment type `17`, and API verification reports equal source-row, imported-row, and attachment counts.
- Daily inquiry backfill: source shop/date/column and target date/shop match exactly, both inquiry fields match on reread, and unrelated target fields are unchanged.
- A stable session is evidence for the current run only; it does not guarantee future login persistence.
- Product-data chain (`scripts/run-product-data-job.mjs`, 销售1部 8 shops): the number of rows written is decided by the source — as many rows as 生意参谋 exports get written, no more and no fewer. **An empty platform export is not a gap**: when the export holds only the prompt rows, the header, and the 平均值/汇总值 rows, nothing is created and no `0` is substituted (receipt shows `sourceRows=0`). Verify by matching the receipt's `sourceRows` against the rows actually present (same-day duplicate protection excepted). Do not add extra gates for "a row might have been dropped" — the chain copies rows verbatim and its only filter removes non-data rows.

## Version and commit discipline (2026-10-12)

Born from the HEAD-vs-worktree incident: `ef629d0` committed the consumer side of a cross-file contract but not the supply side, so from 1.8.1 a clean checkout of HEAD could not even load the promotion chain (`SyntaxError: does not provide an export named 'pendingForKind'`). CI had flagged it in black and white and nobody looked, because CI had been red on every push for two weeks. Full investigation: `docs/ops/HEAD-VS-WORKTREE-DIVERGENCE-2026-10-12.md`. Five rules, all machine-checkable or already machine-checked:

1. **A cross-file contract never splits across commits.** If file A statically imports a new export of file B, both A and B land in the same commit. Explicit-path staging stays (it protects other sessions' in-flight files), but the path list must cover the whole contract — "my half only" is how ef629d0 broke HEAD. The guard `runtime/head-loadable.test.mjs` parses every import at HEAD against every export at HEAD and goes red on the next half commit the same day it is made.
2. **A version number in CHANGELOG ⇔ a commit whose VERSION equals it exists.** `1.7.18` documented a delivery whose code was never committed — the entry now carries a correction note, and `runtime/version-consistency.test.mjs` is the place to extend if this ever repeats. Two work streams share the single VERSION file: before cutting a version, read the latest version from `git log`, not from memory.
3. **Push after committing, and look at the CI verdict before calling the work done.** An unpushed commit or an unread red run is not a delivered change (see `check:delivery`). Chronic red is not background noise — it is the alarm with its battery removed; fix CI red the day it appears.
4. **Evidence is committed with its round.** Run outputs under `evidence/` are tracked on purpose (audit trail). A finished round ends with its evidence committed, not left floating; the backlog was archived 2026-10-12. `runtime/sop-runtime/scheduled-*/` and `/.tmp-*` are runtime artifacts and stay gitignored.
5. **Claim your files before editing.** Parallel sessions share this working tree. Before touching a file, check its mtime and `git log -1 -- <file>`; announce the file list you will touch in the session's daily log. Never commit a file another session is actively editing — hand it back instead.

Line-ending note (same incident): source-scanning tests (readFileSync + `\n` needles) are EOL-brittle — a clean CRLF checkout fails them while the dev tree passes. Every source-scanning test must normalize (`replace(/\r\n/g, '\n')`) before matching; five such sites were fixed 2026-10-12. A repo-wide LF renormalization (`.gitattributes`) is deliberately deferred until the working tree is clean, because renormalizing while other sessions have files in flight would swallow their edits.

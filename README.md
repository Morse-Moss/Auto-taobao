# 生意参谋到飞书自动化

> 十几家天猫/淘宝店铺的日报、商品、推广三条数据链，每早自己跑完，并在写飞书前后各核对一遍。

这不是一个采集脚本集合。它每天固定时间自动打开一批店铺后台，把生意参谋和阿里妈妈的报表取下来、
按团队写进飞书多维表格，然后**逐项回读**证明自己真的写对了。对不上就停下并告警，不猜、不硬写。

---

## 这是什么

一套跑在一台 Windows 机器上的多店铺电商数据自动化，服务多个运营团队的十几家店铺。

它做三件事：每日 08:00 取店铺日报与推广报表写飞书；10:00 取商品与推广明细；11:00 取推广日报。
三件事共用同一批浏览器与同一把运行锁，因此串行执行，互不打断。

它不做的：不预测、不给运营建议、不改平台数据。它只负责把平台上的数字准确搬到该去的地方，
并在搬错的时候当场说清错在哪一步、哪一行。

---

## 它凭什么可信

同类工具市面上不少，能采到数的很多，能证明自己没采错的很少。这一节是这个项目唯一真正的差异化。

- **写前量基线，写后独立回读。** 验收不看调度器返回的 `success`，也不看自己生成的 summary，
  只看飞书底单和一次独立的重新读取。两者不一致就是失败，哪怕流程"跑完了"。
- **对不上就停。** 行数、字段、日期、店铺身份、报表类型，任何一项对不上都拒绝写入（fail-closed），
  不做"尽力而为"。宁可这一轮空着，也不留一行错数在表里。
- **口径纪律写进代码。** 比率必须"窗口 × 店铺集合 × 指标定义"三者同时相同才能相比；
  广告花费等于关键词、人群、全站三个渠道之和；推广后台自记的成交额不许与商品层成交混算。
  这类规则有专门文档与门禁守着，不靠人记住。
- **每一轮都留证据。** `evidence/` 下按业务日与批次归档，能回溯到哪家店、哪一步、哪一行、
  当时的页面长什么样。
- **改数字要过门禁。** 四道门禁分别守着报告、演示材料、对外文档和表格的逐格取值，
  全部逐项断言、不抽样。想改一个数，先过门禁——门禁只查数字是否站得住，改口径还得另跑一次全仓检索。
- **判不了就说不知道。** 登录态、报表页是否就绪、滑块是否在冷却，这类判断不许猜。判不了就停在
  那里等人，不降级、不"应该没问题"。

## 一天是怎么过的

```
06:50   起浏览器：每家店一个独立 profile + 独立代理端口，互不串号
08:00   日报链（11 步 × 全店）
        体检 → 切阿里妈妈日期 → 提交推广报表生成 → 切生意参谋日期
        → 下载店铺日报 → 取推广压缩包 → 写飞书 → 页面回位
        → 再切一次 → 询单回填 → 独立回读
10:00   商品链：商品报表（含推广明细）与询单
11:00   推广日报链：关键词、人群两张表，按团队分别写入
之后    对账门逐店核对；异常按可修复/需人工分诊，需人工的才发告警
```

三条链的间隔不是随便定的：它们共用同一把锁，间隔按各链实测耗时（推广 3–7 分钟、
商品 11–13 分钟、日报 25–60 分钟）留冗余。有人问"为什么不并行"——并行会抢浏览器，
抢浏览器的结果是两家店的数混在一起。

## 现在能跑什么，跑不了什么

能跑（真机验过）：

- 十几家店铺每日三条链全自动，含自修复与飞书告警
- 日报 11 步完整链路、商品含推广明细、推广日报两表按团队写入
- 单店单步重跑与断点续跑；锁冲突时识别"是别的链还是自己重复触发"

跑不了（已知边界，不是待办清单）：

- **历史日（非昨日）不能重采。** 采集器会把页面日期控件拨回"昨日"，补历史日需要新增
  "驱动页面日期控件"的能力，不是重跑一次就能解决。
- **部分店铺的飞书表缺应用编辑权限**，写入返回 403。这是人工闸门（要对方开权限），
  不是代码问题；这类缺口与另一团队的缺口必须分开汇报，不能合并成一个数。
- **周报链必须在周一跑。** 窗口是周日到周六，过了那天不自动补跑，补跑是显式动作。
- **滑块是频率窗口，不是账号锁。** 挂住了就等冷却，不做自动过滑块——对抗只会换来更长的封禁。
- **08:00 早于阿里妈妈的数据静止点（11:20）。** 低值当日仍需二次导出核对，这一步目前是人工的。

## 快速开始

需要 Node 22 或更新（`engines.node` 为 `>=22`，更低版本 `npm ci` 会以 `EBADENGINE` 拒绝）。

```powershell
# 1) 装依赖（不跑安装脚本）
npm ci --ignore-scripts

# 2) 只做离线自检：三个确定性 self-test，不碰浏览器、数据库、飞书
npm run test:offline
```

跑真链之前，还差两件不在这份文档里的事：一份本机凭据文件（只在命令里传路径，不复制值进仓库），
以及一份按店铺登记的端口与 profile 清单。这两件事按 `docs/ops/DAILY-REPORT-STANDALONE-DEPLOYMENT.md`
逐步做，不要跳。

第一次接真实店铺时，先只用定位模式：它会把页面开到该去的地方并校验报表页，**不提交任何任务、
不写任何一行**。定位通过，再跑单店单链，最后才上全量。

```powershell
# 只定位与校验报表页，不提交任务（最安全的一次真机验证）
node skills\sycm-alimama-daily-report\scripts\run-promotion-daily-report.mjs --locate-only --shop <店铺>
```

## 架构

```
┌─ 浏览器层 ───────────────────────────────────────────┐
│ 店铺 profile × N（一店一 profile + 一店一代理端口）      │
│ 商家后台 profile（生意参谋 / 阿里妈妈）                  │
└───────────────────┬─────────────────────────────────┘
                    │ CDP，每店固定端口；脚本只认代理，不认"随便连一个"
┌───────────────────▼─────────────────────────────────┐
│ 采集层  14 个 skill + runtime/ 运行底座                │
│  登录判据 · 页面就绪判据 · 重试与冷却 · 自修复分诊        │
└───────────────────┬─────────────────────────────────┘
                    │ 本地 CSV / XLSX + 回执
┌───────────────────▼─────────────────────────────────┐
│ 上报层  飞书多维表格（按团队分 base，按店分表）           │
│  写前量基线 → 幂等键去重 → 写入 → 独立回读               │
└───────────────────┬─────────────────────────────────┘
                    │
┌───────────────────▼─────────────────────────────────┐
│ 验收层  对账门 · 四道门禁 · evidence/ 按业务日归档        │
└─────────────────────────────────────────────────────┘
```

| 层 | 技术 |
|---|---|
| 浏览器 | Edge + CDP，一店一 profile、一店一代理端口，统一带 `--disable-sync` |
| 采集 | Node 22，直连 CDP（不逆向签名、不用第三方采集器） |
| 编排 | `runtime/`：运行锁（owner 三态）、批次、驻留、排期、告警投递 |
| 存储 | 飞书多维表格（唯一对外口径）＋ 本地 `evidence/` 归档 |
| 门禁 | 4 道：报告、演示材料、对外文档、表格逐格，逐项断言而非抽样 |

细节见 `docs/architecture/README.md`。本文不复述架构细节——**复述过一遍的东西，迟早两处不一致。**

## 数据与安全边界

- 本文档以及所有对外文档中的店铺、租户、凭据位置，一律用类别或占位表述；具体标识不进文档。
- 账号密码、Cookie、浏览器用户目录、验证数据不属于项目资产，不复制进仓库。
- 采集只读平台自身已授权的报表；不绕过验证码，不做频率对抗。
- 真实店铺标识、表 id 与凭据只存在于本机运行配置与私有部署环境。
- 本仓库为内部自用工具，未授权外部使用。

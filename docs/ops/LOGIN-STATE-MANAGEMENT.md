# 登录态管理设计（检查、判据、失效、自助恢复）

日期：2026-09-15 ｜ 场景：单机单店铺，部署在一台**专用电脑**上（只跑自动化系统，无其他人日常使用）
起因：用户要求在落地无人值守方案前先把「登录态检查」讲清楚，并指定参考 `E:\小红书` 的实现。

本文件回答四件事：**登录态为什么会失效**、**怎么检查才算检查到位**、**判定结果怎么分级与动作**、
以及**参考项目里哪些能抄、哪些抄不了**。它是 `UNATTENDED-AGENT-RUNTIME-PLAN.md` §2 第①步「体检」的展开。

## 0. 结论

1. **「不关机」不是登录态的保障**。登录态失效与关机几乎没有关系，主因是凭证自然过期、
   同一个浏览器配置被别的账号登录、以及平台侧风控。
   2026-09-15 补充：部署机是**专用机**（无其他人日常使用），第 2 条的触发条件从
   「别人登了」收窄为「**自己为了看商家后台而用商家账号登录了同一个浏览器配置**」——
   概率降下来了，但**没有归零**，因为商家账号登录是日常运营动作，而且 2026-09-13 那次事故
   正是发生在自己的调试机上，与「有没有别人用」无关。
2. **只检查「有没有登录墙」不够，必须同时检查「登录的是谁」**。本项目 2026-09-13 的真实事故
   就是登录态完全正常、但登的是**商家账号**，被淘宝风控拒绝看别家店铺详情页——
   当时系统给不出这个结论，是人打开页面才发现的。
3. **检查分四层，成本从 0 到高**：身份层、环境层、会话层最便宜，端到端探活最贵。
   便宜的三层每次都跑，端到端只在通过后按预算跑一次。

## 1. 先纠正一条被写错的判断

我在 `UNATTENDED-AGENT-RUNTIME-PLAN.md` §8 与 `CLIENT-DESKTOP-DELIVERY-PLAN.md` 里写过：

> 「客户电脑上通常同时装着千牛，千牛会顶掉 Edge 的买家账号登录态。」

**这句话写过头了**，用户的质疑是对的。它的来源是 `runtime/daily-report-2026-09-13.md` 的问题 #3，
原文是：

> 现象：商品详情页打开即跳「访问被拒绝」风控页
> 原因：调试 Edge 登录的是商家账号（千牛调试时顶替了买家登录），淘宝新规禁止商家账号看别家店铺详情页

也就是说，真实事实是 **「当时为了调试，在同一个 Edge 用户配置里登过商家账号，把买家账号挤掉了」**，
而不是「千牛客户端会在后台自动踢掉浏览器登录态」。前者是一个**明确的、可检查的、可预防的状态**
（登录身份不对），后者是一句无法验证的因果断言。

修正后的口径见 §2，两份文档已同步改。

## 2. 登录态到底为什么会失效

按「在专用机上实际发生的概率」排序（括号内标明部署形态变化后的影响）：

| # | 机制 | 与关机有关吗 | 在专用机上的表现 |
| --- | --- | --- | --- |
| 1 | **凭证自然过期**：淘宝会话 cookie、小旺神插件自身的登录 token、灰豚会话各有各的有效期 | 无关 | 隔几天就会发生一次；**不关机照样发生**（专用机无改善，仍是第一主因） |
| 2 | **同一浏览器配置被别的账号登录**：在这个 Edge 用户配置里登了另一个账号（商家账号、别的店铺账号） | 无关 | 专用机不再有「别人」，但**自己看商家后台时会用商家账号登录**，仍会发生（2026-09-13 的 #3 事故就发生在调试机上） |
| 3 | **多实例/多 profile 互踩**：同一个 `user-data-dir` 被两个 Edge 实例使用，或切换内置 profile | 无关 | 专用机风险下降，但手工调试时同样会踩（例如双击图标开出了默认 profile 的窗口） |
| 4 | **浏览器侧清理**：手动「退出登录」「清除浏览数据」、隐私清理工具、Edge 大版本更新后偶发重置会话 | 无关 | 专用机只剩后两项（Edge 自身更新、手工清理） |
| 5 | **平台侧风控**：同账号异地/异机登录、访问频率异常 → 强制登出或跳验证码 | 无关 | 生意参谋对频率最敏感；被顶后需要人工过验证码（专用机无改善） |
| 6 | **域间不共享**：淘宝主站已登录 ≠ 生意参谋已登录 ≠ 小旺神插件已登录 ≠ 灰豚已登录 | 无关 | 常出现「淘宝好好的，生意参谋跳登录」（专用机无改善） |
| 7 | 关机/注销/重启 | 有关（唯一一条） | 会中断正在跑的浏览器；登录态本身未必丢。专用机通常不关机，但 **Windows 自动更新会替你重启** |

**结论**：换成专用机消掉的是第 2、3、4 条里的「别人」因素，第 1、5、6 条一条都没消。
所以「登录态会失效」这件事的**优先级不因专用机而下降**，四层检查一样要做。

**反过来，不关机带来的是新问题，不是保障**：定时任务会在没人看着的时候去动浏览器；
如果那时登录态已经失效，任务会失败；15 分钟一次的心跳若无脑重试，反而可能触发风控。
所以正确的做法不是「靠不关机维持登录态」，而是 **「高频轻量检查 + 可靠通知 + 人工确认后续跑」**。

**2026-09-18 补充一条与本节同族、但形态不同的机制**：登录本身被平台拦下（短信验证码 / 实人认证）
**不是「登录态失效」，而是「这次登录被当成新设备」**。它会让 §4 的状态词表里多出一种需要人的情形，
但处置完全不同（不是「重新登录」，而是「别再重新登录」）。详见 §10。

## 3. 检查怎么做：四层判据

原则：**便宜的层每次都跑，贵的层只在便宜层通过后按预算跑一次**；任何一层给出确定结论就短路。

### L0 身份层（最便宜，必须先做）

检查「当前登录的是不是我们要的那个身份」，而不是「有没有登录」。

| 对象 | 判据（示例，需实测确认） | 不一致时 |
| --- | --- | --- |
| 淘宝 | 页面上的账号昵称/会员名，与配置的**买家账号**期望值比对 | `ACCOUNT_MISMATCH` |
| 生意参谋 | 页面上的店铺名，与配置的**目标店铺**比对 | `ACCOUNT_MISMATCH` |
| 小旺神 | 插件内展示的登录账号 | `ACCOUNT_MISMATCH` |

**这三条必须按浏览器分组跑**：淘宝/小旺神只能在**买家浏览器**的端口上查，生意参谋只能在**商家浏览器**的端口上查。
在错的浏览器上查，会得到「已登录」而实际那是另一个账号 —— 这正是 `ACCOUNT_MISMATCH` 要拦、却最容易被漏掉的一侧。
两条链各归哪个浏览器、各要哪种账号：见 [`PROJECT-BROWSER-AND-PORTS.md`](PROJECT-BROWSER-AND-PORTS.md) §1.3。

这是 §1 那条事故的正确防线：**登录态「有效」但身份「不对」，在业务上等价于没登录**。

### L1 环境层（0 成本，纯进程与端口）

- CDP Proxy 在不在：`GET {proxy}/targets` 是否返回。
- Edge 在不在、用的是哪个用户配置：`user-data-dir` 路径必须是那个**专用**配置。
- 目标标签页在不在：按 `automationLabel` 找（现有 `discoverTarget` 已实现）。
- 插件是否加载：`pluginPresent`（现有实现已有）。

### L2 会话层（读凭证，不发起业务请求）

读取各平台的会话凭证是否存在、是否临近过期：

- 判据 = 「关键 cookie/键存在」+「到期时间 - 现在 > 预警阈值」。
- 只读**存在性与到期时间**，**不记录明文值**（与项目规范一致）。
- 关键 cookie 名单**必须在真实环境实测采集一次后写死进适配器**，不许凭记忆或凭文档抄——
  平台改版会改名单，所以这是「随时间要维护的适配器资产」，不是常量。

### L3 端到端层（最贵，只读探针）

用一次「已知结果的只读请求」验证真的能用：

| 平台 | 探针 | 成功信号 | 失败信号 |
| --- | --- | --- | --- |
| 淘宝 | 打开一个自家/已知页面 | 正常渲染 | 跳登录页 → `AUTH_REQUIRED`；跳风控/验证码 → `RISK_BLOCKED` |
| 生意参谋 | 打开 sycm 首页 | 正常渲染 | 同上 |
| 小旺神 | 现有 `PAGE_EXPRESSION` 的 `loginMarkers` + `visibleLoginDialog` | `AUTH_READY` | → `AUTH_REQUIRED` |
| 灰豚 | 打开一个已知关键词页 | 正常渲染 | 扫码+拼图 → `HUMAN_REQUIRED`（**不可自动化绕过**） |

L3 必须带预算与冷却：一轮只跑一次，失败不重试（重试只会加速风控）。

## 4. 判据分级与动作

状态词表（在现有 `xws-sku-auth-preflight.mjs` 的 `AUTH_READY / AUTH_REQUIRED / PLUGIN_UNAVAILABLE /
PLUGIN_NOT_READY / SOURCE_MISMATCH` 基础上扩，**只加不删**）：

| 状态 | 含义 | 通知 | 通知里写什么（人话） | 后续 |
| --- | --- | --- | --- | --- |
| `AUTH_READY` | 四层全过 | 不通知；若之前有未恢复告警则补一条「已恢复」 | — | 继续本轮 |
| `AUTH_EXPIRING` | 凭证未失效但快到期 | **提前通知（低优先）** | 「XX 登录预计 N 天后到期，建议今天点一下重新登录」 | 不阻断本轮 |
| `AUTH_REQUIRED` | 需要登录 | 强通知 | 「XX 登录已失效」+ 操作步骤 + 一键重登入口 | 停止本轮，等人 |
| `ACCOUNT_MISMATCH` | 登录的是别的账号 | 强通知 | 「当前登录的是 A 账号，系统需要 B 账号」 | 停止本轮，等人 |
| `RISK_BLOCKED` | 验证码/风控页 | 强通知 | 「需要人工在浏览器完成验证，系统不会绕过」 | 停止本轮，等人 |
| `PLUGIN_UNAVAILABLE` / `PLUGIN_NOT_READY` | 插件没加载/没就绪 | 强通知 | 「小旺神插件未就绪」+ 重开指引 | 预算内自愈一次，仍失败则升级 |
| `SOURCE_MISMATCH` | 页面不是目标商品/店铺 | 不通知（属流程参数问题） | — | 记证据，按缺陷处理 |
| `AUTH_UNKNOWN` | 判据缺失，给不出结论 | 不通知，但**不放行**（fail-closed） | — | 记证据；连续 N 轮 UNKNOWN 升级为强通知 |

三条硬规则（沿用现有实现，不改）：

1. **去重与恢复成对**：同一原因不重复轰炸（现有 `delivery.status=DEDUPED`）；恢复时必须补一条
   「已恢复」（现有 `resolveAlert` 已实现，保留）。
2. **通知必须带「下一步做什么」**，不能只报状态码。
3. **通知失败不影响主流程**，且要留证据（现有 `delivery.status=FAILED` 写入告警文件，保留）。

## 5. 参考实现：`E:\小红书`（用户指定）

### 5.1 它的多租户怎么做

| 位置 | 做法 |
| --- | --- |
| `backend/app/models/tenant.py` | `Tenant`（name/slug/kind/status）+ `TenantMember`（tenant_id, user_id, role，唯一键 tenant+user） |
| `backend/app/models/platform_account.py` | 账号表的唯一键是 **(user_id, platform, sub_type, external_user_id)** —— 按归属人隔离身份 |
| `backend/app/core/deps.py`、各 API | 一律从当前用户出发过滤，跨用户取不到 |
| `usage_quota` / `beta_concurrency` | 按租户做配额与并发闸门 |

**我们是否需要**：不需要（单机单店铺）。**但其中一条必须抄**：
`PlatformAccount` 的「身份唯一键 = (归属人, 平台, 子类型, 外部账号 ID)」。
这正是 §3 的 L0 身份判据——**账号是一个有唯一身份的对象，不是一个 cookie 串**。

### 5.2 它的登录态怎么存

| 位置 | 做法 |
| --- | --- |
| `models/platform_account.py` → `AccountCookieVersion` | 凭证**版本化**：每次登录追加一版（`encrypted_cookies` + `created_at`），永远取最新一版 |
| `core/security.py` → `encrypt_text/decrypt_text` | 凭证明文不进库，Fernet 加密存储（secret 变更会导致旧凭证解不开，这是已知代价） |
| `services/account_service.py` → `latest_cookie_version/latest_cookie_header` | 取最新凭证的唯一入口 |

**为什么值得抄**：凭证有了历史与版本，就有了三件事——可审计（什么时候换的）、可回滚（哪一版还能用）、
可判据（最新一版是否存在且未过期）。我们现在登录态只活在 Edge 的 user-data-dir 里，
应用侧没有任何副本，所以「体检」只能靠注入表达式看页面现象，判据天然薄弱。

**抄法（与本项目规范不冲突）**：profile 仍然是唯一执行源；
但每次体检把 **会话指纹**（各平台关键凭证的**存在性 + 到期时间 + 身份标识**，不含明文值）
加密存进 PG，作为告警、续跑、报表的权威依据。这样既不落明文凭据，也不改变执行路径。

### 5.3 它的登录怎么做

| 位置 | 做法 |
| --- | --- |
| `models/login_session.py` | 一次登录过程是一个对象：`status`（pending/scanned/confirmed/expired）、`login_method`（qr/phone）、`qr_id`、`encrypted_temp_cookies`、`poll_in_progress` |
| `api/login_sessions.py` → `_claim_login_session_poll/_release_login_session_poll` | **单飞闸**：同一会话的并发轮询只有一个真去打上游，其余直接读库（超时 90s 自动释放） |
| `api/login_sessions.py` → `pc_qrcode/creator_qrcode` | 二维码为主：生成 → 前端轮询 → 用户扫码 → 自动确认 → 落账号 + 追加凭证版本 |
| 同上 → `pc/phone/send-code` + `pc/phone/confirm` | 手机验证码为备选路径（同一条状态机，只是 `login_method=phone`） |

**为什么值得抄**：我们现在只有一个「体检快照」，没有「一次登录过程」的对象。
而我们要做的「扫码重登 + 人工确认继续」本质上就是一个**有人参与的会话**：
谁发起的、二维码什么时候过期、谁确认的、结果如何——这些必须落库，否则并发点击会重复开登录窗口，
且「继续」动作无法幂等。

### 5.4 它的登录态「检查」怎么做（最值得抄的一节）

| 位置 | 做法 | 对应我们的哪一层 |
| --- | --- | --- |
| `services/account_service.py` → `_evaluate_xhs_pc_login_readiness` | **本地字段判据**：账号状态 active + 最新凭证存在 + 关键字段（`web_session`）非空 → `login_ready`，否则给出**人话原因**「账号登录信息不可用，请重新登录」 | L2 会话层 |
| `api/accounts.py`（账号检查接口） | **主动探活**：拿凭证打一个只读接口；成功 → `active`；失败 → `expired` + 人话原因；无凭证直接 `expired` | L3 端到端层 |
| `api/platforms/xhs/pc.py` → `_get_owned_pc_account_and_cookies` | **运行前检查**：不 ready 就先把账号标 `expired`，再返回 409 + 人话原因——**不带着已知无效的登录态往下跑** | 体检前置 |
| `api/platforms/xhs/pc.py` → `XHS_MISSING_LOGIN_SIGNALS` + `search_failure_kind` | **运行中失效信号识别**：把上游返回文本里的「无登录信息/请先登录/not logged in」映射成「账号失效 → 立即停止」，不当作普通失败重试 | 运行中 |
| `services/platform_readiness_service.py` | 就绪度报告 = 逐项 check + `verdict` + `user_impact` + `next_action`，面向人读 | 通知话术模板 |

最后一条尤其重要：**「运行中识别失效」和「运行前检查」是两件事，缺一不可**。
只做前置检查，会在「刚检查完好、跑到一半被风控踢掉」时把失效当普通失败重试，越试越糟。

### 5.5 哪些抄不了

`E:\小红书` 是**服务端持凭证直接调 API**（`apis/` + `static/` 的签名层 + `requests`），
所以在服务器上跑，凭证是执行源，可无头、可多账号并行。

我们的采集对象是**小旺神插件 + 生意参谋 + 灰豚**，必须真实浏览器（插件、签名、风控），
凭证落在浏览器 profile 里。因此：

- 执行源永远是浏览器，不能改成「库里拿 cookie 直接请求」；
- 必须管理的是 **Edge 用户配置（user-data-dir）的生命周期**，这是它不需要面对的问题；
- 多账号并行（它按 user_id 隔离实现）我们做不了也不必做：单店单账号，浏览器写操作恒 1、串行。

## 8. 边界与不做的事

- **不做账密代登**：系统**不持有、不代填、不代存**凭据，也不代替人提交登录表单。
  **2026-09-18 把这条切细了**（本轮实测后必须切，否则文档与代码互相打脸）：
  - 允许：**浏览器自己的密码管理器**填充（值不经我们的代码），外加**一次可信手势**
    （CDP `Input.dispatchMouseEvent` 点一下空白处）让填充真正落进 DOM —— 见技能
    `chromium-autofill-preview-vs-trusted-gesture`。这是「让浏览器干它本来就干的事」，不是代登。
  - 不允许：从我们这边把账号密码**写进**表单并点提交（凭据会经过我们的进程与内存/日志）。
  - 两者都成立的前提是**凭据存在浏览器 profile 里**（本机 `Login Data`，用户自己点保存）。
    所以这条路对「客户机」是可选增强：客户没存过密码 → `NO_SAVED_CREDENTIAL` → 走通知叫人。
- **不绕验证码与风控**：命中 `RISK_BLOCKED` / 短信验证 / 实人认证只通知，不做任何自动化尝试。
  **并且不做「换个新会话再试一次」** —— 2026-09-18 实测证明那恰恰是触发风控的动作（§10）。
- **不因为「检查失败」就自动重试登录**：重试是风控的加速器。
- **凭证明文不入库、不进日志、不进通知**（沿用 `docs/standards/README.md` 安全边界）。
- **判据会过期**：三个平台的标记与键名都是**要随平台改版维护的适配器资产**，
  所以必须有「判据健康度」的可见性——连续 `AUTH_UNKNOWN` 就是平台改版的早期信号。

## 10. 2026-09-18 实测：短信验证码是**设备属性**，不是账号属性

**起因**：用户报「我发现要短信验证码才能登录」。此前四家店铺（里可林家居 / 网林家居旗舰店 /
随心品质定制 / j873522735，子账号都是 `阿彦`）的登录探针全部没能进登录态。

### 10.1 决定性对照（同一台机器、同一个 profile、同一天）

| 观察对象 | 会话来源 | 结果 |
| --- | --- | --- |
| 生意参谋 `sycm.taobao.com/qos/service/frame/shop/performance/new#/shop` | **默认 context**（用户手动登录留下的持久会话） | 掉登录=false，页面读到「科塔全卫定制 主店」，统计时间 2026-09-17 |
| 阿里妈妈 `one.alimama.com/index.html` | 同上 | 掉登录=false，页面读到「j873522735:阿彦 ID：412070158」 |
| 同四家店，`shop-login-check.mjs` 每店一次登录 | **每店一个新 `Target.createBrowserContext`**（隔离会话） | 里可林 → `passport.taobao.com/iv/normal_validate.htm`；网林 / 随心 → `passport.taobao.com/iv/identity_verify.htm`（手机验证码，189\*\*\*\*\*\*36）；j873522735 → 提交后**仍停在登录页** |
| 同上，第一轮（run1） | 同上 | 里可林 → `zizhanghao.taobao.com/authenticate/login/login_auth_intercept.htm`（子账号实人认证） |

**结论**：同一个账号，**持久会话里不需要任何验证**，**全新隔离会话里必然被要求二次验证**。
所以「要短信验证码」不成立为账号的固有属性；它是**「这台浏览器在平台眼里是首次见到的设备」**的结果。

### 10.2 我们自己的探针就踩在这个机制上

`shop-login-check.mjs:94` 每店 `Target.createBrowserContext` —— 隔离 context **不共享** cookie 与
存储，等于给平台报了一个**全新设备指纹**（没有 `cna` / `cookie2` / `sgcookie`）。叠加第二种触发条件：
**同一个 profile 在半小时内连续登录四个不同商家账号**。两条都是风控最敏感的形态，
而且**两条都不是业务必须的，都是探针为了「四家店互不干扰」自找的**。

**这条同时否掉了三条本来很自然的做法**（§8 已同步收口）：

1. 否掉「命中验证码就换个新会话重试」——那等于每次都伪装成新设备，是风控的加速器。
2. 否掉「四家店各自开一个全新隔离 context 来跑」——多店并行必须**每店一个 profile**，不是每店一个 context。
3. 否掉「自动登录是常规路径」——自动登录只在**已有持久会话但降级为未登录**时兜底；
   首次登录只能是**一次性 setup**（人工过一次，且那一刻的验证由人来做）。

### 10.3 由此定下的口径（这才是「怎么修」）

登录的正确形态是 **「一次性 setup + 长期持有」**，不是「每次运行时登录一次」：

- 每个店铺一个**专用 profile**（§9 的「交付专用 profile」），profile 里的持久会话就是登录态本体。
- 运行时的动作是**检查**这份会话还在不在（L0 身份 + L2 会话），不是重新登录。
- 会话真没了才两路兜底：① 浏览器自己的密码管理器填充 + 一次可信手势（§8 允许的那种）；
  ② 兜底失败 → 飞书提醒叫人（`login-merchant.mjs --notify`，2026-09-18 已接线）。
- **验证码 / 实人认证永远由人过**，我们只负责把「需要人」这件事可靠地喊出来。

### 10.4 附带改掉的判据与两个待核事实

**判据层面（已生效）**：`run3` 第一版结论里，里可林被误判成 `LOGGED_IN_AS_EXPECTED` ——
因为**实人认证拦截页上印着账号名**，而旧判据是「离开登录页 + 页面文字含店铺名」。
权威判据只能是**下游业务站点进没进去**（四家最终全部落在生意参谋 `custom/login.htm`）。
这条与 §3 的 L0 同源：**页面上的名字不是身份证据，下游站点的登录态才是**。

**顺手量到一条可直接用的身份判据**（补 §3 L0 四平台全缺的那一项）：

- 只读读取（**不发起任何业务请求、不新建标签**）：CDP `Storage.getCookies`（不传 `browserContextId`
  ⇒ 默认 context 全量）。身份键 = `sn`（就是「主账号:子账号」）、`unb`（数字账号 ID）、
  `sgcookie` / `cna`（长寿命标记）。**`sn` 是明文的，可以直接与配置的期望账号比对。**
- 实测：生产浏览器（19022）= `sn: 盖文旗舰店:阿彦` / `unb: 2222876427638`；
  测试 profile（19026）= `sn: j873522735:阿彦` / `unb: 2223103073716`。
- **限定**：这只能证明「这台浏览器现在以谁的身份持有会话」，**不能证明「这个身份有权限做那件事」**
  ——「有会话」与「有权限」是两件事，后者仍要 L3 端到端探针。别把它当成 L3 的替代品。

**两个待核事实（都还没结论，不许当已知）**：

1. 测试 profile 的会话身份是 `j873522735:阿彦`，而该 profile 里**生意参谋当前圈定的店铺是
   「科塔全卫定制 主店」**。这不是账号冲突（`taobao.com` 与 `alimama.com` 的 `sn` 同一个值），
   但说明这个子账号名下**不止一家店** ⇒ **L0 对生意参谋必须比对店铺名**，
   否则会出现「账号登对了、看的是另一家店」——这正是 §1 那条事故的另一副面孔。
2. 四家店的凭据只有两家被浏览器存下（里可林家居:阿彦 落 `login.taobao.com/havanaone/login/login.htm`、
   随心品质定制:阿彦 落 `havanalogin.taobao.com/mini_login.htm`），网林家居旗舰店、j873522735 都没存下；
   已查 `blacklisted_by_user=1`（「从不保存」名单）**为空**，所以不是被拉黑，原因待查。
   另：`mini_login.htm` 这个 origin **不能独立打开**（报「非法请求 [appNameError]」），
   所以「保存的 origin 不统一」对自动化不是等价的两条路。

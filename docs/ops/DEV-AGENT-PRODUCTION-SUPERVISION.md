# 开发 Agent 对生产运行的监管契约

> 状态：**部分已落地**。每一条都标了「已实现 / 未实现」，不把设计当能力。
> 日期：2026-09-15
> 与 `SUPERVISOR-AGENT-DESIGN.md` 的关系：那份讲的是**系统内部**的运行时监督（S0→S4、proposal 合同、ActionIntent），
> 主角是 Controller 和 Agent Runtime。**本文讲另一个东西**：当流程由「开发 Agent + 人工授权」驱动时，
> 开发 Agent 对**真实生产运行**承担什么监管责任、用什么证据说话、什么情况下必须停手。两者互补，不重叠，也不要合并。

## 0. 为什么单独立这份契约

用户的原话是「现在系统没有 agent 监管吗？你是开发 agent，是监管生产 agent 的 agent」。

对照代码现状，这句话点出的缺口是真的，但**不是「没有监督代码」**，而是监督的**覆盖面**有洞。2026-09-15 之前：

- `runtime/supervisor-agent/` 有确定性分诊，但它吃的是人工拼装的 incident JSON，不是活着的运行；
- `runtime/sop-runtime/round-notify-policy.mjs` 有「该不该通知」的判据表，但只在**一轮结束时**说话；
- 一次真实的 40 页采集**死在第 29 页**，全过程没有任何机制报出来 —— 因为那一层判据**根本不存在**。

缺的两个维度（这是本文的由来）：

1. **进程活着但停在某阶段** —— 「死活」判据看不见「卡住」；
2. **长任务有没有独立于对话会话的宿主** —— 进程树随宿主被回收这件事，此前完全没人管。

## 1. 三层监管（当前实现）

### L1 进程层：`runtime/supervise-collection.mjs`

只播报，不拥有状态、不自愈。四个判据维度：

| 维度 | 判据 | 出口 |
|---|---|---|
| 死活 | `process.kill(pid,0)` | `FAILED` / `RUNNING` |
| 阶段静止 | 末事件名 → `PHASE_BUDGETS` 允许静止秒数 | `SUSPECT_STALLED` |
| 进度不推进 | `PROGRESS` 的 `completedPage:rows` 签名超过 `--progress-budget-seconds` 不变 | `SUSPECT_STALLED` |
| 持久化证据 | 给了 `--stdout-file` 时以终端标记 `ADAPTIVE_DONE` 为准 | `COMPLETED` / `FAILED` / `UNKNOWN` |

**它抓得到**：进程死了、卡住、退出非零、阶段静止、进度不推进。
**它抓不到**：「判据写错但进程还活着、事件流还在正常往前」—— 2026-09-15 那 30 秒 settle 卡死，它一直显示 `RUNNING`。
所以判据读到的**原始状态必须写进收据**（`loadingMasksAtSettle` / `startDisabledAtSettle`）。收据里没有原始状态，事后就无法区分「没卡」和「判据没看见」。

### L2 宿主层：`runtime/run-collection-host.mjs`

解决「活没活」之外的问题：**还有没有人在管这件事**。

三条硬规矩：

1. 子进程 stdout/stderr **直写文件描述符**（不是管道）。父进程管道被关会 EPIPE 直接把启动器带走，进程一死，退出码文件永远不落盘，监督环只能判 `UNKNOWN`。
2. 子进程 `detached: true`，拿到自己的进程组，尽量不被宿主的进程树一起回收。
3. 宿主自己写心跳 `.collection-host-heartbeat`：`{host.alive, collector.alive, supervise.lastStatus, notify}`。

第 3 条是关键：**心跳是分片的**。外部（人，或另一个 agent）不连 stdout 也能回答「这一批到底还有没有人在管」，以及「监管者自己还活着吗」。监管者死了却没人发现，是监管体系最典型的失效方式。

### L3 周级层：`runtime/run-weekly-collection.mjs`

按页分段串起来跑，每段留收据，最后合并成一个带图工作簿。收据 `.weekly-collection-receipt.json` 写清：题目、每段成功/失败、失败原因、合并产物路径。收尾告警一次讲清「覆盖了哪些段、缺了哪些段、产物在哪」。

分块不是性能优化，是**正确性要求**：飞书「商品图片」是附件字段（type 17），导入器从 **xlsx 里抽内嵌图**再上传换 `file_token`（`import-runner.mjs`）。而采集器一旦卡住转 partial 导出，结算窗口只有 5 分钟（`PARTIAL_EXPORT_SETTLEMENT_MS`），878 行 + 878 张图做不出来 → 那一段只剩 CSV → **图片没了**。段越大越容易卡，卡了又把窗口从 60 分钟砍到 5 分钟，所以段要小（当前 4 页/段）。

## 2. 判据的 fail-closed 方向

- 读不到证据 → 只写 `UNKNOWN`，**不写 OK**（空值不是零）。
- 证据自相矛盾（退出码非 0 但出现终端标记）→ 按 `FAILED`。
- 阶段预算查不到 → 回落到 `--stale-seconds`，**不回落到「不检查」**。
- 告警「没发出去」→ 非零退出码（`notify-feishu.mjs`），调用方不许把未送达记成送达。
- 收据缺字段 → 事后无法复核，所以字段是**全量写**，断言用 `Object.hasOwn`。

## 3. 开发 Agent 自己的授权边界

监管者本身也会出事，所以它的动作分两类：

- **可自主动作**：读文件、读日志、只读探测、起只读监督、写收据与本地日志。
- **必须用户明确点头**：对外可见或不可撤销的动作 —— 真发飞书、外部写入、重启/停任何运行中的服务或进程。
  - 「继续」「修复吧」「失败了」这类指令**只授权排查与修复本身，不包含重发/重试**。
  - 动手前必须报「我将对 PID xxx（属于哪个项目）做什么」，并等回复。

这条与「严禁越权操作运行中的服务」同级，凌驾于效率偏好之上。

## 4. 诚实清单

**已实现（有实测证据）**
- L1 四判据 + 17 例离线测试；两条真实路径实测：`FAILED :: 退出码 1`、`COMPLETED :: 退出码 0 + ADAPTIVE_DONE`。
- L2 宿主：fd 直写、detached、心跳；2026-09-15 实跑观察到「监督环自行从日志认领运行目录」。
- L3 周级驱动 + 收据。
- 飞书投递第一跳（个人）、第二跳（群兜底）已真实发送过；第三跳（webhook）用户明确取消，代码保留不部署。

**未实现（不许读成已实现）**
- **宿主存活仍未获独立验证**：`detached` 能不能扛过会话回收，本身还没做过对照实验。当前的实际保障是「不结束对话轮次」，那是权宜，不是能力。
- L1 抓不到「判据本身写错」。这类只能靠把原始状态写进收据 + 人工复核。
- 体检层（运行前体检）与自愈执行器**刻意没有假装存在**，收据里写 `NOT_IMPLEMENTED` / `NO_HEALER_CONFIGURED`。
- 监管层目前只覆盖「采集」这一种能力；建周表 / 导入 / 公式重建 / 分类统计 / SKU 富化 / FAQ / 发布都还没有对应的监督环。
- 排期层驱动不了竞品周更（多步流程），只有 `sycm.feishu.weekly` 是单能力整链。

## 5. 下一步（按价值排序）

1. **宿主独立性的对照实验**：起一个 detached 心跳进程，结束对话轮次后回来看它是否还在。这决定长任务能不能真正无人值守。
2. **把 L1 推广到后续各步**：每步一个「阶段静止预算 + 幂等键 + 收据」，否则监管只覆盖 1/8 的流程。
3. **运行前体检**：浏览器 9222、代理 3457、`browser.id`、下载目录、登录的是谁 —— 五个前置条件，缺一个就 fail-closed 不发起。

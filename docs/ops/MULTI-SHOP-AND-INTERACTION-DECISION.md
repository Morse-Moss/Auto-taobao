## 0. 结论（先行）

1. **「定时放 agent 宿主」不是新主张，本项目 09-15 就允许了。** `round-schedule.json` 的 `_readme`
   第 3 行原文写着宿主三选一，其中一项就是「WorkBuddy 的定时任务」。真正缺的不是「要不要 agent」，
   而是两步**尚未接线**：第 3 步自愈执行器、第 4 步体检前置与登录会话对象（见 §2）。
2. **CLI 不升 API。** 升 API 的触发条件是「跨机器」或「多调用方并发共享同一份资源」，
   现在两条都不成立。但**现在就要把 CLI 的输出契约固定成机器可读**——这件事无论后面接运营台、
   调度器还是 API 都不浪费（§3）。
3. **13 店铺是结构性变化，不是参数变化。** 它会让「失败」从异常变成常态（§4.5），
   并暴露出一个**当前配置校验拦不住**的幂等键缺口（§4.1）。
4. **agent 的定位不变**：它是「处置」这一格的载体，不是「知情」和「触发」的载体。
   用户对「监督 + 及时反馈」的判断是对的，但监督的产物必须落成机器可读文件，
   不能让 agent 的叙述成为客户看到的状态（§5）。

## 2. 已定的部分，与尚未接线的部分

`UNATTENDED-AGENT-RUNTIME-PLAN.md` 的实施计划里，**第 1、2、2b 步已完成**（通知出口三跳、
一轮运行生命周期、排期配置）；**第 3、4 步待做**：

| 步 | 内容 | 状态 | 与用户本轮的关切 |
| --- | --- | --- | --- |
| 3 | 自愈执行器：把 `diagnose.actions` 的 5 个动作接上真实实现 | 待做 | ＝「出了错要能自己先救一次」 |
| 4 | 体检前置 + 登录会话对象（四层身份/环境/会话/端到端） | 待做 | ＝「各种登录的问题」＋「需要登录时飞书提醒」 |

**当前是「到点自己跑 + 出故障叫人」，但登录态失效还不能被提前挡住。**
体检层与自愈层现在如实写 `NOT_IMPLEMENTED` / `NO_HEALER_CONFIGURED`，
没有假装它们在工作——这个诚实本身要保住。

**「需要登录时飞书提醒」这条路已经走了大约九成**：通知出口（自研应用个人消息 → 兜底收件人 →
群 webhook）第 1、2 跳已真实验证过，`round-notify-policy.mjs` 里 `HUMAN_REQUIRED` 也已登记为
「强通知 + 修完自动继续」。**缺的不是通知，是「怎么知道需要登录」**——那正是第 4 步的体检层。
所以这条要求的正确落点是第 4 步，不是新建一条通知链。

多店铺会让第 4 步的必要性从「重要」变成「必需」：单店时登录失效一周打扰 0–2 次，
13 店时是 0–26 次，没有体检前置会被登录告警刷屏（§4.3）。

## 3. CLI 要不要升成 API

### 3.1 两者的差别不是「现代不现代」

- **CLI 的契约**：命令行 + stdout + 退出码 + 落盘文件。它天然绑定同一台机器、同一个用户、
  同一套环境变量与工作目录。
- **API 的契约**：网络 + 请求/响应 schema + 鉴权。它把「在哪台机器上执行」解耦了。

所以判据只有一句：**调用方和被执行方是否必须分离？**

### 3.2 什么时候真的需要 API（三个触发条件，任一成立才考虑）

1. **跨机器**。例如采集在服务器跑、客户电脑只负责登录扫码。这条一旦成立就必须有 API。
2. **多调用方并发共享同一份资源**。13 店铺共用一台机器的一套浏览器 profile 时，
   定时器 / 运营台 / agent 三个调用方要互相排队。
3. **需要历史查询与并发**。例如「过去 30 天每家店的成功率」需要一个有状态服务。

### 3.3 一个必须分清的区别

**「需要串行化」不等于「需要 HTTP API」。** 条件 2 要的是一个**拥有资源的中介**，
它可以是文件锁、本地队列或进程内的串行闸门。运营台现在的「全局串行 + 409 `ACTION_BUSY`」
就是这个中介的雏形；多店铺要把它升级成**按店铺排队**，但不必升级成 HTTP 服务。

强行上 API 的代价是真实的：多一个常驻服务要部署、要鉴权、要版本兼容，
而它解决的问题（跨机、并发）现在都不存在。

### 3.4 现在就该做的一件事：固定输出契约

不管后面接谁，都需要回答同一组问题：**这次跑了哪家店、卡在哪一步、成功还是失败、为什么。**
现在这些信息散在 stdout 文本、退出码和收据文件里。

**动作**：给四条链的 CLI 约定一份**结构化结果**（机器可读 JSON：`storeId` / 阶段 / 状态 /
原因码 / 产物路径）。这是「早绑定投资、晚绑定决策」——API 是晚绑定，结果是早绑定。
理由与本仓库既有的「判据只到执行态」教训同源：**输出不可解析，就无法被聚合、被展示、被通知。**

## 4. 13 店铺对现有设计的影响（逐子系统，带证据）

### 4.1 幂等与业务键：一个当前校验拦不住的缺口

**现状（可核对）**：

- 排期层默认业务键模板是 `{capability}/{windowKey}`（`runtime/sop-runtime/round-schedule.mjs:40`）。
- 渲染函数**已经支持** `{storeId}`（同文件 `:183`），但**默认值不用它**。
- 配置校验只要求模板含周期占位符（`:229-233`），**不要求含店铺**——所以这个坑不会被校验拦住。
- 运行层的身份契约**已经带店铺**：`{tenantId:'sycm', storeId:'bathtub-flagship'}`，
  lane 形如 `sycm/bathtub-flagship/...`，真实收据里的幂等键也含它
  （`runtime/sop-runtime/two-stage-mu10zyr2/receipt.json`）。

⇒ **两处口径不一致**：运行层有店铺，排期层的默认键没有。
`runtime/round-schedule.json` 的 `notes` 里已经写明这一点：「当前两套 SOP 都没有店铺维度，
storeId 只是身份契约里的占位值；等运营日报阶段再按店铺拆成多条排期。」

**多店铺下的后果**：按店铺拆成 13 条排期后，若沿用默认模板，13 条会算出**同一个业务键**。
而业务键同时是「该不该跑」判定（`due({businessKey})`）、告警去重与恢复
（`openAlert.businessKey`）、以及收据（`ROUND_RECEIPT_FIELDS`）的主键
（`runtime/sop-runtime/round-runner.mjs`）——同一个键上 13 家会互相覆盖、互相压制。

**修法（一行 + 两条判据）—— 2026-09-17 已执行（用户「按你推荐的来」）**：

- 默认模板改为 `{capability}/{storeId}/{windowKey}`（`round-schedule.mjs`）。
  为什么不只是加校验：**默认值即目标**（坑 35）——默认模板长什么样，别人就照抄什么样。
- 补两条**校验**（第二道闸，防手写模板绕过默认值）：
  ① 同一 capability 排了多条时，模板必须含 `{storeId}`；
  ② 同一 capability 下不许两条排期落到同一个 `storeId`。
  两条都会**点名是哪几条排期**，而不是只报一句「配置不合法」。
- 改动安全性：`runtime/round-schedule.json` 出厂 `enabled:false`，且「还没有在任何一台机器上
  接上叫醒者」⇒ 不存在已经产出的生产业务键会因这次改名而对不上。
- **突变验证**（两次都精确点名，还原后逐字节一致）：
  ① 把默认模板改回 `{capability}/{windowKey}` ⇒ 6 条转红，其中一条正是「三条排期三个键」；
  ② 摘掉模板校验 ⇒ 2 条转红（缺 storeId 的、同 storeId 重复的）。
- 连带改动：`round-schedule.json` 的 `_readme`（写明默认键含店铺、以及为什么必须区分店铺）、
  两条既有测试的夹具（原本三条排期共用一家店 ⇒ 改为三家店，这也更贴近多店铺的真实形态）。
- 基线：`sop-runtime` 套件 **355 → 360 全绿**；`runtime` 套件 **546 → 552 全绿**。
- **仍未覆盖的一处**（如实标注）：模板字符集校验只看**模板**、不看**渲染结果**，所以一个带中文的
  `storeId` 会渲染出一个带中文的键而不会被拦。这一层由 `config/customer.json` 的 `stores[].id`
  字符集校验兜住（`STORE_ID_PATTERN`），两条路径合起来才完整。

### 4.2 浏览器与端口登记表：现在是「按身份两条」，需要「按店铺」

`runtime/browser-ports.mjs` 的 `PROJECT_PORTS` / `BROWSER_PROFILES` / `BROWSER_IDS`
都是按**身份**（`competitor` 买家 / `dailyReport` 商家）编的，各一条。多店铺要引入第三维。

关键约束（今日实测过）：**同一个 Edge profile 只能有一个实例**（同 profile 起第二个会并入旧实例并退出）。
⇒ 13 家店要么 **13 个 profile 目录**（每店持久化登录态），要么串行复用同一 profile 并**每天重新扫码 13 次**——
后者不可接受。所以必然是「**每店一个 profile + 串行调度**」。

连带影响：

- 端口从「每个身份一对」变成「每个店铺一对」，登记表要能表达「按店铺实例化」，且默认值仍必须单一来源。
- 13 个 Edge 实例不可能同时跑 ⇒ 串行是硬需求（也就回到 §3.3 的中介）。
- 磁盘占用按 profile 数增长。

### 4.3 登录态：从附带问题变成核心问题

**13 组凭据**（一个主号管一家店），**会话可能是 2×13 个**（生意参谋与阿里妈妈的会话各自到期与否
需要实测——这正是既有缺口 G7 要回答的事）。过期是分散发生的。
⇒ 客户界面上**第一等的信息**是「今天谁要重新登录」，不是「今天跑完了没」。

三个必须守住的边界：

1. **凭据自动填充是一回事，「绕验证码与风控」是另一回事**——前者用户已要求开启（见 §5.1），
   后者**不随这次改变而放宽**。多店铺还把风控风险放大了：同一台机器短时间内 13 次登录，
   正好是风控最喜欢的模式，所以自动登录必须**串行、有间隔、失败即停**。
2. **体检判据必须是「登的是不是我们要的那个账号」，不是「有没有登录」**（`LOGIN-STATE-MANAGEMENT.md` §7）。
   13 组凭据里登错店比没登录更危险——数据会静默写到别人家的行上。
   **账号分离（每店一个 profile、一份凭据）让这条从「更危险」变成「可判定」**：
   身份层与期望的 `storeId` 一比就知道，而不是靠人眼认页面。
3. **登录会话对象尚不存在**（第 4 步待做）。没有它，「谁确认的、确认后怎么幂等继续」无从承载；
   自动登录降低的是它的使用频率，不是它的必要性——**「偶发必须人」这条永远在**（§5.1）。

### 4.4 飞书侧：好消息与新缺口

**好消息**：飞书表通用 ⇒ 数据面不用改。

- 底单查重键是「同一天 + 同店铺」，天然支持多店；家数就是飞书表里的行数。
- 询单表当天已经有 12 行（每家一行）的骨架。

**新缺口（店名归一化）**：查重键的「店铺」是个**字符串**，而它在两个平台上并不一致：
阿里妈妈显示「盖文旗舰店:阿彦 ID 2995200080」，生意参谋显示「盖文旗舰店 主店」，
飞书底单里的「店铺」是派生 Lookup（读不到，只能看同表的「店铺名称」）。

⇒ **必须建一份「店铺标识对照表」**：内部 `storeId`（如 `bathtub-flagship`）
↔ 生意参谋显示名 ↔ 阿里妈妈显示名 ↔ 飞书「店铺名称」。
没有它，多家店迟早会写成多个不同的名字、或两家撞成一行。

**2026-09-17 已落**：`config/customer.example.json` 的 `stores[]` + `runtime/customer-config.mjs`
的 `validateStores()`。四条校验都是 fail-closed：形状、必填、未知字段、
**`feishuName` 重名直接拒绝**（飞书店名就是查重键，重名＝两家撞进同一行）、
`id` 字符集（它会进幂等键，见 §4.1 末尾）。
**诚实标注：这一段目前没有读方**——按店铺拆排期的生成器还没做，此刻它只被校验、不被使用；
配置与 README 里都写明了这一点，不为它造一个临时的打印脚本假装接上了。

### 4.5 时间和失败率：多店铺把「失败」变成常态

- **时间预算**：单店 16 分钟（首次完整跑）⇒ 13 家串行约 **3.5 小时**；
  若能复用已生成任务则 7 分钟/店 ⇒ 约 1.5 小时。这也再次印证「日更不要赶早，过午再跑」。
- **失败率**：设单店全绿概率为 p，13 家独立时「全绿」概率是 p¹³。
  p=98% ⇒ 全绿 77%；p=97% ⇒ 67%。**「有一两家没跑成」是日常，不是异常。**

**推论（对界面影响最大的一条）**：产品的默认状态不是「成功/失败」，
而是「13 行里 12 行绿、1 行红，红的那行要人扫个码」。这直接改写 §6 的层 2 内容。

### 4.6 运营台：进度块要从「一条链跑第几步」变成「店铺矩阵」

- 现在「进度」块读的是 `runtime/faq-analysis/<周期>/operator-status.json`，只有 FAQ 一条链
  （缺口 G6：其它链没有 `operator-status.json`）。
- 多店铺后它要显示 **店铺 × 阶段** 的矩阵，红色格子可点、可**单店重试**。
- **账号体检从「示例数据」变成第一屏刚需**。它现在是一张假卡（页面上显式标注「示例」、
  一个按钮都不给）；多店铺下它是整个界面最该可信的一块。
- 「重试单店」必须是一等动作，且必须**幂等**——靠飞书查重键（同一天 + 同店铺）兜底，
  这条是「agent 自动重试」能安全存在的前提。

## 5. agent 该做什么、不该做什么

对齐 `WHERE-LLM-IS-NEEDED-DECISION.md`（2026-09-16 已定）：LLM 在本项目里唯一的合法位置是
「词表兜底」，而那份文档把「单 agent 分诊」列为 **P4，可以不做**。

本轮用户的主张（「必须要有 agent 监督着跑」）针对的是另一个角色——
不是「用 LLM 判断内容」，而是「用 agent 驱动流程、发现失败、及时反馈」。这两件事必须分开评估：

| 角色 | 定位 | 结论 |
| --- | --- | --- |
| LLM 作为**内容判断/生产**的组件 | 属性分类、字段补全 | **已否**（除 P3 词表兜底）。多店铺不改变这条。 |
| agent 作为**流程驱动与监督** | 定时叫醒、发现哪家没成、通知、白名单内自愈 | **合理，且是第 3/4 步待接线的部分**。多店铺显著提高其价值。 |

**三条必须守住的前提**（缺一条，agent 监督就会变成新的静默失败源）：

1. **监督的产物必须落盘成机器可读文件**（每店成功/失败/原因码 + 写入结果）。
   客户看到的状态从文件读，不从 agent 的对话读。否则就是「第二份状态真相」的变体：
   客户看到的是叙述，不是状态。
2. **自动重试必须幂等**。单店重试的幂等靠飞书查重键；跨店并发靠串行闸门。
3. **通知必须走不依赖 agent「讲清楚」的通道**（`notify-feishu` 三跳链已就绪），
   并且**去重与恢复成对**（已有实现，直接复用）。

### 5.1 凭据与自动登录：要改一条非目标，且改动范围有上限

**用户要求（2026-09-17 18:30）**：账号密码登录；账号分离；切店铺时不需要人工登录；每家店都能自动登录。

**这条请求直接触及一条既有非目标。** `LOGIN-STATE-MANAGEMENT.md` §8 第一条原文：
「**不做账密代登**：登录一律人工（扫码/人工确认），与 README §2 非目标一致，也避免凭据保管责任。」
**我不会自己改这条。要你明确说一句「允许」，我才动它**（这条纪律和「授权≠开始」同一族）。
下面是改动前你必须看到的全部取舍。

**先说做不到的部分（避免一个兑现不了的承诺）**

- 淘宝/阿里系的登录页在换设备、异地、或风控命中时会要求**滑块或短信验证**。
  账号密码自动填充只能覆盖「不需要二次验证」的那一段。
  ⇒ 真实能达到的最好状态是「**大部分时候自动，偶尔必须人**」，不是「每家店都能自动登录」。
  把它写成后者，等于给自己埋一个必然会兑现不了的交付承诺。
- **不做任何反检测、指纹伪装、验证码识别**；命中验证码或风控页 ⇒ 立即停下通知人。
- **不做「检查失败就重试登录」**（既有边界：重试是风控的加速器）。
  13 家的规模把这条的风险放大了——一个 IP 上短时间内 13 次登录正好是风控最喜欢的模式，
  一次误触发可能连带把一批账号打进保护性锁定。

**所以这件事的主题不是「每天自动登录 13 次」，而是「尽量不登录」**

1. 每店一个 profile ⇒ 登录态是**持久化**的，正常运行日根本不该触发登录。
2. 真正要解决的是**会话过期后的续期**，而不是每天一次的例行登录。
3. 自动登录只在「体检判定该店会话已过期」时触发一次；失败即转人工。

**四条不可放宽的边界（即使你同意开这条口子，也建议写死）**

| 边界 | 内容 | 为什么 |
| --- | --- | --- |
| 凭据存放 | Windows 凭据管理器（DPAPI）或加密文件；`config/customer.json` 里只放 `credentialRef`（位置标识） | 那份配置跟着机器走、会被复制、会被人用记事本打开，它不承担保管秘密的职责 |
| 凭据可见面 | **明文不入库、不进日志、不进证据目录、不进通知** | 沿用既有安全边界（`LOGIN-STATE-MANAGEMENT.md` §8 第四条） |
| 失败熔断 | 同一账号连续 2 次失败 ⇒ 当天不再试、通知人 | 「再试一次看看」在 13 家规模下就是风控加速器 |
| 节奏 | 13 家**串行**、每次之间留间隔、一天最多一轮 | 同 IP 短时多次登录是风控的典型特征 |

**另外一条工程要求：它必须是一个开关，且默认不改变现有行为。**
默认关闭时，系统行为与今天**逐字相同**（人工登录 + 体检提示）。
这与 `runtime/customer-config.mjs` 文件头那条硬约束同源：**新增能力不该悄悄改变默认路径。**

**等你点头后要做的事（顺序不能颠倒）**

1. 改 `LOGIN-STATE-MANAGEMENT.md` §8 与 README §2 的非目标表述——**加上例外与上表四条边界**，
   而不是简单删掉那句话。
2. 凭据存储与读取模块 + 一条「明文凭据不得出现在仓库任何文件里」的守卫测试。
3. **第 4 步体检层**（先做，因为「什么时候需要登录」是自动登录的输入；它顺便兑现了「登录时飞书提醒」）。
4. 登录适配器：**按站点各一个**，且按键名/到期语义的**实测**结果写（G7 明令禁止照抄）。

**结论**：技术可行，但它是**改非目标**、不是加功能；且它把风控风险从「单店偶发」变成
「一批账号同时暴露」。我的建议是：**先做第 4 步体检 + 飞书提醒（零风险，且独立有价值）**，
把「到底多频繁需要人」实测出来，再决定要不要开自动登录这条口子——因为如果实测是「一周一次」，
那这条口子的收益不值得它引入的风险。

## 8. 不承诺什么

- **不承诺「无人值守」**：跑中可能撞验证码；账号密码自动填充（若开）也只能覆盖不需要二次验证的那一段。
  正确承诺是「人一周可能被打扰 0～2 次」（单店口径）；多店下这个数字必须先实测，不要先写进交付承诺。
- **不承诺多店能同时跑**：浏览器写操作串行是既有硬约束（`UNATTENDED-AGENT-RUNTIME-PLAN.md` §3）。
- **不承诺「服务器侧无人值守」**：只要验证码这一步需要人，执行就必须发生在有屏幕的那台机器上；
  账号密码自动填充改变的是频率，不改变这条。
- **本文件区分清楚「已做」与「待做」**：§4.1 的模板改动、§4.4 的配置段与校验**已在 2026-09-17 完成**
  （含突变验证与套件复跑）；§5.1 的凭据自动登录**没有动任何代码**，它要等一条非目标的明确授权。

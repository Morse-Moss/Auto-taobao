## 0. 结论（先行）

1. **「定时放 agent 宿主」不是新主张，本项目 09-15 就允许了。** `round-schedule.json` 的 `_readme`
   第 3 行原文写着宿主三选一，其中一项就是「WorkBuddy 的定时任务」。真正缺的不是「要不要 agent」，
   而是两步**尚未接线**：第 3 步自愈执行器、第 4 步体检前置与登录会话对象（见 §2）。
2. **CLI 不升 API。** 升 API 的触发条件是「跨机器」或「多调用方并发共享同一份资源」，
   现在两条都不成立。但**现在就要把 CLI 的输出契约固定成机器可读**——这件事无论后面接运营台、
   调度器还是 API 都不浪费（§3）。
3. **13 店铺是结构性变化，不是参数变化。** 它会让「失败」从异常变成常态（§4.5），
   并暴露出一个**当前配置校验拦不住**的幂等键缺口（§4.1）。
4. **agent 的定位不变**：它是「处置」这一格的载体，不是「知情」和「触发」的载体。
   用户对「监督 + 及时反馈」的判断是对的，但监督的产物必须落成机器可读文件，
   不能让 agent 的叙述成为客户看到的状态（§5）。

「强通知 + 修完自动继续」。**缺的不是通知，是「怎么知道需要登录」**——那正是第 4 步的体检层。
所以这条要求的正确落点是第 4 步，不是新建一条通知链。

多店铺会让第 4 步的必要性从「重要」变成「必需」：单店时登录失效一周打扰 0–2 次，
13 店时是 0–26 次，没有体检前置会被登录告警刷屏（§4.3）。

## 3. CLI 要不要升成 API

### 3.1 两者的差别不是「现代不现代」

- **CLI 的契约**：命令行 + stdout + 退出码 + 落盘文件。它天然绑定同一台机器、同一个用户、
  同一套环境变量与工作目录。
- **API 的契约**：网络 + 请求/响应 schema + 鉴权。它把「在哪台机器上执行」解耦了。

所以判据只有一句：**调用方和被执行方是否必须分离？**

### 3.2 什么时候真的需要 API（三个触发条件，任一成立才考虑）

1. **跨机器**。例如采集在服务器跑、客户电脑只负责登录扫码。这条一旦成立就必须有 API。
2. **多调用方并发共享同一份资源**。13 店铺共用一台机器的一套浏览器 profile 时，
   定时器 / 运营台 / agent 三个调用方要互相排队。
3. **需要历史查询与并发**。例如「过去 30 天每家店的成功率」需要一个有状态服务。

### 3.3 一个必须分清的区别

**「需要串行化」不等于「需要 HTTP API」。** 条件 2 要的是一个**拥有资源的中介**，
它可以是文件锁、本地队列或进程内的串行闸门。运营台现在的「全局串行 + 409 `ACTION_BUSY`」
就是这个中介的雏形；多店铺要把它升级成**按店铺排队**，但不必升级成 HTTP 服务。

强行上 API 的代价是真实的：多一个常驻服务要部署、要鉴权、要版本兼容，
而它解决的问题（跨机、并发）现在都不存在。

### 3.4 现在就该做的一件事：固定输出契约

不管后面接谁，都需要回答同一组问题：**这次跑了哪家店、卡在哪一步、成功还是失败、为什么。**
现在这些信息散在 stdout 文本、退出码和收据文件里。

**动作**：给四条链的 CLI 约定一份**结构化结果**（机器可读 JSON：`storeId` / 阶段 / 状态 /
原因码 / 产物路径）。这是「早绑定投资、晚绑定决策」——API 是晚绑定，结果是早绑定。
理由与本仓库既有的「判据只到执行态」教训同源：**输出不可解析，就无法被聚合、被展示、被通知。**

### 3.5 定时怎么触发：三层，各管一件事（2026-09-18 用户问了这个问题）

用户原话：「你想怎么触发定时任务，我知道 WorkBuddy 有定时任务，你有什么更好的办法吗？」

先说结论：**定时器不是这条链的瓶颈，「链还不是一条命令」才是。** 三层要分开：

| 层 | 干什么 | 选什么 | 为什么不选另一个 |
| --- | --- | --- | --- |
| 触发层 | 到点敲一下 | **Windows 任务计划**（`schtasks`）跑一条命令 | 一条已经自检自证的命令不需要 agent 在场；WorkBuddy 定时任务每天要起一次完整会话（模型在场、要花钱），而这里要的是「确定性地跑同一套动作」 |
| 判据层 | 决定「今天能不能写」 | **命令自带**：三页各恰好一个、目标日命中 0 行、推广 CSV 与上一次逐字节相同 | 这三条都已经有判据了（§10 起跑前逐项确认表），缺的是**把它们接进命令**，而不是再找人来盯 |
| 叫人层 | 需要人时喊人 | **命令自己发飞书**（§11.4 已有） | 让 agent 转述只会多一跳延迟；飞书提醒里要带可点链接 + 人话原因 + 能照做的下一步 |

**WorkBuddy 定时任务仍然有用，但定位是兜底而不是主路**：`schtasks` 那条命令失败（登录掉了、页面被导走、
平台改了页面）之后，飞书提醒会到人手里；**需要我接手排障时**，由我用一条 WorkBuddy 定时任务或手动会话来接。
把它当主触发器的话，会出现「到点了但没人在 WorkBuddy 里」这种更差的失败形态。

**时间窗不是纪律，是可测的**：`08:04` 那份推广 CSV 与 `11:22 / 12:36 / 12:5x` 三份**逐字节不同**，
而 `11:22 → 12:5x` 三份**完全相同**（§6.6）⇒ 回补在 **11:20 前后静止**。
所以「过午再跑」这条咒语可以换成一条**自动判据**：跑正式之前，同一目标日再导一份推广，
解出的 CSV 与手上那份**逐字节相同**才写；不相同就**不写**、只报告，等下一轮。
这样时间可以提前到 **约 11:40**，而且比「过午」更安全 —— 它检查的是事实，不是钟点。

**这三层里只有第一层今天就能挂**；第二层是 P0-2（一条命令），第三层已有。

**2026-09-19 更新（照实记，别把计划读成现状）**：
- 第二层**已经成了**：`run-multi-shop-day.mjs --date yesterday --commit --notify` 一条命令即全链，
  目标日的字面量解析、出错才发的飞书告警都在命令里（用法与前提见 `sop.md` §13）。
- **第一层（任务计划）当晚补齐了「入口」，但注册这一步被本机的安全策略挡住**（2026-09-19 深夜）：
  - `scripts/run-daily-job.mjs` 是到点要跑的**那一条命令**：先 `scripts/start-all.mjs` 把声明实例起齐
    （幂等、已就位的不碰），再跑全链；两步的默认值在 `runtime/daily-job-plan.mjs` 里被离线断言
    （日期只用 `--date yesterday`、不加 `--allow-missing-peer`、告警默认 `--notify-print` 只落日志）。
  - `scripts/schedule-install.mjs` 负责把这条命令注册成每日任务（默认只打印，`--install` 才真挂）。
  - **实测硬约束：本机把 `schtasks.exe` 列进了程序黑名单** ⇒ 注册与查询在我这边都执行不了
    （脚本会如实报「读不出来」，刻意**不报成「没挂」** —— 那是假阴性）。
    注册需由人来做：移出黑名单后跑 `--install`，或用 `taskschd.msc` 手工挂，或用平台定时任务兜底。
  - **尚未实测**：由任务计划拉起的 `detached` 子进程能否活过任务本身（沙箱里实测过 detached
    **没有**脱离宿主进程树）。所以「保活归属」是**有了归属、缺一次实测**，不是已完成。
- 上面那条「再导一份、逐字节相同才写」的**自动判据仍未实现**（链里只有产物 sha256 记账，
  没有「同目标日二次导出比对」这一步）。所以在它实现之前，**触发时刻本身就是唯一的安全边界**：
  不要往 11:20 之前放。

## 4. 13 店铺对现有设计的影响（逐子系统，带证据）

### 4.1 幂等与业务键：一个当前校验拦不住的缺口

**现状（可核对）**：

- 排期层默认业务键模板是 `{capability}/{windowKey}`（`runtime/sop-runtime/round-schedule.mjs:40`）。
- 渲染函数**已经支持** `{storeId}`（同文件 `:183`），但**默认值不用它**。
- 配置校验只要求模板含周期占位符（`:229-233`），**不要求含店铺**——所以这个坑不会被校验拦住。
- 运行层的身份契约**已经带店铺**：`{tenantId:'sycm', storeId:'bathtub-flagship'}`，
  lane 形如 `sycm/bathtub-flagship/...`，真实收据里的幂等键也含它
  （`runtime/sop-runtime/two-stage-mu10zyr2/receipt.json`）。

⇒ **两处口径不一致**：运行层有店铺，排期层的默认键没有。
`runtime/round-schedule.json` 的 `notes` 里已经写明这一点：「当前两套 SOP 都没有店铺维度，
storeId 只是身份契约里的占位值；等运营日报阶段再按店铺拆成多条排期。」

**多店铺下的后果**：按店铺拆成 13 条排期后，若沿用默认模板，13 条会算出**同一个业务键**。
而业务键同时是「该不该跑」判定（`due({businessKey})`）、告警去重与恢复
（`openAlert.businessKey`）、以及收据（`ROUND_RECEIPT_FIELDS`）的主键
（`runtime/sop-runtime/round-runner.mjs`）——同一个键上 13 家会互相覆盖、互相压制。

**修法（一行 + 两条判据）—— 2026-09-17 已执行（用户「按你推荐的来」）**：

- 默认模板改为 `{capability}/{storeId}/{windowKey}`（`round-schedule.mjs`）。
  为什么不只是加校验：**默认值即目标**（坑 35）——默认模板长什么样，别人就照抄什么样。
- 补两条**校验**（第二道闸，防手写模板绕过默认值）：
  ① 同一 capability 排了多条时，模板必须含 `{storeId}`；
  ② 同一 capability 下不许两条排期落到同一个 `storeId`。
  两条都会**点名是哪几条排期**，而不是只报一句「配置不合法」。
- 改动安全性：`runtime/round-schedule.json` 出厂 `enabled:false`，且「还没有在任何一台机器上
  接上叫醒者」⇒ 不存在已经产出的生产业务键会因这次改名而对不上。
- **突变验证**（两次都精确点名，还原后逐字节一致）：
  ① 把默认模板改回 `{capability}/{windowKey}` ⇒ 6 条转红，其中一条正是「三条排期三个键」；
  ② 摘掉模板校验 ⇒ 2 条转红（缺 storeId 的、同 storeId 重复的）。
- 连带改动：`round-schedule.json` 的 `_readme`（写明默认键含店铺、以及为什么必须区分店铺）、
  两条既有测试的夹具（原本三条排期共用一家店 ⇒ 改为三家店，这也更贴近多店铺的真实形态）。
- 基线：`sop-runtime` 套件 **355 → 360 全绿**；`runtime` 套件 **546 → 552 全绿**。
- **仍未覆盖的一处**（如实标注）：模板字符集校验只看**模板**、不看**渲染结果**，所以一个带中文的
  `storeId` 会渲染出一个带中文的键而不会被拦。这一层由 `config/customer.json` 的 `stores[].id`
  字符集校验兜住（`STORE_ID_PATTERN`），两条路径合起来才完整。

### 4.2 浏览器与端口登记表：现在是「按身份两条」，需要「按店铺」

`runtime/browser-ports.mjs` 的 `PROJECT_PORTS` / `BROWSER_PROFILES` / `BROWSER_IDS`
都是按**身份**（`competitor` 买家 / `dailyReport` 商家）编的，各一条。多店铺要引入第三维。

关键约束（今日实测过）：**同一个 Edge profile 只能有一个实例**（同 profile 起第二个会并入旧实例并退出）。
⇒ 13 家店要么 **13 个 profile 目录**（每店持久化登录态），要么串行复用同一 profile 并**每天重新扫码 13 次**——
后者不可接受。所以必然是「**每店一个 profile + 串行调度**」。

连带影响：

- 端口从「每个身份一对」变成「每个店铺一对」，登记表要能表达「按店铺实例化」，且默认值仍必须单一来源。
- 13 个 Edge 实例不可能同时跑 ⇒ 串行是硬需求（也就回到 §3.3 的中介）。
- 磁盘占用按 profile 数增长。

**2026-09-18 晚实测补记（把这条待决项的量级定下来了）**：

1. **「按店铺实例化」其实不需要改逻辑**：两个正式启动器已经是**环境变量驱动、默认值才回落到登记表** ——
   `start-project-browser.mjs` 读 `PROJECT_BROWSER_PORT` / `PROJECT_BROWSER_PROFILE`，
   `isolated-proxy/cdp-proxy.mjs` 读 `CDP_PROXY_PORT` / `CDP_BROWSER_PORT` / `CDP_BROWSER_ID` / `CDP_BROWSER_LABEL`。
   ⇒ 要做的只是把「每店一组（profile 目录 + 浏览器端口 + 代理端口 + 身份 id/label）」写进登记表，
   并让现有守卫扫到它；驱动脚本按店铺设好这几个环境变量即可。**改动量是「登记表 + 守卫 + 一个循环驱动」，不是重写。**
2. **但每店必须配一个代理**：`collect-shop-report.mjs` / `collect-promotion-report.mjs` 走的是代理的
   `/targets`、`/eval`，而裸 CDP 端口只提供 `/json/list` ⇒ 现在那四个「已经在跑」的店铺窗口
   （端口 19031…19034，2026-09-18 晚实测**仍活着**、各自的隔离 profile 里 cookies 库被占用＝登录态还在）
   **采集脚本连不上**。这是「今天要采四家店」被挡住的那一步。
3. **profile 名不能当身份用**：商家浏览器 `edge-daily-report-profile` 做完一次自动登录后，
   生意参谋里登的是 **里可林家居**（不是盖文旗舰店）—— 浏览器密码库里第一条凭据决定了登进谁。
   ⇒ 「这一屏是哪一家」必须每次读页头，不能按 profile 目录名推断。

**2026-09-18 后续（第 2 条的「按店铺实例化」已落地，第 3 条又复现了一次）**：

- `runtime/browser-ports.mjs` 新增 `SHOP_BROWSERS`（四家店 × profile／调试端口／代理端口／browserId／label）
  与 `allDeclaredPorts()`；`runtime/start-shop-proxy.mjs` 是一家店一个代理进程的启动器
  （接受「运营叫法」或「profile 目录名」两种键；显式传了不一致的环境变量就拒启，
  防「把 A 店代理指向 B 店浏览器」）。三条新守卫把它们钉住，并做过四条突变验证。
  现役组合：19031/19041 里可林、19032/19042 网林、19033/19043 盖文淘宝、19034/19044 科塔淘宝。
- **仍然缺的是一个「按店铺循环」的驱动**（把采集→推送→回填串起来的那一层）。
  2026-09-18 的四家店是靠人工逐条敲命令跑完的，登记表与启动器只是把「能按店铺实例化」这件事做实。
- **第 3 条又复现了一次，而且这次撞出了新形态**：只读复测显示 **19022 的生意参谋页头 = 里可林家居**，
  与 19031（`likelin-home`）**同一家店**；且 19022 **没有阿里妈妈页**。
  起因是 SOP §11.3 记的那次「商家浏览器持久 profile 掉了生意参谋会话、重新登录后登进了里可林家居」
  —— 也就是说这个共享窗口的身份**在同一天里变过**。
  ⇒ 结论加固：**店铺身份只能从源产物读**（xlsx 的「店铺名称」列），
  审计表 `shop_name` 记的正是这个来源；不要用共享窗口的页头认店。

### 4.3 登录态：从附带问题变成核心问题

**13 组凭据**（一个主号管一家店），**会话可能是 2×13 个**（生意参谋与阿里妈妈的会话各自到期与否
需要实测——这正是既有缺口 G7 要回答的事）。过期是分散发生的。
⇒ 客户界面上**第一等的信息**是「今天谁要重新登录」，不是「今天跑完了没」。

三个必须守住的边界：

1. **凭据自动填充是一回事，「绕验证码与风控」是另一回事**——前者用户已要求开启（见 §5.1），
   后者**不随这次改变而放宽**。多店铺还把风控风险放大了：同一台机器短时间内 13 次登录，
   正好是风控最喜欢的模式，所以自动登录必须**串行、有间隔、失败即停**。
2. **体检判据必须是「登的是不是我们要的那个账号」，不是「有没有登录」**（`LOGIN-STATE-MANAGEMENT.md` §7）。
   13 组凭据里登错店比没登录更危险——数据会静默写到别人家的行上。
   **账号分离（每店一个 profile、一份凭据）让这条从「更危险」变成「可判定」**：
   身份层与期望的 `storeId` 一比就知道，而不是靠人眼认页面。
3. **登录会话对象尚不存在**（第 4 步待做）。没有它，「谁确认的、确认后怎么幂等继续」无从承载；
   自动登录降低的是它的使用频率，不是它的必要性——**「偶发必须人」这条永远在**（§5.1）。

### 4.4 飞书侧：好消息与新缺口

**好消息**：飞书表通用 ⇒ 数据面不用改。

- 底单查重键是「同一天 + 同店铺」，天然支持多店；家数就是飞书表里的行数。
- 询单表当天已经有 12 行（每家一行）的骨架。

**新缺口（店名归一化）**：查重键的「店铺」是个**字符串**，而它在两个平台上并不一致：
阿里妈妈显示「盖文旗舰店:阿彦 ID 2995200080」，生意参谋显示「盖文旗舰店 主店」，
飞书底单里的「店铺」是派生 Lookup（读不到，只能看同表的「店铺名称」）。

⇒ **必须建一份「店铺标识对照表」**：内部 `storeId`（如 `bathtub-flagship`）
↔ 生意参谋显示名 ↔ 阿里妈妈显示名 ↔ 飞书「店铺名称」。
没有它，多家店迟早会写成多个不同的名字、或两家撞成一行。

**2026-09-17 已落**：`config/customer.example.json` 的 `stores[]` + `runtime/customer-config.mjs`
的 `validateStores()`。四条校验都是 fail-closed：形状、必填、未知字段、
**`feishuName` 重名直接拒绝**（飞书店名就是查重键，重名＝两家撞进同一行）、
`id` 字符集（它会进幂等键，见 §4.1 末尾）。
**诚实标注：这一段目前没有读方**——按店铺拆排期的生成器还没做，此刻它只被校验、不被使用；
配置与 README 里都写明了这一点，不为它造一个临时的打印脚本假装接上了。

### 4.5 时间和失败率：多店铺把「失败」变成常态

- **时间预算**：单店 16 分钟（首次完整跑）⇒ 13 家串行约 **3.5 小时**；
  若能复用已生成任务则 7 分钟/店 ⇒ 约 1.5 小时。这也再次印证「日更不要赶早，过午再跑」。
- **失败率**：设单店全绿概率为 p，13 家独立时「全绿」概率是 p¹³。
  p=98% ⇒ 全绿 77%；p=97% ⇒ 67%。**「有一两家没跑成」是日常，不是异常。**

**推论（对界面影响最大的一条）**：产品的默认状态不是「成功/失败」，
而是「13 行里 12 行绿、1 行红，红的那行要人扫个码」。这直接改写 §6 的层 2 内容。

### 4.6 运营台：进度块要从「一条链跑第几步」变成「店铺矩阵」

- 现在「进度」块读的是 `runtime/faq-analysis/<周期>/operator-status.json`，只有 FAQ 一条链
  （缺口 G6：其它链没有 `operator-status.json`）。
- 多店铺后它要显示 **店铺 × 阶段** 的矩阵，红色格子可点、可**单店重试**。
- **账号体检从「示例数据」变成第一屏刚需**。它现在是一张假卡（页面上显式标注「示例」、
  一个按钮都不给）；多店铺下它是整个界面最该可信的一块。
- 「重试单店」必须是一等动作，且必须**幂等**——靠飞书查重键（同一天 + 同店铺）兜底，
  这条是「agent 自动重试」能安全存在的前提。

### 4.7 证据目录：缺「店铺」这一维（2026-09-18 多店铺实测暴露）

**现象**：`evidence/daily-report-<日期>[-rerunN]/` 只按日期取名，**没有店铺维度**。
`run-daily-report.mjs --commit` 用 `policy:'latest'`（并入最新一代），`run-inquiry-backfill.mjs` 也用
`latest` ⇒ 四家店串行跑时，后一家的 `plan.json` / `paste.tsv` / `receipt.json` /
`inquiry-backfill-*.json` **会覆盖前一家的同名文件**，一个目录里最后只剩最后一家。

**这是同一类缺口的第三次出现**：`PROJECT_PORTS` 缺店铺维（§4.2）、查询键缺店铺维（§4.1）、
现在是**产物路径**缺店铺维。判据可以照抄 §4.1 的手法：把「幂等键／去重键／锁键／收据主键／
**产物目录**」这五类「默认生成规则里带不带维度」列成一张表逐个检查。

**本轮的真实代价**：`evidence/multi-shop-run-2026-09-18/` 里丢了 5 个文件的本地副本
（里可林的询单两件、网林按店铺抄的推送三件，后者是被一次「全抄」操作覆盖的 —— 见该目录
`wanglin-tmall/generation/READ-ME-证据被覆盖.md`）。**业务事实一件没丢**：
每个 recordId、每个字段值、每次审计都有独立来源（stdout 台账 + `daily_report_push_audit` + 两条回读通路）。
但「一键拿到那一家店的完整产物」这条能力现在是缺的。

**修的方向（2026-09-18 晚：已实施并验证）**：把店铺并进目录语义 ——
`evidence/daily-report-<日期>-<shopKey>[-rerunN]`，其中 `<shopKey>` 是**运营叫法**。
实现只有一处：`daily-report-runtime.mjs` 的 `evidenceBaseDir({ evidenceRoot, reportDate, shopKey })`，
三个写入方（推送 / 回填 / 独立回读）共用它，**不再各自拼目录名**。
不给 `--shop-key` 时返回的仍是 `daily-report-<日期>`，**默认行为逐字不变**（单店跑与所有历史目录一个字都不用改）。

**那个「必须先想清楚的约束」是这么解的**：不动「先定代次、再动任何东西」的语义 ——
`evidenceBaseDir` 是**纯函数**（只吃 reportDate + 键，不读任何文件），所以它能留在
`main()` 的原位置上；`resolveOutputDir` / `resolveEvidenceDir` 照旧在 `extractSources` 之前跑。
代价是键变成了**调用方的显式输入**，而不是「读完 xlsx 自动得出」——
这正是「按店铺循环」那层驱动要做的事（它本来就知道自己在跑哪家店），
而共享窗口的页头**不是**可靠的来源（§4.2：19022 的页头实测是里可林，与 19031 撞店）。

**键是断言，不是标签** ⇒ 两道守卫，都有用例 + 突变验证（`evidence/shop-key-dimension-2026-09-18/`）：

- `assertEvidenceShopKey(key, observed)`（`shop-identities.mjs`）：键必须是**已登记**的运营叫法；
  能观察到的店名都要与登记表对上 —— 推送方比源 xlsx 的「店铺名称」列，回填方比同一命令的 `--shop`，
  回读方只核「已登记」这一半（它没有源产物可核）。**错标签比不贴标签更糟**：
  `daily-report-2026-09-17-网林天猫` 里装着里可林的数据，下一个复盘的人会得出完全错误的结论，
  而且从文件名上看不出来。
- 键的字符集收窄到 `/^[\p{L}\p{N}_.-]+$/u`（挡 `../`、斜杠、空格、不可见字符），在拼路径前就拒。

**还没验到的一条（如实记）**：`run-daily-report.mjs` 是「先认飞书页（`inspectTarget`）、再 mkdir」，
所以死代理下它**不会**建目录 ⇒ 推送方带键的真实落点只能在真跑时看
`plan.json` 的 `evidence.outputDir` 或 stdout 的 `[shop-key] …` 那行。
回读与回填两条的接线已用真命令行验过（7 个用例，见证据目录 `03-cli-wiring.txt`）。

**顺带修掉的一个洞**：`readback-daily-report.mjs` 原先不核键 ⇒ 任意字符串（含页头店名）都能当目录后缀，
而且核的位置在 `mkdirSync` **之后**。现在核在 mkdir 之前，错标签的目录根本不会被建出来。

教训与 §4.1 同源：把「幂等键／去重键／锁键／收据主键／**产物目录**」这五类
「默认生成规则里带不带维度」列成一张表逐个检查。这一维是这一族的**第三次出现**
（① §4.2 端口登记表 → ② §4.1 查询键 → ③ 证据目录名，也就是本节）。
修的时候还在第三处**内部**又翻出一个小号同类：回读方只顾着拼目录、从不核键 ——
补上之后，「任意字符串都能当目录后缀」这条通道也一起关了。

## 5. agent 该做什么、不该做什么

对齐 `WHERE-LLM-IS-NEEDED-DECISION.md`（2026-09-16 已定）：LLM 在本项目里唯一的合法位置是
「词表兜底」，而那份文档把「单 agent 分诊」列为 **P4，可以不做**。

本轮用户的主张（「必须要有 agent 监督着跑」）针对的是另一个角色——
不是「用 LLM 判断内容」，而是「用 agent 驱动流程、发现失败、及时反馈」。这两件事必须分开评估：

| 角色 | 定位 | 结论 |
| --- | --- | --- |
| LLM 作为**内容判断/生产**的组件 | 属性分类、字段补全 | **已否**（除 P3 词表兜底）。多店铺不改变这条。 |
| agent 作为**流程驱动与监督** | 定时叫醒、发现哪家没成、通知、白名单内自愈 | **合理，且是第 3/4 步待接线的部分**。多店铺显著提高其价值。 |

**三条必须守住的前提**（缺一条，agent 监督就会变成新的静默失败源）：

1. **监督的产物必须落盘成机器可读文件**（每店成功/失败/原因码 + 写入结果）。
   客户看到的状态从文件读，不从 agent 的对话读。否则就是「第二份状态真相」的变体：
   客户看到的是叙述，不是状态。
2. **自动重试必须幂等**。单店重试的幂等靠飞书查重键；跨店并发靠串行闸门。
3. **通知必须走不依赖 agent「讲清楚」的通道**（`notify-feishu` 三跳链已就绪），
   并且**去重与恢复成对**（已有实现，直接复用）。

### 5.1 凭据与自动登录：要改一条非目标，且改动范围有上限

**2026-09-18 已拍板：开这条口子。** 用户原话「**能自动登录最好，不能再退**」——
即：按 §5.2.4 的**轻量口径**开（借客户浏览器自己的密码库 + 一次可信手势），
**不接受退回「纯人工扫码」**。§8 第一条与 README §2 的非目标表述已按此改（见 §7 第 1 行）。
下表的四条边界**不因这次授权而放宽**。

**用户要求（2026-09-17 18:30）**：账号密码登录；账号分离；切店铺时不需要人工登录；每家店都能自动登录。

**这条请求直接触及一条既有非目标。** `LOGIN-STATE-MANAGEMENT.md` §8 第一条原文：
「**不做账密代登**：登录一律人工（扫码/人工确认），与 README §2 非目标一致，也避免凭据保管责任。」
**2026-09-18 用户已答「允许」**（原话「能自动登录最好，不能再退」），据此 §8 第一条已切成
「允许＝密码库填充 + 一次可信手势／不允许＝我们写值进表单」两半。
下面是改动前你必须看到的全部取舍（**保留**，它是这条口子为什么长成今天这个形状的依据）。

**先说做不到的部分（避免一个兑现不了的承诺）**

- 淘宝/阿里系的登录页在换设备、异地、或风控命中时会要求**滑块或短信验证**。
  账号密码自动填充只能覆盖「不需要二次验证」的那一段。
  ⇒ 真实能达到的最好状态是「**大部分时候自动，偶尔必须人**」，不是「每家店都能自动登录」。
  把它写成后者，等于给自己埋一个必然会兑现不了的交付承诺。
- **不做任何反检测、指纹伪装、验证码识别**；命中验证码或风控页 ⇒ 立即停下通知人。
- **不做「检查失败就重试登录」**（既有边界：重试是风控的加速器）。
  13 家的规模把这条的风险放大了——一个 IP 上短时间内 13 次登录正好是风控最喜欢的模式，
  一次误触发可能连带把一批账号打进保护性锁定。

**所以这件事的主题不是「每天自动登录 13 次」，而是「尽量不登录」**

1. 每店一个 profile ⇒ 登录态是**持久化**的，正常运行日根本不该触发登录。
2. 真正要解决的是**会话过期后的续期**，而不是每天一次的例行登录。
3. 自动登录只在「体检判定该店会话已过期」时触发一次；失败即转人工。

**四条不可放宽的边界（即使你同意开这条口子，也建议写死）**

| 边界 | 内容 | 为什么 |
| --- | --- | --- |
| 凭据存放 | Windows 凭据管理器（DPAPI）或加密文件；`config/customer.json` 里只放 `credentialRef`（位置标识） | 那份配置跟着机器走、会被复制、会被人用记事本打开，它不承担保管秘密的职责 |
| 凭据可见面 | **明文不入库、不进日志、不进证据目录、不进通知** | 沿用既有安全边界（`LOGIN-STATE-MANAGEMENT.md` §8 第四条） |
| 失败熔断 | 同一账号连续 2 次失败 ⇒ 当天不再试、通知人 | 「再试一次看看」在 13 家规模下就是风控加速器 |
| 节奏 | 13 家**串行**、每次之间留间隔、一天最多一轮 | 同 IP 短时多次登录是风控的典型特征 |

**另外一条工程要求：它必须是一个开关，且默认不改变现有行为。**
默认关闭时，系统行为与今天**逐字相同**（人工登录 + 体检提示）。
这与 `runtime/customer-config.mjs` 文件头那条硬约束同源：**新增能力不该悄悄改变默认路径。**

**2026-09-23 更正上面这句的适用范围**（不改就是文档与代码打脸，必须写清**谁默认什么**）：

| 层 | 默认值 | 为什么 |
| --- | --- | --- |
| `runtime/daily-job-plan.mjs`（建计划的纯函数） | `autoLogin` **默认关** | 它会被**直接调用**（用例、别的入口），且带 `--login` 会真的碰页面。纯函数不该有副作用默认值 |
| `scripts/run-daily-job.mjs`（定时链宿主） | **默认开**，`--no-auto-login` 可退 | 这是**自动化入口** —— 用户 2026-09-23 的授权就是针对它。默认关等于把「无人值守」作废 |
| `scripts/run-batches.mjs`（分批驱动） | **默认开** | 同一条链的另一个宿主，口径必须一致，否则「定时跑会自愈、手动分批不会」 |

所以这条工程要求**没有被推翻，是被落实到正确的层**：出厂配置里没有它、模块单独被调用时行为不变；
**只有自动化宿主显式打开了它**。这与 1.0.0 那条「默认关闭的 `--batches`」是同一个手法。

用户指出「浏览器本来就记住密码、会自动补齐」——这条改变了实现方式，**不需要我们保管任何凭据**。

#### 5.2.1 只读探测：库里确实有淘宝凭据

#### 5.2.2 端到端实测：自动填充会不会发生（本次新做）

做法刻意保守：**全新一次性临时 profile**（不碰任何生产 profile），用我自己编的假账号假密码
（`PROBE-DUMMY-USER` / `PROBE-DUMMY-PASS-1234`）写入该临时 profile 的密码库，
再真实打开淘宝登录页。全程不读、不解密、不复制任何真实凭据；实验 profile 与密钥文件已删除。

**实测结果（四条，按顺序）：**

1. **自动填充确实发生，且是无人干预的。** 页面加载完 15 秒内我没做任何操作，
   账号框与密码框都命中 Chromium 的 `:autofill` 伪类，**截图里账号框显示 `PROBE-DUMMY-USER`、
   密码框是一串圆点** ⇒ 「浏览器会自己填」这件事在真实淘宝登录页上成立。
2. **但它只是「预览绘制」，值没有进 DOM。** 同一刻 `el.value.length` 是 **0**。
   用脚本（不可信）点击「登录」后，页面报「**请输入账号名**」——说明页面自己的 JS 读到的也是空。
   ⇒ **光有自动填充，登录是走不完的。**
3. **一次真实鼠标事件之后，值才落进 DOM。** 用 CDP `Input.dispatchMouseEvent` 往页面空白处点一下，
   再读：账号框 `valueLength` **0 → 16**、密码框 **0 → 21**（正好等于那条假凭据的长度）。
   ⇒ **可信手势是必需的，而 CDP 能发可信手势。** 这条把"要不要自己填"的问题缩小成
   「要不要多发一次点击」。
4. **提交后遇到的是协议二次确认弹窗**（「服务协议及隐私保护 … 不同意 / 同意」），
   **没有出现滑块、也没有图片验证码**。协议勾选框默认**未勾**，得先勾上。

#### 5.2.3 登录页结构（顺带实测，**更正上一轮的一处记法**）

- `login.taobao.com/member/login.jhtml` 会跳到 → `login.taobao.com/havanaone/login/login.htm?bizName=taobao`。
  凭据按 `signon_realm = https://login.taobao.com/` 匹配，跳转不影响填充（已实测）。
- **表单在顶层文档里，不在跨域 iframe 内。** 页面唯一 iframe 是一个隐形的 tmall 第三方 cookie 页。
  （上一轮我记成「淘宝登录页嵌在 iframe」——**记错了，这里更正**。iframe 那条说的是生意参谋的门户壳，两回事。）
- 字段：`#fm-login-id`、`#fm-login-password`（`autocomplete` **未设**，没有关掉密码管理器）、
  `#fm-login-checkcode`（图片验证码，提交前 `visible=false`）、`#fm-agreement-checkbox`（默认未勾）。
  「密码登录」是默认 tab。
- `havanalogin.taobao.com/mini_login.htm` **裸 URL 不能独立打开**（报「非法请求 [appNameError]」）——
  它是被别的应用内嵌调用的迷你登录页。库里存着这条凭据只说明历史上被用过，不代表它是入口。
  **2026-09-23 补充（并排实测，两句话都要留）**：① 带上平台自己给的参数、**顶层打开就是活登录页**
  （账号框/密码框/登录按钮全 visible）⇒ 「不能打开」只对**裸 URL**成立；
  ② **「能被打开」≠「会被填充」** —— 同一台机器上把那条带参数地址真打开、真点击，
  `:autofill` **恒 false**、值不落地（0/3）⇒ 存在**某些 origin，其凭据永远不会被装饰**。
  所以「改成凭据所属 origin 那条地址」**不是**一条可用的修法（本条曾被写成可用修法，已证伪）。
  进候选表的是 `login.taobao.com` 上的两条：`havanaone/login/login.htm?bizName=taobao`（实测 3/3）
  与 `member/login.jhtml`（2/3），**顺序即优先级**，逐条打开试到 `:autofill` 为真为止。
  取证＝`evidence/login-candidate-loop-2026-09-23/README.md`。

#### 5.2.4 修正后的方案（**不保管、不填充、不解密**）

1. 每店一个 profile；首次由人工在该 profile 里登录一次并勾选「保存密码」——**一次性 setup，13 次**。
   **保存那一刻地址栏必须停在以 `login.taobao.com` 开头的登录页上**：在别的 origin 的登录页保存，
   下次一样填不上（而这件事**没有任何地方会报错**，只表现为下一次 `NO_AUTOFILL`）。
2. 会话过期时：**按候选表逐条打开**（`login-merchant-core.mjs` 的 `LOGIN_URL_CANDIDATES`，
   顺序即实测命中率）→ **不填任何字段** → 等密码管理器自己填 → 读 `:autofill` 判有没有出手；
   这一条不成立就换下一条，全试完仍不成 ⇒ `NO_AUTOFILL`。
3. **然后必须补一次可信手势**（CDP `Input.dispatchMouseEvent`，不是 `el.click()`）——
   这是 §5.2.2 第 2/3 条的直接后果：不发可信事件，值就留在预览态、页面读不到。
4. 勾协议 → 点登录 → 若出现协议二次确认则点「同意」。
5. 判据只看「输入框有没有值、长度非零」，**值绝不进日志、不进证据目录**。
6. **身份守卫（先于提交）**：填进来的账号必须等于该店登记的会员名；不等（或为空）⇒ **不点提交**、
   判 `WRONG_ACCOUNT` / 空值，转人工。理由见 `MEMORY` 里「同 origin ≥2 条 ⇒ 浏览器自己挑一条」——
   「登成了别人」不会报错，比「登录失败」贵得多。
7. 任何一步没成 ⇒ 停下，走飞书通知要人。
8. **明确不做**：不解密 `Login Data`（DPAPI + Chromium AES key）。那正是「代账密」的定义，
   而且等于把「解密客户密码库」这段代码交付出去。

**仍然未验证、且必须写清楚的一条**：真实账号提交之后**会不会触发滑块或短信验证**。
假账号在走到协议确认那一步就停了，测不出真实风控的反应。而 13 家 = **13 个新 profile =**
淘宝眼里的 13 台新设备，这一步的触发概率不低。**这条是整条路线剩余的主要不确定性。**

**零凭据接触的体检判据**（可做）：只 `COUNT(*)` 统计该 profile 有没有该站点的行、不读密码列，
就足以驱动「该店需要人工登录」这条提醒。

**结论**：用户提的这条路**能达成日报目标**（已实测），但它不是「零动作」——
是「自动填 + 一次可信手势 + 勾协议」。而这恰好把「agent 自己填」的唯一优势（少一次点击）
压到了几乎没有，代价却是我们要持有 13 组店铺主号明文密码。**所以采纳浏览器自动填。**

#### 5.3.1 「新建 profile」≠「干净 profile」—— 2026-09-18 实测出的配方

只把 `--user-data-dir` 指到一个空目录**不够**。实测（同机、同一天、同一份启动参数）：

| # | 做法 | 结果 |
| --- | --- | --- |
| A | 空目录直接启动 | 启动后几十秒内 `Preferences` 就出现 `account_info.email=1074083863@qq.com`、`sync.passwords=true`；`Login Data` **47 条**——个人密码库（Google/EA/GitHub/Cloudflare/OpenAI/本地开发面板…）**外加**当时在旧 profile 里存的另外两家店的淘宝凭据，全被同步进来 |
| B | 空目录 + **启动开关 `--disable-sync`** | `account_info` 仍出现（微软账号仍会被自动登录），但 `sync.passwords` 为 `null`；`Login Data` **0 条**，几分钟后仍是 0 |

结论与两条推论：

- **有效的是启动开关 `--disable-sync`**，不是「预置 Preferences」——
  本次也预置了 `signin.allowed=false`，它**被保留但没能拦住**自动登录（键读回来确实是 `false`，账号照样登进去了）。别把这条当成保护。

  而淘宝登录页的自动填充是按站点匹配的 ⇒ 出现「在里可林家的窗口里填出盖文/随心家的账号」，

- **顺带观察（未定论）**：A 那个实例在约 5 分钟内以 `msedge exited code=4294967295`（= -1）退出、
  调试端口消失；B 的实例同时长内仍存活。**我们没有定论**（可能与登录/同步触发的自动重启或崩溃有关），
  只把它记为事实；但**交付口径取 B**，因为它同时挡住了两件事。

## 8. 不承诺什么

- **不承诺「无人值守」**：跑中可能撞验证码；账号密码自动填充（若开）也只能覆盖不需要二次验证的那一段。
  正确承诺是「人一周可能被打扰 0～2 次」（单店口径）；多店下这个数字必须先实测，不要先写进交付承诺。
- **不承诺多店能同时跑**：浏览器写操作串行是既有硬约束（`UNATTENDED-AGENT-RUNTIME-PLAN.md` §3）。
- **不承诺「服务器侧无人值守」**：只要验证码这一步需要人，执行就必须发生在有屏幕的那台机器上；
  账号密码自动填充改变的是频率，不改变这条。
- **本文件区分清楚「已做」与「待做」**：§4.1 的模板改动、§4.4 的配置段与校验**已在 2026-09-17 完成**
  （含突变验证与套件复跑）；§5.2.2 的自动填充实测也是**已做**（但那是**一次性临时 profile 上的设计验证**，
  ~~不是生产实现）；§5.1 的凭据自动登录**没有动任何生产代码**，它要等一条非目标的明确授权。~~
  → **2026-09-23 更正**：§5.1 的凭据自动登录**已动生产代码并接进两个自动化宿主**，
  授权见 §7 B 项与 §5.1 那张默认值表；**但真机整链没跑过**（六个实例当天会话全失效），
  所以「已接线」不等于「已验证」。
- **不把「实测过」说成「已经能用」**：§5.2.2 证明的是机制成立，不是「13 家能自己跑完」。
  从机制到可用之间还差：第 4 步体检、登录适配器、会话到期语义（G7，必须实测不许照抄）、
  以及**真实账号的风控反应**这一条完全没测过。

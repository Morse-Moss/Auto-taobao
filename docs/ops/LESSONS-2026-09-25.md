## 三、根因

### 根因 1：宿主沙箱按「每次工具调用」决定要不要掐断同步子进程，分界在 stdin 那条管道

这是当天最大的一个，也是唯一一个**代码缺陷**。

- **症状**：阶段产物只有三行，`exit=null`、`error=spawnSync … EBUSY`、`errno=-4082`（libuv `UV_EBUSY`）、
  `status=null`、`stdout/stderr=undefined`，而且 **1~4ms 内 fail-fast**（不是超时、不是子进程崩了）。
- **判据**：12 组对照下，`stdio` 里 stdin 是 `'ignore'` 的全通；不写 `stdio`（默认三根管道）、
  `['pipe',…]`、`input:` 的全灭。宿主日志 `%USERPROFILE%\.workbuddy\logs\<日期>\<工作区>__*.log` 里
  **每次调用**都有一行 `[SandboxOrchestrator] OUTCOME`：`sandbox-disabled` 的两次全通（08:14、08:55 的那次手动），
  `background-sandbox`／`sandbox-success` 的每一次全灭。⇒ 与代码、数据、Node 版本都无关。
- **两个反直觉的推论**（都实测过）：① 它**穿透到孙进程** —— 用 `['ignore',…]` 起起来的子进程，
  自己再做默认 stdio 的同步 spawn 照样炸；② 它**只掐同步那一条路** —— 异步 `spawn` 没事，
  Python 的同步 `subprocess` 也没事，收 stdout/stderr 更是完全没事。
- **处置（1.7.1，已落地并提交 `0c6d060`）**：3 个生产调用点（链的阶段 spawn、整轮告警投递、
  第 7 步 push 内部的 `py extract-sources`）＋ 2 处测试 ＋ 2 个门禁脚本，一律显式 `stdio:['ignore','pipe','pipe']`；
  告警改走 `notify-feishu.mjs --alert-file`（不再用 `input:`）；新增跑前自检 `probeSyncSpawnSanity`，
  把「宿主掐断」与「数据坏了」打在 job.log 第一行分开。
- **仍未修**：`scripts/delivery-status.mjs:7`（`check:delivery` 因此直接崩）、仓库里另外 10 处测试侧同类调用、
  `runtime/browser-inventory.mjs` 与 `scripts/stop-all.mjs` 三处静默降级点。

### 根因 2：早于「阿里妈妈静止点」跑，写进去就是低值，而且当天无法重推

- 阿里妈妈推广块上午有未回补窗口，CSV 到 **11:20 前后才静止**（08:04 那份与 11:22 之后逐字节不同）。
- 而写入的查重键是「同一天＋同店铺」⇒ 上午写进去的是低值，**无法同日重推**，只能先删掉那天的记录再跑。
- 第 1~5 轮全部落在 11:20 之前。所以即使第 3 轮技术上跑通了，它写进的也是低值 —— 这也是后来
  「先删了重跑」的原因。
- **处置**：补历史日一律排在 **11:40 之后**（11:40 是唯一安全边界）。这条已经写进新挂的自动化 prompt。

### 根因 3：默认策略是「首家失败即停整轮」

- 第 3 轮就是这样：里可林成功了，网林一停，**其余 3 家一步都没跑**，整轮只写进 1 家。
- **处置**：补多店必须带 `--keep-going`。这是跑法，不是代码，但没有它，任何一家出问题都会让整轮白跑。

### 根因 4：商家浏览器（19022/19023）没有自动登录维护

- 第 1 轮的死法：整轮一步不跑，且原因**被写成了「页面不齐，请各开一个」** —— 而真因是登录墙，
  照告警的下一步做只会开到登录页。
- 1.7.0 已经修掉一半（预检先归位、新结论 `PAGES_ABSENT`、告警整轮一条、抽出去重）；
  1.7.1 起补跑前会先跑 `login-preflight`。
- **仍未修**：19022/19023 真正的自动登录（1.7.0 起一直押后）。这是目前整条链唯一的单点。

### 根因 5（当天新识别）：幂等闸门的退出码被读成「失败」

- 第 9 轮退出码 1，但每一处输出都在说同义词：「这一天飞书里已经有数据了，脚本按『不许写第二遍』停住了」
  「下一步：不用处理」。
- 它不是故障，是**防线生效**。可是它和真失败共用同一个退出码，任何按退出码做判断的自动化都会误判。
- **处置建议**：给「因已有数据而停手」单列一个结论值（或专门退出码），别再让它和「跑到一半炸了」混在一起。

## 五、一条「看起来像缺数据、其实不是」的降级

09-20 科塔淘宝的「同层同行询单量」是空的，而其它 4 家（09-21 当天写的）两个字段都齐。差异不在店，在**跑法**：

`skills/sycm-alimama-daily-report/scripts/run-inquiry-backfill.mjs:177-183` 写了显式降级：

```
degraded: metrics.peerBenchmark === 'PEER_UNAVAILABLE'
  // 历史日（自定义日期）实测只剩 3 行，数据源不返回同行同层对比行。
  // 这是显式降级：单据里写清缺什么、为什么缺，而不是静默留空或写 0。
  ? { code: 'PEER_UNAVAILABLE',
      reason: 'SYCM 自定义日期模式下表格不含「同行同层均值」行（预设「1天」才有）',
      omittedFields: ['同层同行询单量'], ... }
```

⇒ 补历史日时，生意参谋走「自定义日期」模式、表格只剩 3 行、不含「同行同层均值」，
所以脚本只写「询单量」、把那格留空。收据是 `{"询单量": 7}` ＋ `status: COMMITTED_AND_VERIFIED`，
**这是预期行为，不要当缺陷去修**。

**但它有一个必须记住的代价**：补历史日写出来的行，与当天正常跑出来的行**字段完整性不同**。
拿补出来的行做同比／环比时要先看这个字段在不在。

# 卡点、智能丧失、通知失效：第一性原理归因与解决方案

日期：2026-09-16
问题（用户描述）：
1. 数据收集流程中频繁出现卡点，系统没有自愈能力、不能自动恢复；
2. 此前用 codex 配合 skills、AI 全程运行的方式效果稳定，改成固化系统后这种智能性基本丧失；
3. 流程虽相对固定，卡点仍不断出现；
4. 触发卡点时飞书未收到提醒。

方法：不罗列现象。先把「卡点」按失败机理分类，再找它们共同的形状；然后把「智能」定义成可验证的行为，看它具体丢在哪一步；再把通知链按「有没有可发的信号」逐层拆开。

---

## 0. 四条结论（每条一句话）

1. **卡点的根因不是流程不固定，而是「系统内置的假设」与「环境的实际状态」之间的差集，且系统没有重建假设的能力。** 流程固定化提高了可重复性，同时把「适应环境的自由度」也一起固定掉了。
2. **智能丧失不是退化失误，是一次取舍，但取舍放错了位置。** 系统把 fail-closed 纪律同时施加到了「读与观察」和「写与提交」两侧；而前者本来无副作用、可以自由试错。AI 当年能跑通，靠的是每一步重新观察（闭环），不是它知道得更多。
3. **飞书没提醒不是一次故障，是四个各自都「设计正确」的选择叠加出来的必然结果**：判据保守、覆盖只做了一段、投递默认关、调度未启用。
4. **恢复智能的正确做法是「按风险重新分配自由度」，不是把 AI 放回全流程。** 读侧放开给 AI，写侧保持确定性加人工闸门。

## 1. 卡点产生的根因

### 1.1 先把「卡点」分类（不同类，修法不同）

| 类 | 机理 | 最近的真实实例 |
| --- | --- | --- |
| **A 外部契约漂移** | 外部系统的结构/命名/行为变了，系统的内置假设失效 | 建周表脚本的 `CLONABLE_TYPES` 不含 19/20/21 → 新周表字段从 39 掉到 35；`buildCompetitorFieldMigrationPlan` 抛 `Unsupported AI field type for 尺寸: 19`；周表命名日期是采集日不等于周期结束日（`WEEKLY_NAME_PATTERN` 还不覆盖「关键词分析 V1（日期）」） |
| **B 身份与权限** | 登的是谁、有没有权限，和系统以为的不一样 | 飞书应用不是 base 协作者 → `403 / 91403`；买家账号被千牛顶掉；调试配置里小旺神扩展缺失 |
| **C 环境假设失效** | 对宿主环境的假设被违反 | 本机 bash 包装器缺 `dirname/sed/cat/grep/sleep`；PowerShell stdout 不返回；沙箱只允许连会话内已监听的端口；`Start-Process` 启 Edge 静默失败 |
| **D 数据语义缺失** | 结构全对、跑完全绿，但数值本身是坏的 | 采集包只覆盖列表的一个区段（低值周包内最大月收货人数 ≤ 48，而 A 级要求 ≥ 80）；`材质分类` 整列为空 → B 级为 0 |

### 1.2 四类卡点共同的形状

把上面四类抽象一层，它们完全同构：

```
卡点 = 环境的实际状态  −  系统内置的假设（写代码那一刻成立的假设）
```

而系统的行为是：**假设被违反 → fail-closed → 停住**。
它没有的行为是：**发现假设被违反 → 现场重建假设 → 继续**。

所以「卡点不断出现」不是偶然：**每一个没被写进代码的环境事实，都是一个潜在的卡点。** 环境会变，而代码不变，所以卡点的数量随时间单调增长。

### 1.3 为什么「流程固定」反而让卡点更显性

这一点值得说清楚，因为它和直觉相反。

- AI 全程运行时，流程表面上是「活」的：每一步都重新看环境、重新决定怎么做。环境的漂移被**当场吸收**了，所以看不出卡点。
- 流程固定化之后，自由度被写死成一条路径。环境一漂移，路径就走不通 —— 而**同一个漂移在 AI 时代根本不会被观察到，因为它不产生错误，只产生一次不同的选择**。

⇒ 换句话说：**不是固化制造了卡点，是固化把原本被 AI 悄悄吸收掉的卡点暴露出来了。** 这是固化应有的代价，问题在于我们只保留了「暴露」，没有保留「吸收」。

## 2. 智能为什么丧失

### 2.1 开环与闭环的差别（这是根因）

| | AI 全程运行 | 固化系统 |
| --- | --- | --- |
| 假设来源 | **当场建立**（每一步看完环境再决定） | **写代码时建立**（提前写死） |
| 控制方式 | 闭环：看到结果再决定下一步 | 开环：按剧本走 |
| 遇到未知 | 换一条路径再试 | `fail-closed` 停住 |
| 失败的价值 | 一次反馈，用于调整 | 一次终止 |

⇒ 结论：**固化系统保留了「执行」，丢掉了「意图」。** AI 运行时手里是目标（「我要把这周数据拿到」），系统手里是步骤（「跑这个脚本，参数是这些」）。步骤与环境不匹配时，AI 会改步骤，系统只会报错。

### 2.2 具体丢了三样能力

1. **多路径探索**：元素找不到时换选择器、换入口、换时机。系统只有一条路径。
2. **语义质疑**：AI 看到「包内最大月收货人数只有 48」会怀疑是不是漏了区段。系统只校验结构（行数、字段、哈希、回读），**不校验数值合不合理**。
3. **现场修复**：AI 会就地重试、换参数、跳过再回来。系统的修复动作必须提前写在代码里。

### 2.3 这是一次取舍，但取舍放错了位置

把系统的动作按「有无外部副作用」分成两边：

| | **无外部副作用**（读、观察、探测、重试读操作） | **有外部副作用**（飞书写入、发布、推进游标） |
| --- | --- | --- |
| **当前策略** | `fail-closed`（同样严格） | `fail-closed` + 幂等 + 回读 + 人工闸门 |
| **应该是什么** | **放开：允许多次尝试、允许 AI 决策、允许换路径** | 保持现状 |

⇒ **核心错配：fail-closed 被同时施加到了两侧。** 对写侧它是正确的（错一次就在真实数据上错一次）；对读侧它是纯损失 —— 读操作失败没有代价，而它失败时停住，等于把「可以再试一次」变成「需要人来救」。

这就解释了你感受到的「智能性丧失」：**AI 的自适应能力主要作用在读与观察上，而那一侧被关掉了。**

### 2.4 一个可验证的退化实例

仓库里 AI 能力其实一直都在：`runtime/local-provider-runner.mjs` 真 spawn 三个外部进程（`claude -p --output-format json` / `codex exec -` / `workbuddy run`）。

但它只被 3 个**手工发起的 CLI** 用过（`run-weekly-local-analysis.mjs`、`run-faq-ai-review.mjs`、`run-legacy-feishu-prompt-analysis.mjs`）。

更直接的对照：**当年 AI 在环的那个环节，现在退化成了人工操作。** `外形 / 安装方式 / 功能 / 风格` 这四个属性列的官方实现方式，是「飞书 AI 字段提示词 + **人工逐字段粘贴**、先抽样再批量运行」，并且**不属于自动化链的一环**。

⇒ 也就是说：智能没有丢，是**从自动链路里被移出去了**。所以「AI 含量」下降不是模型能力问题，是接线问题。

## 3. 飞书未触发提醒的失效环节

先给结论：**通道是通的，问题是没有任何一环产生「值得发的信号」，而且发信开关默认是关的。** 四层叠加，逐层给代码证据。

### 层 1（判据层，最根本）：监督判据全是「执行态」，判不出「结果坏」

`runtime/supervise-collection.mjs` 的四个判据（文件头注释就是契约）：

```
RUNNING          进程活着，末事件没超预算、进度还在推进
SUSPECT_STALLED  进程活着，但末事件静止超预算，或进度签名（页/行数）超过预算没变
COMPLETED        进程已退出、退出码 0（给了 --stdout-file 时还要求出现 ADAPTIVE_DONE）
FAILED           进程已退出、退出码非 0
```

**这四个判据全部回答「跑完了吗」，没有一个回答「跑对了吗」。**

而你遇到的卡点（§1.1 的 A 类与 D 类）恰恰都是「退出码 0 + 出现 ADAPTIVE_DONE」的形态：导出覆盖不足、`材质分类` 整列为空、周表少了 4 个字段、采的是别人账号的数据。

⇒ 后果不只是「没提醒」，是**更糟的一种**：`COMPLETED` 默认是**要投递**的（`--quiet-completed` 才压掉）。也就是说，只要它被跑起来，它会发一条「采集完成」——而数据是坏的。**监督环会把坏结果报成完成。**

### 层 2（覆盖层）：监督只挂在链的第 1 步

竞品周更实际是 8 步，实测的挂点分布：

| 步骤 | 外部监督 | 通知挂点 |
| --- | --- | --- |
| 1 采集导出 | 有（`supervise-collection.mjs`） | 有，但默认 dry-run |
| 2 建周表 | 无 | 无 |
| 3 导入 | 无（能力内自带 validator/回读/收据） | 无 |
| 4 公式重建 | 无 | 无 |
| 5 分类统计 | 无 | 无 |
| 6 SKU/尺寸富化 | 无 | 无 |
| 7 FAQ | 无 | 无 |
| 8 发布历史总表 | 无 | 无 |

而你说「数据收集流程中频繁出现卡点」—— 其中建周表、公式重建、分类统计这几步正是最近出问题最多的地方（周表字段回归、Lookup 被拒、B 级为 0），**它们既没有监督，也没有任何可以挂通知的点**。

### 层 3（开关层）：投递默认关闭

`runtime/run-weekly-collection.mjs`：

- `parseDriverArgs` 的默认是 `{ notify: false }`；
- 派给段级监督环的参数是 `...(options.notify ? ['--notify','--quiet-completed'] : ['--dry-run'])`（第 110 行）；
- 收尾告警同样分叉：`if (!options.notify) { log('DRY-RUN 收尾告警：...') } else { ... spawnSync(NOTIFY_CLI) }`（第 186-190 行）。

⇒ 我实际跑的那几轮用的都是默认值，所以**即使监督环判出了异常，也只在终端打印，不会发出去**。

注意这一条**本身是设计正确的**：飞书告警是对外可见动作，按项目纪律（以及你自己的规则）不能在未确认的情况下发。所以问题不在「默认关」，而在**关的时候没有任何替代通道**——dry-run 的告警只落进终端，而终端会随会话被回收。

### 层 4（调度层）：唯一有真投递的通道没启用

`runtime/sop-runtime/round-runner.mjs` 是唯一同时具备「通知判据表 + 真投递链」的地方（`round-notify-policy.mjs`，36 例双向覆盖，第三跳 webhook 已被取消）。

但：
- `runtime/round-schedule.json` 出厂 `enabled: false` + `target: null`；
- 部署机上还没接任何叫醒者；
- 而且它驱动不了竞品周更这条链 —— 8 步里只有导入段是运行时能力（`xws.feishu.import`），其余是手工 CLI（PROJECT-NOTES §12.6）。

⇒ 这层是「装了引擎没发动」。

### 四层的叠加关系

```
卡点发生（语义态）
  → 层 1 判据看不见        → 不产生信号
  → 层 2 就算看得见，这 7 步也没挂点
  → 层 3 就算挂了点，默认 dry-run 不发
  → 层 4 唯一会真发的通道没启用
= 飞书收不到任何东西
```

**这不是一次故障，是一个必然结果。** 四层里没有任何一层是错的设计，组合起来就是「静默」。

## 4. 解决方案：按风险重新分配自由度

### 4.1 核心原则

**读与观察放开，写与提交收紧。**

| 动作类型 | 策略 | 谁决策 |
| --- | --- | --- |
| 读页面、探测结构、试选择器、重试读操作、比对数值分布 | **放开**：允许多次尝试、允许失败重试、允许换路径 | AI 可决策 |
| 判定「这个结果对不对」 | 先用确定性判据；判据覆盖不到才问 AI | 规则优先，AI 兜底 |
| 写飞书、发布、推进游标、选账号/profile/写入目标 | **不变**：fail-closed + 幂等 + 回读 + 人工闸门 | 确定性 + 人工 |

一句话：**把 AI 放回读侧，不要放回写侧。**

### 4.2 动作 1：监督判据从「执行态」扩到「语义态」

新增四条判据，**全部本地可算、不需要 AI、不违反 fail-closed**：

| 判据 | 怎么算 | 成功拦住什么 |
| --- | --- | --- |
| `SUSPECT_COVERAGE` | 把本次采集包的数值分布（最大/中位月收货人数）与历史同期比，落在历史区间外即报 | 导出只覆盖一个区段（A 级为 0 的根因） |
| `SUSPECT_FIELD_EMPTY` | 关键字段（如 `材质分类`）的有值率为 0 即报 | B 级为 0 那条链 |
| `SUSPECT_SCHEMA_DRIFT` | 新建周表的字段数与主表比对；缺普通字段或派生字段即报 | 周表字段从 39 掉到 35 |
| `SUSPECT_IDENTITY` | 采集前后各读一次登录身份，与期望身份比对 | 登录的是别的账号（买家号与被顶掉的商家号） |

第三条最有价值，因为它把「字段回归」从「下次用的时候才发现」变成「建完表就报」。

### 4.3 动作 2：通知从「一轮收尾」改成「卡点事件驱动」

现状：通知挂在轮次收尾（`round-runner` 的 `finish`），而链在中间卡住时，一轮**永远不会收尾**（人停了链就停了）。

改成：
- 每一步进入/结束各产生一次状态变更事件；状态**变化**才投递（沿用 `supervise-collection` 已有的「同状态只投一次」语义，避免告警轰炸）；
- 增补「步骤停滞超预算」的即时告警；
- 分级：`INFO`（正常完成，可汇总）/ `WARN`（可疑，如 `SUSPECT_COVERAGE`）/ `ERROR`（失败或需人工）。

关于「对外可见动作要授权」这条纪律怎么办 —— **不要用「默认不发」来遵守它**，改成：
- **告警的落点先写本地持久化收据**（不是终端），保证信号不随会话消失；
- 投递通道默认打开**只读的 `INFO/WARN` 汇总**（每天/每轮一条，不是每个卡点一条），`ERROR` 保持即时；
- 需要更细的即时推送时显式开。这样纪律不破，静默不再。

### 4.4 动作 3：给手工的 6 步补「链级进度账本」

现状：8 步里只有 1 步有运行时状态，其余 6 步各自输出到终端 → 没有单点知道「这条链到第几步、卡在哪」。

改：加一个轻量链进度记录，**写 PostgreSQL 不写文件**（正好是 G1 的修法，也与 README §5「本地 JSON 不得决定业务恢复位置」一致）。每步进入/结束各记一条，含：步骤名、开始/结束时间、退出码、产物路径、失败分类。

收益：
- 能回答「卡在哪一步」（现在只能靠人回忆）；
- 断点续跑有了依据；
- §4.2 的语义判据和 §4.3 的通知有了统一的观察点与触发点。

### 4.5 动作 4：AI 回到读侧（三个只读角色）

全部只读、全部产出提案、全部过 validator，**都不能写、不能改 selector、不能选账号、不能决定发布**：

| 角色 | 输入 | 输出 | 用在哪里 |
| --- | --- | --- | --- |
| **探索器** | 当前页面 DOM/截图 + 目标描述 | 候选选择器/入口的**建议** | 页面改版、元素找不到时（人确认后固化成代码） |
| **分诊器** | incident（来自 §4.4 的进度账本 + §4.2 的判据） | 类别 + 下一步建议 + 理由 | 失败签名不在 7 类里时 |
| **语义审阅器** | 数值分布与历史对比 | 「这个分布像不像漏了区段」+ 理由 | `SUSPECT_COVERAGE` 触发后，给人工一个可读判断 |

关键：**三者都只在「读侧」放宽，写侧完全不动。** 这与 `SUPERVISOR-AGENT-DESIGN.md` §11 的「不做什么」不冲突（那条禁的是 Agent 直接采集/点击/写入）。

### 4.6 动作 5（最重要的机制）：卡点解决必须沉淀成判据

这是回答「流程固定但卡点不断出现」的那把钥匙。

AI 在环时，一个卡点解决了就过去了，**下次还会再卡** —— 因为解决过程只存在于对话里，而对话会被回收。这就是为什么「效果稳定」的时期，问题也并没有真正减少。

改：**每次卡点解决后，强制在仓库里留一条判据**，格式固定为三段：

```
症状（可观测的现象）
  → 检测方式（能被监督环自动算出来的判据）
  → 处置（确定性动作 / 需人工的动作）
```

然后让 §4.2 的监督环能加载并使用它。这样系统是「越跑越知道」，而不是「每一次都从零踩」。**这条是把 AI 的临时智能变成系统永久智能的唯一机制**，优先级高于任何单个 bug 的修复。

---

## 5. 保持稳定性的边界（明确不改什么）

- **不动** fail-closed 对「外部写」的约束：飞书写入、发布、游标推进、租约仍然严格。
- **不动** 幂等键、提交账本、发布回读。
- **不动** 「Agent 不能选租户/账号/profile/写入目标」（`SUPERVISOR-AGENT-DESIGN.md` §11）。
- **不动** 「移除模型后确定性流程仍可运行」这条硬不变量 —— 动作 4 的三个 AI 角色都必须是可移除的。
- **不引入** Temporal（见 `AGENT-ARCHITECTURE-FIT-ANALYSIS.md`），本轮结论不变。

## 6. 落地顺序

| 序 | 动作 | 依赖 | 解决哪条问题 |
| --- | --- | --- | --- |

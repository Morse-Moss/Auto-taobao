## 3. "零 LLM"结论的实测检验

原结论：当前没有任何部分必须接 LLM。用真实数据检验后，**结论未被推翻，但需要精确化**。

### 3.1 词表外的表达占多少（本周表全量）

对每列，把"推导为无注明"的行再分成两类：标题里出现了同义表达（词表没收），还是标题里根本没有这个维度。

| 字段 | 词表内命中 | 词表外候选 | 真无信息 | 现状 → 词表回归后上限 |
|---|---|---|---|---|
| 材质分类 | 1120 | 40 | 234 | 80.3% → 83.2% |
| 安装方式 | 1028 | 22 | 344 | 73.7% → 75.3% |
| 外形 | 388 | 163 | 843 | 27.8% → 39.5% |
| 功能 | 391 | 116 | 887 | 28.0% → 36.4% |
| 风格 | 320 | 69 | 1005 | 23.0% → 27.9% |

"词表外候选"是**宽口径**统计（包含"弧""简约"这类很宽或已部分覆盖的词），所以上表右列是**收益上限**，实际可用增益只会更小。

### 3.2 由此得到的判断

- **60%~72% 的"无注明"是标题里真的没写**这个维度。浴缸标题普遍只写"独立式浴缸 / 材质 / 尺寸"，很少写风格与功能。这部分**任何方法都变不出来**，包括 LLM——它读的是同一个标题。
- **词表外表达只占 3%~12%**，用**词表回归**（把线上高频未命中词补进词表）就能吃掉大部分，成本远低于 LLM，且可审计、可离线回归。
- **LLM 唯一可能的超额收益**在"词表永远追不上的长尾表达"，但实测上限只有 +5~12 个百分点。
- **让"无注明"真正下降的唯一路径是引入新信息源**（详情页参数、类目属性、图片 OCR），不是换更强的模型。

**结论：LLM 不是当前瓶颈的解。当前瓶颈是"写入方缺失"与"判据不到结果态"。**

## 4. 第一性原理：为什么"一两天"和"一个月"都不奇怪

### 4.1 两者在优化不同的东西

| | AI + skills（一两天） | 固化系统（一个月） |
|---|---|---|
| 优化的对象 | **这一次**产出结果 | **每一次**产出同样可核对的结果 |
| 卡点出现时 | 当场发现、当场换法子绕过去 | 要求卡点被永久解决，不能只绕过 |
| 知识驻留处 | 会话里（漂移当场吸收） | 代码与判据里（不依赖某次会话） |
| 失败的表现 | 这次不成，重来一次 | 必须可复现、可定位、可回归 |
| 无人时 | 走不动 | 应当能自己走 |

AI 的"一两天"不是因为它快，是因为**它不需要解释**。它看到菜单结构变了就换选择器，看到登录的是商家账号就换买家账号。每一次都重新发现，但每一次都能发现。代价是：**知识不在任何可核对的地方，下次从零开始。**

系统的"一个月"不是因为它慢，是因为它在做一件 AI 不做的事：**把隐式知识变成显式判据**。

### 4.2 慢的部分，哪些合理、哪些是浪费

**合理的慢**（不可压缩）：
把环境漂移固化成判据本身要付代价。小旺神菜单的两阶段兜底、账号身份边界（商家号看不了别家详情页）、断点续传、日期字段口径——这些都得逐条踩出来才能写进代码。这部分一个月不算离谱。

**不合理的慢**（可压缩的浪费）——"建好了没接"，目前 5 例：

1. `sop-runtime/agent-{proposal,review,planned-run}.mjs` 契约层：`createAgentPort` 只有测试实例化过，无生产调用点
2. `compression-service.mjs`：零调用点
3. 分层 `memory-store.mjs`：只有 `index.mjs` 导出，PG 后端指向不存在的文件
4. 五个属性列的算法：全部存在，无写入方（本报告 §1）
5. 日期字段回填：方案已定，未接进导入管线（日报 #8）

这五例都不是"难"，是"没接线"。**这是纯粹的返工，不是必然代价。**

**被误判为"没跑通"的部分**：09-06 那周流程跑通了，但仪表盘空。系统把"坏结果"报成了"完成"，人看到的是"没通"。

### 4.3 真正的问题：顺序倒置

正确的顺序是：

1. 先用 AI 把流程**真跑通一次**，并留下**收据**（哪一步、什么输入、什么输出、判据是什么）
2. 把这次的**成功条件**固化成判据
3. 让系统复现这次

而实际发生的顺序是：

1. 先建通用的 agent 契约层、分层记忆、压缩服务、监管设计
2. 再想怎么把流程接进去

后者一个月还在接线，前者一两天就能出结果——**因为它们的信息流方向相反**。前者是"从一次真实运行反推判据"，后者是"先造判据再找运行"。**这不是 AI 与系统的差距，是顺序的差距。**

### 4.4 什么算合理、什么算浪费

- **合理**：为把漂移固化成判据而多花的时间。
- **浪费**：建好了不接、接了不验结果、判据停在"执行成功"而不看"结果对不对"。
- **可砍**：任何"先建通用框架再看怎么用"的部分。Temporal 属于这一类——它至今是"没下定论的 POC"，且真正的触发条件（≥2 台机器共享限流、跨天跨重启长 timer）一条都没出现。

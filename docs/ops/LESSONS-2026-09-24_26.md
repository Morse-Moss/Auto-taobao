## 二、教训一：把「读不到」当成「掉了」／当成结论

**这是这三天反复出现、代价最大的一类错。**三个不同地方栽在同一件事上。

### 症状

- 09-24：预检报「生意参谋/阿里妈妈后台掉登录了」，**连发 5 条飞书**叫人去登录。而真因是那一轮浏览器刚冷启动、窗口里**一个页面都还没有**。
- 09-25：链第 0 步报「页面不齐，请把这两页各开一个」。**照做只会开到登录页** —— 真因是共享商家浏览器的会话没了。
- 09-25：登录脚本报「登录没成功，可能是密码不对」，**连错四次**。真因是登录页同意协议那一屏**地址不换**，脚本只看地址。

### 根因

判据写成了「没读到 ⇒ 就是没有」。而「读不到」至少有三种完全不同的成因：

1. 页面还没归位（什么都不用做，链自己会归位）
2. 会话真的没了（需要登录）
3. 页面在、只是换了一屏（需要点一下）

三者的**下一步动作完全相反**，却共用一条会叫人的结论。

### 解决方案

- **把「读不到」和「实锤掉了」拆成两个结论**：`loggedIn === null`（页面不在）走新结论 `PAGES_ABSENT` —— 它**刻意不进「要人处理」的词表**，不发告警、退出码 3。
- **判据改成结构判定，不用字符串包含**：登录墙按 `host + pathname` 结构判（`isSycmLoginWallUrl`），
  而不是 `url.includes(片段)` —— 后者会被「登录页把目标地址放在 `_target=` 参数里」这种形态假命中。
- **叫人之前先区分「会话没了」与「页面不在」**，并把这句话写进了代码注释，避免后人改回去。

### 怎么核

`runtime/alert-throttle.json` 的 `sentAt` 只在真的投递时变。09-24 那次它一整天没动过 ⇒ 证明那 5 条假红**根本没走去重**。
1.7.0 之后 09-26 08:14 那轮的预检是 `exit 0 / verdict=ALL_IN`

## 三、教训二：执行环境的限制会被误读成「数据坏了」

### 症状

阶段产物只有三行：`exit=null`、`error=spawnSync … EBUSY`、`errno=-4082`，而且 **1~4 毫秒内就返回**（不是超时、不是子进程崩了）。
最要命的是：**连告警都发不出去**（同一个病根）⇒ 没有任何通知，看起来像偶发环境抖动。

### 根因（已定位到宿主）

不是本机、不是 Node、不是仓库，是 **WorkBuddy 宿主的沙箱对「每一次工具调用」的决定**。
分界精确到 **stdin 那条管道**：

- `stdio: ['ignore','pipe','pipe']` ⇒ 通
- 不写 `stdio`（默认三根管道）、`['pipe',…]`、`input:` ⇒ **必炸**

判据（读宿主日志，不靠推理）：宿主日志里每次调用都有一行 `[SandboxOrchestrator] OUTCOME`，
`sandbox-disabled` 的那两次全通、`background-sandbox` 的每一次全灭。
另外两条反直觉的实测：**它穿透到孙进程**（改了子进程还要顺着调用链 grep 到底）；**它只掐同步那一条路**（异步 `spawn` 没事）。

### 解决方案（1.7.1）

- 5 个生产/测试调用点一律显式 `stdio: ['ignore','pipe','pipe']`；
  其中最关键的一处是**第 7 步 `push` 内部的 `py extract-sources`** —— 它在第一次往飞书写字的那一步里，不修则前面六步全白做。
- 告警不再用 `input:`，改 `notify-feishu.mjs --alert-file <json>`。
- **新增跑前自检**：链开跑前先探一次坏形态，把「本次宿主会不会掐断同步子进程」打进 `job.log` 第一行，
  并明写「这是宿主执行环境限制，不是数据问题」。⇒ 从此不会再有「跑完了却不知道环境不对」。

### 顺带纠正的两个认知（都很值钱）

- **权限 ≠ 沙箱，是两套。**把权限开满不会让沙箱消失，只会让失败更静默（沙箱开着时宿主反而跳过权限确认）。
- **沙箱里跑测试会假红**：断言原样是 `null !== 0`，真因是 EBUSY。⇒ **判红绿之前先看这次调用过没过沙箱。**

## 四、教训三：时间窗与时序 —— 数据正确性不只在代码里

### 4.1 跑得太早 = 写进低值，而且当天无法重推

阿里妈妈推广块**上午有未回补窗口**，CSV 到 **11:20 前后才静止**（08:04 那份与 11:22 之后的逐字节不同）。
而写入的查重键是「同一天 ＋ 同店铺」⇒ 上午写进去的是低值，**无法同日重推，只能先删掉那天的记录再跑**。

**规则**：补历史日一律排在 **11:20 之后**（11:40 是安全边界）。
09-25 那天 9 次尝试里的前 5 次全落在 11:20 之前 —— 即使技术上跑通了，写进去的也是低值，这就是后来「先删了重跑」的原因。

### 4.2 「关不掉的弹窗」其实关掉了，是复核判据误判

- 判据原文是 `dismissed = 剩余全屏层数 === 0`，而「算不算全屏层」**只看几何（覆盖 ≥85% 视口）、不看 z-index**。
- 于是窗口一小（938×442），**页面自带的图表容器**也够到了 85% ⇒ 这个数**永远回不到 0** ⇒ 永远报「没关掉」。
  两次成功纯属运气（那两天窗口是 1442×684，页面容器没够到阈值）。
- **两条反向证据**：关后残留的 5 个里**没有那个弹窗**（`wrapper_dlg_*` 已消失），剩下的全是 `z=auto` 的页面自身容器；
  而且同一句里已经写着**「目标可点=true」** —— 被挡的按钮已经能点了。
- **解决（1.7.4）**：判据放宽成「**层归零 或 目标可点**」，并补齐关法顺序：
  真实 **ESC** → 有序候选（关闭语义 → 消失确认词 → 右上角图标，带危险词黑名单，封顶 3 个）→
  都不行才**真重载一次**（只在阿里妈妈页；采集店铺报表那一侧没有现场证据，就不加带副作用的动作）。

### 4.3 一条「看起来像缺数据、其实不是」的降级

补历史日时生意参谋走「**自定义日期**」模式，表格不含「同行同层均值」⇒ 脚本只写「询单量」、把那格留空，
收据里写明 `PEER_UNAVAILABLE`。**这是显式降级，不是缺陷。**
**但要记住代价**：补历史日写出来的行，与当天正常跑出来的行**字段完整性不同**，拿它做同比/环比前先看这个字段在不在。

## 五、教训四：长生命周期资源 —— 「不释放」不等于「窗口还在」

### 症状

用户 09-25 晚上说：「我发现提醒了，但界面已经关闭」。告警正文里明明写着「登录页已经开在某某窗口了」。

### 根因（两层，都已实测）

1. **口径是拍反的**：`releaseAfterBatch` **一律释放**（链成功、链失败、链没跑到都放），
   依据是 09-23 那次「每一轮跑完要释放浏览器资源」。⇒ 告警发出时，它承诺的那个窗口已经开始被收走。
2. **更硬的一条**：**驱动命令结束会回收整棵进程树**，窗口在命令结束 **0.26 秒**后就消失。
   ⇒「不释放」只是「我不去停它」，**不等于「窗口还在」**。

### 解决方案（1.7.4）

**唯一可靠的形态是「需要人的那一轮不结束」** —— 让驱动进程自己活着。

- 定时链由四步变**五步**，第五步 `hold-and-resume` 带 `onlyWhenChainFailed`：
  **只在链失败时执行**，所以链全绿那天它对行为的影响是零。
- **只有两类失败会驻留**：掉登录（`NEEDS_LOGIN`）与关不掉的遮挡层（`PAGE_OBSTRUCTED`）。
  驻留期间**只读、不碰页面**，每 15 分钟写一行 `[驻留] …`（不许静默），默认等到**当天 12:00**。
- **人处理完自动续跑**：只补失败那几家（`--shops`）、从失败阶段跑到结尾、**绝不整轮重跑**
  （同天同店有查重键，整轮重跑会在已写成的那几家上硬停）。
- 退出码单列一套：`0=不需驻留｜1=续跑没成功｜2=判不了｜3=等到截止｜4=续跑成功`，
  它是非阻断步骤、**不覆盖链的退出码**，**只有 4 允许把整轮翻红为绿**（它对应一件真发生过的事）。

### 顺带修掉的两处「会悄悄发错消息」的代码缺陷

- 整轮告警的 `dispatchRoundAlert` **缺了「关掉」那个分支** ⇒ 传 `off` 会落到去重+投递，**真发飞书**。
- 续跑的成功与失败通知**共用了同一个 `alertId`** ⇒ 先成功过一次，之后那次**失败**会被 6 小时去重挡掉，
  而日志里只留一句「没往外发」。两处都有用例与突变验证钉住。

## 六、教训五：默认策略会放大每一次局部失败

- **「首家失败即停整轮」**：09-25 第 3 轮里可林成功了、网林一停，**其余 3 家一步都没跑**，整轮只写进 1 家。

  1.7.4 补了 `ensure-merchant-login`（`--target sycm`、非阻断、没登成不额外叫人）。

## 七、教训六：工程纪律 —— 几件「看起来在跑、其实没跑」的事

1. **门禁跑不完就等于没有结论。**`test:staged` 曾在 664 条用例里花 **7.64 小时**，
   其中 7 条各等满 60 分钟的下载 deadline、占 92%。⇒ 1.7.2 给每条命令加了**墙上时钟预算**
   （默认 1800 秒，超预算连根终止并退 **3 = INCOMPLETE** —— 既不是通过也不是失败）。
   **报「门禁绿」之前先确认拿到的是结论还是 INCOMPLETE。**
2. **指向被忽略目录的「证据清单」等于没有证据。**1.7.0 那版把证据路径全写成 `tmp/…`，
   而 `/tmp/` 就在 `.gitignore` 里 ⇒ 那份清单在提交那一刻已经是空的（路径存在、文件在、跑得动，只是进不了库）。
   ⇒ 现在有一个机械动作：写任何证据路径前先 `git check-ignore -v <路径>`。
3. **函数级用例全绿 ≠ 接线接上了。**1.7.4 的驻留能力写完时，一条「入口有没有真的把 `--shops`/日期传下去」的用例是缺的，
   而漏传的症状是静默的（日志少一行、能力一次也不发生）。
4. **一个写错的判据，靠重试永远修不好。**登录脚本连错四次都停在同一步，因为它只会说「地址没离开登录页」；
   而那一屏地址本来就不会换。⇒ 沉淀成技能：**提交后出现的第二个现场，URL 检查是看不见的**。

## 八、系统现在的形态（1.7.4）

定时链现在是**五步**（`node scripts/run-daily-job.mjs --notify`，每天 08:14）：

```
① ensure-instances        把声明的 7 个实例起齐（幂等：已就位的一个都不碰）
② login-preflight         跑前登录体检（会碰页面：掉了就自己登一次），结论落文件交给链
③ ensure-merchant-login   共享商家浏览器守卫（链的整轮级体检跑在它上面）
④ chain                   11 个阶段：体检 → 阿里妈妈落位 → 推广提交 → 生意参谋落位 →
                          店铺报表 → 推广取件 → 写飞书底单 → 复位 → 再落位 → 回填询单 → 独立回读
⑤ hold-and-resume         只在链失败时执行：把窗口留住等人，人处理完自动只补那几家
```

判「某天跑完没有」**永远先看底单命中行数**（底单 `tblkY3W8tnPWPcnh`，字段「统计日期」），
不看当轮 `summary.json`（它每轮覆盖、补跑不回写）。

**飞书告警**：默认只把文案打进日志、**一个字节都不发**；要真发必须显式 `--notify`。
同一天同一处再出问题会被 6 小时去重挡住。

## 九、还没解决的（诚实清单）

**已修但没被真跑考到 —— 下次出问题时先想到这三条**

1. **「驻留 → 人处理 → 自动续跑」一次真机都没跑过。**第一次入口就是下一次 08:14，
   而且要有店恰好停在掉登录/遮挡层上才会触发 ⇒ **可能连着几天不被考到**。判据＝日志里出现 `[驻留]` 开头的行。
2. **1.7.4 的关遮挡（ESC / 有序候选 / 失败后重载）没在真跑里被考到。**
   09-26 补跑那轮的 submit 日志里**没有任何 `[遮挡]` 行** ⇒ 说明那一轮压根没碰到广告层。
3. **共享商家浏览器「真掉登录时能不能救回来」没验证过**（至今只跑到 `ALREADY_LOGGED_IN`）。

**未修、已知**

4. **`stop-all.mjs` 的释放路径会假绿**：读进程表失败时（同一个 EBUSY 病根）它会断言「没有在跑」，
   而同刻另一条命令却读到「占用中」⇒ 给 `--yes` 也什么都不做**却报成功**。
   绕法：`Get-NetTCPConnection -LocalPort <端口>` 取 PID → 核对命令行含该 profile → 停 → **端口回读两次**（第一次可能是旧值）。
5. **链第 0 步 `TARGET_PAGE_MISSING` 的告警归因错**：真因是登录墙，正文却写「页面不齐、请把这两页各开一个」。
6. **`login-merchant.mjs` 同类假红**（只因窗口里没有阿里妈妈页就判 `PARTIAL`、发告警），且仍不走去重。
7. **幂等停手与真失败共用退出码**：「这一天飞书里已经有数据了，按不许写第二遍停手」也是退出码 1 ⇒
   任何按退出码判断的自动化都会误判成故障。建议给它单列一个结论值。
8. **推广取件偶发「点击全对但文件不落盘」**：复选框和下载入口两次点击都命中，30 秒内目录没有新文件。
   判据＝同一天成功的那几家**点完直接落盘、连一行「等待下载…」都没有**（不到 3 秒）⇒ 不是超时给得紧。
   **补救＝原样重发同一条命令**（09-26 实测第 1 次重试即成功，用的是同一笔任务、同一坐标）。
   重试是安全的：提交段开头会先查台账，已有未取任务就**直接复用、一个东西都不点**。建议以后给取件段加一次「重点一遍」。

## 十、速查表：遇到这些情况怎么办

| 你看到的现象 | 先做什么 | 别做什么 |
|---|---|---|
| 收到「某个后台掉登录」的提醒 | 先看链第 0 步的归位日志：URL 里带 `custom/login.htm?_target=` 才是真掉登录 | 别照着「把这两页各开一个」去开页面（会开到登录页） |
| 提醒里说「登录页已经开在某窗口了」 | 去那个窗口操作；处理完**不用回复**，系统会自己续跑 | 别去重跑整条链（同天同店会硬停在已写成的那几家） |
| 某家店某天没写进去 | `node scripts/run-daily-job.mjs --date <那天> --shops <店名>`（在仓库根） | 别自己拼 `run-multi-shop-day.mjs`（会漏掉起实例和登录守卫） |
| 取件阶段报「没等到新 zip」 | **原样重发同一条命令** | 别去调超时、别改代码 |
| 想知道某天齐没齐 | 看底单命中行数（`onDateCount`，且 `IsLowerBound=false`） | 别看当轮 `summary.json` |
| 链报「一轮体检没过」 | 先看 `evidence/daily-job-<日>/job.log` 里的归位那几行 | 别先去重启机器或浏览器 |
| 要补历史日 | 排在 **11:20 之后** | 别在上午补（会写进低值且当天无法重推） |
| 脚本报 `EBUSY` / `exit=null` | 看 `job.log` 第一行那条环境自检 | 别按数据问题排查（那是宿主执行环境限制） |
| 觉得「门禁绿了」 | 确认拿到的是结论还是 `INCOMPLETE` | 别无脑加白名单/放宽断言去让它变绿 |

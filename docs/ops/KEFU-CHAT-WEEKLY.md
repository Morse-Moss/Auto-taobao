# 客服聊天记录 · 每周收集（2026-10-19 第一版）

运营需求：每周一份「四家店全部客服的聊天记录」。平台不提供批量导出，这条链用千牛
「聊天记录查询」页的 mtop 接口逐会话读取，再整理成人能直接看的文件。

本文件只讲**怎么跑、怎么判、坏了怎么处理**。接口语义与坑写在
`skills/qianniu-kefu-chat/SKILL.md`，判据的离线用例在同目录 `*.test.mjs`。

## 一、口径（先认这三条，不然会拿错数）

1. **周 = 上一自然周，周一到周日，+08 时区**。默认 `--week last-week`，即今天是 2026-10-19（周一）
   就跑 `2026-10-12 ~ 2026-10-18`。
2. **只含窗口内的消息**。会话只要在这个窗口里有过消息就会出现在交付里，会话本身可能是更早创建的。
3. **不写任何线上数据**。全程只读接口，交付只落 `output/kefu-chat/<周号>/`，证据落
   `evidence/kefu-chat-<周号>/<runId>/`。

## 二、跑之前要有什么

- 四家店的浏览器**已经在跑**（端口来自 `runtime/browser-ports.mjs`，一店一 profile）：
  里可林家居 19031/19041、网林天猫 19032/19042、盖文天猫 19035/19045、里可林天猫 19051/19061。
- 对应店铺**登录态正常**。没登录的店不会自动登，也不会去碰别的店的 profile。
- 想省事可以先起浏览器（会留窗口，必须后台托住）：

```bash
node scripts/start-all.mjs --only 里可林淘宝,网林天猫,盖文天猫,里可林天猫
# 起完要托住窗口（否则命令结束窗口就没了）：
node scripts/start-all-hold.mjs
```

## 三、跑

```bash
# ① 采集（四家，默认全部在采店铺）
node skills/qianniu-kefu-chat/scripts/export-kefu-chat.mjs --week last-week --lookback-days 30

# ② 打包（--src 用上一步打印的证据目录）
node skills/qianniu-kefu-chat/scripts/package-kefu-chat.mjs \
  --src evidence/kefu-chat-2026-W42/<runId> \
  --out output/kefu-chat/2026-W42

# ③ 验收（独立复核，不信脚本自报）
node skills/qianniu-kefu-chat/scripts/verify-pack.mjs --out output/kefu-chat/2026-W42
```

- 指定店铺：`--shops 里可林家居,盖文旗舰店`（内部叫法或店铺全称都认）。
- 指定某一天所在的周：`--date 2026-10-18`。
- 只补某店：`--shops <店>`，其余店不动。
- 通知：`--notify-dry-run` 只把「将要发到飞书的原文」打出来、不发送；`--notify` 才真发。

## 四、要多久

2026-10-19 实测（四家全量，回溯 30 天）：**11 分 37 秒**。

分店体量（2026-W42）：盖文旗舰店 176 场/4777 条、网林家居旗舰店 55 场/1376 条、
里可林旗舰店 56 场/665 条、里可林家居 42 场/972 条。单店 `里可林家居` 约 15~20 秒。

**为什么抓 541 场只用到 176 场**：会话列表按创建时间过滤，回溯 30 天是必须的
（创建于本周之前、本周有消息的会话占活跃会话 22.6%，单周查询根本不返回）。
`modifyTime` 不能用来预筛——它可能比真实末条**早最多 17 天**，据此跳过会漏数据。
所以「抓了 67% 空会话」是这套口径的固有代价，不是可省的浪费。

## 五、掉登录会自己救一次（2026-10-19 加）

接口不认会话时，脚本会调仓库既有的登录流程（生意参谋/阿里妈妈那条），然后**重新加载聊天页并再探一次**。
所以状态 `NEEDS_LOGIN` 的含义是「**自动登录也没救回来**」，不是「没试过」。

三种处置要分清：

| `error` 里出现 | 人要做的事 |
| --- | --- |
| `自动登录报了成功…但接口仍然拒绝` | 说明两个后台登上了、聊天记录这套会话没跟上 ⇒ 在那家店窗口里手工打开一次聊天记录页 |
| `CAPTCHA_REQUIRED` / `WRONG_ACCOUNT` / `NO_SAVED_CREDENTIAL` | 去那家店窗口人工登录一次（滑块只能人做；填成别家是凭据混了） |
| `登录脚本自身没跑通` | 先看证据目录里的 `login-<店铺键>.json`，多半是脚本层或连通性问题 |

想在平时就证明这条接线通不通（不改任何状态）：

```bash
node skills/qianniu-kefu-chat/scripts/export-kefu-chat.mjs --date 2026-10-18 --shops 里可林家居 --rehearse-login
```

账号本来就登着时，登录脚本只会判 `ALREADY_LOGGED_IN`，然后照常重探、照常采集。

## 六、怎么判「这天/这周齐了」

**只看 `summary.json`**，别看控制台最后一行：

| status | 含义 | 怎么办 |
| --- | --- | --- |
| `OK` | 这家店采完了 | 无需处理 |
| `NEEDS_LOGIN` | 登录态失效 | 在该店窗口人工登录后重跑该店 |
| `BROWSER_DOWN` | 浏览器/代理没在跑 | 先起浏览器再重跑该店 |
| `PAGES_ABSENT` | 页开了但接口 15 秒没就绪 | 人去看一眼那个窗口，可能被弹窗盖住 |
| `LIST_FAILED` | 会话列表接口报错 | 看 `error` 里的 ret 码，多半是登录态或接口变更 |
| `COLLECT_FAILED` | 会话列表拿到了、消息没采完 | 看 `failedCids`，重跑该店会自动重试 |

另外三条必看：

1. `failedSessionCids` 必须为空。非空说明有会话连重试回合都没成功——先按 cid 单独重放确认是
   「真的没消息」还是「数据缺口」。
2. `stats.first` / `stats.last` 应分别落在周的起止附近。某家店 `last` 停在周三，就是那天之后没采到。
3. 每店消息条数应当与上周同量级；差一个数量级先怀疑登录态或页面变更，别直接交出去。

## 七、交付物长什么样

`output/kefu-chat/<周号>/`

- `总览.html`：四家店一行，会话数/消息数/客服/时间范围，点进去看明细（先给运营看这个）。
- `<店>/客服聊天记录-<店>-<周号>.txt`：人读版，逐会话、逐条带时间与角色（买家/客服(名字)/系统）。
- `<店>/会话清单-<店>-<周号>.csv`：一行一场会话，带 BOM，Excel 双击不乱码。
- `<店>/全量数据-<店>-<周号>.json`：全字段，每条消息保留 `raw`。
- `manifest.json`：机读汇总（跑批核对用）。

## 八、还没做的（第二步）

按「先手工跑稳两周，再上调度」的顺序，这一版**故意没接**：

- 没在 `runtime/workflow-catalog.mjs` 登记 `kefu-chat`；
- 没接 `run-batches` 批次壳（现在是四家并行、一店一页签，没走批次释放）；
- 没有定时任务。计划是**周日 21:00**（周一运营上班就能看到上周数据），
  失败即告警、每周 ok 摘要各一条。

上调度之前必须先解决一件事：**这条链没有任何一步会自动登录商家浏览器**，掉登录就是整轮
`NEEDS_LOGIN`。定时跑之前先确认四家店的登录态能撑过一周。

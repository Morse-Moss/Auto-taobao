## 0. 结论先行

三条候选路线，**它们不是三选一**：

| 代号 | 一句话 | 性质 |
| --- | --- | --- |
| **B** | 飞书提醒人工登录 | 机器**叫人** |
| **A2** | 浏览器自己的密码管理器自动填 + 补一次可信手势 | 机器**尝试登录**（不接触凭据） |
| **A1** | AI（模型）参与定位与填写 | 机器**尝试登录**（凭据会经过模型） |

三条结论：

1. **B 是地基，A 是可选加速器。** 任何 A 方案失败（撞滑块、撞短信验证、协议弹窗没处理干净）
   都必须落到 B。所以 B 必须先有，而且它独立有价值：**它是唯一能回答「到底多频繁需要人」的装置**。
2. ~~**A2 可行但有一处硬前提（交付专用 profile），且有一处未验证（真实账号的风控反应）。
   现在不开工。** 先把 B 做出来量一段时间，再决定这条口子值不值得开 —— 这与 §5.1 末尾的推荐路径一致。~~
   → **2026-09-23 已开工并已接线**：用户明令「**可以自动登录把项目规则改了**」。
   A2 已接进定时链与分批驱动两个宿主（宿主默认开、`--no-auto-login` 可退），
   风控那一条用**串行 + 20 秒静默期**兜（§3.5 已更新）。
   **一处硬前提仍未满足**：交付专用 profile 里的密码库是空的（**这是刻意的**，见
   `MULTI-SHOP-AND-INTERACTION-DECISION.md` §5.3.1：只有带 `--disable-sync` 才能拦住个人密码库同步进来）
   ⇒ 在客户机上 A2 会落 `NO_SAVED_CREDENTIAL` 并走 B。**本机能用 ≠ 客户机能用，别混。**
3. **A1 不落地。** 唯一可采纳的形态是「让模型**离线**产出候选选择器、人复核后写进适配器」，
   那是 AI 辅助开发，不是 AI 代登。理由见 §4。

## 2. B：飞书提醒人工登录（推荐先做）

**它解决什么**：把人叫到**正确的那台机器**上做一次登录；同时**量出频率**。

**它不解决什么**：不减少人的动作，只是让人的动作有方向。别把它当成自动化。

### 2.1 两个触发来源，今天各是什么状态

| 来源 | 机制 | 今天的状态 |
| --- | --- | --- |
| B-1 **事后** | 采集链撞登录墙 → `FLOW_HUMAN_GATE` / `LOGIN_REQUIRED` | **已经能发**（通知出口第 1 步已完成，两跳真实发送实测过） |
| B-2 **提前** | 体检层 L0/L2 判定会话已失效 | **未实现**（F9） |

⇒ 落地顺序上，**先做 B-1，B-2 等 L0/L2**。B-1 不需要新代码，需要的是「通知里的话够不够一个人照着做」。

### 2.2 落地步骤（可执行）

1. **确认通知出口**：已通（`notify-feishu-core.mjs` + `notify-feishu.mjs`，两跳实测过）。
   不做任何改动，只是复用它。
2. **把通知里要说清的三件事补齐**，缺一条人就得到处找：
   - **哪台机器** → `source.machine`（自动取本机主机名，2026-09-18 加）
   - **哪家店** → `identity.storeId` + `source.shopName`
   - **做什么** → `source.browserProfile`（哪个浏览器配置要重登，2026-09-18 加）+
     到哪个 profile 目录、登哪个站点、登录后要不要重跑这一轮
   前两个标识加进 `READABLE_SOURCE_KEYS` 白名单后，告警会长这样：
   ```
   【需要处理】插件或平台登录已失效
   店铺：浴缸A店
   任务：sycm.alimama.daily
   机器：DEPLOY-01
   浏览器配置：daily
   原因：DailyReport login state could not be confirmed
   下一步：在同一个浏览器配置里重新登录。
   ```
   缺值的键整行不输出，所以对没填这两项的来源，渲染结果与加它们之前**逐字相同**。
3. **去重与恢复沿用既有锚**：同一个 `businessKey` 只叫一次；人登录完重跑成功时，
   通知链路按既有规则**自动收掉那条未解决的告警**（不要新做一套）。
4. **把「需要人」变成可统计的事件。** 原件这一条写的是「今天做不到，得先补落点」，
   并**猜**落点是「照日报链 `daily_report_push_audit` 的样子建一张只追加的表」。
   2026-09-18 逐处核对代码后，**这个猜测是错的，实际选的是 JSONL 文件**。理由四条：
   - **DB 表天然看不见最该统计的那一类。** 体检拦下（`BLOCKED_BY_HEALTH`）与队列等人工
     （`PAUSED_FOR_HUMAN`）这两类最常见的「需要人」，**刻意不创建运行** ——
     所以 `durable_runs` / `durable_attempts` 里连一行都没有。按 DB 统计会把它们全漏掉。
   - 能用的 DB 列都是**单槽**：`context.blocker` 是一个对象，写一次覆盖一次；
     `human_gate_status` 是运行行上的可变列。它们答「此刻被什么挡住」，答不了「多久来一次」。
   - `round-state.json` 也只有 `lastOutcome` + 一个 `openAlert` 槽，没有理由历史。
   - 建表要动生产库（迁移 + 授权），而这次的问题**根本不需要碰数据库**。
   ⇒ 落点是 `runtime/.round-history.jsonl`（只追加，一行一个事件）。选这个路径也是刻意的：
   它是运行态（点号前缀与 `runtime/.collect-child-pid` 同类），且被 `.gitignore` 的
   `runtime/**/*.jsonl` 覆盖。**不落在 `workDir` 里** —— `workDir` 默认是
   `runtime/sop-runtime/round-<时间戳>`，每次起进程都换一个新目录，历史写在那里会随重启清零。
   **这个文件只写不读来决策**：没有任何判定读它，`round-state.json` 仍是「该不该跑」的唯一记忆。
5. **跑满一个登录周期再下结论**：先单店跑，统计「一周需要人几次、每次要几分钟」。

### 2.5 B-1 已落地（2026-09-18）

| 项 | 现状 | 证据 |
| --- | --- | --- |
| 落点 | `runtime/.round-history.jsonl`，只追加 | `runtime/sop-runtime/round-history.mjs` |
| 写什么 | 过了到期闸门的轮次（未到期/已完成不写） | `HISTORY_SKIP_OUTCOMES` + 用例 |
| 分类口径 | 新增 `needs` 轴（谁去办），逐条写在通知判定表里 | `round-notify-policy.mjs` 的 `NEEDS_KINDS` / `needsAxisErrors()` |
| 读取端 | `node runtime/sop-runtime/round-history-report.mjs --days 30` | 人话报告 + `--json` |
| 默认行为 | **不配就不记**（收据里落 `NOT_CONFIGURED`），与接线前逐字相同 | 用例 `没配历史端口时收据如实写 NOT_CONFIGURED` |
| 告警文案 | 加「机器」「浏览器配置」两行 | `notify-feishu-core.mjs` 的 `READABLE_SOURCE_KEYS` |

**口径上必须记住的三件事**（写错了会得出相反的结论）：

1. **「需要人」的分子只数新发生。** 同一起还没收掉的后续轮次是 `DEDUPED`，
   单列成「持续中」。把它们算进频率，会让一次登录失效（拖三天）看起来像几十次事故。
2. **分母是「过了到期闸门的轮次」**，不是「每 15 分钟醒一次的次数」。
   告警文案里也写清楚了是「在 N 次打扰中占多少」，不是「每 N 分钟要人一次」。
3. **`UNSPECIFIED`（表里写了 null：升级/预算耗尽这类「动作型」理由）与
   `UNCLASSIFIED`（表里根本没这条理由）必须分桶。** 后者非 0 说明有理由漏登记，是要去补的。

**它答不了什么（诚实边界）**：

- **无法回填。** 账本从落地那一刻开始写。在那之前发生过多少次要人的事，
  没有留下机器可读的痕迹 —— 飞书群里的历史消息是唯一的间接线索。
- **短期内数字还没意义。** 「一周几次」要跑满一周才有第一个可信读数，
  在此之前它只是个位数样本，**不足以支撑「要不要做 A2」的决定**。


### 2.3 验收判据

- 制造一次真实的会话过期 → **恰好一条**飞书通知 → 人工登录后重跑成功 → 通知被收掉。
- 「一周几次」这个数字能从落点里查出来，而不是靠回忆。
- **该静默的时候真的静默**：一轮跑完没出问题，一条通知都不许发（这条已有双向用例守着）。

### 2.4 成本与风险

成本：低（复用既有链路，主要工作是**文案与落点**）。
风险：只有一条 —— **通知疲劳**。一天响十次之后就没人看了。用「只在真的需要人时发 + 同店同窗口去重」控住。

## 3. A2：浏览器自动填 + 一次可信手势

**它解决什么**：把「需要人」里的**不需要二次验证的那一部分**自动化掉。

**它不解决什么**：滑块 / 短信验证（F5 未验证）；协议弹窗仍要处理；会话过期这件事本身仍要能被判出来。

### 3.1 三个硬前提（缺一不可，且前两个与 A 无关也该做）

| # | 前提 | 现状 |
| --- | --- | --- |
| P1 | **每家店一个交付专用 profile**，只登项目要用的站点 | **没有**（F6：现有两个 profile 混着个人密码库，不能交付） |
| P2 | 首次由人工在该 profile 里登录一次并勾选「保存密码」（一次性 setup，店铺数那么多次） | 未做 |
| P3 | 「什么时候该登录」的判据 | 今天只有 B-1 事后触发；B-2（提前）依赖 L0/L2 |

**P1 是最容易被跳过、也最贵的一条。** 没有它，A2 的每一步都会在「一个混着个人密码库的 profile」上发生，
而我们还要把这个 profile 交付给客户。§5.3 建议的三条（单独新建、加白名单判据、`stores[].profileDir` 指向它）
应当在 A2 之前完成。

### 3.2 落地步骤（照 §5.2.4 的 7 步，逐条给工程动作）

1. 每店一个 profile；首次人工登录 + 勾「保存密码」（一次性，人工）。
2. 会话过期时：导航到登录页 → **不填任何字段** → 等密码管理器自己填。
3. **补一次可信手势**（CDP `Input.dispatchMouseEvent`，**不是** `el.click()`）—— F2/F3 的直接后果。
4. 勾协议 → 点登录 → 若出现协议二次确认则点「同意」（F4）。
5. 判据只看「输入框有没有值、长度非零」；**值绝不进日志、不进证据目录**（F7）。
6. 任何一步没成 ⇒ 停下，走 B 通知人。
7. **明确不做**：不解密 `Login Data`（DPAPI + Chromium AES key）。那是「代账密」的定义本身。

### 3.3 边界（即使授权也不放宽）

沿用 §5.1 四条：凭据存放走 Windows 凭据管理器 / 加密文件（配置里只放 `credentialRef`）；
明文不入库不进日志不进证据不进通知；**同一账号连续 2 次失败 ⇒ 当天不再试**；
13 家**串行**、留间隔、一天最多一轮。
再加一条工程要求：**它是一个默认关闭的开关**，关闭时行为与今天逐字相同。

### 3.4 验收判据

- 在**一个**交付专用 profile 上、用**一个**真实店铺号，做一次「会话过期 → 自动走完登录」的演练；
  时段可控、一次只跑一家。
- 演练必须同时证明**失败路径**：把密码库里的凭据删掉，脚本必须在「没等到值」时停下并通知，
  而不是继续点登录（点下去就是一次可被风控记到的失败尝试）。

### 3.5 风险（**2026-09-23 起口径变了：不是「不开工」，是「开了工、用串行兜」**）

- **F5 原本未验证**：真实账号提交后会不会撞滑块/短信验证。→ **2026-09-18 有答案了**：
  会用新会话必撞（三个撞短信、一个卡登录页），而**同一台机器上的持久会话零验证**
  ⇒ 风控盯的是**设备/会话**，不是账号属性（见 `LOGIN-STATE-MANAGEMENT.md` §10）。
- 一个 IP 上短时间内多次登录，正好是风控最喜欢的模式（§5.1）。13 家一次铺开，
  最坏情况不是「跑失败」，是**一批账号被保护性锁定**。
- **2026-09-23 的处置（不是忽略这条风险，是把它变成工程约束）**：
  带 `--login` 时**强制串行**（`check-login-shops.mjs` 里 `for` 循环）＋两店之间
  **`LOGIN_GAP_MS = 20000` 静默期**；只读体检仍走 `Promise.all` 并行。
  **没有实现在「连续失败熔断」**（同一账号 2 次失败当天不再试）—— 今天靠「一天最多一轮」
  的调度兜着。这条仍是欠账，记在这里而不是记成已完成。
- 所以正确的读数是：**风险被压到「一天一轮 × 串行 × 20 秒间隔」，但没有被消除**。
  如果将来要一天多轮，第一件事是把上面的熔断补上，而不是把间隔调小。

## 4. A1：AI 自动填 —— 不落地

**A1 是什么**：由模型参与定位元素、决定填什么、执行输入。

**为什么不推荐（按严重度排）**

1. **凭据可见面直接冲突。** 模型要「知道填什么」，凭据就得经过模型上下文 ——
   而 F7 把边界写死为「明文不入库、不进日志、不进证据目录、不进通知」。
   代理型 API 还会把上下文送到第三方。这条不是「有风险」，是**逐字冲突**。
   （退一步：如果让模型只定位、不取值，那它相对 A2 只剩「定位方式不同」，
   而 A2 的定位是**固定选择器 + 已实测**的，更可靠。）
2. **不确定性被放到了最不该放的地方。** 登录是强副作用动作，要么成要么不成。
   A1 每一步都可能不同，失败形态是「填了一半」「填到了错误的元素」——
   平台看到的是一串奇怪行为，**恰好就是风控特征**。
3. **收益已经被 A2 压没了。** §5.2.4 的结论：A2 相对「agent 自己填」的唯一代价是
   「多一次点击」，而 agent 自己填的代价是「我们持有 13 组店铺主号明文密码」。
   A1 换的是「少写几个选择器」，代价与第 1 条相同。

**A1 唯一可采纳的形态**：站点改版导致选择器失效时，用模型**离线**产出**候选**选择器，

## 7. 不承诺什么

- **不承诺「每家店都能自动登录」。** 真实能达到的最好状态是「**大部分时候自动，偶尔必须人**」（§5.1）。
- **不承诺跳过滑块 / 短信验证**（F5 未验证；这是平台风控，不是我们这一侧的实现问题）。
- **不承诺 A2 在真实账号上一定不撞风控。** 13 家 = 13 台新设备，触发概率不低。
- **不承诺「无人值守」**：只要验证码这一步需要人，执行就必须发生在有屏幕的那台机器上。
  （2026-09-23 起 A2 会**自己先试一次**再叫人，但「试不成还是要有屏幕那台机器」这条没变。）
- **不把「实测过机制」说成「已经能用」**：F1–F4 证明的是机制成立，不是「13 家能自己跑完」。
  从机制到可用之间还差：交付专用 profile、L0/L2 判据、登录适配器、以及**真实账号的风控反应**这一条完全没测过。
  （2026-09-23 状态：A2 的**接线**做了、**真机整链没跑过** —— 六个实例的会话当天全部失效，
  要人先登一次才有机会验证「掉登录 ⇒ 自己登回来」这条成功支路。别读成「已经能用」。）
- **不把「装置建好了」说成「数字有了」**：B-1 的账本与读取端**已落地并有实测证据**（§2.5），
  但「多久需要人一次」这个数字要跑满一段时间才有第一个可信读数。**装置 ≠ 结论。**

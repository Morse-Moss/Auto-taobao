首次失败的真因不是平台侧：入口把 `--downloads` 指到了 evidence 目录，而五店浏览器真实下载目录是 `C:\Users\Administrator\Downloads`。脚本报「下载超时」，字面指向平台，实际是传参错误 —— 原样重跑必然同样失败。

重跑的实际结果（数字来自 run-receipt 与各店导入收据）：

| 阶段 | 五家源行数（里可林/网林/盖文淘宝/盖文天猫/科塔） | 飞书表行数变化 |
| --- | --- | --- |
| 商品底单 | 24 / 14 / 52 / 43 / 32 | 4581 → 4746 |
| 商品询单 | 0 / 4 / 7 / 9 / 3 | 1005 → 1028 |
| 商品推广 | 92 源行 → 92 计划行 | 2472 → 2564，重复 0 |

幂等复核：同批产物重算计划行数全部为 0，即重跑不会新增重复行。里可林 09-26 询单 0 行是平台真实返回（该店当日没有询单），不是漏采。

修复清单 —— 四个症状、一个病根（把「读不到」当成「没有」）：

| 症状 | 真因 | 修法 |
| --- | --- | --- |
| 十个导入点全灭：`XLS parser failed`、`ZIP parse failed`，且报错是空串 | 三个导入脚本的同步子进程调用没写 `stdio`，宿主沙箱对「带 stdin 管道的同步 spawn」直接返回 `EBUSY`，拿到的状态是 `null`、stderr 是空串 | 三处补 `stdio: ['ignore','pipe','pipe']`，报错带上真因 |
| 释放脚本的端口回读恒为真 | 读不到时 `Number('')` 为 0，导致「已释放」永远成立 | 读不出来返回 `null`（等于没有证据），只在确认为 0 时判定已释放 |
| `stop-all` 假绿：读不到监听表却断言「没有在跑」并退 0 | 同一病根，且没有错误分支 | 读失败时明说「这一项无法判断」；显式确认模式下按未确认收场并退 1 |
| 浏览器盘点在进程表读不到时静默变空 | 同一病根 | 两处补齐；不补这一处，前三处会把假绿变成假红（代理永远被拒停） |

第二条独立缺陷（被上面掩盖）：询单表头契约与真实文件不符。

五家全部报「询单报表缺少 12 列标准表头」。真实导出列名是 `最终付款人数 / 最终付款金额 / 最终付款件数`，**不含「延」字**；契约里写的是「延最终付款人数」。这不是平台改版 —— 仓库里 09-23 存档的原始导出（当初立契约的依据）同样不含「延」。「延」是当初读乱码、靠「第 6 个使用行 + 12 列形状」兜底匹配留下的痕迹。旧用例把契约常量自己当夹具，因此从未验证过「契约与真实文件是否一致」，已补 3 条回归用例。

收尾时又抓到一个交付缺陷：该入口引用了三个**当时未被 git 跟踪**的模块（全局锁、收据、环境预检），本机文件在所以跑得通，但远端克隆出来会直接报找不到模块。已补一个只 add、不改内容的提交，并逐字节核对哈希一致、单测 9 条全过。

## 五、这两天暴露的问题，归成四类

1. 把「读不到」当成「没有」：同一个病根在六处出现（三个导入脚本、端口回读、停止脚本、询单表头）。
2. 静默空产物：0 字节收据、阶段状态恒为待定、参数解析了却从未使用 —— 共同点是「不报错，但也没有效果」。
3. 参数契约两端不一致：入口与采集脚本的下载目录、总控与驻留脚本的通知参数。
4. 交付不自洽：提交里引用了未入库的模块；门禁只报四个布尔值，查不出这类问题。

## 六、还没解决的（诚实清单）

1. 「驻留 → 人处理 → 自动续跑」一次真机都没跑过，而且要先修掉上面第二条里的参数契约不一致才可能跑到。
2. 全仓版「禁止裸同步子进程」的守卫还没做，目前只钉了商品数据这条链的 13 个文件。
3. 停止脚本的释放路径假绿虽已修，但「只信退出码」的习惯性风险仍在，验证释放仍必须独立回读端口两次。
4. 链第 0 步「页面缺失」的告警归因仍会写成「页面不齐」，真因常常是登录墙。
5. `login-merchant` 的同类假红（只因窗口里没有某个页就判部分失败并发告警），且仍不走去重。
6. 幂等停手与真失败共用退出码，任何按退出码判断的自动化都会把「已有数据、按规矩不再写」误判成故障。
7. 推广取件偶发「点击全对但文件不落盘」，原样重试即好，机制未修。
8. 灰豚关键词链的一条测试在这台机器上恒红，是环境导致的假红（详见文末说明），每次跑门禁都要人工解释一遍。

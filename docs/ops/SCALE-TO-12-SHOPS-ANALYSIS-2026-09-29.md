# 从 5 家扩到 12 家店铺：先把不稳定治住，再接店铺

**写给谁**：下一个对话（要接新店铺的那个会话），以及现在这个会话的收尾。
**什么时候写的**：2026-09-29 18:2x。**依据全是可核对的证据**（逐条给了路径），不是印象。

---

## 0. 结论先行（四句话）

1. **现在的「不稳定」不是随机抖动，是三处具名缺陷**在同一批店里反复出现：`promotion-fetch`
   找不到下载入口（09-28 两家）、`alimama-date` 筛条不就绪（09-28 一家）、`push` 撞查重键（09-27 两家）。
   修这三处＝把失败率从「每天 2–3 家」压到「接近 0」。**这是接新店铺的前置条件**，不是并行任务。
2. **扩容的瓶颈不是代码，是内存与端口容量**。每实例约 1.7 GB；本机 31 GB 实测同时开 5–6 个。
   **12 家店不可能一次全开**（12×1.7 + 1.5 ≈ 22 GB，加上 Windows 与 Edge 自身必爆）。
   必须走分批：本机 `--batch-size 5` ⇒ 3 批；客户机按内存档位下调。
3. **代码侧扩容的准备工作比想象的小**：店铺登记表已经是「数据驱动」的
   （`SHOP_BROWSERS` / `SHOP_IDENTITIES` 各加一行即可），**但端口段只有 19031-19039 / 19041-19049
   这 9 个槽位**，12 家需要扩段，且 `refresh-shop-pages.mjs`、多处硬编码「五家」要把文案改成中性。
4. **`--batches 5` 这个值扩到 12 家后需要重新算**：现在它恰好等于「五家一批」，12 家会变成 3 批跑，
   总时长约翻倍。定时任务的 15:30 起跑时间要重新评估（现在单批约 1.5–2 小时）。

## 1. 不稳定的真实分布（近三天逐店逐阶段）

数据来自 `evidence/batches-<日>/b1/summary.json` 的 `shops.<店>.failedStage`。

| 日期 | 里可林 | 网林天猫 | 盖文淘宝 | 盖文天猫 | 科塔淘宝 |
|---|---|---|---|---|---|
| 09-26 | ok | ok | ok | ok | ok |
| 09-27 | ok | **push** | **push** | ok | ok |
| 09-28 | **promotion-fetch** | **alimama-date** | ok | ok | **promotion-fetch** |

**关键观察**：09-26 五家全绿。说明**链路本身是通的**，失败是**特定条件下的**，不是「整体不可靠」。
这一点决定了修法：不是重写，是把三处具名缺陷堵掉。

### 缺陷 A：`promotion-fetch` 找不到下载入口（09-28 里可林 + 科塔，两家）

原始输出（`evidence/batches-2026-09-28/b1/summary.json`）：

```
[fetch] 真实鼠标点它的复选框 (143,342) → {"clicked":true,...}
[fetch] 回读 checked=true，当前勾选 = [1]
[fetch] 入口第 1 次没定位到（action-row-hidden，操作行=第 2 行，操作行 display=none，操作行内「下载」叶子=1）｜400ms 后重试（第 2/4 次）
[fetch] 入口第 2 次没定位到（action-row-hidden，...）｜400ms 后重试（第 3/4 次）
[fetch] 入口第 3 次没定位到（action-row-hidden，...）｜400ms 后重试（第 4/4 次）
采集失败：找不到 营销场景报表_20260929_15...
```

**机制**：复选框点中了、回读 `checked=true`，但**该行的操作行（含「下载」）始终没显形**
（`display:none`）。现有重试是 **4 次 × 400 ms ≈ 1.2 秒**（
`collect-promotion-report.mjs:538-539`）。

**为什么不稳**：1.2 秒是照 09-27 那一轮「页面重排时长」量出来的（见该文件 534-537 行注释）。
**同时开着五个实例、每个 15 个进程的时候，页面重排显然会更慢** —— 而重试预算没有跟着并发度变。
09-28 两家同一步、同一种失败，说明这**不是单店偶发**。

**这是本轮最值得先修的一处**，因为：
- 它是**已知未修缺陷 ⑤**（`MEMORY.md` 第 60 行，09-25 首次记），已经跨了三天；
- 它是**唯一一处「失败了但现场信息足够、修法明确」**的（判据是 `action-row-hidden`，
  要么放宽重试预算、要么把「等它显形」改成「等到显形或超时」）；
- 它挡的是**第 6 步**——`push` 之前的最后一步 ⇒ **这一家店的当天数据一个字都写不进飞书**。

### 缺陷 B：`alimama-date` 筛条不就绪（09-28 网林天猫，一家）

```
Error: alimama: state did not settle to 2026-09-28（读了 16 次 × 1200ms；其中读不到 16 次）
; lastReadError=proxy .../eval?target=...  failed: HTTP 400 Error: alimama filter bar not ready; triggers=0
```

**机制**：筛条（filter bar）`triggers=0`，即**页面结构还没长出来**。重试了 16 次 × 1.2 秒 ≈ 19 秒。

**与缺陷 A 同源**：都是「并发高 ⇒ 页面响应慢 ⇒ 固定重试预算不够」。区别是这一处**已经重试得比较久**
（19 秒），所以更像是**那一台实例的状态问题**（比如代理慢、页面没加载完）而非纯时序。

**建议**：先只加日志（把 `triggers=0` 时的页面 DOM 快照留下来），**不急着改判据** ——
19 秒已经不算短，盲目加长是在赌一个没量过的数（本项目纪律：不许用「多等一会儿」代替判据）。

### 缺陷 C：`push` 撞查重键（09-27 网林 + 盖文淘宝，两家）

```
Error: duplicate daily report row exists: recvwuXUkNPUkJ
    at run-daily-report.mjs:453
[audit] 未写入（不影响本次结论）：append failed: connect ECONNREFUSED 127.0.0.1:5432
```

**机制**：这一家当天**已经写过了**（查重键＝同一天＋同店铺）。
**这不是缺陷，是设计**（本项目口径：早跑的低值无法同日重推，只能先删那天）。

**但 09-27 这个现场暴露了一个真问题**：那一轮是**定时任务重跑**（第一次低值被重推）。
⇒ **「重复跑同一天」这件事在扩容后会变多**：12 家店、3 批、任何一批失败后补跑，
都会撞上「已经写过的那几家」。**必须让补跑自动只补失败的那几家**（`--shops` 已有这个能力，
但定时任务不会自动带）。

> 另注：`[audit] ... connect ECONNREFUSED 127.0.0.1:5432` —— **审计表连不上**（PostgreSQL 没起）。
> 这是**下游旁证**，不影响日报结论，但意味着**审计链是断的**。扩容前建议确认这是预期内。

## 2. 扩容的容量账（12 家店）

### 2.1 内存（本机 31.1 GB）

沿用 `CLIENT-MACHINE-CAPACITY.md` §1 的实测：每实例 **1.1–2.3 GB，均值 1.7 GB**，
加共享商家浏览器约 1.5 GB。

| 场景 | 浏览器峰值 | 本机 31 GB 够不够 |
|---|---|---|
| 12 家全开 | 12×1.7 + 1.5 ≈ **21.9 GB** | **不够**（加上 Windows + Edge 自身 + 其它软件，必换页） |
| 每批 5 家 | 5×1.7 + 1.5 ≈ **10 GB** | 够（这是当前 5 家店的实际形态） |
| 每批 6 家 | 6×1.7 + 1.5 ≈ **11.7 GB** | 够（文档 §5 给 32 GB 的档位就是 5–6） |

**⇒ 12 家必须分批，本机上限就是每批 5–6 家**。现有 `--batch-size 5` 可以用，
12 家会切成 **b1(5) + b2(5) + b3(2)**。

### 2.2 时长（扩容后要重新评估定时任务起跑时间）

现在单批 5 家 ≈ 1.5–2 小时（每店 11 阶段串行）。12 家＝3 批 ⇒ **约 4.5–6 小时**。
定时任务现在 **15:30** 起跑 ⇒ 跑完约 20:00–21:30。

**要点**：如果 3 批之间有「等上一批释放」的间隙，实际会更长。**建议**：
- 要么把起跑时间提前（但要避开阿里妈妈上午的未回补窗口 —— 补历史日必须 11:20 之后；
  当日日报没有这个限制，但凌晨数据可能不全）；
- 要么把 `--batch-size` 提到 6（本机可行，3 批变 2 批，b1(6)+b2(6)）。

### 2.3 端口容量（**这是代码侧最容易漏的一条**）

`runtime/browser-ports.mjs:104-105` 写死了段位：

```
端口段 19031-19039（调试）/ 19041-19049（代理）：与日报链（19022/19023）、运营台（19024）都不重叠。
2026-09-19 起五家店用掉 19031-19035 与 19041-19045。
```

**19031-19039 只有 9 个槽位 ⇒ 最多 9 家店**（当前用掉 5 个）。扩到 12 家**必须扩端口段**。

**建议方案**：把店铺段扩成 **19031-19059（调试）/ 19041-19069（代理）**，留足余量（29 个槽位）。
改一处常量即可，但**要同步改 `runtime/browser-ports.test.mjs` 的段位断言**（否则测试不会红，
等于没有守卫 —— 这正是本项目反复踩的「能力删在生产者侧、故障显在消费者侧」）。

## 4. 执行顺序（建议）

**不能并行**：先治不稳定，再接店铺。理由：新店加进来后，失败面**翻倍**——
本来每天 2–3 家失败，12 家会变成 5–7 家，而**每家的失败症状都一样**（同一批缺陷），
到时你会分不清「是新店配错了」还是「老缺陷又来了」。

```
阶段 0（前置，半天的量）：确认审计链（PostgreSQL 5432）为什么连不上
阶段 1（治不稳定）：三处缺陷 —— A 优先（修法明确）、B 只加日志、C 是设计不改
阶段 2（扩容准备）：端口段 + 登记表 + 文案，全部零行为变化（加新店但不跑）
阶段 3（首店试跑）：先接 1 家新店，单独 `--shops <新店>` 跑通 11 阶段
阶段 4（全量）：12 家分批跑，重新评估定时任务起跑时间
```

**阶段 3 为什么必须先接 1 家**：本项目反复验证「函数级用例全绿 ≠ 接线接上了」。
新店的 profile / 会员名 / 页头店名三者**只有真跑一次才知道对不对**，一次接 7 家会把
7 个错误混在一起。

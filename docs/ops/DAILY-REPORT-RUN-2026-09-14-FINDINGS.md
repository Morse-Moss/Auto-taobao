## 1. 日期策略：默认「昨天」还是支持自定义

### 1.1 两条路径的真实成本（本次实测）

阿里妈妈侧（营销场景报表）：

| 维度 | 预设「1天」＝昨日 | 自定义区间 |
| --- | --- | --- |
| 交互步数 | 约 3 步（切页签 → 点预设 → 回读） | 约 15 步（开面板 → 定位日格 → 点起 → 点止 → 确定 → 回读） |
| 数据内容 | 相同 | 相同 |
| 脆弱点 | 相对时间（跨零点会漂） | 日历组件（同名日格、面板位移、坐标失效） |
| 能否回填 | 否 | 是 |

生意参谋侧（询单到付款）：

| 维度 | 预设「1天」＝昨日 | 自定义区间 |
| --- | --- | --- |
| 表行数 | 7 行：日期行 ＋ 汇总值 ＋ 平均值 ＋ 全店汇总值 ＋ 全店平均值 ＋ 同行同层优秀 ＋ 同行同层均值 | 3 行：日期行 ＋ 汇总值 ＋ 平均值 |
| 关键差异 | 唯一能拿到 `同行同层均值` 的模式 | **同行基准整块消失** |

要点：在正常日更上，自定义不是「等价但繁琐」，而是「更繁琐且更差」——它在生意参谋侧还会丢数据。

### 1.2 但只支持「昨日」不可接受

日更链路的固有失败模式就是「昨天没跑成、今天要补」。若只保留预设，最后一次漏跑会变成永久缺口（除非人工），且无法幂等重放、无法在事故复盘时指定日期复现。所以：

- 预设 = 正常路径（快、全）
- 自定义 = 回填路径（慢、必须显式记录丢了什么）

### 1.3 建议方案：双轨 ＋ 冻结语义日期 ＋ 三道断言

runner 接口（只改 runner 决策，不改变任何页面操作）：

```text
--date YYYY-MM-DD                    # 目标日；缺省时取 Asia/Shanghai 的昨日
--date-mode auto|preset|explicit      # 缺省 auto
```

`auto` 判定：`target == today-1 (Asia/Shanghai)` → 走 `preset`；否则走 `explicit`。

`reportDate` 必须在 runner 启动时**冻结一次**，执行过程中不要反复取 `now`。否则跨零点会把「昨日」漂到另一天——这正是相对日期的最大风险，而冻结可以让预设路径安全地使用相对日期。

三道断言，任何一条不成立就 fail-closed：

1. 动作前：读页面 `统计时间` 文本，记为 `observedBefore`，写进 plan。
2. 动作后：读 `统计时间`，必须等于目标日。**不信任预设已生效**：预设是相对的，页面可能残留上一次状态或缓存。生意参谋侧还要同时断言当前页签为 `询单到付款`。
3. 表格级：断言表内日期行等于目标日；询单还要断言「`当日询单人数` 列 × `同行同层均值` 行」这个交叉点存在（不存在就走 §2.2 的显式降级）。

日期选择器原语化——把整条链上最脆弱的一环做成可单测的单元：

`runtime/date-picker.mjs` → `selectExactDay(page, isoDate)`：

- 打开面板后**先枚举日历块**。本次实测两块日历都渲染 2026 年 9 月，「14」在页面里有两个，日格文本不唯一。
- 定位规则用「日历块索引 ＋ 星期列名 ＋ 日号」，不用绝对坐标，也不要用 `elementFromPoint` 硬猜。
- 点完先回读面板内 `已选择：YYYY-MM-DD 至 YYYY-MM-DD`，必须等于目标日，再点 `确定`。
- 目标日格在当前块内的数量必须为 1，否则报错，而不是「取第一个」。

建议为这个原语补三条测试：同名日格、两月同显、面板展开后位移。

### 1.4 降级要显式，不要静默

explicit 路径拿不到同行基准，应写成显式事实进收据：

```json
"inquiryPeerBenchmark": {
  "status": "UNAVAILABLE_IN_EXPLICIT_MODE",
  "source": "sycm.shop-performance.inquiry-to-payment",
  "observedRows": ["2026-09-14", "汇总值", "平均值"]
}
```

而不是让 `extractInquiryMetrics` 抛 `expected one benchmark row 同行同层均值, got 0`。后者会被读成「脚本坏了」，前者会被读成「业务上确实没有」。这与本项目坑 30/38 同类：能力不足必须由能力自己说出 code。

## 3. 操作复盘：本次为什么慢

本次 09-14 单日回填，交互/探测调用有近一半消耗在日期选择器上。逐条列原因：

1. 先点后读，顺序反了。在阿里妈妈我直接按截图估的坐标点「14 日」，但面板展开后日格整体右移（`x:621` → `x:646`），白点一次。正确顺序是「先读唯一锚点 → 再点 → 回读断言」。
2. 拿坐标当锚点。日历展开/收起都会改变布局，绝对坐标随时失效；本次靠「重新探测 → 改坐标」补救了至少两次。
3. 没做唯一性校验。日历里「14」有两个（左右两块都渲染 9 月），我默认取第一个，导致分不清点的是哪一块，只能靠 `已选择` 文本反推。
4. 截图当探针。几乎每步都截图，而截图是 CDP 里最慢的一环（还超时过一次）。中间态本可用一次 `eval` 读到精确坐标与状态，更快也更可断言。
5. 覆写探针文件导致自伤。反复覆写 `runtime/tmp-eval.js`，其中一次把「读询单表」的探针覆盖成了「读飞书页」的探针，白跑一轮并误判 `tableCount 0`。
6. 关键差异识别滞后。「09-14 只有 3 行」在 `step24` 的截图上已经可见，我又多跑了三四次探测才把它归因为「同行基准不可得」。看到差异应当立即收口成假设并做一次决定性验证。
7. 页面漂移无预案。生意参谋绩效页把筛选重置回默认（09-15 ＋ 汇总分析）后才被我被动发现，于是又走了一圈「重切页签 → 重设日期 → 重探」。若流程里一开始就有「每次动手前回读 统计时间 ＋ 页签」，这一圈不存在。
8. 报错归因绕路。`commit` 抛 `derived shop field was not populated` 后，我先怀疑数据、又写脚本核对，多花 2-3 轮。报错关键词本身就是「派生字段」，直接指着时序问题，应当立即用 `--verify-existing` 复核。
9. 批量删除没先对账。清 `runtime/tmp-*` 时把已被 git 跟踪的 `runtime/tmp-inspect-feishu-ui.mjs` 一起删了，只能 `git checkout` 恢复。删除前应先 `git ls-files` 交叉核对。

## 7. 双轨日期策略的实施与实测（2026-09-16）

### 7.1 阿里妈妈不需要点日历

实测发现阿里妈妈的筛选状态**完整编码在 URL hash 里**：

```text
...#!/report/account?rptType=account&startTime=2026-09-14&endTime=2026-09-14
   &effectEqual=30&bizCodeIn=["onebpSearch","onebpDisplay"]&granularity=day
```

直接 `navigate` 就能同时落位日期、两个场景、归因周期与粒度，无需任何点击。§1 里为「点日历」估的那部分成本整个消失，坐标/日历路径对阿里妈妈一侧可废弃（日历代码只保留给生意参谋的 explicit 路径）。

两点必须注意：

- 页面等于昨日时回显 `昨日` 而不是日期，断言要把 `昨日` 按站点时区换算回具体日期。
- `startTime=endTime` 才是单日；漏掉会静默变成区间累计。

### 7.2 派生字段竞态已自愈（不是「绕过去」）

重跑时 `--commit` **第一次就成功**，收据里 `derivedReadbackAttempts: 2` —— 第一次回读 `店铺` 确实是空数组，重试一次就拿到了。这证明 §2.1 记的不是偶发，而是每次创建都会发生的一次读；加有界重试是对的，而重试预算耗尽后仍然报错（不是重试到成功为止）。

### 7.3 生意参谋的页签是日期控件的前置条件

实测：活动页签是 `汇总分析` 时，`1天` 按钮的**文案读出来是空串**，`日/月/自定义` 正常 —— 因为那是另一套日期控件（本月/自定义粒度），`1天` 属于 `询单到付款` 的控件。所以「读到的日期对」不等于「页签对」，两件事都必须断言；脚本现在先切页签再落日期，切完回读确认。

### 7.4 三个把「点击静默落空」变成显式报错的判据

这一轮最费时间的三处，都不是逻辑错，而是**点击没生效也不报错**：

1. **元素在视口外**：视口宽 1031，`自定义` 按钮在 x=1035，`elementFromPoint` 返回 `null`，真实鼠标点击落空。→ 取点前先 `scrollIntoView`，再用 `elementFromPoint` 复核命中；不命中就抛错。
2. **`innerText` 假空**：`1天`/`按7天为周期`/`按30天为周期` 三个按钮的 `innerText` 全是 `""`，`textContent` 正常。用 `innerText` 找按钮会得出「按钮不存在」的错误结论。→ 文案匹配一律用 `textContent`。
3. **隐藏的面板仍在 DOM 里**：日历菜单关闭时 `display:none`，但格子节点都在、`rect` 全 0。`querySelector` 会找到它并返回「面板已打开、格子都在 (0,0)」。→ 判「面板是否打开」必须看它是否真的渲染出来。

另外两处与结构假设不符、靠实测纠正的地方：年月是 `.oui-dt-calendar-control.year` 与 `.month` **两个独立元素**（不是一个「2026年 9月」）；日格的类名是 `oui-dt-calendar-day-0/1/…` 带星期后缀，`td.oui-dt-calendar-day` 这个选择器**匹配不到任何东西**。本月日格由 `current-month` 类直接给出，早期那套「靠两个 1 划月」的几何推算已删除。

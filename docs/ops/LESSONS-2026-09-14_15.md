## 1 会把失败伪装成成功的那一类（最危险）

这类问题的共同点：**不报错、不留痕、看起来正常**。凡"安静"的地方都要主动找判据。

### 1.1 失败路径连收据都写不出来

- **现象**：发布段真实 `--commit` 失败时，`two-stage-receipt.json` 根本没生成，进程 exit=4。
- **根因**：`supervisor_commit_records.status` 的 CHECK（001 定义）里没有 `FAILED`，而运行时 `COMMIT_STATUS` 有 → 账本写失败路径被 PG 拒绝 → 异常穿出 `ledger.commit`。
- **为什么长期没露头**：离线测试全用内存 store（`updateCommit` 就是 `Object.assign`，不校验值域）；成功路径的三态恰好都在词表内。**这是"发布段从未真实跑过"的代码侧原因。**
- **修法**：`db/migrations/006-commit-record-status-vocabulary.sql`（回滚脚本刻意 fail-closed）+ 仓库守卫 `runtime/sop-runtime/commit-status-vocabulary.test.mjs`（从迁移文件推导生效约束，再与运行词表对账）。006 已 apply 到业务库（先 `pg_dump`，单事务，回读四项）。
- **顺带教训**：推导"最终生效的 DDL"时，`*-rollback.sql` **不能进正向序列**（字典序上 `006-rollback.sql` 排在 `006-commit-*.sql` 之后）——守卫第一次运行就因此把"回滚后的 6 值"误判成现状。

### 1.2 外部写入成功，却被判 UNKNOWN

- **现象**：`sycm.feishu.weekly` 发布段外部写入**成功**（decisions 记 `PUBLICATION COMMITTED`），但自动回读报 `readBack requires FEISHU_APP_ID and FEISHU_APP_SECRET` → 整段被判 UNKNOWN。
- **根因**：框架调 `createPublisher` 时只传 `artifactBytes/evidence/period/target/collectInput/publishInput/manifest`，**不给 env**；而该能力的 `readBack` 只认注入的 `env`。同族能力一直是读 `publishInput.envFile` 的。
- **为什么离线照不到**：唯一走这条路径的是真实网络客户端，其余回读用例统一注入 `deps.readRecords`，而它在**凭据解析之后**才被用上——**测试缝开在缺陷后面**。
- **修法**：能力内 `resolveReadEnv()`（注入 env 优先，否则读 `publishInput.envFile`；文件不存在给 `INPUT_REQUIRED`）+ `deps.createReadApi` 测试缝。回归 22 → 23 例。

### 1.3 `ADAPTIVE_DONE` 不等于成功

- **现象**：曾误判为"完美收官"，实际 `final/` 不存在、退出码 1、只产出一个 partial 导出。
- **根因**：`ADAPTIVE_DONE` **只走 stdout，从不进 `events.jsonl`**（末事件是 `DONE`/`TARGETS_CLEANED`）；而且它只表示"流程走到头"，不表示产物合格。
- **修法**：成功只由**持久化证据**证明——退出码文件 + `final/<关键词>-adaptive-merged.xlsx` 存在 + `--require-images` 通过 + 终端标记。四者互相印证，缺一降级。

### 1.4 解析器的兜底分支没消费游标 → OOM 而不是报错

- **现象**：重渲染客户交付 docx 时 `FATAL ERROR: Ineffective mark-compacts near heap limit`，堆吃到 4GB，退出码 134。
- **根因**：markdown 段落行以行内代码开头（`` `尺寸`、… ``），而解析器的 `isSpecial` 字符类含反引号（本意识别代码围栏）→ 这一行被判"特殊"却没有任何分支接住 → 段落兜底 `while (!isSpecial)` 一次都不转就 break，`index` 不前进 → 无限 push 空段落。同族形态还有「`#` 后不带空格」和五级井号。
- **修法**：兜底分支先判断"这一轮到底消费了没有"，没消费就强制消费一行；守卫 `runtime/generate-competitor-field-reference-docx.test.mjs`（含三种滞留行的最小 md 必须 exit 0，并端到端渲染交付 md）。
- **教训**：**兜底分支的正确性判据是"游标一定前进"，不是"看起来能处理"。** 这类缺陷表现是"崩"，不是"报错"，别当环境问题。

### 1.5 写死环境标识的脚本会"成功"地指向错目标

- **现象**：`export-live-competitor-formulas.mjs` 把旧租户 appToken / tableId 写死在源码里，换租户后跑它只会"成功"地采到**已废弃租户**的公式——是假证据，不是报错。
- **同族**：`diagnose-material-derivation.mjs` 把两张周表 id 写死（会随周次腐烂）；`repair-weekly-tables.mjs` 写死旧租户 appToken + 08-23 周期（废弃脚本，**别误跑**）；`feishu-targets.scratchTable` 换 base 后悬空（指向一个两个 base 里都不存在的表 id）。
- **修法**：任何断言"这是当前环境的事实"的脚本，环境标识必须从单点配置（`runtime/feishu-targets.mjs`）取，或至少可 `--profile` / `--table-id` 覆盖。**换环境后要重跑一遍只读工具，别引用换之前的结论。**

### 1.6 遮盖敏感信息的正则吞掉自己的编号

- **现象**：`[A-Za-z0-9_-]{32,}` 把告警编号 `xws-login-678598686014-20260915T030000` 也遮成 `[redacted-token]`，而那个编号正是运营与服务方对账时唯一能引用的东西。
- **修法**：字符集去掉 `-` / `_`。

### 1.7 单位混用让判据永不触发

- **现象**：监督环的 `silentMs` / `mtimeMs` 混用秒，判据永不触发（被 `not ok 14` 精确抓到）。
- **修法**：时间量一律毫秒，并在收据里带原始值。

### 1.8 套件并发 flaky 被当成回归

- **现象**：整套复跑 8 条失败，但**单跑**涉及文件 `xws-export-market-analysis/tests/prepare-flow.test.mjs` 是 36/36 全绿（该测试只 import skills 内脚本，与本轮改动零依赖）。
- **判据顺序**：①先看依赖链 → ②单跑该文件复现 → ③再考虑 `--test-concurrency`。

### 1.9 基线数字过期被当现值（**今天刚犯**）

- **现象**：记忆里记着 runtime 套件 427（62 文件）、skills 532。实测是 **447（64 文件）** 与 **539**——427/62 是当天 12:28 那次快照，之后有测试落地就涨了；532 本身就少 1。
- **修法**：基线记录必须带时间戳；引用前先看它是什么时候跑的。PROJECT-NOTES §4 已改成"末次实测 + 注明漂移原因"。

### 1.10 断言计数把 skipped 算成"试过"

- **现象**：收据里会带一条 skipped 的兜底通道记录（"没配"而非"试过又失败"），用 `attempts.length` 断言"没有重试"会把话说过头。
- **修法**：先过滤 skipped 再数。

## 2 状态机与流程：缺出口比判据太严更常见

### 2.1 发布轴没有 UNKNOWN 出口（缺口 A）

- **现象**：运行落到 UNKNOWN 后**永远到不了 VERIFIED**，即使提交记录已对账成 VERIFIED，实测抛 `PUBLICATION_STATE`。
- **根因**：`settlePublication(VERIFIED)` 要求 `current==='COMMITTED'`，`markPublicationCommitted` 只收 `READY|COMMITTED`，而 `reconcileUnknown` 只回写提交记录、从不回写运行。**不是判定太严，是缺一条合法迁移。**
- **修法**：新增 `controller.reconcilePublication`，前置状态 `UNKNOWN` **与** `READY`；`VERIFIED` 要真实回读收据且该 run 所有提交记录已 VERIFIED（**先对账账本、再收敛运行**）；`ABSENT` 要具名 operator 且没有记录处于 `COMMIT_HANDED_OFF`。
- **修的过程中发现的同源第三格**：真实库读出 `b4e7e120` 是 `publicationStatus=READY` + 提交记录停在 `COMMITTING`，回收会正确拒绝、`settlePublication` 也不收 → **同样没有出口**。所以 `READY` 必须也进对账入口，否则只修半截。

### 2.2 未终结的运行永久占住幂等键（缺口 B）

- **现象**：同一幂等键被挡两次，都只能手动 `controller.cancel(runId)` 释放。
- **根因**：准入去重走 `listActiveRuns`（含 `RUNNING`），**无 stale 回收**；`duplicateOf` 全仓库无人消费（无 resume 通道）。
- **修法**：`runtime/sop-runtime/run-liveness.mjs` + `assessRun` / `reclaimStale` / `reclaimStaleRuns`。**核心是两个判据必须分开**：
  - **死活只看租约**，不看运行状态——状态描述"它在等什么"（`RETRY_WAIT` 等退避、`PAUSED` 等人工），把 `PAUSED` 回收等于杀掉正在等审批的运行；
  - **能不能回收只看外部写入有没有在飞行中**——回收会释放幂等键 → 新 run 新 `commitKey` → **再写一次**。
  - 时间阈值只配用于**没有开放 attempt** 的 `QUEUED`。
- **可复现**：任何 `--commit` 后未被验收的运行都会造成这个后果。

### 2.3 到期判定写成单调阈值

- **现象**：排期把 `due` 算成 `now >= 最近一次触发时刻`，而"最近一次触发"永远在过去 → **第一次触发之后恒为真** → 每条排期每醒一次就跑一遍。不报错、不失败，只是安静地重复干活。
- **修法**：到期必须是"当天成立的窗口"（`dateKey(trigger)===dateKey(now)`）。口径是**只算触发日当天、不跨天自动补跑**（补跑用显式 `--force`）——宁可漏跑（在 `--show-plan` 里看得见）不要偷跑（看不见）。
- **守卫写法**：把时间推到 1 个月后 / 1 年后仍不许 `due`（4 例同时暴露）。

### 2.4 通知判据表：静默必须显式声明

- 判据表是**唯一清单**：静默必须显式声明，表里查不到的理由一律 fail-closed 通知并标 `unmapped`。
- **"要不要通知"与"该不该自动重试"是两个轴**：登录失效＝通知 + 自动重试；配置错 / 疑似缺陷 / `COMMIT_UNKNOWN`＝通知 + 当天收工（**写入结果未知明确禁止静默重试**）。
- **空队列既不碰浏览器也没跑流程，不许收掉登录告警。**
- 未治愈的失败一律升级：`TRANSIENT_EXTERNAL` / `RESOURCE_BUSY` 属静默类，但**只在"自愈已处理掉"时成立**。
- **两处 fail-open，方向一致也刻意**：探测无确定结论、体检无结论时都照常发起（"多做一次本来会失败的运行"可见，"少做一次本该做的活"不可见），但状态只许写 UNKNOWN / NOT_IMPLEMENTED，**不许写 OK**。

## 3 宿主与环境：我们到底被什么限制住

### 3.1 `run_in_background` 不是生产级宿主

- **现象**：40 页全量采集"不是卡住，是被会话回收"。第二段跑到第 29 页 188 行时 `collector pid alive:false`、退出码文件不存在、checkpoint `STALLED`、`final/` 不存在。
- **根因**：挂在对话后台任务上，**turn 一结束整棵进程树被回收**。
- **推论**：长任务必须由独立于对话会话的宿主保活，或让子进程 `detached` 且**不依赖父进程的 stdout 管道**（父进程管道被关 → `process.stdout.write` EPIPE → 启动器崩 → 退出码文件永远不落盘 → 监督环只能判 UNKNOWN）。
- **现状**：`detached: true` 实测**也没脱离**任务树（停掉驱动后台任务后，宿主 / 采集器 / 监督环一起消失，`process.kill` 直接 `ESRCH`）。**"独立宿主"这件事仍未解决**，当前真正的保障是"不结束对话轮次"——那是权宜，不是能力。

### 3.2 沙箱的端口约束 → 固定端口方案

- **约束**：会话内只能连「会话前已在监听、或本会话自己起」的端口；`dangerouslyDisableSandbox` 起的进程活不过那次调用、端口对会话内不可见；`Start-Process` 启 msedge 静默失败。唯一可行＝**会话内 node spawn + `setInterval` 保活，用后台任务跑**。
- **定下的固定端口**：调试 Edge **9222**（`--user-data-dir=D:\Retire\edge-debug-profile`，里面装了小旺神）；项目专用 CDP 代理 **3457**；`/health` 报 `browser.id=edge-isolated`。导出必带 `XWS_PROXY=http://127.0.0.1:3457` + `XWS_BROWSER_ID=edge-isolated`。
- **别碰 3456**：那是别的项目的代理，挂用户的日常 Edge（商家号，**没装小旺神**）。

### 3.3 本机 shell 的四个坑

- bash 包装器坏：`dirname` / `sed` / `cat` / `grep` / `ls` / `head` / `tail` / `sleep` / `mv` 全缺 → 别用 `cd x && …`、别用管道；改文件用 node 的 fs 或 Edit 工具。
- PowerShell 不能从 Bash 调（安全拦截）→ 用专门的 PowerShell 工具。
- **bash 双引号里的 `node -e` 不能带反引号**：bash 先做命令替换，于是 `` `材质分类` `` 这类内容被当命令执行，而 `appendFileSync` **根本没执行**——日志没写进去却不报文件错误，只在 stderr 留一串噪音。绕法：要写的文本先用 Write 工具落成文件。
- 含引号 / 反斜杠 / 反引号 / 多行的 JS 一律写临时 `.mjs` 再跑（`node -e` 多行里 require + top-level await 会报 `ERR_AMBIGUOUS_MODULE_SYNTAX`）。

### 3.4 删除类操作会被拦

- 本机 PowerShell 的 `Remove-Item` 被安全删除代理包装：**中文路径 fail-closed**（报 `SAFE_DELETE_FAIL_CLOSED`，路径还会被 GBK 乱码）。绕法：先 `Rename-Item` 改成纯 ASCII 再删。
- 单次删除目标文件数超过阈值会被拦；对上万文件的大目录一次性 trash 会报 "Some operations were aborted"（改为先 `Move-Item` 到 `GetTempPath()` 再删）。

## 4 数据口径：看不见的输入

### 4.1 A=0 的真因是"导出只覆盖了列表的一个区段"，不是市场

- **真实现象**：08-30 与 09-13 两个相隔两周的独立快照，top10 **几乎逐位相同**（46/32/31/30/27/26/25/22 vs 48/36/34/33/30/28/24/22）——独立市场快照不可能这么像。高值周独有的正是高销量条目（100 / 200 人数那些），低值周**整条不在集合里**；低值周反而多出 ~270–330 条 `月收货人数=0` 的死链接。
- **决定性对照**：本周采集其实跑过两次。首次（15:08–15:58）合并产物 **1476 行 / max=200 / ≥80 两条**，其中一条 m=81、金额 213086.84 **本来就满足 A**；该次在 page 24 卡住后按"放宽判据"切成 10 段重跑，**十段全部落在尾段**（147–192 行，max≤48），最终导入用的是重跑那批 → **头部被丢掉 → A 必然是 0**。
- **为什么之前没发现**：采集侧校验只看 `rows / columns / rank_range / empty_links / duplicate_links`，**不看内容是否覆盖高销量区段**。147 行的尾段切片与 1476 行的完整榜单，在它眼里是同一类东西。
- **工具**：`runtime/diagnose-raw-export-head.mjs`（**必须在导入之前跑**；`--strict` 时无 A 候选退出码 2；类目数 >5 判"异类目"，不许当头部）。
- **已排除的嫌疑（都有证据，别再重走）**：公式没坏 / 字段语义没变（888 条同款标题中 621 条人数完全相同）/ 排序没配错（分段人数严格递减，是销量降序；插件文件名说"价格从高到低"是插件自己的命名 bug）/ 传入参数一致（所有历史 manifest 都是 `sort=sales` `channel=all`）。
- **仍未定位的最后一跳**：为什么 15:08 落在头部、之后十段全部落在尾段。候选变量＝首次 proxy 3458 vs 重跑用 3457，或视图未回顶。**拿不到受控对照前不写结论。**

### 4.2 B=0 的真因是"材质分类整列为空"；三层因果必须分清

这条今天被追问过一次，结论要按层次说，否则会被读成"补回字段 B 就出来了"：

| 层 | 结论 |
| --- | --- |
| 公式输入层 | `竞品分类` 只吃 5 项：是否有效竞品闸、`价格`、`月收货人数计算值`、`月收货金额`、`材质分类`（含「人造石」）。**周表缺的那 5 个字段一个都不在里面**，补回它们不会改变任何一条的 A/B/C/D。 |
| 数据层（B=0 的直接机制） | `材质分类` 的**值**整列为空。这个**字段本身在周表上是存在的**（不在缺的 5 个里）。 |
| 提示层（人因） | `待补数据项`（"还缺什么"）被丢掉了 → **靠人看提示再手填**那条路断了。但"AI 自动填"那条路在周表上**本来就不存在**。 |

- **数据层的证据**：全仓只有三处碰 `材质分类`，**没有一处写周表**——`migrate-competitor-v2-analysis.mjs` 只对**竞品主表**写哨兵值（`无注明`/`不适用`，回执 `aiRunTriggered:false`，明确不跑 AI）；`competitor-history-publish-core.mjs` 写的是**历史总表**；`update-competitor-class-labels.mjs` 是标签改名且指向废弃租户。四周实测为空的行数：08-23 = 670/1461、08-30 = 1423/1423、**09-06 与 09-13 各 100% 为空**。
- **公式没坏的反证**：08-23 那周「含人造石且人数≥10 = 8」与该周 B 的实际条数 **8 完全一致**。
- **修法**：新增步骤 `runtime/fill-weekly-material-labels.mjs`（默认干跑；`--apply` 必须带匹配的 `--confirm-app-token`；**只填空白格、绝不覆盖非空值**；无字段或类型 != 1 一律抛错拒绝猜写入形态；写后回读校验）。链上位置＝「公式重建 → 分类统计」之间。干跑已验：本周 1417 行全空，补后 **B 0→1**（人数 10 压线），A 不受影响仍 0。
- **另一条容易误判的**：`migrate-competitor-v2-analysis.mjs` 对 `材质分类` **只写哨兵、不写「人造石」**，而 `无注明` 在 `待补数据项` 判据里仍算缺项。所以**解开它的 fail-closed 也不会把 B 变出来**。

### 4.3 周表字段 35 → 40：`CLONABLE_TYPES` 不含 19 / 20

- **实测**：竞品主表 **36** 字段；竞品周_08-23 = **39**（**直接复制主表而来，字段 id 与主表逐一相同**）；08-30 / 09-06 / 09-13 = **35**。
- **丢失机制**：建表脚本的 `CLONABLE_TYPES = {1,2,3,4,5,7,11,13,15,17,18}` **不含 19(Lookup) / 20(Formula) / 21**（property 里内嵌表 / 字段 id，照抄会指向旧表）→ `尺寸`/`适用空间` 无人重建 → 直接丢；`数据状态`/`待补数据项` 的表达式引用这两项 → 重写后残留旧表引用 → 脚本打 `unmapped refs remain` 并 `DEFERRED` → 一并丢；`当前周状态` 又因"克隆上一周"沿链继承缺失。
- **修法**：①建表基准从「克隆上一周」改回**主表**（`prepare-weekly-competitor-table.mjs`，新增 `--apply-missing`）；②派生字段那趟 `create-weekly-formula-fields.mjs` **先建 Lookup 再建公式**，默认 dry-run。修完的周表 = **40 = 主表 36 − 1 + 5**。
- **刻意不做**：`SKU采集明细`（21 双向关联）不在周表重建——它带 `back_field_name`，在周表再建一次会给「SKU明细」多生成一个与主表冲突的反向字段；且一条 SKU 记录归属于主表的一条商品、不归属于某一周。
- **下游读者（只读核查过）**：缺的这 5 个字段里，**只有 `数据状态` 有跨表读者**（发布脚本把它抄进历史总表的 `数据状态` 列，金额不可计算时强制写「金额不可计算」）；`尺寸`/`适用空间`/`待补数据项`/`当前周状态` **全仓无运行时读者**。下游全部按"单期"定位周表，没有脚本遍历历史周表。

## 5 权限与凭据

### 5.1 `403 / 91403`：应用没被加为可编辑协作者

- **现象**：发布 `--apply` → 收据 `mode=BLOCKED` / `FEISHU_PERMISSION_REQUIRED`；独立写探针拿到 **HTTP 403 / code 91403 / Forbidden**；失败后重跑 dry-run `updates` 仍 `1462/1462` → **零写入**。
- **根因**：应用 `cli_a96ee8749078dbcf` 是「浴缸竞品分析 V2（测试）副本」的协作者，当年补的权限补在副本上，正式 base 没加。
- **修法**：把应用加为正式 base 的**可编辑协作者**。2026-09-15 用户加完后实测翻真（幂等写探针从 `403/91403` 变 `200/code 0`），`writeVerified: true`。
- **守卫**：任何"外部写"能力跑之前，先跑只读幂等写探针；**权限类失败必须先原始码落库**（`evidence/publish-blocked-permission-20260915.json`）。

### 5.2 采集段不校验 base token 的存在性

- **现象**：手抄错的 base token 会一路过到发布段才暴露（§8 里那条真实命令的 token 就抄漏了一个字符，采集段照样 ok）。
- **根因**：`parseTarget` / `parseBaseUrl` 只校验格式；采集段按设计不发网络请求。
- **对策**：跨段调用时把 target 的**存在性**校验前移到发布前的只读探测。

### 5.3 改完 scope 必须重新发布版本

飞书「以应用的身份发消息」＝ `im:message:send_as_bot`（应用身份）。**改完权限必须重新发布版本**，否则不生效。通知失败的 `99991672` 就是这条，脚本会提示"开权限 + 重新发布版本"。

## 8 这两天验证有效的方法论

1. **换环境后重跑一遍只读工具，别引用换之前的结论。** 租户搬迁、base 切换、字段结构变更之后，所有"实测"都要重测——旧结论会在新环境里变成假证据。
2. **凡"只在真实入口才走到的分支"，必须有一条走真实入口的用例。** 这两天三次同类缺陷（词表漂移只让失败路径炸、readBack 接线被假件掩盖、凭据解析在 deps 生效之前）全部是"测试缝开在缺陷后面"。
3. **交付物必须真的渲染出来看，并且"是否发生过"本身要成为判据。** 文本计数会漏掉编号错位、标记泄漏这类只在渲染图里可见的缺陷；而"没有任何一条对应的显式信号记录"必须判失败，不能判通过。
4. **写完必须跑一次真实入口。** 布尔开关漏给下游解析器、遮盖正则吞掉自己的编号、时间渲染成 ISO Z——三次同类缺陷全部由干跑真实入口发现，离线用例当时都没覆盖。
5. **先问"这个状态有没有出口"，再问"判定严不严"。** 缺口 A / B 都不是判据太严，而是缺一条合法迁移。

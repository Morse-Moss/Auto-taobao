# 协作约定（COLLAB-CONVENTIONS）

生效：2026-10-23（用户拍板）。本文件是「用户给 AI 下指令」的格式约定，目的是把指令粒度提到和验收粒度一致——历史教训：单字指令把验收标准全部留空，修复就退化成「修掉当次报错即结束」，这正是实例式返工在协作层的镜像。

## 1. 执行类指令：三段式

现象 + 期望终态 + 验收标准。三段可以短，但不可缺。

示例（旧写法）：
修复吧

示例（新写法）：
修复。现象：询单 0/8，报错与证据在 evidence/某目录。终态：8/8 有值且独立回读一致。验收：一是同族实例按 docs/ops/REPAIR-PROTOCOL.md 第三节扫描并汇报清单；二是每个改动配反回归用例加突变；三是构造旧代码失败现场证明新代码通过；四是真机内存不足就挂起并说明窗口。

## 2. 分析还是执行，开头声明一句

「只分析不动手」或「分析完直接按推荐执行」。分析类问题同时声明期望输出（要结论 / 要方案 / 要排期）。

## 3. 修复类任务的默认验收值

用户指令没写验收时，以下默认值自动生效（即 REPAIR-PROTOCOL 的门禁，不需要用户每次重复）：
1. 同族清单必须扫描并汇报（问一）。
2. 修复是否引入新条件组合必须回答（问二）。
3. 调用侧契约必须核验（问三）。
4. 每处修复留反回归用例 + 突变（攻击包）。
5. 验证状态必须明示（桩化已验 / 真机已验 / 真机未验+挂起窗口）。

## 4. 拍板问题

需要用户决策时，给固定 5 个问题（上限也是目标数量），每个带推荐默认值放第一个，让用户能直接回「全按建议」。禁止只甩代号或数据库 ID，一律用可读名称。

## 5. 汇报

结论先行，然后理由，最后「下一步你来做」清单。修复类汇报按 REPAIR-PROTOCOL 第 1 节四件套分别报（改动 / 三问 / 攻击包 / 验证状态）。

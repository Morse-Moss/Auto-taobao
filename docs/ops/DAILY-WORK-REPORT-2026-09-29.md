## 二、今天查清并修复的三个接线断点

### 问题 ⑧：询单回填报「got 0」，连续四天以为「写错了表」

**现象**：09-28 那轮日报，四家店的 `backfill` 阶段回读都是 `got 0`；报表显示 09-28 缺 3 家。

**初版误判（已撤回）**：我先写成了「backfill 写错了表」——把它当成「tableId 指向了 inquiryTable 而不是 sourceTable」。**这是错的。**

**真因**（实读 OpenAPI 全表 2197 行 + 翻历史成功收据后确认）：
- `tableId` 从 09-16 第一天起就是对的，这条链 09-14 ~ 09-27 天天成功。
- 字段「店铺」是 **SingleSelect 类型**，OpenAPI 返回的是**选项 id**（如 `optFFaXJeh`），不是店名。
- 而 `inquiry-core.mjs` 的匹配写的是「拿店名比」⇒ **恒不相等** ⇒ 永远找不到那一行。
- 决定性旁证：盖文淘宝在询单表的日期序列是 `…09-24 → 09-25 → 09-26 → 09-27 → 09-29`，**独缺 09-28**，12 家全如此 ⇒ 09-28 我方该写的那行确实不存在，所以是 `got 0` 而不是 `got 2`。

**修法**：新增 `findDailyStoreRow()`（认「店名」与「选项 id」两种形态、返回 matchedBy、找不唯一时**不抛错**）；从 API 反查 optionId；写前与回读用**同一个匹配器**。

**我为什么会误判（教训）**：我没去找「最近一次成功产物」就直接拿「两个 table id 不同」当根因。纪律改成：**判「是不是回归」，先翻上一份成功收据，再谈根因。**

### 问题 ⑨：`--auto-repair` 自动修复整条路径是死的

**现象**：09-28 重跑时 5 家的 `autoRepair` 全是 `applied=false`、`detail` 写着 `Failed to parse URL from [object Object]/targets`。

**真因**：候选动作是**对象** `{action, mutating, why}`，而代码写的是 `const action = list[0]`，把整个对象当**动作名**往下传 ⇒ 四个动作分支的 `===` 比较全部落空 ⇒ 一个动作都没执行过。

**为什么测试没抓住**：用例传的是**字符串数组**，生产传的是**对象数组**。这是本项目第三次吃「函数级用例全绿 ≠ 接线接上了」的亏，已写进纪律。

**修法**：新增 `actionNameOf()` 归一动作名（不合法当场抛）；重排逻辑改按名字定位。

### 问题 ⑨b：说好的「最后才叫人」，脚本层根本不成立

**现象**：09-28 重跑失败时，链级告警**当场就发了飞书**，根本没问「要不要先交给 agent 试一下」。

**真因**：告警由 `run-multi-shop-day.mjs` 直接发出，代码里**没有「先唤醒 agent」这个概念**。一条硬事实：`run-daily-job.mjs` 是 shell 子进程，**没有 `Agent` 工具**，脚本不可能唤醒对话，只有会话能。

**修法**：抽出 `classifyShopEscalation()`（告警闸门与派单**同一来源**）；新增**默认关**的 `--defer-agent-actionable-alert`：整批失败都够格交 agent 时才拦下、落交接单；**只要有一家「只能人上」，照旧叫人**（fail-closed 不放水）。

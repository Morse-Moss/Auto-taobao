## 四、四个根因

### 根因 1（新发现）：平台「零数据」被当成文件损坏

网林家居推广 ZIP 只有 596 字节，解压后是「78 列表头 + 一个空行」，文件以 `\n\n` 结尾。
Python `csv.reader` 为这一行产出 `[]`（长度 0 ≠ 78）⇒ `promotion-core.mjs:27` 抛「第2行列数与表头不一致」。

后果放大：这一抛**杀掉整批 3 店导入**，把本来能成的盖文淘宝、里可林天猫一起推迟到逐店导入。
（若当时没有批量导致的中断，这两家本来在上午轮就能完成。）

判据修正：`rows.length > 0 && rows.every(blank)` ⇒ 返回 `{rows:0, empty:true, blankRows:n}`，
收据打 `emptyReport:true`；有行但混进空行仍照旧拒绝（那是被截断或被追加垃圾）。
日期校验对空集恒真，不需要额外分支。

### 根因 2：询单 `link` 只读一次

`collect-inquiry-report.mjs:78` 读 React `memoizedProps.link`（异步填充）**一次**，读到空就抛。
现场证据：入口 DOM 存在、日期按钮正确、只有 `link` 空。19 分钟后同店同命令成功写出 8 行
⇒ 是竞态，不是配置、也不是页面改版。

判据修正：`planLinkPollStep` + `pollInquiryLink`（20s / 1s 有界轮询，可注入 `read`/`delay`/`now`）；
超时**不抛**，把最后读数与读次数交回去；身份校验对空状态兜底，避免 `state.shop.includes` 的
TypeError 把「页面没读出来」盖成一句 JS 报错。

### 根因 3：推广下载按钮判据过窄

`collect-product-report.mjs:73` 旧判据压了三个窄条件：叶子节点 + `innerText==='下载'` + `width>0`，
再加全文档扫描与单次 `elementFromPoint`。
失败现场：报表已渲染 35 行、URL 日期正确、遮挡层 0，却报「下载入口不可见」；
同一现场还有 `Runtime.evaluate` 500（30 秒全文档扫描撞 CDP 超时）。

判据修正：页面侧只负责「取候选 + 报视口」，**文字包含「下载」即候选**（精确相等只用于排序）；
尺寸 > 0 且中心点在视口内；候选按优先级排好后由 Node 侧逐个交给浏览器 `elementFromPoint` 复核。
失败时用 `describeDownloadFailure` 说清是「压根没有下载字样」「有但尺寸为 0」还是「在视口外」。

### 根因 4：`stoppedAt` 设计放大了缺口数

某阶段失败会跳过该店后续阶段 ⇒ 告警里 1 个故障看起来像 2 个缺口。
（例：盖文淘宝询单失败 → 推广段直接跳过，报出「询单+推广」两个缺口，实际只有 1 个故障。）

### 第 3 项暴露的盲点（本轮最重要的教训）

第一次对第 3 项做突变（把页面侧探针退回 `trim()==='下载' && children.length===0`）——
**13 条用例一条都没红**。

因为排序层用例钉的是「拿到候选之后怎么排」，而 10-20 那次假红的病根在**页面侧根本没把候选取回来**。
这正是本项目已发作三次的同一条教训：「用例全绿 + 突变过了」不等于接线接上了。

修法：加两条接线守卫，不测行为、只钉**调用侧到底传了什么判据**（源码文本级断言）：
- `download-entry-wiring.test.mjs`（4 条）：必须用 `includes('下载')`、不许退回叶子节点或精确相等、
  必须走 `rankDownloadCandidates` / `describeDownloadFailure` / `elementFromPoint`、失败信息不许退回一句符号。
- `inquiry-link-wiring.test.mjs`（4 条）：必须 import 并 `await` 调用 `pollInquiryLink`、
  不许退回一次性 `evalOn` 读页面状态、报错必须带轮询次数、身份校验必须兜空。

复验：再把探针退回旧判据 ⇒ 接线守卫 **2 红**；把 `polled.state` 退回 `await evalOn(...)` ⇒ 接线守卫 **1 红**（精准命中）。
两处均逐字还原，`diff` 与备份逐字一致。

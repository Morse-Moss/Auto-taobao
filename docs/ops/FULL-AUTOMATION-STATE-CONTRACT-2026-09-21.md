# 完全自动化到底缺什么：日报链的「状态契约」分析（2026-09-21）

起因：用户问「你每次采集完也不会关浏览器，所以页面一直留在期望 URL 上 —— 第一性原理分析清楚，
到底怎么样才能达到完全自动化」。这篇不是又一次打补丁，而是把这条链**为什么无法无人值守**讲清。

**结论先行**

1. 「采集完关掉浏览器」不是解法，而是把可控问题换成不可控问题。这条链上**唯一必须人的事是登录**，
   关掉浏览器就没人能替你登回来 —— 你会用一个「状态漂移」问题换来一个「登录失效」问题，而后者无解。
2. 浏览器必须长期活着 ⇒ 它的状态在两次运行之间**必然漂移**。所以自动化成不成立，不取决于关不关浏览器，
   取决于**每一步在动手之前，是否自己建立了它依赖的前置状态**。
3. 09-21 那次失败不是「运气不好」，是**一次正确性改进暴露了既有漏洞**：09-18 加的「回位」把页面留在了
   能被 URL 判据认出来的地址上，于是次日不再重载；在此之前，页面停在预览页这个**缺陷**恰好在替它做重载。
4. 因此「完全自动化」不是「多写几个重试」，而是**把状态契约补完**：入口自己建立前置、出口留下声明过的后置、
   preflight 从「检查」升级为「修复 + 边界判定」、每步可重入。缺哪一条都会周期性失效。

## 一、第一性原理：浏览器是「租来的资源」，不是「自己的变量」

普通程序里，一个变量在这一步和下一步之间不会自己变。浏览器不是：

- 它是**长生命周期**的（不能关，见上）；
- 它的**真实状态**（当前渲染的日期、当前页签、滚动位置、被遮挡的弹层、会话有效性）
  **不在我们手里**，只能通过协议去问；
- 而我们问得出来的东西是**代理量**（URL、targetId、某段文本），代理量和真身**不是一一对应**。

本次失败就是代理量失真的教科书案例：

```
URL 与期望完全一致   → 判据认为「已经就位」
实际渲染仍是昨天的日期 → 真身和判据说的不是一回事
```

⇒ **判据必须落在观察值上，不能落在 URL 上。** URL 命中只能说明「这个页签是谁」，
不能说明「它现在是哪一天」。

## 二、无人值守时，「前置状态」为什么必然不可知

四种来源都会改它，而且都不通知我们：

| 来源 | 例子 | 后果 |
|---|---|---|
| 上一次**中断** | 停在某个中间步骤，页签/日期被带走 | 状态是「半路的样子」，谁也不认识 |
| 上一次**成功** | 收工时的收尾动作把页面留在某个地址 | 次日不再是新加载，读数过期（**本次**） |
| **人工**动过 | 运营/th 自己点开看了一眼、手动切了日期 | 无法枚举 |
| **平台**自己变 | 默认预设、页面结构、风控弹层 | 我们没改一行代码却全红 |

普通程序可以让「上一步」保证「这一步」的输入。这里不行 —— 因为上一步可能是**上一个自然日**的、
或者根本是**人**做的。所以：

> **只有「这一步自己建立 / 自己断言」的前置，才算前置。**
> 任何形式的「上次跑完时它大概是干净的」，都是伪装成自动化的人工依赖。

## 四、为什么偏偏是 09-21 第一次炸（有据可查）

按代码与 git 逐条对上：

1. `date-picker.mjs:422 resolveTarget` 的判据是 **URL 片段命中**：命中恰好一个就直接复用，
   **不导航** ⇒ 没有重载。
2. 而「第 4 步之后，页面必然在入口地址上」——**不在就导航过去**（`resolveTarget` 的 `entryUrl`
   恢复分支，`matches.length === 0` 时才会走），**在就原样保留**。两者都留下同一个结果：
   页面位于 `https://sycm.taobao.com/qos/service/frame/shop/performance/new#/shop`。
   步骤 8（`sycm-reset`，**09-18 加入**，commit `77d7141`）则是在页面被步骤 5 带走之后
   **显式导航回同一个入口地址**（`resetSycmPage` 用 `SITE_SYCM_ENTRY`），**实测确认**它回到的地址
   正是含 `SYCM_FRAGMENT` 的那个。
3. ⇒ 一轮跑完（或跑到步骤 4 之后）留下的地址，**正好满足次日的 URL 判据** ⇒ 次日不重载
   ⇒ 页面还是**上一次加载那天**的渲染 ⇒ `1天` 这种相对预设**只在页面加载时解析一次**
   ⇒ 点已选中的「1天」不重新取数 ⇒ 读数不变 ⇒ 停在第 4 步。
4. 而历史上的成功是有原因的：那些观测**全是同一天内的重复运行**。同一天里，页面在当天早些时候
   已被渲染过，`1天` 解析出来的就是「昨天」＝当天要的目标日 ⇒ `observedBefore == requested` 天然成立
   ⇒ 看起来「点击生效了」，其实**从未跨越过一个自然日边界**。（与既有的「排练全绿 ≠ 真跑能跑」同源。）
5. 09-18 之前更早的形态：页面被步骤 5 留在**预览页**，那个地址**不含**片段 ⇒ `matches.length === 0`
   ⇒ 走 `entryUrl` 恢复分支 ⇒ **真的导航了一次** ⇒ 顺带完成了重载。**是一个缺陷在替它做重载。**

⇒ 一句话：**这条链的日常成功，靠的是「当天有人/有东西已经把它重新加载过一次」这件外部事件。**

## 五、要成立，必须补的四处（每处给可执行判据）

### A. 每步入口「落地化」：判据从代理值换成观察值

- 做法：把「页面在不在」升级为「页面此刻**是不是我要的那一天 / 那一页**」。`sycm-date` 已按这个思路修完；
  其余阶段照抄这个形状（`alimama-date` 走 URL hash，天然可靠，可留）。
- 判据：**从任意页面状态出发**，这一步都能自己到达前置；做不到就抛，且抛的文案**点名是哪一种成因**
  （「页面停在旧渲染」已排除 / 平台这天还没数 / 落位坏了）。
- 反面：`if (url === expected) return;` 这种写法一律视为「没有前置判据」。

### B. 轮次出口留下**声明过的**后置（成功与失败都要）

- 做法：回位从「尽力而为」改成**断言**（回位后再读一次，确认落在中性态）；
  并且放进 `finally`，**失败路径也回位**。
- 重要细节：**先取证、再归一化**。失败时页面的样子本身就是证据，所以顺序是
  ① 把「这家店被留在了什么状态」写进 `summary.json`（可审计），② 再回位。
- 判据：一轮结束（无论退出码）后，五家店的页面落在**声明的**中性态；不是就报，且报告里能看出「谁留下了什么」。

### C. `health-check` 从「检查」升级为「检查 + 修复 + 边界判定」

- 修复：把页面**拉到**中性态（导航 + 重载 + 断言读数），而不是「看着不对就停整轮」。
  现在它只报错，于是每一次残留都要人来擦 —— 这正是「不是全自动」的日常形态。
- 边界：**在动任何平台数据之前**判定「需要人」的那一类（登录 / 扫码 / 验证码 / 风控）。
  现在 L0（身份）与 L2（会话）都未实现 ⇒ 需要人的事**看不见** ⇒ 只能等它中途炸，
  而那时平台侧副作用已经发生（09-20 就留下了一个没人取的生成任务）。
- 判据：需要人的情形**一律在 preflight 报**，并且这一轮「已发生的平台副作用 = 0」；
  无人值守的失败必须都是「没开始」，不能是「做了一半」。

### D. 每步可重入、轮次可续跑

- 现状：`--only <阶段>` + `--shops` 已经是一半能力。
- 要补的判据：逐阶段声明「可重入 / 必须配 `--expected-before-count` / 必须先从零回位」，
  以及对**平台侧副作用**的幂等判据（「已提交未取」的任务是复用还是当阻断，要写死一个口径）。
- 判据：任取一个中断点，都能续跑到底，且不会产生第二份副作用。

## 六、「完全自动化」的可证伪定义（这是验收判据，不是口号）

不是「跑一次成功」，而是：

> **从每一种「上一次留下的现场」出发，整轮必须能自己恢复；或者在产生任何平台副作用之前，明确拒绝并说清为什么。**

现场清单（每一种都要能自动重放，用一次性实例，绝不拿生产实例试）：

1. 页面停在**昨天的渲染**上（本次）—— ✅ 已可自恢复
2. 页面停在**报表预览页**（步骤 5 之后中断）
3. 页面停在**别的页签**（`询单到付款` 之类）
4. **上一轮已写飞书**（推了一半）⇒ 重跑必须撞「不许写第二遍」并判成「不用处理」
5. **下载目录里有同名旧文件** ⇒ 不许把旧文件当新产物
6. **平台侧有已提交未取的生成任务** ⇒ 复用或阻断，二者必须显式
7. **登录失效** ⇒ 必须在 preflight 报，且平台副作用为 0
8. **页面被人工打开在看别的日期** ⇒ 要么能归一化，要么明确说清「有人正在用」

只做 1 而说「已修复」是不成立的：1 只是**已知的那一个**成因。这 8 条才是「能不能无人值守」的判据。

## 七、不可自动化的那部分（写清楚，否则「完全自动化」是自欺）

- **登录 / 扫码 / 验证码 / 风控**：不可自动化。能做的是**提前发现**，并把它压成
  「一件可以在无人值守之前批量做完的事」（一次性把五家店验一遍）。
- **平台改版**（选择器漂移）：不可自动化，但可以 fail-loud（现在已经是这个形状）。
- **会话寿命**：不可控，但可测 —— 会随着时间必然到期，所以目标是把它从
  「每次失败打扰一次」降到「会话到期打扰一次」，且**每次都发生在动手之前**。

⇒ 真正可交付的目标：**把「需要人」的次数降到会话寿命的量级，且每次都不带半成品副作用。**

3. §11.3 那次稳定性复读仍然要做（它管的是别的一类现场），但优先级低于第 1 项。

## 十三、09-24 那轮暴露的第三处缺口：**「页面不在」被算成了「会话没了」**（2026-09-24 修）

本文件 §3 那张表里第 3 行（登录 / 会话 = `implemented:false`）与 §8 的第 7 项
（「登录失效 ⇒ 必须在 preflight 报，且平台副作用为 0」）至今未变，但**围绕它的判据**补上了一处 ——
这一节记录 09-24 08:14 那轮的实测与随之而来的修法。

**实测（09-24 08:14 定时轮，目标日 09-23）**：链 **11/11 全绿、退出码 0、底单 5 行齐全**，
而跑前登录体检发了 **5 条飞书告警，每店一条，全是假红**。同轮链的第 0 步（health-check）
把页面归位之后，五家店一步没停。⇒ 收信人被叫去处理一件系统自己 20 秒后会修好的事，被叫了五次。

**根因（一句话）**：体检只读「站点页面的最终地址」，而那一轮浏览器是**冷启动**的、
窗口里一个页签都没有 ⇒ 判据只能得出「读不到」⇒ `--login` 档把「读不到」推进「需要人处理」。

**修法（1.7.0，四处）**：

1. 跑前体检**先归位再判断**（仅 `--login` 档；失败不阻断），复用 §9 第 ② 项的同一份实现
   `runtime/page-normalize.mjs`，不另造第二份补页逻辑；
2. 把两种同形成因**分开量**：`loggedIn === null`（页面不在）→ 新结论 `PAGES_ABSENT`
   （**刻意不在 `VERDICTS_NEEDING_HUMAN` 里**，不发告警）；`loggedIn === false`（页面在但被弹回
   登录页）→ 才是实锤掉登录；
3. 告警从「每店一条」收成「**整轮一条**」，且投递权整体收到本层（子进程一律 `--notify off`）；
   只有「`--login` 档 **且** 结论是 `NEEDS_LOGIN`」才发 —— 只读体检一个字都不发；
4. `resolveAlertDedup` 抽成 `runtime/alert-throttle.mjs`，两条链共用一份状态
   （此前**这条路径根本没有去重**：一次预检能并发 5 条同一天的告警）。

**仍未补的（明确记下来，别当成已解决）**：

- §3 表第 3 行本身没动：`IDENTITY` / `SESSION` 两层体检仍是 `implemented:false` ——
  本版只是把「读不到」从「要人处理」里切出去，**没有让体检真的能判定会话身份**。
- **商家浏览器（19022/19023）仍没有任何一步会自动登它**，而链第 0 步要求它的生意参谋工作页
  **恰好一个** ⇒ 它掉登录时整轮**一步都不跑**。这是 09-23 就记下的缺口，本版押后
  （理由：要在上面 1/2 之后做，否则等于用一个「会自己去登」的动作换掉一个「只报不猜」的动作）。
- `PAGES_ABSENT` 只有离线判据，**真机现场复现未做**（需要先有「窗口里没有该站点页面」的现场）。

**可核产物**：`evidence/login-alert-round-2026-09-24/`（该目录的 README 逐文件说明「证明了什么、怎么复现」）——
受影响用例 155/155、跨目录守卫**先红后绿**（两次原始输出都在）、整轮告警过真渲染器 `--dry-run`
（一个字节没发）、只读真跑一次预检的收据。

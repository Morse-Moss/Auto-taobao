# 无人值守 Agent 运行方案（定时自动跑 + 异常才通知）

日期：2026-09-15 ｜ 场景：单机单店铺 ｜ 目标：到点自动跑，成功安静，出故障才叫人

本文件回答两件事：**「定时自动跑 + 出故障才飞书提醒」怎么实现**，以及**飞书消息走哪条通道**。
它与 [`CLIENT-DESKTOP-DELIVERY-PLAN.md`](CLIENT-DESKTOP-DELIVERY-PLAN.md) 是**正交的两件事**：
那份讲「客户看到什么」，这份讲「系统自己怎么跑」。运行内核先成立，界面才有东西可显示。

## 0. 结论

1. **不需要新建一套 agent 框架。** 你要的「自主跑、自己修、修不了才叫人」，
   在本仓库里已经有三块现成骨架：确定性运行底座（`runtime/sop-runtime/`）、
   故障诊断与处置白名单（`runtime/supervisor-agent/diagnose.mjs` + `actions.mjs`）、
   失败分类与人工介入状态机。**要补的是一个常驻调度器 + 一个通知出口 + 把它们接起来的编排**。
2. **飞书通道：主线用自建应用发消息，群机器人做兜底投递。**
   理由见 §6——核心是「提醒要发给运营**个人**」，而群机器人做不到发给个人。
3. **无人值守的正确形态是「人在环上、不在环内」**：人只在两处出现——登录到期时扫码、以及真出故障时处置。
   其余时间系统自己跑。这条决定了 §4 的静默规则必须是「默认安静」。

## 1. 先对齐一个词：这里的「agent」指什么

不是「LLM 自由发挥的智能体」，而是**受控自主**：

| | 脚本 | 受控自主（本方案） |
| --- | --- | --- |
| 流程 | 固定步骤，出错就停 | 有目标（本周数据入库），自己决定先体检还是先采集、失败先自救还是先叫人 |
| 出错 | 停在原地等人看日志 | 先按白名单自愈，预算用尽才升级人工 |
| 自主权 | 无 | **有限**：动作白名单 + 预算 + 白名单外 fail-closed |

这套「有限自主」的设计仓库里已经有了（`actions.mjs` 的 5 个动作 + 每小时重启上限 + 白名单外拒绝），
并且与 README §2 的非目标一致：**Agent 不得绕过登录、验证码、风控，不得自己改页面选择器**。
所以你的方向和现有架构是同向的，不需要推翻重来——需要的是**接线**。

## 2. 一轮运行的生命周期（这是整个方案的主干）

每一轮（例如每周一 09:00）都走同一条链，任何一步失败都进 §4 的判据表：

```
定时触发（幂等键：店铺 + 周期）
  ↓
① 体检（0 成本，先做）
   身份层：登录的是不是「我们要的那个买家账号 / 目标店铺」（不是「有没有登录」）
   运行环境：CDP Proxy 在吗 / Edge 在吗 / 浏览器身份（user-data-dir）对不对 / 插件加载了吗
   会话层：各平台凭证是否存在、是否临近过期（只读存在性与到期时间，不记明文）
   端到端：低成本的只读探针（每轮一次，失败不重试）
   账号：淘宝、生意参谋、小旺神插件、灰豚、飞书凭据有效性
   → 任一不过：立刻通知 + 结束本轮（不浪费一次采集）
   详细判据与状态词表见 LOGIN-STATE-MANAGEMENT.md
  ↓
② 探队列（复用 capability-scheduler 的 probe 语义）
   没有活可干 → SKIPPED_EMPTY_QUEUE → 结束本轮（不通知、不留失败记录）
  ↓
③ 执行（复用 two-stage-runner）
   采集段 → 证据验证 → 发布段 → 回读验收，游标只在验证过的证据上前进
  ↓
④ 收尾判定
   全部成功 → 记录 + 按 §4 决定要不要发「今日完成」汇总
   有失败   → 进 ⑤
  ↓
⑤ 自愈（Agent 处置层）
   diagnose.mjs 分类 → actions.mjs 白名单动作 → 预算内重试
   自愈成功 → 记录「今天自动修复了什么」（不打扰人）
   预算用尽 / 无对应动作 → 升级人工（这才是要通知的事）
  ↓
⑥ 通知（唯一出口）
   §4 判据 → notify-feishu.mjs → 主通道自建应用，失败降级群机器人
```

关键设计点：**体检放在最前面**。登录失效是客户环境里最高频的故障，
把它挡在①，既省下一次注定失败的采集，也让通知来得更早、更具体（「登录失效」而不是「采集失败」）。

## 3. 定时怎么落地（Windows，最少依赖）

**用「任务计划程序 + 进程内幂等」的组合，不要守护进程。**

- 任务计划程序：设「开机启动」+「每 15 分钟运行一次」+「错过触发后尽快补跑」。
- 进程内判断：今天这一轮**是否到期、是否已经跑过**。
  「是否已跑过」由 `sop-runtime` 的幂等键回答（`店铺 + 周期`），不靠本地文件——这是本仓库既有原则。
- 好处：进程崩了不需要额外守护（15 分钟后再触发一次，幂等键保证不会重复写）；不需要装服务、不需要管理员权限；
  进程启动本身很便宜，没到点就立刻退出。
- 不引入的东西：不装 Redis / 不加消息队列 / 不常驻一个「永远活着」的进程。
  README §9 的口径是「每个基础设施组件都必须对应已验证的需求」，这里没有这个需求。

**并发约束**：单店铺写操作恒 1（沿用现有 lane 约定）。定时触发与人工手动触发可能撞车，
必须靠 lane 闸门互斥，而不是靠「我们不会同时点」。

## 4. 「出故障才提醒」的判据表（本方案最该被审查的一节）

默认安静。只有「需要人动手」才打扰人。逐条对应现有的失败分类：

| 情形 | 现成分类 | 要不要通知 | 通知什么 |
| --- | --- | --- | --- |
| 本轮无活可干 | `SKIPPED_EMPTY_QUEUE` | **不通知** | — |
| 全部成功 | — | 默认不通知 | 可配「每天/每周一条汇总」 |
| 临时外部抖动，自愈成功 | `TRANSIENT_EXTERNAL` | **不通知**（但记入「今日自动修复」） | — |
| 资源忙，排队后成功 | `RESOURCE_BUSY` | **不通知** | — |
| 登录态失效 | `HUMAN_REQUIRED` | **强通知** | 「小旺神登录已失效」+ 一键重登入口 |
| 验证码 / 风控页 | `PLATFORM_CONTROL` | **强通知** | 「需要人工在浏览器完成验证」——明确说明系统不会绕过 |
| 页面改版导致选择器失效 | `CAPABILITY_DEGRADED` | **强通知** | 「该能力需更新，请联系服务商」+ 诊断包已就绪 |
| 配置/授权不对 | `POLICY_DENIED` | **强通知** | 「配置有误」+ 具体缺什么 |
| 外部写入结果未知 | `COMMIT_UNKNOWN` | **强通知** | 「本次写入结果需对账确认」——**不许静默重试** |
| 疑似自身缺陷 | `BUG` | **强通知** | 「已停止自动化」+ 诊断包 |
| 自愈预算耗尽 | — | **强通知** | 「已尝试 N 次仍失败」+ 最后一次的原因 |

三条容易做错的细节：

1. **去重与恢复必须成对**。同一个原因不重复轰炸（现有 `DEDUPED` 已实现），
   恢复时补一条「已恢复」——否则运营会一直以为还是坏的。这两条现有 `xws-sku-auth-preflight.mjs` 已经做过，直接复用。
2. **通知必须带「下一步做什么」**，不能只报错误码。运营看不懂 `HUMAN_REQUIRED`。
3. **通知发送失败不能影响主流程**，且要留下证据（现有 `delivery.status=FAILED` 写进告警文件的做法是对的）。

## 5. 自愈层：能做什么、做不到什么

**能自愈（对应已有动作）**：

| 故障 | 处置 | 现有基础 |
| --- | --- | --- |
| 进程崩溃留下未终结的运行 | 回收并续跑 | `reclaimStale`（PHASE-ARCHIVE §13.7，已实现） |
| 标签页被顶掉 / 关闭 | 重建标签并重试阶段 | `restart_flow_with_params` / `retry_export_with_params` |
| CDP Proxy / Edge 没起来 | 拉起后重试 | 需补执行器实现 |
| 短暂超时 / 下载慢 | 预算内重试 | `Budgets`（每小时重启上限，已实现） |
| 外部写入结果未知 | **不自愈**，转对账 | `reconcilePublication`（已实现） |

**做不到自愈**（必须通知，别硬扛）：页面改版、风控封禁、权限被回收、登录必须人扫码。
硬扛的代价是把「一次可恢复的失败」变成「一周数据全丢」。

## 6. 飞书通道选型：主用自建应用，群机器人做兜底

两条途径的实测差异（依据本仓库现有代码与 `docs/ops/FEISHU-APP-SETUP-NEW-TENANT.md`）：

| | 自建应用消息（`POST /im/v1/messages`） | 群自定义机器人（webhook） |
| --- | --- | --- |
| 凭据 | **复用现有 `FEISHU_APP_ID/SECRET`**，零新增 | 新建一个 webhook URL |
| 能否发给**个人** | **能**（`receive_id` = open_id/email/user_id） | 不能，只能发到它所在的那个群 |
| 权限成本 | 加 `im:message:send_as_bot` 并**重新发布版本**（自建应用通常自己就是管理员） | **零审批**，5 分钟可用 |
| 消息能力 | 卡片、@人、按钮（可放「重新登录」跳转） | 文本/卡片（能力较弱，@人要 user_id） |
| 失效模式 | token 2 小时过期、scope 被回收、用户不在应用可见范围 | webhook 被删、群解散、被安全设置（关键词/签名/IP 白名单）拦 |
| 代码改造 | `FeishuClient` 加一个 `sendMessage()`；**token 缓存要改成带过期时间 + 401 重试** | 一个独立的 `fetch` POST，与现有客户端无关 |

**选型：主线自建应用，群机器人兜底。** 判据是「提醒的**收件人**是谁」：

- 故障提醒应该发给**运营本人**，而不是吵一整个群——群机器人发不到个人，所以它做不了主线。
- 自建应用又恰好是零新增凭据：项目已经在用同一个应用写多维表格，
  `FeishuClient` 已有 tenant token 获取与请求封装（`skills/xws-to-feishu-base/scripts/feishu-client.mjs`），
  加一个方法就能发消息。**这是两条路里唯一能同时满足「发给个人」和「零新增凭据」的。**
- 群机器人成本极低（一个 URL），作为**投递兜底**：「主通道发送失败 → 降级到群」，
  保证「故障一定有人知道」。通知这件事上，冗余比优雅重要。

**两个必须处理的实现细节**（都是「常驻进程 vs 一次性 CLI」的差异，容易踩）：

1. **token 过期**：现在 `FeishuClient.#token` 是进程内永久缓存。CLI 跑几分钟没事，
   但常驻服务跑几周一定会撞上 2 小时过期 → 必须改成「记录过期时间 + 收到认证错误时清缓存重取一次」。
2. **频率限制**：不要每条告警都单独发。按「一次运行一条汇总」聚合，去重后发送。

## 7. 落地顺序

1. **常驻调度器 + 一轮能自动跑完**（不接通知）——最小闭环。
   完成后系统已经能「到点自己跑，跑完停下」，只是错了还没人知道。
2. **接通知出口**（自建应用 + 兜底 webhook + §4 判据表）——做完这步才算「出故障才提醒」。
   这一层与调度器解耦，可以并行开发（输入只是一份告警 JSON）。
3. **接自愈层**（`diagnose` → `actions` 的真实执行器）——把「失败就叫人」降级为「先自救，救不动才叫人」。
4. **体检前置 + 扫码重登**——因为无人值守下「登录失效」是最高频故障，
   没有自助重登，前面的静默规则会被登录告警刷屏。

第 1、2 步即可交付「定时自动跑 + 异常提醒」这个核心诉求；
第 3 步决定运营被叫的频率；第 4 步决定运营自己能不能搞定。

## 8. 已知风险与边界

- **无人值守 ≠ 无人参与**：登录必须人扫码，跑中也可能撞验证码。
  所以正确承诺是「人一周可能被打扰 0～2 次」，不是「永远不用管」。
- **登录态失效是高频事件，且与关不关机无关**：主因是凭证自然过期、同一个浏览器配置被别的账号登录、
  以及平台侧风控（2026-09-15 更正：此前写「千牛会顶掉 Edge 买家账号登录态」是从一次事故过度概括，
  事实是「调试时在同一 Edge 用户配置里登过商家账号把买家账号挤掉」）。
  这不是异常而是常态，必须由「体检 + 通知 + 一键重登 + 人工确认续跑」这条链兜住。
  四层检查（身份/环境/会话/端到端）见 [`LOGIN-STATE-MANAGEMENT.md`](LOGIN-STATE-MANAGEMENT.md)。
- **单机时钟**：任务计划按本机时间触发。时间不对会导致「今天没跑」，建议启动时校验一次时间并在偏差过大时通知。
- **验证留痕**：本方案的每条判据（尤其 §4 的静默规则）都必须有离线用例覆盖——
  「该安静的时候安静」和「该响的时候响」是同一件事的两面，只测一面会出现「故障被静默吞掉」。

## 9. 已定决策（2026-09-15，用户拍板）

| 议题 | 决定 | 落地含义 |
| --- | --- | --- |
| 通知收件人 | 主发**运营个人**（自建应用消息），群机器人做**投递兜底** | 需开 `im:message:send_as_bot` 并重新发布版本；收件人标识优先用邮箱（可免开 contact 权限，待实测） |
| 「点这里继续」的落点 | 运营**就在那台公用电脑前** | 做成托盘/控制台上的按钮，**不做 `127.0.0.1` 外链**（手机与别的电脑打不开）；需要一个「登录会话对象」承载「谁确认的、确认后可幂等继续」 |
| 执行顺序 | 流程**线性、不可乱序** | 用户能调的只有「这条线什么时候跑」（触发时机）；段的先后写死在配置里，不向界面暴露。每个能力仍声明前置，前置未就绪则本轮跳过并记录（不报错、不通知） |
| 运营日报 | **属下一阶段，与采集链分开做** | 第一版定时化的对象是现有这条线性采集/发布链；日报是独立能力（只读 PG + 生成 + 发送），风险更低，可作为第二阶段第一个无人值守能力 |
| 自动重试预算 | 沿用现状：`maxActionsPerIncident=3`、`maxRestartsPerHour=6` | 不改代码默认值 |
| 定时指纹 | 开机启动 + 每 15 分钟唤醒 + 错过触发后尽快补跑 | 「这轮跑过没有」由业务幂等键（店铺 + 周期）回答，不靠本地文件 |
| 成功时是否通知 | 默认**不通知** | 需要「每周一条已完成汇总」时另开开关 |
| 本地证据保留 | 截图与告警 30 天、原始采集文件留最近 2 个周期 | 需要配套清理任务与磁盘上限告警 |

## 10. 仍待拍板

1. **公用电脑上要不要建专用 Windows 账户**（定时任务与浏览器都跑在它名下，别人日常用机不影响它；
   代价是每次要切换用户）。推荐：建。不建的话，登录态会被别人日常登录反复顶掉。
2. **原始数据在这台公用机上谁能看见**（竞品周表、SKU 快照、截图）。推荐：锁在专用账户目录下。
3. **允许运行的时段窗口**。采集要抢占浏览器；公用电脑上别人在用机器时被抢会很烦，也更容易撞登录态变化。
   推荐：体检全天（低干扰），**采集类任务只在配置的时段窗口内发起**（默认放在午休与下班后）。

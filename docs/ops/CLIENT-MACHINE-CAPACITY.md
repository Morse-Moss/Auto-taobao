# 客户电脑跑得动几家店（多店铺采集的容量档位）

**问题**（用户 2026-09-18）：后续店铺有点多，客户电脑性能可能不够。他自己提的候选方案是「4 个 4 个一轮处理」。

**结论先行**：

1. **瓶颈是内存，不是 CPU。** 每个店铺浏览器实例约 **1.1–2.3 GB**、约 **15 个进程**（实测见下）。
2. **「4 个 4 个一轮」这个说法本身不影响内存** —— 一轮里的店铺是**串行**跑的，串行不并发。
   真正决定峰值的是**同时开着几个浏览器实例**。所以旋钮不是「一轮几家」，而是「**同时开几个**」。
3. **清页签已经做了，实测：省不了内存**（2026-09-18 深夜）。窗口里原来混着重复千牛页与空白页
   （19034 有 3 个千牛页），现在每台只留 1 个千牛 + 1 个标签页、空白页已全清。
   但五实例合计从 6,297 MB 变成 6,726 MB —— **没有下降**。原因见 §3 方案 A：
   空白页几乎不占内存，而这一步同时给每台新建了 1 个标签页。
   **清页签的价值是消除判据干扰，不是省内存。**
4. 分批（同时只开 N 个、跑完一批关掉再起下一批）是**正确形态**，但它需要新增一层驱动，
   而且「关浏览器」属于中断性动作 ⇒ 必须显式设计、由人或计划任务驱动，不能顺手做。

## 1. 实测数字（2026-09-18，本机）

方法：CDP `SystemInfo.getProcessInfo` 拿每个实例的 PID 列表，配 `tasklist /FO CSV` 拿 PID→内存
（`Win32_Process.CommandLine` 在本机读回来是空的，按 profile 归组这条路走不通）。

下表是当天**傍晚**的现场：
| 实例 | 调试端口 | 进程数 | 合计内存 |
|---|---|---|---|
| 商家浏览器（日报链，推送/回读用） | 19022 | 16 | 1,512 MB |
| 里可林淘宝 | 19031 | 15 | 2,284 MB |
| 网林天猫 | 19032 | 16 | 2,166 MB |
| 盖文淘宝 | 19033 | 15 | 1,134 MB |
| 科塔淘宝 | 19034 | 15 | 1,230 MB |
| **五个合计** | | **77** | **8,326 MB** |

> 这张表是 2026-09-18 **傍晚**的现场：当时每台还堆着重复的千牛页与空白页。
> 当天深夜清完页签、挂上标签页之后又量了一次，见本节末尾 —— 那时的现场与这张表**不是同一个状态**，
> 不要拿两张表的数字互相当成「变化量」，除非把「新建了 4 个标签页」这件事算进去。

单实例分布：**1,134–2,284 MB，均值约 1,665 MB / 实例、15.4 进程 / 实例**。

本机：物理内存 **31.1 GB**、当时可用 **6.4 GB**（已用 24.6 GB）；CPU 型号是 12 核的 Ryzen 9 9900X，
但 `os.cpus()` 只报 **6 个逻辑核**（可能被虚拟化或亲和性限制，**这一条只按它报的数字用，不去解释**）。

> 注意：**8,326 MB 是本机同时开五个实例的量**。它的意义不是「客户机需要 8.3 GB」，
> 而是「**每多开一家店，峰值就多约 1.7 GB**」。

### 清完页签之后又量了一次（同一天深夜）

| 时刻 | 五实例合计 | 当时窗口里有什么 |
|---|---|---|
| 傍晚 | 8,326 MB（上表） | 含重复千牛页与空白页 |
| 清理**前** | 6,297 MB | 已无重复千牛；每台 1 个空白页；19031/19034 无标签页 |
| 清理**后** | 6,726 MB | 四台各多 1 个标签页；19031/19034 各多一个关不掉的 `edge://nurturing/` |

**6,297 → 6,726 不能读成「清理让内存变差」**：这一步同时新建了 4 个标签页。
反过来也不能读成「清理省了内存」。两份原始输出在
`evidence/window-label-and-prune-2026-09-18/`（`01-memory-before-cleanup.txt` 与 `08-memory-after-everything.txt`）。

**结论**：每实例约 **0.9–2.0 GB** 这个量级不变；**能调的是实例个数**（方案 B）。

## 2. 为什么「一轮几家」不是那个旋钮

`run-multi-shop-day.mjs` 是**按店铺串行**的：一家店跑完十一阶段再跑下一家。
所以「一轮 4 家」与「一轮 5 家」的**并发度相同** —— 峰值内存只取决于「这 4/5 家的浏览器是不是同时开着」。

如果「4 个 4 个一轮」的实际含义是「同时只开 4 个，跑完关掉再起下一批」，那它=方案 B（分批），是对的；
如果含义是「一轮里只有 4 家店参与」，那它对性能没有帮助。

## 3. 三条路，按性价比排

### 方案 A（已做，实测：省不了内存）：把多余的页签清掉

**先说结论**：2026-09-18 深夜真清了（4 个空白页），**内存没有下降**（6,297 → 6,726 MB）。
所以这一项**不能算作内存方案**。它解决的是另外两件真实的事：

- **判据干扰**：链的判据是「这个后台**恰好一个**页面」，同一个后台出现两个页面 ⇒ 整家店停在第一步。
  重复页签不是「看着乱」，是会拦人的。
- **人眼困惑**：用户原话「我看到每个浏览器里面有多个界面」—— 报告现在会把每个页签标出性质。

实测细节（为什么没省）：这一步里同时给每台**新建了 1 个标签页**，
而一个**真实页面**（renderer 进程）是 200~300MB 量级，**空白页几乎不占**。
数量上也对得上：19032/19033 只减了空白页（renderer 9→8、8→7），内存反而各升 69MB / 47MB。

现在每台的页签构成（清完之后的真实状态）：

- **必需**：生意参谋工作页 ×1、阿里妈妈工作页 ×1、窗口标签页 ×1。
- **只留一个**：千牛工作台（SOP 里的预留槽位，日报链不读）。
- **关不掉的**：`edge://nurturing/`（新建标签页时 Edge 自己打开的）——
  实测 `/close` 返 `{"success":true}` 但页面不消失，所以它已从关闭计划里移除，
  报告里标成「脚本关不掉，忽略即可」。原来把它列进计划，等于每轮报一个假动作。

`node runtime/shop-window-label.mjs`（不带 `--commit`）会把每台窗口的页签逐个标出来并单列残留；
`--prune` 只报告关闭计划，`--prune --commit` 才真关。**默认不开** —— 千牛是预留槽位，
一律当垃圾关掉会误伤。

> 关于「清页签能省多少」这个问题的正确答案：**省不了多少，别把它当内存方案**。
> 要降峰值只能少开实例（方案 B）。

### 方案 B（正确形态）：分批 —— 同时只开 N 个

一次只起 N 家店的浏览器，跑完这 N 家就**关掉**，再起下一批。这样峰值 ≈ `N × 1.7 GB + 商家浏览器 1.5 GB`。

按这个式子给客户机的档位（留 1.5–2 倍余量给 Windows、Edge 自身与生意的其它软件）：

| 客户机物理内存 | 建议同时开店数 N | 预估浏览器峰值 |
|---|---|---|
| 8 GB | **2** | 约 4.9 GB（已很紧，不建议再多） |
| 16 GB | **4** | 约 8.3 GB |
| 32 GB | **5–6**（再往上要看余量） | 约 10–11.7 GB |

**代价**：批次之间要**真的把上一批关掉**，否则峰值不降。而「关浏览器」是本项目的**中断性动作**
（纪律：未经许可不动任何进程）⇒ 这一层必须做成交付件里显式的一步，不能藏在脚本里顺手做。

### 方案 C（不建议）：一个浏览器跑多家店

按 profile 切店最省内存，但会破坏「**一个 profile = 一个淘宝身份**」这条隔离
（`BROWSER_ACCOUNT`）：同一 profile 里换个账号，采集链会**静默**读到另一家店的数据。
这条以前踩过，不要为了省内存把它换回来。

## 4. 那一层：分批驱动（2026-09-23 已建）

**「按店铺起浏览器 / 分批 / 跑完关掉」的驱动已经建出来了**，两半都在：

- 切批与「该不该释放」的**纯函数**：`runtime/batch-plan.mjs`（离线判据 `runtime/batch-plan.test.mjs`）。
  每批家数是配置（`--batch-size`），默认 5 家；客户机档位映射见 §3 那张表（8 GB→2、16 GB→4、32 GB→5）。
- **IO 层**：`scripts/run-batches.mjs`。每一批走四段：
  `start`（`scripts/start-all.mjs --only <本批>`，幂等）→ `label`（每店挂窗口标识页）→
  `chain`（`run-multi-shop-day.mjs --shops <本批>`）→ `stop`（`scripts/stop-all.mjs --yes --only <本批>`）。
  整轮只在开头起一次**共享实例**（商家浏览器 `dailyReport`）：推送段与回读段跑在它上面，
  所以它**整轮都不停**。

```bash
node scripts/run-batches.mjs --print                 # 只打印每一批要执行什么（不起任何进程）
node scripts/run-batches.mjs --batch-size 2          # 排练（不写飞书），跑完释放
node scripts/run-batches.mjs --commit                # 真跑：写飞书，跑完释放
node scripts/run-daily-job.mjs --batches 2 --commit  # 定时形态：把「整轮一次跑完五家」换成分批
```

**默认关闭**：定时链不带 `--batches` 时三步与从前逐字相同（仍是整轮一次跑完五家店），
这一条由 `runtime/daily-job-plan.test.mjs` 逐字守着。

失败时**不主动释放**（第 5 条口径：失败优先解决问题，需要人工的就转人工），释放命令写进日志。
但有一条实测边界必须说清：本层的 `start` 用的是 `scripts/start-all.mjs`（**起完就退**），
而宿主要在**命令结束时回收整棵进程树** ⇒ **这批窗口活不过本轮命令**；
「不释放」只等于「我不去停它」，不等于「它还活着」（2026-09-23 实测：命令结束 0.26 秒后
浏览器连同启动器一起消失、代理还在，看起来像「停了一半」）。
要让窗口真的留到人来看，得用 `scripts/start-all-hold.mjs` 在后台托住；人不在现场时，
可查的证据是证据目录里的 `batches.log` 与链自己的体检原始输出。

> 旧说法（已过时，留作对照）：SOP 第 1 步按店铺人工起浏览器；`start-shop-proxy.mjs` 只起代理；
> `run-multi-shop-day.mjs` 假设「这些店的浏览器都已经开着」；没有分批驱动。

## 5. 一句话给客户的说法

> 每家店需要一个独立浏览器（因为一家店一个登录身份，不能混），每个约占 1.5–2 GB 内存。
> 一次同时开几家可以调：8 GB 内存的机器建议一次 2 家，16 GB 建议 4 家，32 GB 可以 5–6 家。
> 店铺多的时候是一批一批跑，不是一次性全开。

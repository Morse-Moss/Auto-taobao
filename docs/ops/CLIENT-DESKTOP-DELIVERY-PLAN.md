# 面向客户电脑的交付评估与改造方案（单机单店铺版）

评估日期：2026-09-15 ｜ 场景：单机、单店铺、不考虑多租户 ｜ 客户画像：传统电商运营，此前手工收集数据

> 本文件讲「客户看到什么」（交付形态与自助能力）；**运行内核**——定时自动跑、自己修、修不了才叫人——另见
> [`UNATTENDED-AGENT-RUNTIME-PLAN.md`](UNATTENDED-AGENT-RUNTIME-PLAN.md)。两者正交，运行内核先成立，界面才有东西可显示。

本文件回答两件事：**现在能不能直接装到客户电脑上让不懂技术的人独立操作**；如果不能，**要改什么、按什么优先级改**。

## 0. 结论

**不能直接交付。** 差的不是功能，是产品形态：现在是一套**工程师的 CLI 工具链 + 三个仓库外前置**，
客户侧需要的是一套**装了就能用、坏了能自救的桌面程序**。

但可用基础比预想的多——四块重点需求里，**登录态检测、通知通道、故障诊断、人工介入状态机都已经有骨架**，
不是从零开始：

| 现有基础 | 位置 | 已经做到了什么 |
| --- | --- | --- |
| 登录墙检测 | `runtime/xws-sku-auth-preflight.mjs` | 经 CDP 注入表达式检测登录标记与可见登录弹窗 → `AUTH_REQUIRED` / `AUTH_READY` |
| 可插拔通知通道 | 同上 `notifyOperator(command, alert)` | 把告警 JSON 由 stdin 交给外部命令发送；**含去重（DEDUPED）与恢复通知** |
| 故障诊断（确定性优先） | `runtime/supervisor-agent/diagnose.mjs` | 7 类失败签名 → `rootCause` + `remedy` + 白名单动作；登录失效已映射为「开登录窗 + 转人工」 |
| 处置白名单与预算 | `runtime/supervisor-agent/actions.mjs` | 5 个动作、每小时重启上限、白名单外 fail-closed |
| 人工介入状态机 | `runtime/sop-runtime/` | `PAUSED` / `HUMAN_REQUIRED` / blocker 分类；stale 回收与续跑（PHASE-ARCHIVE §13.7） |
| 运营级断点续跑入口 | `runtime/run-faq-operator.mjs` | `--status` 只读检查、`--advance` 每次只推进一个阶段——已经是「面向运营」的雏形 |

缺的是把它们**串成一个客户看得懂、点得动的产品**，并补三个平台里还没覆盖的登录检测。

## 1. 为什么现在不能直接给客户（逐条证据）

1. **三个仓库外前置，客户机上一个都不存在。**
   - 共享 `web-access` Skill 与 CDP Proxy 位于 `D:\codex\skills\web-access`（README §外部依赖）；
   - 「已登录的 Edge 用户会话」是人工成果，不是安装项；
   - 飞书凭据在 `E:\小红书\.env.local`，仓库只传路径（README 明写「不属于项目资产，不复制到本目录」）。
2. **交互形态是 PowerShell + 参数。** 举例，周更的 AI 结算后发布要这样跑：
   `run-weekly-post-ai.mjs --publish-artifact <PUBLISH_READY 的 analysis-artifact.json> --apply --confirm-base <token> --confirm-current-table <id> --confirm-history-table <id> --confirm-library-table <id>`。
   注意入口是 `--publish-artifact`（`--pre-ai-manifest` 已被脚本显式拒绝），且这个发布器**只**写编号库 creates / 当前表 updates / 历史表 updates 三件事 —— 它不吃 pre-ai 的 `pre-ai-manifest.json`，也不跑灰豚与历史同步。
   让运营填 app-token 与 table-id 是不现实的。
3. **需要理解领域概念才能用。** `LOCAL_INPUT_READY`、批次有效性、两个 table ID、`--replace-current`——
   这些是工程语义，不是运营语言。
4. **没有界面、没有常驻、没有定时。** 全仓库搜不到本地 HTTP 服务或计划任务实现；
   现在每一次运行都要人打开终端敲命令。
5. **登录态检测只覆盖小旺神。** 淘宝与生意参谋的登录标记没有实现（`PAGE_EXPRESSION` 里只有小旺神的
   `XWS_LOGIN` / `XWS_LOGIN_REDIRECT` 标记）；且**只检测、不引导登录**，更没有扫码流程。
6. **通知只有「可插拔通道」，没有内置发送实现**，产出的是一条 `xws-sku-operator-alert.json`，人得自己去看。
7. **运行时依赖对客户过重**：Node 22 + Python 3（openpyxl/Pillow/python-docx）+ Edge + 小旺神插件 + 管理员权限的调试端口约定。

## 2. 客户侧目标形态（交互形式建议）

### 2.1 形态选择：桌面托盘程序 + 本地控制台，不做云后台

推荐「Windows 桌面程序（托盘常驻）+ 浏览器打开 `http://127.0.0.1:<port>` 的本地控制台」。三条理由：

- 这套系统的本质是**本机浏览器自动化**：它必须用客户本机的 Edge、本机的插件、本机的登录态。
  既然是本机强依赖，做成桌面应用最诚实；云后台只会多一层服务器与网络依赖，却不减少本机要求。
- 运营已经习惯「打开一个网页看表格」，本地控制台的认知成本最低。
- 与现有 CDP Proxy 架构天然契合，不需要重写执行链——业务侧 `skills/` 与 `sop-runtime` 可以原样复用。

### 2.2 界面只留四块

| 区域 | 内容 | 运营要做的动作 |
| --- | --- | --- |
| 状态卡 | 今天该做什么、上次跑完是什么时候、结果在哪（飞书表链接） | 看一眼 |
| 一键按钮 | 「开始今天的工作」/「继续上次未完成的」 | 点一下 |
| 账号体检 | **买家浏览器**（淘宝买家号 ＋ 小旺神插件）与**商家浏览器**（生意参谋 ＋ 千牛/阿里妈妈 ＋ 飞书）**分两组**各自亮灯，另加灰豚、飞书凭据；两组不能合并成一个浏览器 | 红了就点「重新登录」，出二维码 |
| 修复与求助 | 红黄条 + 「一键修复」；修不了时「导出诊断包，发给服务商」 | 点一下 / 复制粘贴 |

**本节只是「留哪四块」的取舍；字段级规格（每块读哪个文件、按钮按状态怎么映射、三种队列脸怎么显示、
阶段清单怎么画）见 `docs/ops/OPERATOR-CONSOLE-INTERACTION.md`。** 两份文档冲突时以那份为准 ——
它写着每个界面元素的真相源，而这份只写着运营要做什么动作。落地上它是五块（多了独立的「进度」块）。

### 2.3 交互隐喻：体检 + 一键，不是配置 + 参数

运营的心智模型是「今天的数据收了吗」而不是「周期参数、批次号、目标表 ID」。
所以所有工程参数必须由系统从一份**极简配置**里解析：店铺名、飞书表链接（粘贴链接而不是填 ID，由系统解析出 token 与 table ID）、
每周一几点跑。界面上不出现 token、ID、manifest、批次号这些词。

### 2.4 运营的一天（目标体验）

早上打开电脑 → 托盘气泡与飞书消息：「本周数据将在今天 9:00 开始收集，无需操作」→
9:00 系统自检（Edge、代理、三盏登录灯）→ 全绿则自动采集，运营什么都不用做 →
跑完飞书收到「本周完成：新增 300 条，已同步到历史总表」→
若红灯：飞书收到「小旺神登录已失效，请打开本地控制台点『重新登录』扫码」，运营点一下扫码即恢复，系统自动续跑。

## 3. 四块重点需求的改造方案

### 3.1 登录态统一检测（淘宝 / 小旺神 / 生意参谋）

**做法**：把现有 `xws-sku-auth-preflight.mjs` 的检测模式抽成一个通用的「账号体检」模块，为每个平台各写一份登录标记。

- 检测载体仍是 CDP：开一个后台标签（或复用），注入表达式读页面文本与可见弹窗，不截图、不猜测。
  **检测必须按浏览器分组进行**：买家链的标记只能在买家 profile 的端口上查、商家链的只能在商家 profile 上查。
  否则会得出「已登录」而实际登的是另一个账号 —— 这正是 `ACCOUNT_MISMATCH` 要拦的形态。
- 每个平台的判定要各自写死并各配一组离线用例：
  - 淘宝：登录页/扫码页特征 + 顶栏昵称存在性；
  - 生意参谋：`sycm` 域名下的登录跳转与权限提示；
  - 小旺神：沿用已有的 `XWS_LOGIN` / `XWS_LOGIN_REDIRECT` / 可见登录弹窗。
- 输出沿用现有三值语义：`AUTH_READY` / `AUTH_REQUIRED` / `AUTH_UNKNOWN`。
  **必须保留 `AUTH_UNKNOWN`**——探测拿不到确定结论时不许当成「已登录」（这是本项目一贯的 fail-closed 口径）。
- 飞书凭据有效性也纳入体检（调一次只读接口），因为它同样是「客户能自己修」的那类问题。

**一个重要提醒**：登录态失效在客户环境里是**高频事件而非异常**，而且**与关不关机无关**——
主因是凭证自然过期、同一个浏览器配置被别的账号登录、以及平台侧风控。
2026-09-15 更正：此前这里写「千牛会顶掉 Edge 的买家账号登录态」，是从
`runtime/daily-report-2026-09-13.md` 问题 #3 概括来的，但原文的事实是
**「调试时同一个 Edge 用户配置里登过商家账号，把买家账号挤掉了」**，不是「千牛客户端在后台踢人」。
正确口径与四层检查设计见 [`LOGIN-STATE-MANAGEMENT.md`](LOGIN-STATE-MANAGEMENT.md)。
这条把「登录检测 + 提醒 + 一键重登」从「锦上添花」提升为**P0**：没有它，系统每周都会失败一次而客户不知道为什么。

### 3.2 扫码登录与账号统一管理

**建议：扫码为主，不承诺「系统内输入账号密码代登」。** 三条理由，必须提前与客户讲清：

1. 平台侧：淘宝/生意参谋的账密登录基本会触发短信、滑块或风控，程序化代填成功率低且易触发封禁；
2. 原则侧：README §2 明确把「绕过登录、验证码、风控」列为非目标，代填凭据会踩到这条边界；
3. 安全侧：一旦系统持有账密，它就成了凭据保管者，客户电脑的安全责任会整个转移过来。

**可行的扫码流程**（复用现有骨架）：

1. 体检发现 `AUTH_REQUIRED` → 控制台对应灯变红并给一个「重新登录」按钮；
2. 点击 → 系统用同一 Edge profile 打开**可见窗口**到该平台登录页（`diagnose.mjs` 已有 `reopen_login_window` 动作）；
3. 运营用手机对着屏幕扫码（或在窗口里自行输入，系统不接触输入内容）；
4. 系统轮询同一套登录标记，检测到 `AUTH_READY` → 关闭该窗口 → 把 `PAUSED` 的运行**自动续跑**；
5. 超时未登录成功 → 保持红灯 + 发飞书提醒，不静默重试。

**账号统一管理（单机单店铺简化版）**：不需要多账号切换。需要的只是
「一个店铺 = **两个** Edge profile（买家 ＋ 商家）＋ 各自的平台账号」的登记，以及一个**只存标识不存密码**的配置项（店铺名、账号昵称）。
两个 profile 不是设计洁癖：**卖家版账号用不了小旺神**（商家号登录看不到别家商品详情页），
而生意参谋/千牛/阿里妈妈又必须商家号，一个 profile 只能是一个淘宝身份，合并必然有一侧静默失效。
真正的凭据留在浏览器 profile 里，与现在一致——这条不要为了「统一管理」而破例。
权威归属表见 [`PROJECT-BROWSER-AND-PORTS.md`](PROJECT-BROWSER-AND-PORTS.md) §1.3。

### 3.3 飞书提醒

现有 `notifyOperator(command, alert)` 已经是通用口径（外部命令 + stdin 收 JSON），缺的是**内置发送实现**与**分级**：

- 新增 `runtime/notify-feishu.mjs`：用自建应用消息接口（或群机器人 webhook）把 alert 渲染成人话。凭据沿用现有飞书应用配置。
- 三级模板，**只在需要人动手时打扰人**：
  - 需要立即处理（登录失效、风控页、下载失败）→ 直达消息 + 一句「点这里重新登录」；
  - 仅知会（今日完成、新增 N 条、有 M 条待补）→ 汇总一条，避免逐条刷屏；
  - 无法自愈（页面改版、权限变更）→ 带诊断摘要 + 「已导出诊断包」。
- 去重与恢复通知**已有实现**（`DEDUPED` + `recovered`），继续沿用：同因不重复轰炸，恢复时补一条「已恢复」。
- 发送失败不能影响主流程：现有 alert 已把 `delivery.status=FAILED` 写进证据文件，保持这个做法。

### 3.4 傻瓜修复（本轮最关键的体验目标）

把「修复」拆成三档，并明确每档的边界：

**档 1 · 自愈（运营无感）**
Edge 未启动 → 拉起；CDP Proxy 未运行 → 启动；标签页被顶掉/关闭 → 重建；
短时超时 → 按预算重试；进程崩溃 → 用已实现的 stale 回收接管续跑（PHASE-ARCHIVE §13.7 的 `reclaimStale` + 续跑）。
自愈必须记一条「今天自动修过什么」，否则失败时会无法复盘。

**档 2 · 一键（运营点一下）**
重新登录（扫码）；启用/重装小旺神插件；重置浏览器 profile；清理锁文件与临时目录；重启运行时。
每个按钮后面是一条**幂等脚本**，点两次不会产生两份副作用。

**档 3 · 报障（必须人工，但要「零沟通成本」）**
平台页面改版导致选择器失效、账号被风控、飞书权限变更——这类**自愈做不到**，
所以要让「求助」变得极简：一键导出**诊断包**（版本号 + 最近 3 次运行回执 + 关键日志 + 出错的页面截图），
并给出「复制并发送给服务商」的按钮。现有回执与证据体系（receipt / evidence / manifest）**正好就是最小充分证据**，
不需要另造一套。

**为什么这三档能实现「无需技术人员返工」**：本项目所有失败都已经走「确定性分类」而不是靠人读日志
（`diagnose.mjs` 的 7 类签名 + `POLICY_DENIED` / `HUMAN_REQUIRED` / `TRANSIENT_EXTERNAL` 分类）。
把分类结果映射成「三档处置」是接线工作，不是重新设计。

## 4. 改造项清单与优先级

P0 = 不做就不能交付给客户；P1 = 决定客户能否独立用下去；P2 = 规模化与降低长期返工。

| 优先级 | 改造项 | 做什么 | 复用什么 | 主要风险 |
| --- | --- | --- | --- | --- |
| **P0-1** | 打包与安装 | Node/Python 依赖随包、**内置 CDP Proxy**（现在在仓库外）、统一管理 Edge 启动方式与 user-data-dir、插件安装引导、首次运行向导、凭据输入向导 | `.env.example` 的变量清单；`edge-isolated` profile 实践 | Edge 启动参数与调试端口约定必须在客户机上稳定复现，否则全线不可用 |
| **P0-2** | 常驻服务 + 定时 | 托盘常驻、开机自启、按周定点触发、崩溃后自动接管 | `sop-runtime` 状态权威 + stale 回收 | 不能让定时器与手动触发并发跑同一店铺（写恒 1 的 lane 约定要保住） |
| **P0-3** | 本地控制台 | §2.2 的四块界面（落地为五块，含独立「进度」块）；状态从运行时读，不自己造状态。字段级规格＝`OPERATOR-CONSOLE-INTERACTION.md` §2/§5.1 | `run-faq-operator --status` 的只读检查模式；`round-runner --show-plan`（「今天该做什么」） | 界面不得成为第二份状态真相；且**现在没有统一运行清单**，所以一期只能逐链适配，不许先抽一个「通用运行适配器」 |
| **P0-4** | 三平台登录体检 + 扫码登录 | §3.1 / §3.2；含 `AUTH_UNKNOWN` 与 `ACCOUNT_MISMATCH`（登录了但登错账号）——**注意这两个目前只在文档里，代码 `classifyAuthSnapshot` 还没实现**；交互规格＝`OPERATOR-CONSOLE-INTERACTION.md` §3 | `xws-sku-auth-preflight` + `reopen_login_window` 动作；四层检查设计见 `LOGIN-STATE-MANAGEMENT.md` | 凭证过期与「同配置被别的账号登录」导致的高频失效；判据需实测采集并随平台改版维护；**日报主链目前零登录判定**（`skills/sycm-alimama-daily-report/scripts/`），不补则灯全绿也会卡死 |
| **P0-5** | 飞书通知内置实现 | §3.3，三级模板 + 去重 + 恢复 | `notifyOperator` 通道 + 已有 dedup | 自建应用消息权限需提前申请 |
| **P0-6** | 一键诊断包 | 打包版本+回执+日志+截图，一键导出与发送 | receipt / evidence / manifest | 诊断包内不得含凭据与 Cookie（要显式过滤） |
| **P1-1** | 自愈执行器接线 | 把 `diagnose.actions` 的 5 个动作接上真实实现 | `actions.mjs` 白名单 + 预算 | 动作要幂等；预算上限别调太高 |
| **P1-2** | 人话指引库 | 每类故障对应 1-3 步图文指引 + 一个按钮 | `remedy` 文本 | 文案要运营看得懂，禁止出现 token/ID |
| **P1-3** | 配置向导 | 粘贴飞书表链接自动解析 token/table ID；店铺与周期向导 | 现有 CLI 参数面 | 解析失败要有明确提示，不能静默 |
| **P1-4** | 进度可视化 | 「今天跑到哪、还差什么、上次为什么停」 | `sop-runtime` 的阶段与 blocker | 不要暴露内部术语 |
| **P2-1** | 自动更新 | 客户端版本与能力热更新、回滚 | manifest / registry 版本机制 | 更新本身要有回滚路径 |
| **P2-2** | 远程协助 | 运营授权后远程查看状态（可选） | 诊断包 | 隐私与授权必须显式 |
| **P2-3** | 运行历史归档 | 每期结果在本地留档，可回看 | 现有 evidence 目录 | 磁盘占用与清理策略 |

**依赖顺序**：P0-1 与 P0-2 是地基（没有它们，界面与体检都无处安放）；
P0-4 与 P0-5 可以与前两者并行开发（模块相对独立）；
P0-3 依赖 P0-2 的服务化；P0-6 依赖 P0-3 的界面放按钮。

## 5. 必须提前明确的边界

1. **不做账号密码代登**（理由见 §3.2）。如果客户坚持，需要先书面确认风险与合规责任。
2. **页面改版不可自愈**。平台样式一变，任何客户端都修不了自己——只能靠「报障 → 服务商更新适配器 → 热更新」。
   这是这套技术的固有属性，不要对客户承诺「永远不会找你们」。
3. **「无需技术人员返工」的可行边界**：登录态类、环境类（浏览器/代理/插件）可以做到接近 100% 自助；
   页面改版类、风控类做不到。把这条写进交付说明，比事后解释便宜得多。
4. **凭据仍留在浏览器 profile 里**，系统只存标识。这是当前架构的正确决定，不要为了「统一管理」而集中保管密码。
5. **单机单店铺可以不做完整 Browser Broker**，但需要它的最小子集：
   「**两个 profile 各自**的会话检查 + 人工接管入口 + 会话租约」。注意是**两个**：买家 profile 与商家 profile
   各有独立的调试端口、独立代理、独立登录态，「一个 profile 一条会话」的写法会漏掉另一半。
   明确下来，避免以后重做。
6. **运维面仍是硬缺口**（见 PRODUCTION-READINESS §2.3）：交付给客户意味着要能远程判断故障，
   而目前没有监控与备份恢复。§3.3 的飞书提醒与 §3.4 的诊断包，实际上就是这个场景下**最小可行的可观测性**——
   建议按这个思路推进，而不是先上通用监控系统。

## 6. 建议的实施顺序

1. **先做地基**：P0-1 打包安装 + P0-2 常驻定时。这两项做完，客户至少能「装好、到点自动跑、坏了停下来」。
2. **再做可感知**：P0-5 飞书通知 + P0-4 登录体检与扫码。做完这一步，客户在遇到最常见故障（登录失效）时已经能自己恢复。
3. **然后做界面**：P0-3 本地控制台 + P0-6 诊断包。这一步把「命令行」彻底替换成「点按钮」。
4. **最后做打磨**：P1 全部。到这一步才谈得上「不懂技术的人可以独立操作」。

第 1 步不依赖任何架构决策即可开工；第 2 步需要先确认飞书应用的消息权限；
第 3 步开始前建议先定一下「界面只读运行时状态」这条边界怎么落到代码里（避免长出第二份状态真相）。

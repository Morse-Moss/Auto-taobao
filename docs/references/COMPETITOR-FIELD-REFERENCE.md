## 1 先回答「外形、安装方式、功能、风格是怎么推到的」

**由飞书侧的 AI 字段提示词推导，不是自动化链的一环。**

推导规则（五个属性字段共用同一套骨架）：

1. 先看 `是否有效竞品`：不是「是」就输出「不适用」，不分析。
2. 只从 `商品标题` 里**明确写出的文字**取标签（`功能` 额外允许看 `卖点`）。不凭图片猜、不凭常识补、不推断。
3. 命中后**归一化到受控词表**（例如「长方形」→方形、「冲浪」→按摩、「现代简约」→极简、「靠墙式」→靠墙）。
4. 标题里没有明确证据就输出「无注明」；多个值用中文顿号分隔。

这与运营最原始的需求（「根据标题里的文字识别」）一致——**识别是 AI 做的，词表是我们补的**。
逐字段提示词原文见 §6，可直接粘贴回飞书字段；词表与归一化的完整对照见 §7.3；
与运营那张截图的逐项差异见 §7.4。

### 3.1 周表为什么曾经是 35（2026-09-15 已修）

**机制**：建周表的脚本只克隆「可直接复制的字段类型」（`CLONABLE_TYPES`），**19 查找引用 / 20 公式 / 21 双向关联一律不克隆**——它们的 property 里内嵌了具体表/字段 id，照抄上一周就会指向旧表。设计上这两类由 `create-weekly-formula-fields.mjs` 在导入后按**字段名**重写引用再建。

**为什么 08-30 起丢了 4 个**：08-23 那张周表是**直接复制竞品主表**得来的（字段 id 与主表逐一相同，39 字段）。08-30 起改成「克隆上一周 + 二次重建公式」，于是：

- `尺寸` / `适用空间`（Lookup）当时没有任何脚本会重建 → 直接丢；
- `数据状态` / `待补数据项` 的表达式里引用了 `尺寸` / `适用空间` → 重写后仍残留旧表引用 → 被脚本判为 `unmapped refs remain` 而 `DEFERRED` → 一并丢；
- `当前周状态` 08-23 本来就没有（当时主表还没这一列），克隆链把缺失一路继承下来。

**实测差异（以主表 36 为基准）**：周表缺 `尺寸`、`适用空间`、`数据状态`、`待补数据项`、`SKU采集明细`、`当前周状态`；周表多 `商品周期唯一键`、`数据开始日期`、`数据结束日期`、`采集时间`、`主表记录ID`。

**2026-09-15 的修法（三段）**：

1. 建周表的**基准表改成竞品主表**（不再是上一周），5 个周表专有列显式声明 → 缺失不再沿克隆链继承；
2. `create-weekly-formula-fields.mjs` 增加 **19 查找引用**的重建（`property.formula` 按字段名重写到新表），并且**先建 Lookup、再建公式** → `数据状态`/`待补数据项` 不再被 DEFERRED；
3. `SKU采集明细` **刻意不在周表上重建**：21 的 property 带 `back_field_name`，在周表上再建一次会给「SKU明细」多生成一个反向字段、与主表那个冲突；而且一条 SKU 记录归属于主表的一条商品，不归属于某一周。

修完的周表 = **40 = 主表 36 − 1（`SKU采集明细`）+ 5（周表专有）**。

**影响**：周表上现在有「待补数据项」「数据状态」两个提示字段。注意 `尺寸` / `适用空间` 在周表上同样是从 SKU 明细汇总来的，本周还没做 SKU 汇总时它们是空的 → 「待补数据项」会稳定地报出这两项，这是**正确**行为，不是字段出错。

## 5 公式字段的可读参考公式

> 原始表达式每个 2,500 ~ 8,200 字符（`待补数据项` 最长 8,176），**不能手抄**：公式里每个字段引用都写死了
> `bitable::$table[<当前表id>].$field[<当前字段id>]`，换表就失效。原始表达式见
> `evidence/competitor-live-formulas-kcne-20260915.json`；
> 生成器是 `buildCompetitorFieldMigrationPlan()`（`skills/xws-to-feishu-base/scripts/competitor-v2-core.mjs`）。

下面把字段引用写成人话，等价于线上逻辑。

### 5.1 前置闸门（下面每个公式的第一步都是它）

```
有效闸 = AND(标题含浴缸类词, NOT(标题含非浴缸词), OR(标题含主体词, AND(NOT(标题含主体词), NOT(含服务词), NOT(含配件词), NOT(儿童+便携))))
```

- 浴缸类词：`浴缸` `浴桶` `浴盆` `洗澡盆`
- 主体词：`成人` `大人` `老人` `独立式` `嵌入式` `靠墙式` `深泡` `可移动`
- 非浴缸词：`洗脚池` `洗脚盆` `泡脚盆` `足浴` `宠物` `狗洗澡` `猫洗澡` `婴儿` `新生儿`
- 服务词：`上门安装` `维修服务`
- 配件词：`龙头` `花洒套装` `角阀` `下水器` `排水器` `盖板` `扶手` `靠枕`
- 儿童+便携：同时含 `儿童` 与（`浴盆`|`澡盆`|`折叠`|`充气`|`便携`）

### 5.2 逐字段

| 字段 | 可读逻辑 |
| --- | --- |
| 是否有效竞品 | `IF(非浴缸词, "否", IF(主体词, IF(浴缸类词,"是","待确认"), IF(服务词,"否", IF(配件词,"否", IF(儿童+便携,"否", IF(浴缸类词,"是","待确认"))))))` |
| 排除原因 | `IF(非浴缸词,"非浴缸主体", IF(主体词,"", IF(服务词,"服务类", IF(配件词,"浴缸配件", IF(儿童+便携,"非浴缸主体","")))))` |
| 月收货人数计算值 | `IF(NOT(有效闸),"", IFERROR(VALUE(SUBSTITUTE(月收货人数,"+","")),""))` |
| 计算口径 | `IF(NOT(有效闸),"", IF(RIGHT(月收货人数,1)="+","下限值", IFERROR(IF(VALUE(月收货人数)>=0,"精确值","不可计算"),"不可计算")))` |
| 月收货金额 | `IF(OR(NOT(有效闸),ISBLANK(价格),月收货人数计算值=""),"", 价格*月收货人数计算值)` |
| 客单价带分类 | `IF(OR(NOT(有效闸),ISBLANK(价格)),"", IF(价格<1000,"1000以下", IF(价格<3000,"1000-3000", IF(价格<6000,"3000-6000", IF(价格<8000,"6000-8000","8000以上")))))` |
| 竞品分类 | `IF(OR(NOT(有效闸),ISBLANK(价格)),"不适用", IF(AND(月收货人数计算值>=80, 月收货金额>=200000),"A-爆款竞品", IF(AND(FIND("人造石",材质分类)>0, 月收货人数计算值>=10),"B-高价值竞品", IF(价格>=8000,"C-差异化竞品", IF(价格<1000,"D-价格/流量型竞品","无分类")))))` |
| 待补数据项 | `IF(NOT(有效闸),"", IF(缺项文本="","", LEFT(缺项文本,LEN(缺项文本)-1)))`；缺项文本 = 对 8 个字段逐个 `IF(空 或 =无注明 或 =不适用, "<字段名>、", "")` 再 CONCATENATE：月收货人数精确值、材质分类、外形、安装方式、功能、风格、尺寸、适用空间 |
| 数据状态 | `IF(NOT(有效闸),"", IF(待补数据项="","可用","部分待补"))` |

**关键设计约束**（踩过坑）：下游公式不引用 `是否有效竞品` 本身，而是复用「有效闸」这个布尔表达式。
在线上表里让公式字段链式依赖公式字段会造成依赖不收敛。

### 6.3 安装方式

## 7 归一化规则与确定性推导

### 7.1 材质分类有确定性规则（唯一一个）

`selectFirstMaterial(商品标题)`（`runtime/competitor-visualization-core.mjs`）：
在标题里找最早命中的材质词，同位置取更长的；PMMA / 高分子 / 绮美石 / 可丽耐 / 杜邦石 / 亚克力人造石
**全部归一为「人造石」**（所以「亚克力人造石」判为人造石，不是亚克力）；无命中输出「无注明」。

效果校验（2026-09-15 只读实测，`diagnose-material-derivation.mjs`）：在 08-23 周表 791 条可比对行上，与人工/AI 已存值
**一致率 742/791 = 93.8%**；推导出「人造石且人数≥10」共 8 条，与该周 B 类的实际条数 **8 完全一致**。

**粒度差异（重要，别把 93.8% 读成「几乎全对」）**：已存真值是**多值**（如 `人造石,透明`、`陶瓷,铸铁,搪瓷`），
而确定性推导只给**最早命中的单一材质**。剩下的 6.2% 不一致里，主要就是这类「已存多值 vs 推导单值」，
以及 `不适用 → 无注明`（占位值差异）。所以准确说法是：**在「首个材质」这个粒度上一致率 93.8%**。
若将来要完全对齐人审，需要给 `selectFirstMaterial` 加「输出全部命中材质」的模式。

### 7.2 外形 / 安装方式 / 功能 / 风格 没有确定性规则

它们的值只能来自 AI 或人工，**没有任何自动化写入方**（周表尤其如此，见 §8.1）。
唯一带真实值的那张周表（08-23）里这四列的值来自飞书侧 AI/人工，随整表迁移带过来；
竞品主表里这四列也有已存值，但主表的写入方是「哨兵值」而非分类（见 §8.2）。
各表属性列的实际覆盖情况用 `runtime/diagnose-classification-coverage.mjs` 现查（只读），本文不引用易过期的具体计数。

### 8.3 源码字段定义与线上有两处漂移 → 已处理（2026-09-15）

| 位置 | 源码说 | 线上实测 | 处理 |
| --- | --- | --- | --- |
| 材质分类/外形/安装方式/功能/风格 | 多选(4) | **文本(1)** | 生成器按**线上类型**分流：多选用 `CONTAIN`、否则用 `FIND`；选项更新只对真正的多选发 |
| 尺寸/适用空间 | 尺寸=文本、适用空间=多选，且都是 AI 字段 | **都是 Lookup(19)** | 生成器把 Lookup 当**可读不可写**：公式照常引用，记录写入计划与选项更新一律跳过 |

原来的后果：`buildCompetitorFieldMigrationPlan()` 无法对竞品主表运行，抛
`Unsupported AI field type for 尺寸: 19` → 依赖它的 `migrate-competitor-v2-analysis.mjs` 在现表上被 fail-closed 挡住。

现在：`assertSupportedAnalysisFieldType` 放行 `Lookup(19)`，由 `describeCompetitorAnalysisFields()` 把「声明类型 / 线上类型 / 是否可写」三者分开；
`writable === false` 的字段只出现在公式引用里，**不出现在任何记录写入计划里**。真正不支持的类型（日期/复选框/附件/数字）仍然抛错。

两条**仍未处理**的遗留：

- 线上 `竞品分类` 的 B 段是 `FIND("人造石",[材质分类])>0`，**没包 `IFERROR`**（材质为空/「无注明」时报错）；生成器目前也照这个写法生成，是否加容错尚未拍板。
- 五个属性列线上是**文本**、源码声明是**多选**，`COMPETITOR_MAIN_FIELDS` 仍是多选 → 新建主表会与现表不一致（只影响全新建表，不影响现表运行）。

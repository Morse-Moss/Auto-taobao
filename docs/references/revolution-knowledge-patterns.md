# Revolution 知识库参考模式

本文件迁移的是 Revolution 已验证有效的知识组织方法，不复制其项目事实。`sycm-automation` 的事实仍只由本项目源码、测试、运行记录和验收证据确认。

## 1. 项目知识六段式

来源模式：`E:\Revolution\content\site-content.json` 中各项目的 `summary / ownership / knowledgeTopics / implementation / evidence / boundaries`。

本项目采用以下本地结构：

1. 项目定位：为谁解决什么问题。
2. 工作流：输入、处理、输出和人工接管点。
3. 技术实现：浏览器控制、状态机、数据合同和文件校验。
4. 个人贡献：本人实际负责的设计、实现、测试和运行工作。
5. 验证证据：真实运行、离线测试、截图和工件分别记录。
6. 能力边界：未验证、未来计划和禁止表述单独列出。

落地位置：`docs/project-knowledge.md`。

## 2. 证据强度分级

来源模式：`E:\Revolution\content\chat-evidence-catalog.json` 中的 `direct / transferable / unavailableBoundary`。

- `direct`：本项目源码、测试或真实运行直接证明。例如 1-40 页小旺神运行与 1333/1343 行文件校验。
- `transferable`：其他项目证明通用工程能力，但不能证明本项目已完成。例如 Revolution 的 RAG 或生产部署经验可证明个人背景，不能写成此项目能力。
- `unavailable`：当前证据没有证明，必须显式拒绝。例如长期无人值守、绕过风控、所有类目稳定或业务增长效果。

简历与项目介绍优先使用 `direct`；只有解释个人通用能力时才使用 `transferable`；`unavailable` 不进入完成态文案。

## 3. 运行证据与产品事实分离

来源模式：`E:\Revolution\docs\research\project-evidence-matrix-2026-07-13.md`。

- 截图只能证明截图时可见的界面状态，不能代替完整链路验收。
- 测试通过只证明测试合同，不自动证明真实平台、账号和网络环境稳定。
- 一次真实运行只证明该次输入、会话和时间窗口，不承诺未来登录持续或页面结构不变。
- 外部实时数据两次结果不同不等于失败；只要单次数据内部一致且来源状态明确，应保留差异并解释。
- 真实数字必须带证据路径；计划和方向必须明确写成未完成。

## 4. 对当前项目的具体影响

- README 只做导航，详细事实进入项目知识文件，避免说明文档持续膨胀。
- Skill 继续承载可执行流程和安全边界，知识文件不重复选择器或命令实现。
- `evidence/` 保存可复核的验收输出，`runtime/` 保存过程证据；两者不作为实时输入。
- 后续每个稳定里程碑补一份结构化回执，至少记录输入、运行时间、状态、行数、字段、文件哈希、人工接管情况与未验证项。

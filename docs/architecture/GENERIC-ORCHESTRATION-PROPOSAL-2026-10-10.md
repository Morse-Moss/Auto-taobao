## 1. 第一性原理：机械执行 vs 业务策略

### 1.1 机械执行机制 —— 已有实现（复用，不重写）

| 机械能力 | 已有实现（唯一来源） | 现状 |
| --- | --- | --- |
| 批次启动与释放 | `runtime/batch-plan.mjs` 的 `planBatches` / `buildBatchSteps` / `releaseAfterBatch` ＋ `scripts/start-all.mjs` / `stop-all.mjs` | **已落地**，生产在用 |
| 店铺隔离 | `runtime/browser-ports.mjs`（一店一实例一代理）＋ `batchOnlyArgs(batch)`（起、挂、跑、停**四段共用同一份名单**） | **已落地** |
| 锁 | `runtime/workflow-lock.mjs`（`WORKFLOW_LOCK_NAME`，带过期回收与留痕） | **已落地**（`run-daily-job` / `run-product-data-job` 用） |
| 日志与证据目录 | 各宿主自建 `logFd` ＋ `evidence/<链>-<日>/` | **已落地**，但**形状不统一**（§5.2） |
| 收据 | `runtime/workflow-receipt.mjs`（`run-receipt.json`）／`batches.json` | **已落地**，但**两种形状** |
| 失败隔离 | ① 批次内逐店 try/catch（`run-promotion-sales1.mjs:74-86`：一家失败记 `record.error`、**继续下一家**）；② 链的 `--keep-going`；③ 驻留＋按批重跑（`hold-and-resume.mjs`） | **已落地** |
| 飞书幂等写入 | 各能力的字段映射 ＋ 幂等键（`promotionIdempotencyKey` 等）＋ **写后独立回读** | **已落地** |
| 只打印 / 排练 | 每个入口的 `--print` / 默认不 commit | **已落地**（`run-product-data-job.mjs` 没有 `--print`，属欠账） |
| 告警出口唯一化 | 各宿主各写一遍（`--notify` / `--notify-print` 互斥） | **重复实现 3 份**（§5.2） |

**结论**：机械执行这一层，**九项里八项已经在跑**。所以「复用」的正确答案是
**「照着现有入口用」，不是「再造一层」**。

### 1.2 业务策略 —— 留在各流程（不许进公共层）

| 业务策略 | 属于谁 | 具体是什么 |
| --- | --- | --- |
| 阶段顺序 | 各链自己 | 日报 11 步；推广＝提交关键词/人群 → 取件 → 导入 |
| 报表参数 | 各链自己 | 推广：`rptType`、`effectEqual=30`、`granularity=day`、`bizCodeIn`、`queryDomains` |
| 目标表 | 各链自己 | 日报底单／数据日报；推广 `10月推广数据-销售1部` 的 `商品推广数据底单` |
| 数据校验 | 各链自己 | 日报：行数/字段/归属/回读；推广：`validateExportRows`（列数允许集、日期、场景） |
| 维度与筛选口径 | 各链自己 | 推广：关键词维度＝`word,date,campaign,adgroup`；人群维度＝`主题、时间、计划` |

**这条边界是本次评审最重要的一句**：机械执行**可以**抽；上面这五类**永远不抽**——
它们一进公共层，公共层就开始认业务，那时它既不是通用层、也不再是业务层。

## 4. P0 的逐店验证清单（把架构师的四项落成可勾选）

共用入口（口径：**5 家一批、顺序跑完整 8 家**）：

```text
node scripts/run-batches.mjs --workflow promotion-daily --date <目标日> --batch-size 5 [--commit]
# 8 家 ⇒ 第 1 批 5 家（里可林淘宝、网林天猫、盖文淘宝、盖文天猫、科塔淘宝）
#         第 2 批 3 家（网林淘宝、里可林天猫、网林家居）
```

逐店四项判据（**每一项都要落到文件，不许只写"通过"**）：

| # | 项 | 判据落到哪 | 绿的条件 |
| --- | --- | --- | --- |
| V1 | 关键词 ZIP | 每店证据目录里的 `keywordZipPath`（驱动打印的 `[下载] keywordZipPath = …`） | 文件存在、列数落在允许集（75 或 77）、日期列＝目标日、场景列∈`{onebpSearch, onebpDisplay}` |
| V2 | 人群 ZIP | 同上 `audienceZipPath` | 文件存在、列数落在允许集（71 或 75）、日期＝目标日、场景同上 |
| V3 | 日期与场景 | `promotion-daily-report-core` 的两个 `validate*ReportState` 的原始输出 | 页面 href 与 `rptType`、`startTime/endTime`、`effectEqual=30` 全部命中；`day` 粒度命中 |
| V4 | 飞书写入与**回读** | 导入器收据（dry-run / apply 两种模式）＋ **独立回读**结果 | 幂等键命中（不是"新增了一行"）；回读到的字段值与 ZIP 一致；未知列被字段映射过滤掉而不是报错 |
| V5 | 失败隔离 | `run-promotion-sales1.mjs` 的逐店 `record.status` / `record.error` ＋ `batches.json` 的 `rounds[].chainStatus` | **故意让一家失败**（例如先停掉它的实例），其余 7 家仍应 `status: ok`，且 `batches.log` 里能看到那家被点名、后面的店照常跑 |

**V5 是这四项里唯一需要"制造失败"的一项**，而它恰恰是架构师点名的「检查失败店铺是否能隔离而不阻塞其他店」。
做法建议：先跑一遍全绿的（V1–V4），再**单独停掉某一家**的实例重跑一次，观察其余 7 家是否照常完成。

## 5. P2：小范围抽取（什么时候才允许抽、抽哪一块）

### 5.1 允许抽取的四条判据（缺一不可）

1. 同一语义在 **≥2 处**有实现；
2. 这 ≥2 处目前**逐字一致**（或差异是**已记录的**、不是漂出来的）；
3. 每一处都有**≥2 条**用例能断言它（抽走了要能把用例一起搬走）；
4. 连续 **N 轮真机**运行里，这一块**没有出现过分歧**。

### 5.2 候选清单（按证据强度排序，**都不是现在做**）

| 候选 | 重复处数 | 现在能不能抽 | 说明 |
| --- | --- | --- | --- |
| 告警出口唯一化（`--notify` / `--notify-print` 互斥，且"不给就不许有任何东西发出去"） | 3 份 | **优先候选** | 纯口径、零业务、语义逐字一致；且它与「对外发送要先拿授权」这条铁律直接相关 |
| 证据目录 / 日志写出 / 收据写入 | 3–4 份 | 中期候选 | 但**收据有两种形状**（`run-receipt.json` vs `batches.json`），先决定统一到哪一份，否则抽取＝改生产行为 |
| 退出码口径（只有"续跑成功"能把整轮翻绿） | 2 份 | 中期候选 | `run-daily-job.mjs:371` 与 `run-batches.mjs:457` 逐字同源 |
| 切批（`planBatches` / `buildBatchSteps`） | 已在公共层 | **不需要抽** | v1 想做的这块**已经做完了** |
| 阶段顺序 / 报表参数 / 目标表 / 校验 | 各链独有 | **永远不抽** | 见 §1.2 |

### 5.3 P3 三块的触发条件（写下来，免得将来"顺手就做了"）

| 块 | 触发条件 |
| --- | --- |
| 资源管家（申请/交还） | 出现**第二个并发消费方**，且已实测到"串过一次店"或"两轮抢同一实例"；或出现**跨机**消费方（那时 lane 锁才需要从文件迁到 PG） |
| 作业单 | 出现**第四条**需要"多店铺 × 多阶段 × 起停实例"的链，且前三条的阶段顺序已能被逐个命名为独立阶段 |
| 统一外壳 | §5.2 的候选**抽完 ≥2 块**之后——先把能抽的抽干净，再谈"壳" |

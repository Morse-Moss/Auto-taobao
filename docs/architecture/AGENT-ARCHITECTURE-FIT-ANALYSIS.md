# Agent 架构适配性分析（第一性原理）

日期：2026-09-16
问题：这个系统到底适合哪一种架构？「不需要 Temporal」这个说法成立吗？
方法：不比较框架特性。先把这个系统的**不可变事实**定下来，架构形状由它们推出来；再把 Temporal 的能力逐条对到这些事实上，看哪些是真需求。

配套阅读：`docs/ops/AGENT-ROLLOUT-STATUS-AND-REMAINING-PLAN.md`（现状对账与剩余步骤）、`docs/architecture/README.md` §4.2/§4.3/§5、`SUPERVISOR-AGENT-DESIGN.md` §9/§10/§11。

---

## 1. 四个不可变事实

**F1　单一物理出口，有效并发上限 = 1。**
一个淘宝账号、一个浏览器 profile、一个 Edge 实例。这不是配置问题，是账号风控的物理约束。
证据：`docs/architecture/README.md` §4.3 Browser Broker「保证同一账号/profile 的互斥使用」；`SUPERVISOR-AGENT-DESIGN.md` §9 S4「**同一浏览器/profile 仍遵守并发 1**」；`runtime/sop-runtime/fanout.mjs:9`「并发是显式决定：**默认并发 1**，只有拿到资源容量证据才通过 limits 放宽」。
⇒ 推论：**加 worker 不会提高吞吐。** 提高吞吐的唯一途径是减少对出口的占用（更好的重试、更少的失败重跑）。

**F2　外部副作用不可回滚。**
飞书写进去的行、导出的文件、推进的游标——没有「撤销」。错一次就是错在真实数据上。
证据：README §5 的证据链要求 `Idempotent Commit` 才有权推进业务状态或游标；`Publication Receipt` 必须含外部回读结果。

**F3　正确性由「外部可回读的事实」定义，不由「编排记忆」定义。**
证据：`commit-before-response` 的正常处置是「只产生一个业务效果，或稳定进入对账」；`reconcileUnknown` **只对账、不重试**；跨进程故障注入 **15/15 是走 PostgreSQL 路径**跑通的（子进程被杀 → 另一进程收回过期 lease → 从游标 10 续跑到 20），而不是走 Temporal。

**F4　流程数量少、拓扑浅。**
2 条主 SOP（竞品周更、关键词周更）+ 6 条已接线能力；控制流是「线性 + 浅分支 + 一层 fan-out」。没有 saga，没有动态 join，没有跨流程补偿。
证据：`agent-sop-runtime-implementation-plan.md` 第 5 节 7 条流程；`fanout.mjs` 只做到 FAQ 商品级一层。

## 2. 由 F1-F4 直接推出的三个结论

**C1　编排引擎的持久化能力，不是正确性的组成部分。**
这是最关键的一步。Temporal 的核心卖点是「用事件历史重放恢复执行状态」。但 F3 已经把正确性外包给了「游标只在回读证据上前进」+「幂等提交账本」。
⇒ 引入 Temporal 的收益是「恢复更快、编排代码更干净」，**不是「更正确」**。而这两点在当前收益都小：流程只有 2 条，恢复路径已经能跑，而且有真实证据。

**C2　并发上限由物理出口决定，不由编排层决定；需要的是互斥，不是调度。**
⇒ 「多 worker 任务分发」这条采用条件的价值被 F1 抹平。你不是要通过加 worker 扩容，你是要保证**在同一出口上不双写**。互斥的解法是 lease + lane（已有），不是工作流引擎。

**C3　拓扑浅（F4）⇒「复杂重试拓扑无法由 PG + controller 表达」这条采用条件，短期内不会成立。**

## 3. Temporal 能给的东西，逐条对到事实上

| Temporal 能力 | 这里是不是真需求 | 现在的替代 | 替代是否可靠 |
| --- | --- | --- | --- |
| 事件历史重放恢复 | 不是（C1） | PG 游标 + CAS + 幂等账本 | **可靠**（15/15 真实证据） |
| 跨进程 worker 部署与替换 | 不是（C2） | 单一编排进程 | **可靠**（故障注入已验证接管） |
| 长 timer、跨天暂停恢复 | **部分是** | 人工闸门在 PG ✓；**但轮次进度与告警去重在本地 JSON ✗** | **不可靠 —— 真实缺口（G1）** |
| 多 worker 任务分发 | 不是（F1/C2） | lane + lease | 可靠；但限流/熔断计数在进程内（G2） |
| 复杂重试拓扑 / saga | 不是（C3） | `task-queue.mjs` 退避 / 熔断 / 超时清扫 / 取消 | 部分（计数在内存，G2） |
| 可版本化 workflow | 不是 | manifest + semver + `registryDigest` | **可靠** |

⇒ **真实缺口只有两条，而且都是同一个形态：小而关键的状态放错了地方。**

**G1　`round-state.json` 承担了不该由文件承担的权威职责。**
`runtime/sop-runtime/round-runner.mjs:833-834`，生产 CLI 走 `createFileRoundState(resolve(workDir, 'round-state.json'))`（实现见 `:154`）。文件里装 `completed`（哪一轮跑过）、`days`（当天尝试次数）、`openAlert`（**通知去重与恢复的锚点**）。
这**违反 README §5 自己那一行**：「本地 JSON 是缓存或投影，**不得决定业务恢复位置或业务完成状态**」。
`createFileRoundState` 的注释也预见到了后果——「状态文件坏了……那会让『今天已经跑过』的记忆消失，于是同一轮重复写一次」——但它选择抛错，而不是把权威挪走。

**G2　限流与熔断计数在进程内。**
`runtime/sop-runtime/task-queue.mjs:47` 的 `createCircuitBreaker` = 进程内 Map + `Date.now()`。`PHASE-ARCHIVE.md` §9 已记账：「限流/熔断不 durable｜刻意取舍｜跨进程一致的限流需要落库或外置，属独立设计」。

**关键判断：这两条缺口的存在，不构成引入 Temporal 的理由。**
缺口的规模是「一张表 + 两个 CAS」；Temporal 的引入成本是「一个有状态服务 + 一套新的编排语义 + 6 条已跑通能力的重写」。**规模不匹配。** 用 Temporal 补 G1，是拿航母运自行车。

## 4. 「不需要 Temporal」这句话的正确表述

不能笼统说「不需要」。要拆成三句，只有两句成立：

| 说法 | 是否成立 | 依据 |
| --- | --- | --- |
| ① 不需要它来保证正确性 | **成立** | F3：正确性已由 PG + 外部回读承担，且跨进程故障注入是 PG 路径的 15/15 |
| ② 不需要它的调度能力（当前 + 并行多 SOP 阶段） | **成立** | F1/C2：并发受单出口限制，加 worker 无收益 |
| ③ 不需要它管理长时挂起与跨进程进度 | **不成立** | G1：轮次进度与告警去重今天在本地 JSON 上 |

⇒ 正确表述：**「把 G1/G2 补完之后，Temporal 在当前与下一阶段没有需求侧依据。在 G1/G2 补完之前，说『不需要 Temporal』是拿一个缺陷冒充一个决策。」**

这条必须写死，否则「暂不引入」会变成「用一个未修的缺陷顶着一个没做的决策」——那正是这个项目反复栽跟头的形态（见 `LESSONS-2026-09-14_15.md` §1）。

## 5. 那么，这个系统适合哪种架构

第一性原理给出的不是「选哪个框架」，而是**形状**。形状定完后，实现手段几乎没有悬念。

```
                    配置驱动的排期（宿主只负责叫醒）
                              |
                              v
        +-------------------------------------------+
        |   单编排进程 Controller（唯一状态拥有者）    |
        |   Run / Step / Attempt / Lease / Gate      |
        +-------------------------------------------+
          |          |            |            |
          v          v            v            v
     Capability  Capability   Capability   Capability
      (Adapter)   (Adapter)    (Adapter)    (Adapter)
          |          |            |            |
          +----------+-----+------+------------+
                           |
                    物理出口（容量 = 1）
              淘宝账号 + 浏览器 profile + Edge
                           |
          +----------------+----------------+
          v                                 v
   PostgreSQL（唯一权威）            外部回读证据
   业务事实/游标/租约/账本/            飞书回读 / 文件 digest
   编排进度/告警去重/队列状态
```

六条形状约束：

1. **单一权威是 PostgreSQL，不留任何文件态权威。** 业务事实、游标、租约、提交账本、编排进度、告警去重、队列状态，全部落库。（这条直接要求修掉 G1。）
2. **单编排进程 + 容量为 1 的出口。** 并发靠 lane 与 lease **互斥**，不靠 worker 数量。扩容必须基于资源容量证据（`fanout.mjs:9` 已经这么写了）。
3. **能力层是契约，不是脚本。** Capability + manifest + Worker 契约（已有，10 个 manifest）。
4. **监督层是一个共享的确定性监督环 + 一个受限 LLM 分诊器**（见 §6）。
5. **排期层配置驱动，宿主可替换。** 「该不该跑」由配置判定，不绑机器（已有）。
6. **不引入外部工作流引擎。** 除非 §8 的触发条件成立。

一句话概括这个架构：**「单机单出口 + 强权威落库 + 浅拓扑流程」，正确性由外部证据闭环承担，而不是由编排引擎的执行历史承担。**

## 6. 对你选的形态「一条流程一个监督 agent，出错时能自动纠偏」的第一性原理检验

这个方向是对的，但有一处我建议改。理由是三条可验证的事实。

### 6.1 纠偏的价值 90% 在「执行动作」，而那是确定性代码

自动纠偏是三件事：**发现**（监督）→ **判断**（分诊）→ **执行**（处置）。
- 发现：`runtime/supervise-collection.mjs` 已经在做（只播报、不拥有状态、不自愈，四判据：进程死活 / 阶段静止超预算 `SUSPECT_STALLED` / 进度签名不推进 / 持久化证据优先）。
- 判断：`diagnose.mjs` 有 7 类失败签名的确定性映射。**只有模糊分支才需要 LLM。**
- 执行：`--apply` **未接真实动作执行器**——这才是今天真正缺的一环。

⇒ 也就是说：你现在感受到的「不能自动纠偏」，缺的主要是**第三步**，而第三步是确定性代码，不是 agent。

### 6.2 「可纠偏空间」比直觉小，而且可纠偏的那部分本来不需要 agent

把失败模式分成两类：

| 类别 | 例子 | 可自动处置吗 | 手段 |
| --- | --- | --- | --- |
| **可纠偏** | 进程死了、租约过期、下载未到、浏览器掉线、队列饱和 | 可以 | 重跑 / 等租约过期回收 / 重试下载 / 重连 / 退避 —— **全部是确定性动作** |
| **不可纠偏** | 页面改版、风控与验证码、飞书权限变更、数据口径变化、登录失效需扫码 | 不可以 | LLM 也给不出可执行动作，**只能升人工** |

⇒ **「出错时自动纠偏」的真实覆盖面 = 全部失败模式里确定性可处置的那一部分，而它们本来就不需要 agent 来发现或决定。** agent 的增量价值集中在第二类的**分诊与说明**（把「失败了」变成「因为 X，需要你做 Y」），而不在执行。

### 6.3 「一条流程一个 agent」的两个副作用

1. **同构的分诊逻辑会被复制 N 份，然后各自漂移。** 两条 SOP 的失败模式高度同构（都是那 7 类签名）。复制判断逻辑，正是这个项目 28 条坑里反复出现的形态（同一份词表/同一份口径在多处各写一遍，然后不一致）。
2. **隔离性并不会因此提高。** 隔离靠 **lane 与 run 边界**（已有：`laneFor`、`LANE_EXECUTING_STATUSES`、`occupiesLane`、lease），**不靠 agent 实例数量**。两个 agent 抢同一个浏览器出口，该冲突还是冲突。

⇒ **建议形态：一条流程一个 lane（隔离）+ 全局一个监督环和一个分诊器（不复制判断逻辑）。**
如果你要的是「每个流程的监督逻辑能独立演进」，正确做法是给监督环加**流程级判据插件**（数据），而不是复制 agent（代码）。

### 6.4 一条必须先摆上桌的硬约束

「自动纠偏」里凡涉及**外部写**的动作（重发飞书写入、重跑发布段），按项目纪律必须走人工闸门。
⇒ 第一版纠偏闭环的白名单应该很小，只含：**读动作 + 重试 + 释放租约 + 打开登录窗口 + 通知**。外部写一律 `ACTION_INTENT` 人工闸门。

## 7. 修正后的落地顺序

| 步骤 | 内容 | 依赖 | 与 Temporal 的关系 |
| --- | --- | --- | --- |
| Step 0 | 把 agent 层拉回测试门禁（`run-test-suite.mjs` 发现非递归，两个 supervisor 测试不在任何套件里） | 无 | 无关 |
| Step 1 | incident 源从「人工拼装 JSON」换成 `supervise-collection.mjs` 的活输出 | 无 | 无关 |
| **Step 1.5** | **补 G1 / G2：`round-state.json` 权威化挪进 PG；限流/熔断落库或明确限制为单进程** | 无 | **这是「不需要 Temporal」的前提。不做这一步，§4 的结论作废。** |
| Step 2 | 单 agent（= 受限分诊器）真实跑一次 | 凭据 | 无关 |
| Step 3 | 纠偏闭环（白名单见 §6.4） | Step 2 + 授权 | 无关 |
| Step 4 | 并行多 SOP：验证单出口下 lane 互斥、不双写 | Step 1.5 + 3 | 无关（互斥已由 lease 承担） |
| Step 5 | 上升到多 agent | Step 1-4 | **此时才重新评估 Temporal** |

注意 Step 1.5 的位置：它在 Step 2 之前。因为「并行跑多个 SOP」是你已经定下的下一步目标，而它**直接踩在 G1 和 G2 上**——两个 SOP 并行时，轮次去重和限流必须跨进程一致。

## 8. 会让我改主意的东西（可判定触发条件）

不是「以后可能需要」，而是写死四条，任意一条成立就重新评估 Temporal：

1. 需要 ≥2 台机器或 ≥2 个常驻进程同时跑 worker，且共享限流/熔断状态；
2. 需要跨天、跨重启存活的长 timer（G1 修完后这条被大幅推迟）；
3. 单条流程的步骤数与重试拓扑增长到 PG + controller 无法安全表达；
4. 出现一次「因为编排状态丢失而重复干活或漏掉恢复」的真实事故。

同时保留一件事实：`docs/architecture/README.md` §4.2 给 Temporal 的是**默认位置**（该层首选 POC 候选），并写明「Restate 等方案只有在**相同故障模型下完成对比验证后**才能替代它」。所以：**不删 POC、不改依赖、继续标 prototype**；只把 README 里「尚未落依赖或部署」那句失效描述改正（依赖早已装、POC 已存在）。

## 9. 结论（三句话）

1. **形状**：单机单出口 + 强权威落库 + 浅拓扑流程，正确性由外部证据闭环承担，不引入外部工作流引擎。
2. **Temporal**：在当前与「并行多 SOP」阶段没有需求侧依据；但**这个结论只有在 G1/G2 补完之后才成立**——今天说「不需要」，其中有一条是靠本地 JSON 顶着的。
3. **多 agent 形态**：一条流程一个 lane + 全局一个监督环和一个受限分诊器。「一条流程一个 agent」不提高隔离性，但会把同构的判断逻辑复制成 N 份。

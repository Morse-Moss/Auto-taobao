# LLM 放在哪里：内部集成 vs 外部监督的判据，以及 AI-native 的可验证定义

日期：2026-09-16
问题：是否需要在一个 Agent 系统内部集成 LLM，还是像现在这样用外部 Agent 进行监督？给定「要做真正的 AI-native 系统」。

方法：先把问题拆成可判定的维度，再从核心目标与硬约束各自推出结论，最后用本项目已存在的代码事实做对照——不讨论抽象优劣，只讨论「在本项目的约束下哪个位置成立」。

---

## 0. 结论（四条）

1. **这是个伪二选一。** 「内部集成 LLM」与「外部 Agent 监督」不是两个方案，而是同一组三个独立维度上的两种极端组合：进程边界、决策权限、触发方式。混在一起讨论，必然得出「要智能就得放权」这种错误推论。
2. **决定 LLM 放在哪里的唯一有效变量是「该动作的错误能否被回滚」**，不是技术可行性。两处技术上都能做，所以唯一有区分度的约束是代价：不可回滚 × 概率错误 = 期望损失无界。
3. **本项目在这个问题上的选择已经做完了，而且做对了，问题不在选型在接线。** `runtime/sop-runtime/agent-proposal.mjs` 已经写死了「Agent 只出提案、不得触碰状态轴、无证据的断言一律拒绝、必须声明确定性兜底、核心模块不得反向依赖 Agent 层」，并有 40 例测试守着（proposal 13 + review 13 + planned-run 14）。真正缺的是：**生产调用点、事件触发、语义判据**。
4. **因此「外部 Agent 监督」现在扮演的不是「更好的方案」，而是「内部端口尚未接线时的临时替身」。** 它有效，是因为它把读侧放开了（闭环）；它不可持续，是因为它会遗忘、需要人来叫、且不能 24×7。

## 1. 先把问题拆开：三个被捆在一起的维度

「内部集成 LLM」这个词同时隐含了三个设定，而它们应该被独立决定：

| 维度 | 「内部集成」隐含值 | 「外部监督」隐含值 | 本项目应为 |
| --- | --- | --- | --- |
| **进程边界** | 同进程，可读写运行时状态 | 独立会话，只能读仓库与产物 | **独立进程，只读输入**（拿到触发能力，不拿到写能力） |
| **决策权限** | 直接执行（含外部写） | 只出建议给人 | **出提案，过 validator 与人闸门后才能落地** |
| **触发方式** | 事件/定时，自动 | 人叫，有人值守 | **事件自动（但只读）** |

关键：这三者被捆在一起，所以讨论永远在两极之间摆动。一旦拆开，每一维都有自己的判据（§4），而它们的正确答案并不相同——**「同进程 + 只读 + 事件触发」这种组合，才是既拿到智能又不动摇正确性的位置。**

---

## 2. 从核心目标推：智能应该在什么时候被调用

Agent 系统的目标不是「有智能」。可验证的目标只有三个：

- **正确性**：写出去的东西是对的，且由外部可回读事实定义（不是由模型的置信度定义）。
- **可重复**：同一输入产生同一结果。
- **可恢复**：断了能接着跑，不重复干活、不漏活。

智能不是目标，是手段，而且只在一种情形下有用：**环境偏离了系统内置的假设。**

⇒ 推论 1：**LLM 的调用频率应当正比于「环境偏离的频率」，而不是正比于流程的长度。** 把 LLM 铺满全流程 = 在不需要判断的地方引入不确定性，同时抬高成本、延迟与审计难度。

⇒ 推论 2：**凡「偏离」能被确定性判据识别的地方，就不需要 LLM。** 只有「确实偏了，但用规则说不出哪里不对」时，才需要它。这正是分诊器存在的理由，也解释了为什么它必须排在看门狗（判据）之后——判据先滤掉 90% 的已知形态，剩下的 10% 才值得付模型的钱。

⇒ 推论 3：**外部监督的调用频率应当正比于「不可回滚动作的数量」，而不是正比于流程的长度。** 本项目每周只有少数几个不可回滚动作（发布历史总表、写回主表），所以外部监督低频是合理的，而不是缺失。

## 3. 从硬约束推：四条边界

| 约束 | 出处 | 对 LLM 位置的直接约束 |
| --- | --- | --- |
| **C1 外部副作用不可回滚** | 飞书写入/发布没有撤销通道 | 不可回滚动作的决策权不能交给概率系统。不是信任问题，是期望值问题 |
| **C2 正确性由外部可回读事实定义** | `AGENTS.md` Acceptance 段：首末名次匹配、行数相等、字段齐全 | 模型的「我认为对」不构成正确性证据；只有回读结果构成 |
| **C3 单一物理出口，有效并发 = 1** | `fanout.mjs:9`「并发是显式决定：默认并发 1」 | 多开 LLM 实例不增吞吐，只增状态竞争与互相矛盾的判断 |
| **C4 移除模型后确定性流程仍可运行** | `SUPERVISOR-AGENT-DESIGN.md:799`、`agent-proposal.assertAgentRemovable` | LLM 不能进控制流。只能是控制流的旁挂件，且必须声明确定性兜底 |

还有一条不在上表但同样硬：**可复现性。** 模型输出随版本变化，所以 LLM 的输出**不能进入「可重复」的定义域**（不能成为流程正确性的一部分），只能进入「提案 / 审计记录」域。`agent-proposal.mjs:219 toDecision()` 把它落成 `decisions` 而不是状态转移，正是这条约束的实现。

## 4. 判断依据（可直接用）

### 4.1 动作级矩阵：按「可回滚性 × 证据来源」定位

横轴是副作用可否回滚，纵轴是判断能否被规则表达。四个格子里 LLM 的合法形态不同：

- **只读 + 需语义判断** → 内部 LLM 的最佳位置（判据覆盖不到才叫它）
- **只读 + 规则可判** → 确定性代码就够，不需要 LLM
- **写入 + 规则可判** → 确定性代码 + validator（不需要 LLM 参与决策）
- **写入 + 需语义判断** → LLM 只能出提案，且必须经人确认（这是全系统风险最高的一格）

### 4.2 四条可执行规则

**规则 1（动作级）**：按可回滚性切。只读/可回滚 → 内部 LLM 可用；不可回滚 → 决策权保留在人与确定性代码手里。
**规则 2（频率级）**：按事件频率与人的响应能力切。十分钟级的读侧事件 → 必须内部自动；每周一两次的发布类动作 → 外部监督足够。
**规则 3（证据级）**：按「错误能否被确定性判据识别」切。能识别 → 不需要 LLM；识别不了 → 需要 LLM，但输出只能是提案。
**规则 4（连续性）**：需要跨天、跨重启连续观察的 → 必须内部。外部会话会被回收，这条已经在本项目上应验过（卡点解决过程只存在于对话里，对话一回收，「效果稳定」时期的问题一条也没真正减少）。

### 4.3 反向适用：什么时候这两种方案都更差

**外部监督更差的时候**：读侧事件频率高到人来不及（十分钟级）；需要跨天连续观察；需要与运行时状态同步判断；需要 24×7 无人值守。这四条本项目全中。

**内部集成更差的时候**：让 LLM 决定写什么（不可回滚 × 概率错误）；并发 > 1 且多个 LLM 判断互相矛盾；审计要求可复现而模型版本会变；判断本身其实能被规则表达（引入了不必要的非确定性）。

## 5. 「内部 vs 外部」真正的区别不在智能多少

这一点最容易搞错。两者的差别只有三条，而它们都不是「谁更聪明」：

| | 内部（同进程/常驻） | 外部（独立会话） |
| --- | --- | --- |
| **状态可见性** | 能看见运行时状态——**也就能改，这才是危险** | 只能读仓库与产物，看不见过程，因此安全但也盲 |
| **记忆持久性** | 可被事件唤起并持续存在 | 会遗忘（对话被回收） |
| **责任边界** | 错误直接变成外部副作用 | 错误先变成一份提案 |

⇒ 所以「内部还是外部」实际在问两件事：**谁记得住，以及谁按发送键。** 智能多少取决于给了它什么输入，与进程在不在内部无关。

这条也解释了为什么本项目做对了：它把「触发与记忆」放进了内部（端口 + 事件），把「发送键」留在了外面（Controller 是唯一状态拥有者，`agent-proposal.mjs:8`）。

## 6. 什么叫「真正的 AI-native」（可验证定义）

这个词如果不给可验证定义，就会退化成口号。四条，缺一不可：

1. **有明确的不确定性接口**：哪些环节允许模型介入、允许它输出什么形状（结构化 schema，不是自由文本）。本项目已有：`AGENT_ROLES` / `PROPOSAL_KINDS` / `READ_ONLY_TOOLS`。
2. **模型输出必须经确定性验证才能影响外部状态**。这一条是 AI-native 与 LLM-dependent 的分界。本项目已有：`validateProposal` + 五条状态轴黑名单 + `FORBIDDEN_PROPOSAL_FIELDS`。
3. **移走模型后系统降级但不崩溃**。本项目已有：`deterministicFallback` 强制声明，端口把模型失败收成 `ok:false` 而不抛给编排层（`agent-proposal.mjs:266-270`）。
4. **模型介入的判据本身进版本控制，可审计、可回归测试**。本项目**没有**——判据还散在文档里。

**反例（要避免的）**：把 LLM 直接接在控制流上，模型出错就系统出错。这叫 LLM-dependent。它比确定性系统更脆弱，因为确定性系统至少可预测。
**正例**：模型只产出候选，系统只消费「已通过验证的候选」。

补一条我认为比上面四条更本质的判据：**AI-native 的成色，不看系统里有几个 LLM，而看两件事——没有人的时候它能自己走多远，以及走错了它能不能自己发现。** 按这个标准，本项目当前的短板不是 LLM 不够多（端口都建好了），而是：

- 走错了自己发现不了（判据只到执行态，见 `ROOT-CAUSE-AND-SELF-HEALING-PLAN.md` §3 层 1）；
- 模型不在链上（端口没有生产调用点，事件也不存在）。

| planner / reviewer 双角色分离，端口级互斥 | `:243`（reviewer 挂到提案端口 → `ROLE_INVALID`） |
| 对抗性复核，结论 ACCEPT / REJECT / ESCALATE | `agent-review.mjs` |
| 四段流水：Planner → 确定性边界 → Reviewer → Controller | `agent-planned-run.mjs` |
| 可移除性静态证明 | `:287 assertAgentRemovable` |
| 提案只落 `decisions`，不产生状态转移 | `:219 toDecision` |

**仍缺的三样**：

1. **生产调用点**：`createAgentPort` / `createReviewerPort` **只有测试实例化过**，`index.mjs:10` 导出了却没人调。
2. **事件触发**：八步流程跑完只在终端打印，没有产生可供端口消费的事件。
3. **语义判据**：判据只到执行态，所以即使有了事件，也不知道什么时候该叫端口。

⇒ 结论：**在这个问题上，本项目需要的不是「选一种架构」，而是把已建好的端口接上去。** 接线的安全性已经被设计保证（兜底声明 + 可移除性检查 + 只读工具面），所以这是一个低风险动作，不是一个架构决策。

## 8. 一句话判据

**按不可回滚动作的数量决定外部监督的比重；按读侧事件的频率决定内部集成的比重。**

对本项目代入：不可回滚动作每周只有个位数 ⇒ 外部监督（人批准）低频且合理；读侧事件（采集覆盖可疑、字段整列为空、身份不符）是分钟级到小时级 ⇒ 必须内部自动。所以答案是两条同时成立，而不是二选一。

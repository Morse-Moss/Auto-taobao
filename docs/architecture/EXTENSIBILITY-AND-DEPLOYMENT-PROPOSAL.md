## 0. 结论速览（七句话）

1. **分层不重画。** README §4 的六层是对的，与仓库现实已经对过账（`PHASE-ARCHIVE.md` §12、`PRODUCTION-READINESS.md`）。本次只补**唯一缺的那一层**：Browser Broker。它是 §10 验收第 5、6、8 条的共同依赖。
2. **单点真相只保留三张登记表 + 一份客户配置**，并用守卫封杀第二份。过去四类事故（端口写死、飞书表 id 写死、店铺名靠猜、证据目录缺店铺维）都是「同一个事实写了两遍」。
3. **部署形态分三档**：A 工程师旁站（今天就在这一档）／B 单机客户自助（差 P0 里的四项）／C 服务器侧无人值守（**明确非目标**）。
4. **容器化在这套系统里不等于把浏览器装进容器。** 真浏览器 + 真登录态 + 扫码 + 浏览器扩展 + 剪贴板 + 下载目录，把容器化边界压得很窄。可行的第一步是「同一台 Windows 主机上的一键起停」，不是 Docker/K8s。
5. **可扩展性靠三件事**，不靠框架：登记表（加平台/加店铺）＋ 能力接口七段式（加能力）＋ lane 维度（加并发）。
6. **耐久执行先留在 PG。** Temporal 只在 POC 通过后引入，触发条件是「出现跨进程/跨机器恢复且 PG 表达不了」，不是「看起来更专业」。
7. **「不易跑偏」靠四道机制**：单点真相守卫、非目标清单、文档漂移自检、以及**每一步都能被一条命令复现的判据**。缺第四道，前三条都会退化成口号。

## 1. 架构决策与理由

每条按 ADR 五段写：决策 / 为什么 / 否掉的替代 / 代价 / 何时重审。**这一节是全文最重要的部分**——后面的设计都是它的推论。

### D1 只在 README 六层上补一层，不重画分层

- **决策**：保留 README §4 的六层划分。本次唯一的结构性新增是把 4.3 的 Browser Broker 从「文档描述」变成「有最小实现的层」。
- **为什么**：分层已经与仓库现实逐条对过账，重画会让两处对账证据（`PHASE-ARCHIVE.md` §12 的阶段 0-6 结论、`PRODUCTION-READINESS.md` 的四条阻塞线）全部作废，而收益只是「看起来更整齐」。另一方面，README §10 十一条架构验收里，第 5 条（同账号/profile 不并发双写）、第 6 条（失败与人工路径释放资源）、第 8 条（两店并行不串数据）**只有 Broker 在场才证得了**——这不是设计偏好，是缺一块。
- **否掉的替代**：① 引入 K8s/Operator 做「平台化」——README §9 末句明确「不一次性引入」，且需求侧没有并发规模的实测证据；② 把 Broker 塞进现有 `cdp-proxy.mjs`——代理是**无状态转发**（只认 `/targets` `/eval` `/navigate` `/click`），Broker 要**有所有权与租约**，两者的失败模型完全不同，合在一起会让「代理挂了」与「租约没释放」变成同一个症状。
- **代价**：多一个模块要维护，而短期内它只有一个消费方（多店铺驱动），会显得过度设计。
- **何时重审**：出现第二个消费方，或真的发生一次「同一 profile 被两个驱动同时用」。

### D2 单点真相 = 三张登记表 + 一份客户配置，第二份由守卫封杀

- **决策**：端口/浏览器身份/路线/账号映射 → `runtime/browser-ports.mjs`；飞书 base 与表 id → `runtime/feishu-targets.mjs`；客户差异 → `config/customer.json`（读方 `runtime/customer-config.mjs`）。三者互不复制，也不合并。
- **为什么**：这四类事故有共同的形态——**同一个事实存在两份，其中一份先改**。端口在别处写死会被 `runtime/browser-ports.test.mjs` 的守卫扫到；飞书表 id 每周期不同、写死过一次；店铺名有四个名字（飞书选项名/生意参谋页头名/阿里妈妈会员名/运营叫法），猜错过至少三次；证据目录曾缺店铺维度。
- **否掉的替代**：① 把所有配置合进一份大 JSON——`browser-ports.mjs` 的价值正是它是**代码内常量且能被守卫按字面量扫**，搬进 JSON 会让守卫失去锚点；② 把配置放数据库——多一个「必须先活」的依赖，而客户机上不一定有。
- **代价**：三处登记表要人工保持同步（加第 5 家店要同时动 `SHOP_BROWSERS` 与 store 映射，并新起实例）。
- **何时重审**：某张登记表里出现「同一个事实写了两遍」；或客户数量增长到「人工同步三处」开始出错。

### D3 能力边界 = `skills/<capability>/` 目录边界；`runtime/` 不再继续吸收业务

- **决策**：新业务进 `skills/`。`runtime/` 只放跨能力共享的机制（登记表、配置层、CDP 代理、浏览器启动器、窗口标识、体检、通知、运行器）。
- **为什么**：`runtime/` 已经混了三类东西——机制代码、历史产物（上百个 `*-runs/` 目录、几百张 PNG/JSON 截图与探针输出）、一次性迁移脚本。`SYSTEM-OVERVIEW-AND-DEPLOYMENT.md` §2.4 已经把「`runtime/` 被无声升级成业务合同仓库」列为技术债 A2。继续长，`skills/` 的能力版本化就永远落不了地。
- **否掉的替代**：① 立刻做 `SYSTEM-OVERVIEW` 里的 M6（抽 `lib/feishu-client` 收敛散落在 **52 个文件**里的飞书鉴权实现、解开 **31 个文件**的 `skills → runtime` 反向依赖）——本次不做，理由见下条；② 新建 `lib/` 并把旧文件整批搬过去——同一次改动的面太大，且没有守卫托底。
- **代价**：`skills → runtime` 的反向依赖继续存在（实测 31 文件，其中 16 个是生产文件），这意味着**整仓复制是当前唯一成立的交付形态**——「只拷 `skills/`」任何一条链都跑不起来。这条必须写进给客户的说明里，否则部署时会撞墙。
- **何时重审**：要交付到客户机、且「交付物太大/太乱」成为实际问题时。那时应该先做分类（哪些是机制、哪些是产物），再谈抽 lib。

### D4 配置层以「没有配置文件时行为与从前逐字相同」为不变量

- **决策**：`config/customer.json` 不存在 → 全部走内置登记表；存在 → 只覆盖**被允许的字段**；未知段、未知字段、类型不符、非法值**一律抛错**（fail-closed）。
- **为什么**：这条同时支撑两件事——「装到客户机上不必改代码」与「本机行为不被配置层偷改」。这两件事必须同时成立，否则配置层会成为新的漂移源。这个不变量已经被判据锁住：`runtime/customer-config.test.mjs` 有一条「无客户配置时 `getProfile` 逐字段等于内置登记表（且是同一份引用）」。
- **否掉的替代**：① env 优先于文件——env 是**部署差异**（可执行文件路径、端口、配置路径本身），文件是**客户差异**（店铺、飞书目标），层级不同、不该互相覆盖；保留「env 覆盖顶层」的单向能力即可；② 宽松降级（JSON 坏了就当没有配置）——那会让「配置写错了」伪装成「配置没生效」，是最难查的一类问题。
- **代价**：客户首次配置时，一个字段名拼错就会整体失败。这是故意接受的代价。
- **何时重审**：若客户实际配置时因报错放弃——那时该补的是**校验器的报错文案与示例文件**，不是放宽校验。

### D5 部署形态三档，档与档之间不许跨

- **决策**：A 工程师旁站 / B 单机客户自助 / C 服务器侧无人值守。**C 是明确非目标。**
- **为什么**：C 的先决条件是 Browser Broker + 租户隔离 + README §11 的九项决策（部署区域、凭据托管、数据留存与 PII、SLA/RPO/RTO、并发规模、合规边界、模型预算、Temporal 去留）——**九项全部未定**。
- **否掉的替代**：① 直接做 C「一步到位」；② 把 B 做成「半自动的 C」（旁边留个待命的人）——那会掩盖「缺页不自愈」「进程绑会话」这两个真实缺口，让它们只在深夜无人时爆发。
- **代价**：B 的体验上限被锁死（无远程协助、无自动更新、页面改版不可自愈）。
- **何时重审**：`SYSTEM-OVERVIEW` §6.3 的两问有答——「有常开的 Windows 机器 ＋ 有人能随时扫码」若答案为「能」，则 B 就够、不需要 C。

### D6 并发用「维度 + lane」表达，不用进程级全局锁

- **决策**：lane 维度 = `tenant / store / platform / account / browserProfile / capability`。同账号或同 profile 并发为 1；同店写操作串行；不同店铺可并行。
- **为什么**：读侧（采集）天然可并行，写侧（飞书回填）必须串行。全局锁会把「不同店铺可并行」也一起锁掉，等于用正确性换掉了本可用的吞吐。
- **否掉的替代**：文件锁 / 单实例锁做互斥——它锁的是**进程**，不是**资源**；两个不同进程拿不同 profile 依然会写同一条飞书行。
- **代价**：并发正确性依赖调用方**自己声明 lane**。声明错了不会报错，只会静默串数据——所以 lane 必须从登记表推导，不许手写。
- **何时重审**：出现「两家店互相写对方行」；或引入第二个并发消费方。

### D7 耐久执行先留在 PG，Temporal 只在 POC 通过后引入

- **决策**：`runtime/sop-runtime/` 继续作为唯一耐久层的实现（PG 为状态权威）。Temporal 保持「首选 POC 候选」身份，不落依赖。
- **为什么**：README §9 最后一句是硬约束——「每个基础设施组件都必须对应已验证的容量、故障或治理需求」。当前唯一已证实的耐久缺口是「任何未终结的运行会永久占住幂等键」，已由 `run-liveness.mjs`（死活看租约、回收安全性看提交记录，两个判据分开）解决。没有第二个已证缺口，就不该引入第二个耐久引擎。
- **代价**：跨机器恢复能力弱于 Temporal；`sop-runtime` 要自己承担重试/心跳/恢复的表达。
- **何时重审**：出现「必须跨进程或跨机器恢复，且 PG 表达不了」的真实需求；或 README §11 里 Temporal POC 那条有了结论。

### 2.2 模块划分的四条原则

1. **按能力分，不按脚本分。** 一个 `skills/<capability>/` 就是一个能力的全部：`scripts/`（可执行入口）、`references/`（操作单）、`tests/`。跨能力共享的东西才进 `runtime/`。
2. **按所有权分，不按技术分。** 判据是「谁负责创建、谁负责回收」。`cdp-proxy.mjs` 不拥有浏览器（是启动器拥有的），所以它不该管回收；这条判据直接推出 §2.7 的 Broker 边界。
3. **登记表在代码里，差异在配置里。** 结构（有哪些平台、有哪些端口、有哪些路线）是代码；实例值（这家客户有几家店、飞书 base 是哪个）是配置。
4. **产物不混进代码目录。** 现状是 `runtime/` 根下混着上百个 `*-runs/`、截图、日志（`_runtime-suite.log`、`_perfile.log` 一类）。`runtime/INDEX.md` 自己写着：本目录实际含 **15 个** `.md`（含它自己共 16 个）与 **253 个** git 跟踪的顶层条目，其中 14 个是合同/决策文档——这与 `docs/standards/README.md` 把 `runtime/` 定位为「运行入口、阶段指针和单次运行状态；**不是架构事实源**」直接冲突（治理方案 A2 已登记，尚未解决）。这是「部署时哪些该带走」无法机械回答的根因。**分类前不移除任何东西**，只登记。

### 2.4 与 README 的差异声明

本方案**不新增层、不删除层、不改变依赖方向**。唯一与现状不同的是 §2.7 那个新模块。任何往 `runtime/` 加「业务规则」的改动，都要先回答 D3 的问题：它是不是只服务一个能力？是 → 它属于那个 `skills/` 目录。

### 2.5 一份必须写进交付说明的现状（不许粉饰）

`skills → runtime` 的反向依赖是**双向的**：`skills/` 里 **31 个文件**反向 import `runtime/`（16 个生产文件），`runtime/` 里约 **10 处** import `skills/`。

**这条不修，交付形态就被锁死为「整仓复制」。** 所以给客户的部署说明里不能写「把 skills 目录拷过去就行」。这也解释了为什么 P0-1（配置外置）比 M6（解耦）优先级高：配置外置让**同一份整仓**可以装到不同客户机上，而解耦只是让整仓变小。

### 2.6 为什么不做 M6（本轮）

总览 §7 已定「本轮不排」，本方案维持该结论，但补一句判据：M6 的前提不是「风险高就别做」，而是**每批 ≤10 文件、且守卫密度够**。当前 `runtime/browser-ports.test.mjs` 一类守卫能扫端口字面量，但没有守卫能扫「这个 import 是不是反向的」。所以 M6 的第一步应该是**先加一条反向依赖的守卫**（把现状 31 个文件写成白名单，新出现即红），再动结构。这条列进 §9 的可选阶段。

### 2.7 Browser Broker：最小职责集与最小切片

README §4.3 已经定义了它该做什么。本方案只做一件事：**把它拆成「今天有诊断价值」与「等需求」两半**，避免它变成又一次「先建框架」。

它该负责的（照 README §4.3，不增不减）：发放与续期短期租约；保证同账号/profile 互斥；登记创建/认领/释放/孤儿清理的所有权；处理登录、验证码与人工接管；施加平台/账号/profile/浏览器容量限制；不向 Agent 暴露 Cookie/token/浏览器存储/认证头。

**最小切片（推荐先做这一半）**：

| 切片 | 做什么 | 为什么现在有收益 | 不做会怎样 |
| --- | --- | --- | --- |
| BR-1 所有权登记 | 声明「哪些实例应该活着」（从 `browser-ports.mjs` 推导，不另写一份），并记录本次会话实际起了哪些、谁起的、干什么用 | 今天**系统自己不知道有几个实例活着**——「7 个声明、6 个活着」这个事实是仓库外的探针（`D:/Retire/probe-live/137-resource-budget.mjs`）发现的 | 每轮都要靠外部探针盘点；换个人上手就不知道机器上那些 Edge 是谁的 |
| BR-2 孤儿对账 | 对账「声明 vs 存活」，输出报告；**只标注，不擅自终止任何进程** | 与用户既有铁律一致：任何存活进程都受保护，脚本自己打印的建议命令不构成授权 | 孤儿实例长期占内存（实测 6 实例 6416 MB），且没人知道该不该关 |
| BR-3 释放语义 | 给「这一轮跑完了」定义释放动作（至少是「登记表里标记为可回收」） | README §10 第 6 条验收要求「失败与人工路径释放资源」；现在 release 段**是空的**（进程绑会话） | 「跑完没跑完」在资源层面无法区分 |

**这三个切片的落地状态（2026-09-19 夜）**：BR-1 ＋ BR-2 → `runtime/browser-inventory.mjs`（**已完成**，
`buildDeclarationPlan()` 从登记表推导、不持久化，对账输出六桶判决）。
BR-3 → `scripts/stop-all.mjs` ＋ `runtime/launch-plan.mjs` 的 `planInstanceStop()`（**已完成**，
释放动作＝「按证据停掉代理与浏览器进程树」，默认只打印）。
**与这里原先设想的一处差异**：BR-1 不做「记录本次会话实际起了哪些」——
那需要持久化，而持久化一份「我们起过谁」会立刻变成**第二份真相**，且重启之后它就是陈旧事实。
现在的做法是：**存活状态永远当场探测**（端口 ＋ CDP 自报 profile ＋ 父子关系），不落盘。

**等需求的一半（本轮不做）**：租约互斥（lease）、容量限流、tab 级所有权。触发条件是「出现并发消费方」或「真的串过一次数据」。

**两条边界（写下来防跑偏）**：

- **实例存活登记不进 PG。** PG 是业务事实权威（README §5），而「某个 Edge 进程还活着吗」是**进程级事实**，机器一重启就失效。把进程级事实写进 PG，会造出「重启后仍显示持有租约」这种最难查的假状态。所以：**存活登记放进程/文件，业务互斥（lease）放 PG。**
- **Broker 不向 Agent 暴露凭据**（README §4.3 已定），也就是说 Broker 的接口里不会有「取 cookie」这个方法。谁要 cookie，谁去读 profile 目录——那是它自己的事，不是 Broker 的。

### 3.4 依赖方向规则

允许的箭头：

```text
skills/* → runtime/（机制）   ← 现实如此，但记账为技术债
runtime/（机制） → runtime/（机制）
一切 → 登记表（只读）
```

禁止的箭头：

```text
登记表 → 任何东西（登记表必须是无依赖的叶子）
runtime/（机制） → skills/（业务）      ← 现实有约 10 处，记为债
任何 → 「第二份」端口/表 id/店铺名
```

**这条规则的意义**：登记表是叶子，所以它永远可以被任何东西 import 而不会成环；一旦登记表开始 import 业务，它就不再是真相源，而变成「又一个中间层」。

### 4.1 能力接口七段式（README §4.4 的形态，逐段落到实现）

### 4.2 Browser Broker 的接口形状（先定形状，不先实现）

```text
// 只读、可重复调用
declareInstances()   -> [{ profileId, port, proxyPort, purpose, label }]   // 从 browser-ports.mjs 推导
listLive()           -> [{ profileId, port, alive, pid, startedBy, since }]
reconcile()          -> { matched: [], orphan: [], missing: [] }          // 只报告，不动作

// 有副作用，需显式授权
claim(profileId, purpose) -> lease | RESOURCE_BUSY
release(leaseId)          -> RELEASED | EXPIRED

// 明确不存在的方法（写下来防跑偏）
// getCookies()   ← 永远不提供
// killOrphan()   ← 不在 Broker 里做；停任何进程都要人点头
```

**为什么先定形状**：因为「接口形状」是**最难改、最贵改**的东西。仓库里已经吃过一次亏——`cdp-proxy.mjs` 把「连哪个浏览器」做成 import 期常量，结果换端口必须重启进程，而用户不允许擅自重启任何存活进程。接口一旦被两个消费方用上就冻住了。

### 4.3 数据流 = 产物流转（不是控制流转）

README §5 的证据链六段，逐段落点：

| 段 | 产物 | 落到哪 | 谁回读 | 硬规则 |
| --- | --- | --- | --- | --- |
| Observation | 页面事实（行数、页签、登录态） | 日志 + 证据目录 | 判据 | 未知不得写成 0 |
| Candidate Artifact | 导出的 CSV/XLSX | `evidence/<cap>/<day>/shop=<id>/`（分代次） | 校验器 | 候选不算归属 |
| Validated Artifact | 通过身份/范围/结构/行数/哈希校验的产物 | 同上 + sha256 记账 | 编排器 | 未验证不得推进 |
| Decision | 要写什么 | 干跑输出 | 人/规则 | 必须引用输入证据与版本 |
| Idempotent Commit | 飞书写入 | 飞书底单/数据日报 + PG 审计表 | **独立回读** | 只认回读结果 |
| Publication Receipt | 回读收据 | 审计日志 | 编排器 | 必须含外部系统回读结果 |

**数据流的两个不变量**（都在链里落地过）：

1. **写不重试、回读带退避重试。** 写完立刻回读会拿到 `400 1254607 Data not ready`；把「写」和「读」的重试策略混成一个，会把「写成功但读太快」误判成「写失败」并重发。
2. **未知/缺失/未核验不写 0。** 数据源里的文本标记 `NULL` 撞上数字字段时，处置是**该格留空 + `console.warn` 留痕**，不是写 0——写 0 会把「无成交」变成「价值为 0」的假事实。降级必须带 `degraded.code`（例如补跑历史日取不到同行基准时的 `PEER_UNAVAILABLE`）。

### 4.4 三类键的定义（键即契约）

| 键 | 形态 | 约束 | 现状 |
| --- | --- | --- | --- |
| 幂等键 | `<capability>:<targetDay>:<storeId>` | `targetDay` 必须 ISO；`storeId` 受 `/^[a-z0-9][a-z0-9-]*$/` 限制 | 已落地 |
| lane 键 | `<tenant>:<store>:<platform>:<account>:<browserProfile>` | 必须从登记表推导，禁手写 | 未实现（无并发消费方） |
| 证据目录键 | `evidence/<capability>-<targetDay>-shop=<storeId>/` | 三家店一轮必须**同值**；另加代次 | 已落地（`--shop-key` 是**断言不是标签**） |

**为什么 `storeId` 只能用 `[a-z0-9-]`（而不是中文店名）**：它同时进幂等键与目录名。中文进目录名会撞上本机的 safe-delete 代理（对中文路径 fail-closed，且路径会被 GBK 乱码），进幂等键则会让「同一家店」出现两种编码形态。**可读性交给另一个字段（`feishuName`），唯一性交给 `id`。**

## 5. 配置与环境管理策略

### 5.1 三层结构

| 层 | 内容 | 例子 | 谁改 | 变更频率 |
| --- | --- | --- | --- | --- |
| 内置登记表（代码） | 结构：端口、浏览器身份、路线、账号类别 | `SHOP_BROWSERS`、`ROUTES`、`SITE_ACCOUNT` | 开发者 | 随平台/结构变化 |
| 客户配置（文件） | 客户差异：店铺清单、飞书覆盖 | `config/customer.json` 的 `stores[]`、`feishu.*` | 实施者 | 每家客户一次 |
| 环境变量 | 部署差异：exe 路径、配置文件位置、端口覆盖 | `PROJECT_BROWSER_EXE`、`SYCM_CUSTOMER_CONFIG`、`PROJECT_BROWSER_PORT` | 运维/脚本 | 换机器/换路径 |

**层级不重叠**是这套设计唯一的纪律。任何「这个值该放哪层」的争议，用一句话判：**它变了会让代码也需要变吗？** 会 → 代码；不会但每家有差异 → 文件；不会且只在换机器时变 → env。

### 5.2 不变量与验证方法

不变量：**没有配置文件时，行为与从前逐字相同。**

怎么证（不是靠读代码，靠判据）：

- `runtime/customer-config.test.mjs` 的「无客户配置时 `getProfile` 逐字段等于内置登记表（且是同一份引用）」；
- 「覆盖不修改内置登记表，且结果仍冻结」；
- 「配置内容坏了就报错，绝不退回内置值」。

三条合起来才构成不变量：**等于内置 + 不污染内置 + 坏了不降级**。

### 5.3 允许哪些字段（禁止第二份字段名单）

允许覆盖的字段从**内置登记表推导**，不另写一份字段清单。这条在实现里已经体现为：`overlayProfile(builtin, overrides, { where })` 用内置的键集合去校验覆盖项，未知键就抛错。**新增可覆盖字段的正确做法是往内置登记表加字段**，而不是往校验器加白名单——后者就是第二份真相。

### 5.4 凭据策略

| 规则 | 理由 |
| --- | --- |
| 配置里只放**标识**（`credentialRef`），不放密码/令牌 | 客户配置会被复制、被截图、被发给别人 |
| 凭据文件位置由 `envFile` 指，文件本身不进仓库 | 明文不入库 |
| 系统不做账号密码代登 | 已对客户声明过（总览 §6.2 边界第 1 条）；登录靠人扫码 |
| Broker 不向 Agent 暴露 cookie/token | README §4.3 |

### 5.5 加一个新配置字段的四步（顺序不许换）

1. 往**内置登记表**加字段（带默认值，默认值必须等于「现在的行为」）；
2. 在 `overlayProfile` 的校验里覆盖它（通常零改动，因为校验是从内置推导的）；
3. 更新 `config/customer.example.json`——**示例文件自己必须是合法配置**（已有判据在测）；
4. 加一条测试，证明「不配这个字段时，结果与加字段之前逐字相同」。

第 4 步是防漂移的关键：新字段最容易造成的伤害不是「不生效」，而是**悄悄改了默认行为**。

## 6. 可扩展点与预留机制

| 扩展点 | 加什么 | 读它的是谁 | 预留状态 | 加错会怎样 |
| --- | --- | --- | --- | --- |
| 加一家店铺 | `SHOP_BROWSERS` 加键（键=运营叫法）+ store 映射 + profile 目录 + 端口对（调试/代理）+ 新起实例 + 补页 | 启动器、代理、编排器、窗口标识 | **已预留**（五家已登记） | 键与运营叫法不一致 → 告警里点名点错；缺登记 → `shopInstance()` fail-closed 抛错（设计如此） |

| 加一个新能力 | `skills/<name>/` + 注册进能力表 | 编排器、运行器 | **部分**：日报链**尚未注册进能力表**，所以「换宿主只改配置」这一层还不成立（SOP §13 已诚实标注） | 不注册 → 排期/幂等体系管不到它，只能直接跑脚本 |
| 加一个部署环境 | env 覆盖 + 一份 `config/customer.json` | 配置层、启动器 | **已预留**（P0-1 已完成） | 改代码去适配客户 → 正是 P0-1 要消灭的事 |
| 加一个新失败码 | `FAILURE_CAUSES` 闭集 + 告警文案表 + 测试 | 编排器、告警渲染 | **已预留** | 往闭集外写 → 告警渲染不出「人话原因 + 下一步」 |
| 加一个 lane 维度 | README §7 的维度列表 + 调度器的 lane 计算 | 未来的调度器 | **未实现**（无并发消费方） | 手写 lane 而不用登记表推导 → 静默串数据 |
| 加一个 profile 隔离档 | `ISOLATED_PROFILES` + `SHOP_BROWSER_EXTRA_ARGS`（现为 `--disable-sync`） | 启动器 | 已预留 | 漏掉隔离参数 → 两个 profile 共享登录态 |
| 改页面（平台改版） | 新 Capability 版本 + probe + contract test | 体检、能力脚本 | **未实现**（无版本机制，只有文件） | 直接改 selector → 违反 README §4.4「不能让 Agent 自动修改生产 selector」 |

**诚实标注一条**：`config/customer.json` 的 `stores[]` 段**目前没有读方**。它已经被校验（形状、必填、`id` 字符集、重名），但没有任何链按它去驱动——现在的店铺清单真相仍在 `SHOP_BROWSERS`。两处同时存在是**过渡态**，不是设计。消除它的方式是：让下一家客户的接入**必须**先写 `stores[]`，再由它去校验 `SHOP_BROWSERS` 是否登记齐全。

## 7. 多环境与多部署方式适配

### 7.1 判定树（先回答这三问，再谈技术）

```text
有常开的 Windows 机器吗？──否──> 形态 A（工程师旁站）
   │是
有人能随时扫码吗？──────否──> 形态 A 或 B（取决于是否接受「登录失效就停」）

   │是
形态 C 的前置清单（§7.5）满足了吗？──否──> 停在 B，先补前置
   │是
形态 C
```

### 7.2 形态 A：工程师旁站（今天就在这一档）

- **特征**：一条命令跑完全链；跑之前有人确认页面与登录态；跑完有人看回读。
- **已完成的部分**：`run-multi-shop-day.mjs` 把十一个阶段固化成一条命令，四家店串行跑通、零人工干预（`evidence/multi-shop-run-2026-09-18/RUN-LOG.md`），并对同一天做过只读复验（`evidence/multi-shop-2026-09-17/RUN-LOG.md`）。
- **这一档的诚实边界**：它是「一条命令跑完全链」，**不是**「没人管也能跑」。真无人值守还差三件：进程保活、缺页自愈、体检层往上做（L2/L3）。SOP §13 已经这么写了，本方案维持这个口径。

### 7.3 形态 B：单机客户自助（差什么）

| 项 | 现状 | 差什么 |
| --- | --- | --- |
| P0-1 配置外置 | **已落地**（`config/` + `customer-config.mjs`） | 客户实际配置的体验（报错文案、示例文件）；以及上文的 `stores[]` 无读方 |
| P0-2 一条命令 | **部分落地** | 体检段未接 L2/L3；未在目标机验证过 |
| P0-3 登录体检 | 探测与告警已有（含按店铺点名、`--proxy` 判据）；**自助重登未做** | 「灯红 → 开可见窗口 → 扫码 → 检测到就绪 → 自动续跑」这一段 |
| P0-4 常驻与定时 | **半完成**：入口 `scripts/run-daily-job.mjs` 与注册脚本 `scripts/schedule-install.mjs` 已建、`start-all` 补上了保活归属；**注册被本机 `schtasks.exe` 黑名单挡住，待人来挂** | 一次「detached 进程能否活过任务本身」的实测；由人注册 |

### 7.4 容器化的边界（这一节是「部署灵活性」最容易跑偏的地方）

**先说结论**：这套系统**不能**把浏览器装进容器。理由是六条硬件/系统级依赖，缺一条链就断：

| 依赖 | 现状证据 | 容器化后果 |
| --- | --- | --- |
| 真实浏览器 + 真实登录态 | 四个 profile 目录合计 9076 MB，登录态在 profile 里 | 容器重建即丢登录，每次都要人重新扫码 |
| 浏览器扩展 | 仓库里有 `runtime/contentscript.remote.js`、`sycm_market.remote.js`、`tb_list.remote.js` 一类注入脚本；小旺神采集依赖插件 | 扩展装不进无头容器；且 `MAX_WORKER_COUNT>1 必须 headless` 这条硬约束与「需要 GUI 扫码」直接冲突 |
| GUI 扫码 | 登录只能由人扫 | 无头容器没有人能扫 |
| 剪贴板 | 有 `runtime/_clipboard-dump.txt`、多处「复制粘贴」步骤 | 容器无剪贴板 |
| 下载目录与浏览器下载任务 | 「下载任务管理」是取件的可靠路径 | 容器里下载目录语义不同 |
| Windows 专有件 | schtasks（定时）、safe-delete 代理、中文路径 GBK 行为、Edge 路径 | 换 Linux 会同时坏掉四样 |

所以「容器化」在这套系统里应当被重新定义为：**把「进程编排」容器化，而不是把浏览器容器化。**

**推荐的第一步（也就是 §2.7 的 BR-1/BR-2 加上起停对）**——**下面四条命令 2026-09-19 夜已全部落地**
（原先写在这里的 `--dry-run` / `--yes-really` 是当时的设想，实现时统一成「停默认只打印 ＋ `--yes`」，
已按实现改口）：

```text
node runtime/browser-inventory.mjs           # 声明了什么、此刻谁活着（只读）
node scripts/start-all.mjs                   # 起全部声明的实例（幂等：已在的不重起）
node scripts/stop-all.mjs                    # 列出「将会被停的东西」——默认只打印
node scripts/stop-all.mjs --yes              # 才真的停（需人显式加参数）
```

四条设计约束（实现后的版本）：① 起停**幂等**（已在的不重起）；② 任何「停」的动作默认只打印，
必须显式加参数；③ 起停**不写登记表** —— 「谁活着」永远当场探测（端口 ＋ CDP 自报 profile ＋
父子关系），落盘一份「我们起过谁」会立刻变成第二份真相、且重启即陈旧；
④ 与 schtasks 解耦（定时器只负责叫醒，保活是另一个职责）。

**这四条的收益与容器化是同向的**：一台机器上「有哪些实例、谁该活着、怎么一次起停」被说清楚了，将来真要搬到容器/VM 编排才有东西可搬；反过来，跳过这步直接上 K8s，只会把「进程说不清」这个根问题带进去。

### 7.5 形态 C 的前置清单（现在不启动）

按属性排序，不是按难度：

1. **Browser Broker（BR-1 到 BR-3 全部）** —— 它决定并发上限与隔离边界；
2. **租户隔离** —— 现状是「一家店一个 profile + 一个代理」，租户维度只在键模板里预留，没有实现；
3. **README §11 九项决策全部定下来** —— 部署区域、凭据托管、数据留存与 PII、SLA/RPO/RTO、并发规模、合规边界、模型预算、Temporal 去留；
4. 然后才是容器编排。

### 7.6 「部署形态不进代码分支」原则

**不许出现 `if (deployMode === 'customer')` 这种分支。** 形态差异必须落在**配置**（哪几家店、哪个 exe 路径）与**运行时选择**（起哪些实例）上，不许落在代码路径上。理由：分支一旦出现，两条路径就都需要测试与维护，而客户机上跑的是哪条路径通常没人记得——这正是「本机全绿、客户机上红」的典型成因。

## 8. 权衡与风险

### 8.1 权衡（每条给「宁可吃哪个亏」）

| 取舍 | 选什么 | 宁可吃的亏 | 反过来会怎样 |
| --- | --- | --- | --- |
| 合并进程省内存 vs 一 profile 一身份 | **一 profile 一身份** | 多占内存（实测 6 实例 6416 MB） | 合并后不同店铺共享登录态 → **静默串数据**，比多占内存严重得多 |
| 整仓复制交付 vs 拆分 lib | **整仓复制**（暂） | 交付物大、含历史产物 | 先拆后验会同时破坏 31 个反向依赖文件，且当前没有守卫托底 |
| 配置外置 vs 端口也进配置 | **客户差异外置，结构与端口留代码** | 换端口要改代码 | 端口进 JSON 后，守卫（按字面量扫）失去锚点，端口写死会重新长回来 |
| 引入 Temporal vs 留在 PG | **留在 PG** | 跨机器恢复弱 | 无已证需求就引入第二个耐久引擎，会造出「两处都记，谁说了算」 |
| 把浏览器容器化 vs Windows 主机 | **Windows 主机** | 部署形态受限于 Windows | 见 §7.4 六条依赖，容器化会同时坏掉登录、扩展、剪贴板、下载、定时 |
| 写侧 fail-closed vs fail-open | **写侧 fail-closed；读侧（探针/告警渲染）fail-open 但必须给 `reasonCode`** | 客户首次配置易整体失败；探针偶尔多报 | 写侧 fail-open 会造出「以为写了其实没写」；读侧 fail-closed 会让一根网线断掉就整屏红 |
| Agent 在场 vs 不在场 | **确定性链不许 Agent 在场** | 失去「自动想办法」的能力 | 违反 README §10 第 10 条；且 Agent 的「成功」是自然语言，不能替代验证证据 |

### 8.3 明确非目标（写下来防漂移）

1. 不做服务器侧无人值守（形态 C），直到 §7.5 前置清单满足。

6. 不预建空的目录结构（README 第 5 行的约定：`decisions/` 与 `contracts/` 都在条件满足后才新增）。
7. 不在没有需求证据时引入第二份耐久引擎、第二份配置真相、第二份状态真相。

### 10.2 不许写的话（措辞纪律）

- 不许把「脚本化」说成「自动化」。当前档位是「一条命令跑完全链」，不是「没人管也能跑」。
- 不许把「仓库里有这个文件」当作「这个能力已实现」——`agent-runtime/`、`supervisor-agent/` 都是原型不接生产。
- 不许把「测试通过」当作「已获授权」——提交、推送、部署、真实外部写入各自仍需明确授权。
- 不许把「离线层已证」表述成「真实环境已证」。
- 报店铺必须带上**用户看得到的名字**（运营叫法），不许只给内部键或编号。
- 「未验证」不许写成 0、空成功或完成态。

### 10.3 改动纪律

1. **改后必有突变验证**：新增判据之后，要先把它弄红一次（确认它真的拦得住），再还原并用哈希自证逐字节一致。绿灯不算证据。
2. **同一文件禁止并行 Edit**：两条 Edit 打同一文件，后写的会吞掉先写的，而**两次都回报成功**——症状是「改完复跑还是旧行为」。
3. **守卫会扫仓库内的临时探针**：一次性探针写到仓库外（例如 `D:/Retire/probe-live/`），不许为过守卫放宽白名单。
4. **未经许可，绝不停/起/关任何存活进程**。包括本地辅助脚本与代理进程。脚本自己打印的「请运行 xxx 重启」不构成授权。
5. **对外发送必须先拿明确授权**：修好 ≠ 可以发。修好后把「内容 + 发送按钮」摆给人，等人点头。
6. **失败方向要选对**：写侧 fail-closed；读侧 fail-open 但必须给出 `reasonCode`（**假绿灯比红灯危害大**）。
7. **能力自己给出确定性 code + 失败分类**，不要往框架的关键词分类器里加业务词。
